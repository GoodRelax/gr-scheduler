# DEC-006: マルチバー行束ね情報の保持方式（MSPDI 準拠との両立）

- 日付: 2026-07-24
- 種別: アーキテクチャ根本判断（CLAUDE.md「重要判断の基準」: データ構造/データ形式の根本的選択、外部ツール連携の方式）
- 決定者: ユーザー承認
- 関連: iQUAVIS 連携（データ交換フォーマット = MSPDI）, `docs/spec/vendor/mspdi-core-tree.md`, IO-L1-*（入出力要求）, コア価値=マルチバー表示

## 背景

本ツール最大の差別化は**マルチバー表示**（1行に複数の独立アイテムを横並べ）である。
一方、iQUAVIS 連携が必須で、その交換フォーマットが **MSPDI**（Microsoft Project Data Interchange）。
他ツール連携も見据え、データ構造は **MSPDI に極力準拠**させたい。

しかし調査（`mspdi-core-tree.md`）の結論として、**MSPDI には「1行に複数の独立アイテムを束ねる」概念が存在しない**。
MSPDI のデータモデルは「1タスク = 1行 = 1主バー」。MSP の“マルチバー風”表示は
split / baseline / actual の重ね描き、またはビュー書式（ファイル外）に過ぎず、独立アイテムの横並べではない。

したがって「行束ね（どのタスクをどの視覚行に載せるか）」の情報を、どこに持つかを決める必要がある。
制約は「MSPDI 準拠を保つ」「ツールを重くしない（軽さは勝ちの源泉）」の両立。

## 選択肢

1. **Task 自身にマルチバー情報を持たせる**（MSPDI の `ExtendedAttribute` = 固定カスタム欄 Text/Number 等に group-id を刻む）
2. **MSPDI 形状データの隣に TaskGroup 構造を別に持つ**（案2ピュア）（採用）
3. 案2 + 案1 併用ハイブリッド（TaskGroup を真実の源としつつ、export 時に ExtendedAttribute へ保全ヒントを刻む）

## 決定

**選択肢2（案2ピュア）を採用**する。マルチバーの行束ねは **gr-scheduler ネイティブ形式（JSON, 主データ形式）内の
`TaskGroup` 構造**に持つ。MSPDI 形状の日程データ（Task/依存/日付）とは分離する。
**選択肢3（ExtendedAttribute 保全チャネル）は YAGNI により不採用**とする。

動作規約:

| 動作 | 挙動 |
|---|---|
| Export（→ MSPDI） | TaskGroup を落として写像 → **必ず妥当な MSPDI**（iQUAVIS が読める） |
| Import（← MSPDI） | MSPDI 読込 → TaskGroup 空 → **1タスク=1行に自動 fallback** |
| ネイティブ保存（JSON） | Schedule + TaskGroup を両方保持 → 行束ねは完全に保たれる |
| iQUAVIS 往復後の再取込 | ネイティブ JSON があれば UID で TaskGroup を再結合。**MSPDI 単体しか無ければ行束ねは失われ 1タスク=1行**（承知の上のトレードオフ） |

不変条件（投機でない最小担保）: **TaskGroup は Task を UID 参照で束ねる**。これにより、将来もし保全チャネルが
本当に必要と判明しても、export に1ステップ足すだけの純加算で済み、再設計を要しない。

## 根拠

- **MSPDI 準拠は「境界（Adapter）」の責務**であり、内部ドメインモデルではない（CLAUDE.md: 主データ形式=JSON、
  MSPDI は双方向 Import/Export）。準拠を Adapter に閉じ込めれば内部は軽量に保て、「重さで負ける」を回避できる。
- **選択肢3の却下理由（YAGNI + 二重管理）**:
  - TaskGroup と ExtendedAttribute の書き込み経路が2本になり、同期バグの温床（二重管理）。
  - iQUAVIS が未知の ExtendedAttribute を保全して往復させる保証が無く、**未検証の仮定**の上に実装を積むのは投機的。
  - 「MSPDI 単体ファイルだけで行束ねを往復復元したい」要件は現時点で実在しない。出たら作ればよい。
- **選択肢1の却下理由**: MSP のカスタム欄は固定スロット（Text1-30 等）で `FieldID` は数値 PID。空きスロット転用は
  他ツールとの衝突・枯渇リスクがあり、**最大の差別化（レイアウト）を最も制約の強い他社交換形式に従属させる**。
  準拠を守るほどマルチバー表現が窮屈になり、進化自由度を失う。
- **Clean Architecture 適合**: スケジュール（何を）と レイアウト（どう並べる）を分離でき、CLAUDE.md 記載の
  ドメイン境界（マルチバー・レイアウトエンジンをコアドメインに置く）と整合。
- **性能**: TaskGroup は既に行構造のため、レイアウトエンジンは行単位で読め（O(rows)）、行単位の差分再描画に有利。

## 帰結・残留リスク

- **残留（承知の割り切り）**: MSPDI 単体ファイルのみで往復した場合、行束ねは失われ 1タスク=1行に fallback する。
  MSPDI に行束ね概念が無い以上、単体ファイルでの往復保全は原理的に無理筋であり、追うと二重管理に陥るため受容する。
- ネイティブ JSON に `TaskGroup` を定義する必要がある（次工程: データ構造設計）。UID 参照の整合性
  （Task 削除時の TaskGroup 更新）を不変条件として1箇所で担保する。
- 本判断は「MSPDI そのものの解説」ではなく gr-scheduler 固有の設計判断のため、`mspdi-core-tree.md` には載せず
  本 ADR に記録する。将来「なぜ ExtendedAttribute を使わないのか」が蒸し返された際の一次参照とする。
