# GRS Relay —— 初めての AI がページのアドレスを答えられなかった件の報告

> **English.** Incident report (2026-10-21/22): a first-time Claude Code could not give the address of the GRS page
> served by GRS Relay. It records the root causes with evidence, the interim fix (CR-823, live on Pages), a fresh
> Hyper-V trial, the permanent options B1..B6 for the user to choose, the prevention we propose, and a lesson on
> the Pages cache. The text is in Japanese.

本書は、利用者の指示「根本原因とその対策をレポートに書かせて、保存し」（`JDG-3024`、調整役が中継）で書いた。
台帳の行は `DFC-3400`・`DFC-3401`、変更要求は `change-request/CR-823-the-download-page-hands-the-ai-copyable-address-prompts.md`、裁定は `JDG-3010`〜`JDG-3024` である。
⛔ 本書は記録であり、仕様ではない。恒久の直しは利用者が計画のタスク 241 で選ぶ（5 節）。

---

## 1. 起きたこと

利用者の同僚が、自分の PC の Claude Desktop に GRS Relay の拡張機能（`grs-relay.mcpb`）を入れ、Claude Code に「GRS のページを開くアドレスを教えて」と頼んだ。
Claude Code はどの道具を呼べばよいか分からず、アドレスを答えられなかった。
その Claude Code は自分で調べたレポートを残した。要点は次の 4 つである。

| # | レポートの要点 |
|---|---|
| 1 | 初めての Claude Code に最初に見えるのは、GRS Relay の道具の名前と、中継が出す案内文（MCP の `instructions`）だけ。道具の説明は ToolSearch で読み込むまで見えない |
| 2 | ページのアドレスは、ページがつながっていないときの断り（`pageNotConnected`）の中にしか無い。アドレスを返す専用の道具は無い |
| 3 | 案内文もアドレスを「断りへの対処」としてしか書かず、「アドレスがほしいとき」の手順としては書いていない |
| 4 | チャットと Code では別々の中継が動くのでアドレスも別。拡張機能を入れた後に始めた Code のセッションに GRS Relay が渡っていなかった |

当時のダウンロードページの手順 5 は「GRS Relay を使って、GRS のページを開くアドレスを教えて。」と送らせていた。
AI が自分で `agentApiVersion` を呼び、断りの中のアドレスを拾うことを当てにした文である。

## 2. 根本原因

### 2.1 `DFC-3400` —— アドレスは断りの中にしか無く、案内も説明もそこを指さない

| 根拠 | 中身 |
|---|---|
| `src/framework/mcp-relay-server/mcp-relay-server.ts:559` | ページがつながっていなければ、どの道具の呼び出しも `pageNotConnectedResult(state.pageUrl)` を返す。アドレスが外へ出る道はこれだけ（ほかに 567・737・741・748 行の同じ返し） |
| `src/framework/mcp-relay-server/mcp-relay-server.ts:1000` | アドレスは起動ごとに `http://127.0.0.1:<口>/#<鍵>` で作られる |
| `src/framework/mcp-relay-server/mcp-relay-server.ts:1018` | 中継はアドレスを自分のエラー出力に書くが、AI には見えない |
| `src/adapter/mcp-tool-translator/mcp-tool-descriptions.json:3` | 案内文は「Start with agentApiVersion. If a tool answers with the reason pageNotConnected, ask the person to open the address it gives …」—— アドレスを断りへの対処としてだけ書く |
| `src/adapter/mcp-tool-translator/mcp-tool-descriptions.json:12` | `agentApiVersion` の説明は版の形と「Read it first.」だけ。address・URL・connect の語が無い |
| 2026-10-21 の実測（この PC の Code） | `agentApiVersion` を呼ぶと `pageNotConnected` が `pageUrl` を返した。⚠️ ページがつながっているときは、どの道具もアドレスを返さない |

⭐ つまり、AI が「アドレスを教えて」に答えるには、「軽い道具を呼べば断りが返り、その中にアドレスがある」と自分で推し量る必要があった。
賢い AI なら推し量れる（4 節の段 4）。しかし、それを保証する仕組みは無かった。

### 2.2 `DFC-3401` —— チャットと Code は別々の中継を動かす

| 根拠 | 中身 |
|---|---|
| 2026-10-21 の実測（この PC） | GRS Relay だけを入れた Claude Desktop の中で、`127.0.0.1` を待ち受ける中継が 2 つ（口 51474 と 51475）動き、2 つとも Desktop の起動の時刻に立ち上がっていた。測り方: `Get-CimInstance Win32_Process` と `Get-NetTCPConnection -State Listen` |
| 2026-10-22 の実測（Hyper-V の新しい Windows） | Code の会話 3 つは同じ口 50072、シークレットのチャットは口 50065 を答えた（4 節）—— チャットと Code は別の中継、Code の会話どうしは 1 つの中継を共有する |
| `docs/spec/_assets/design-mcp-relay.md` の 6 節（`770ecd63e` の版の 210 行） | 「入れた束を 2 つのタブが共有する」と書いていた。2026-10-17 の `b529e6b1b` で入った文で、測った値ではなかった（`JDG-2782` の席の文案にも同じ主張があり、利用者はそれを「無用」として消させた） |

⚠️ 同僚の PC で「拡張機能を入れた後に始めた Code のセッションに GRS Relay が渡らなかった」ことは、再現していない。
新しい Windows では、起動し直す前から Code に道具が届いた（4 節の段 1）。
同僚の PC で迷った直接の原因は、2.1 の推し量りの失敗よりも、道具がその会話に届いていなかったことの方が近い。
これは Claude Desktop 側の振る舞いで、中継からは直せない。

### 2.3 なぜ私たちの手順は見逃したか

2026-10-18 の初見の AI の試し（7 つの頼みを別々の試しの会話で。所見 27 を `JDG-2813`〜`JDG-2818` で裁き、`CR-799` が当てた）は、次の点でこの件を通さなかった。

| # | 試しの作り | 見逃した理由 |
|---|---|---|
| 1 | 頼みは「GRS Relay を使って、私が開いている日程表につないで。文書の名前とタスク数を教えて」だった | 道具を呼ぶ用事があるので、最初の呼び出しが断りを受け、アドレスが自然に手に入る。⛔ **ダウンロードページが利用者に送らせる文そのもの**（「アドレスを教えて」だけ）は、一度も試していない |
| 2 | 開発の PC の Claude Desktop で、拡張機能が前から入っていた | 入れた直後・起動し直す前の状態を通っていない |
| 3 | Code タブだけ | チャットを試していないので、中継が 2 つあることに気づけない |
| 4 | 試しの会話は試しの席から立ち上げた子の会話で、空のフォルダで動いた | 利用者の全体の設定（`~/.claude` の指示）を読む PC であり、厳密には初見ではない |
| 5 | 仕様の文「2 つのタブが共有する」を測らずに入れた | 誤った前提がページの文になり、手順 5 は「チャットか Code のどちらでも同じ」と読めた |

⭐ まとめると、**試しは「AI が GRS を使えるか」を見ていたが、「ページの手順どおりに初めての人が進めるか」は見ていなかった。**

## 4. Hyper-V の初見の試し（2026-10-21〜22）

利用者が Hyper-V の Quick Create で新しい Windows 11（評価版）を作り、Claude Desktop（英語の画面）を入れ、自分のアカウントでサインインして試した。
案内の子セッションが 1 歩ずつ導き、結果を記録した（記録はリポジトリの外の共有メモ）。
テスト対象の束は develop の組み立て（版 2026.1019.195101、sha256 `10e6e2ed…`）で、中継のコードは公開中の α 版と同じ。
各段は新しい会話で行った。アドレスの鍵は 43 字で、どの段でも欠けなかった。

| 段 | したこと | 結果 |
|---|---|---|
| 1 | 拡張機能を入れた直後、起動し直す前に、Code で頼み文 A（手順 5 の 1 文） | 合格 —— 道具が届き、アドレスを丸ごと答えた（口 50929） |
| 2 | 終了して起動し直す | 合格 —— 通知領域の終わりの項目は `Exit`。タスクマネージャーに Claude は残らなかった |
| 3 | Code で頼み文 A | 合格 —— 口 50072。そのアドレスで開き、文書を開き、Agent API を押すとつながった |
| 4 | Code で元の文「GRS Relay を使って、GRS のページを開くアドレスを教えて。」 | **不具合は再現しなかった** —— 同じ口 50072 のアドレスを答えた |
| 5 | Code で頼み文 C（うまくいかないとき） | 合格 —— 道具を名前で探し、断りの `pageUrl` から答えた。推測しなかった |
| 6 | シークレットのチャットで頼み文 A | 合格 —— 口 50065（Code の 50072 と違う） |
| 7 | 拡張機能を無効にし、Code で頼み文 C | 合格 —— アドレスを作らず、道具が無いことと次にすること（有効か確かめる、終了して起動し直す、新しい会話）を答えた |

試しを受けて直したこと: 英語版の終了の項目の名を `Exit` にした。頼み文 C の「この会話で返ってきたアドレスだけが、この会話で使えます」を「Claude Code の会話どうしは同じアドレスで、チャットのアドレスとは違います」にした（段 5 の AI がその誤りを繰り返したため）。

確かめていないこと: 頼み文 A の英語版、日本語の画面と macOS のメニューの名、同僚の PC で起動し直す前の Code に道具が届かなかったこと。

## 5. 恒久の直しの案 —— ⛔ 決めるのは利用者（計画のタスク 241）

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| **B1** | 中継が自分で答える専用の道具 `getPageUrl` を足す。アドレスと、つながっているかを返す。案内文の 1 行目を「アドレスがほしいとき・作業を始めるときは getPageUrl」にし、説明に address・URL・connect・open の語を入れる | つながっていてもいなくても答えられる。名前で用途が分かり、検索でも当たりやすい。中継が自分で答える前例（`readSchema`、表 T-107 の `AM-30`）がある | 道具が 1 つ増える（表 T-107 と `AG-12` を変える CR が要る） |
| B2 | `agentApiVersion` の答えにアドレスを足す | 道具が増えない | 名前からアドレスを連想できない。ページの答えに中継が手を入れることになり、役割が混ざる |
| B3 | 案内文と説明の文だけを直す | 最も小さい | つながっているときにアドレスを出せないまま |
| B4 | 中継がブラウザでページを自分で開く | アドレスそのものが要らなくなる | Desktop の起動のたびにタブが開く。中継が 2 つならタブも 2 つ。既定のブラウザが Chrome や Edge とは限らない |
| B5 | アドレスを固定する（`JDG-1591`、`CR-697` は未着地） | 起動し直してもアドレスが変わらない | チャットと Code の別は残る（2 つ目の中継は別の口を取る）。AI が迷う件は直らない |
| B6 | チャットと Code で中継を 1 つにする（2 つ目が 1 つ目を見つけて使う） | 中継が 2 つあることによる混乱が消える | 仕組みが大きい。1 つ目が止まったときの扱いが要る |

⭐ 席の推奨は **B1**。2.1 の原因を根から断て、範囲が狭い（中継の原稿 1 か所と仕様の表 2 か所）。
B5 は決まっている別の直しとして計画に残す。B6 は β の後でよい。
⚠️ 4 節の段 4 のとおり、賢い AI は今でも推し量れる。B1 の値は「推し量りに頼らない」ことにある。

| # | 足すもの | 何を捕まえるか | 種類 |

| 1 | **ページが利用者に送らせる文は、そのままの字で、新しい会話の最初の頼みとして試す** —— リリースの前に、試しの表に 1 文 1 行 | 2.3 の 1。今回の見逃しそのもの | 試し（手） |

## 7. もう 1 つの教訓 —— Pages のキャッシュ

配備の直後に利用者が開いたダウンロードページは、古いままだった。
GitHub Pages が `Cache-Control: max-age=600` を返すためである（2026-10-22 に公開の頁の応答の見出しを取得して確かめた）。
ブラウザは最長 10 分、前の版を見せうる。

| 誰が | どうする |
|---|---|
| 配備を確かめる人（調整役・利用者） | 配備の直後は **Ctrl＋F5**（macOS は ⌘＋Shift＋R）で読み直すか、10 分待つ。⭐ 配備の手順の確かめの段に書くのがよい |
| ダウンロードページの読者 | ⭐ 席の推奨は**書かない**。読者は普段 1 度来てファイルを落とすだけで、10 分の古さが害になる場面がほとんど無い。書けば手順が長くなる |

⛔ ページに書くかどうかは利用者が決める。
