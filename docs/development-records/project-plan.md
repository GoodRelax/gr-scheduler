## 行（タスクグループ）

1 行が 1 つの持ち手である。席は並行に動くセッションで、5 つ。1 つの席は 1 度に 1 つのタスクだけを持つ。調整役の合流は短いので届いた順にさばくとし、調整役の行だけは重なってよい。利用者の行のバーは利用者の時間帯をまたいで長く見える —— 中身は時間帯の分で、バーの全体ではない。

| 行 | 中身 |
|---|---|
| 済み | 10-15 02:00〜07:15 に済んだ 16 件（実績を持つ） |
| 調整役 | CR ごとの合流と確かめ、全部の合流と台帳の締め、チェックリストの刷り直し、一括の GT-2、push |
| 利用者 | CR-763/764・766・767 の問いへの答え、OneDrive の停止、1 枚のチェックリスト、正式公開の判断 |
| 席1 | CR-740 の残り → CR-762 → CR-759 → CR-760 → CR-768 → 未検討のトリアージ → その直し → チェックリストの直し |
| 席2 | CR-758 の仕上げ → CR-756 → CR-761 → 罠の束 → 実装待ちの残り → DFC-730 → W4 → W5 |
| 席3 | CR-757 の試験 → CR-755 → CR-754 → CR-766 → 試験待ち 7 行 → 用語集の JSON → CR-695 |
| 席4 | 計画の更新 → T-064 の呼び方 → DFC-2645 の手写し → 古い STOP → 仕様待ちの残り → CR-697 |
| 席5 | 英語の慣習の調べ → CR-765 → CR-763/764 → CR-767 の波 1・2 → 英語の慣習の起草 → 改名 → DFC-2214・2215 |

順の決まり（調整役の指示）: 合流は CR-740 → CR-758 → CR-757（`frame-loop.ts` のため）。表の窓は CR-762 → CR-759 → CR-760（CR-759 と同じ表の前文なので同じ席）、CR-761 は CR-759 の後。CR-756 は CR-758 の合流の後（`schedule-layout.ts`）。CR-754 は CR-755〜757 の合流の後（パネルの幅は足された行の後に測る）。CR-767 の波 1 は CR-759 の後、波 2 は CR-760・762 の後。CR-768 は CR-759〜762 の後。英語の改名は全部の波の後。W4・W5・AI 連携は一括の GT-2 の後。

**いちばん長い道**: 英語の慣習の調べ → CR-765 → CR-763/764（利用者の答え）→ CR-767 → 英語の起草と改名 → 全部の合流 → OneDrive の停止（土 09:00）→ 一括の GT-2 → push → チェックリスト。その後は W4 → W5（日 21:00）→ 合流と GT-2 → 公開の判断（月 06:45、利用者の朝の時間帯）。

**依存線**は「前が終わってから始める」（終了→開始、ずれ 0）だけを使い、次の線は描かない（利用者の指示 2026-10-15）: 同じ行の中の線（行の並びが順を言う）・もっと長い道で同じ所へ届く線・「全部の合流と台帳の締め」へ集まる線（表の下のコメントが何を待つかを言う）。全 96 本のうち描いているのは 53 本。⚠️ 描かない線は文書の依存にも無いので、遅延診断（`BD-2`）はその先の遅れを出さない。この計画は巡ごとに作り直すので、遅れは次の作り直しで拾う。

## 前の計画との比べ方

GRS で `project-plan.json` を開くと、1 つ前の計画が**点線の輪郭**で重なる（文書の `baselineTasks` に `previous-plan.json` の全タスクを入れ、`baselineVisible` を真にした）。重ねの切り替えで消せる。

- 輪郭は **uid が同じタスク**の上に描かれる。同じ仕事は前の計画の uid を引き継ぐ —— 今の 85 タスクのうち 42 が前の計画の uid を持つ（例: CR-740 は 7、一括の GT-2 は 39、正式公開の判断は 44）。新しく出てきた仕事（CR-759〜768 など）は前の計画の最大の uid（49）の続きから振るので、輪郭は無い
- 前の計画にあって今は無い仕事（波 A〜C の合流、JDG-2071 の再検討と規則、聞き取り分の CR の実装など）は、重ねる相手が無いので描かれない。`previous-plan.json` をそのまま開けば見える
- ⚠️ いまの GRS は輪郭を日の単位に丸めて描く（04:15〜08:15 の仕事でも、その日の 00:00〜24:00 の輪郭になる）。仕様 `BL-2` は「予定バーと同じ日付から位置への換算」と言うので、GRS の不具合として調整役へ上げた

## スキーマで迷った点

書式はスキーマ（`docs/spec/_source/grs-document.schema.json`）だけを読んで書いた。次の点はスキーマだけでは決められなかった。台帳の行は括弧の中。

1. **始まっていないタスクの `percentComplete`** —— 0 か `null` か（0 と書いた）。（`DFC-2690`）
2. **予定の全体が稼働の時間帯の外にあるタスク** —— 予定の長さが稼働の分で 0 になるとき、マイルストーンの決まりが及ぶか。（`DFC-2691`）
3. **マイルストーンとプロジェクトの開始を稼働の外の瞬間に置いてよいか**。（`DFC-2692`）
4. **`fadeInDays`／`fadeOutDays` が日の単位** —— 数時間のタスクの「確かでない端」を表せない。仮置きは色で表した。（`DFC-2693`）
5. **ハイライトの箱とコメントの付け根の時刻** —— 出荷物では、どちらも日の単位で描かれた。仕様では、コメントの付け根は日の列の中央と行の帯の中央（`LF-15`）、`anchorDate` は `00:00:00` で書く 1 つの日（`WT-8`）だが、スキーマはどちらも言わない。`bodyOffsetPx` の向きと単位も言わない。（`DFC-2694`）
6. **ずれ 0 の依存の `lagFormat`**（7 と書いた）。（`DFC-2564`）
7. **`minutesPerWeek`・`daysPerMonth` を暦と揃えるか**（10080 と 30 と書いた）。（`DFC-2568`）
8. **基の暦の `baseCalendarUid`**（`null` か `-1` か）と `Calendar.ordinal` の意味。（`DFC-2562`・`DFC-2560`）
9. **マイルストーンでないタスクの `milestoneGlyph`**（`diamond` と書いた）。（`DFC-2563`）
10. **名前の色の暗いテーマでの見え方**。（`DFC-2695`）
11. **「誰がやるか」は行と担当のどちらで表すか**（席を行にした）。（`DFC-2696`）
12. **`documentStamp.lastEditedBy`・`Project.author` に何を書くか**（公開の文書で個人の名を避けたいとき）。（`DFC-2562`）
13. **24 時間稼働の暦の書き方** —— 1 本の時間帯 `00:00:00`〜`00:00:00` で全日になるか。`defaultFinishTime` は `00:00:00` か `23:59:00` か（`23:59:00` と書いた）。（`DFC-2697`）
14. **持ち手ごとの稼働時間を書けない** —— 暦は文書に 1 つで、利用者の時間帯を持たせる場所が無い。（`DFC-2698`）
