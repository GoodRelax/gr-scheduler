# プロジェクト計画の読み方

⭐ **計画の本体は隣の `project-plan.json`（GRS JSON）である。GRS で開いて読む。**本書はその読み方だけを持つ。
⛔ 2 つのファイルは巡ごとに上書きする。前の計画は git の履歴でだけ辿る（本書と JSON は前の計画を引き継いでいない）。

## いつの計画か

| | |
|---|---|
| 時点 | 2026-10-15 04:05 JST（JSON の `statusDate`）。統合の枝の `9670f420` の上で書いた |
| 範囲 | いまから計画の終わり（AI 連携の push）まで。タスク 49（うちマイルストーン 4） |
| 終わり | 非 AI の直しの一括 GT-2 と push が **2026-10-18（日）01:15**、利用者のチェックリストが同日 09:00〜11:00、正式公開の判断が **同日 16:00**、計画の終わりが **同日 18:00** |
| 暦 | **セッションは 24 時間 365 日稼働**（利用者の指示 2026-10-15）。文書の暦は毎日 00:00〜24:00 の 1 つだけ。時刻は日本時間（`scheduleDataTimeZone` = `Asia/Tokyo`） |
| 利用者の時間帯 | **平日 06:45〜07:30 と 21:00〜25:00、休日 09:00〜23:00**（利用者の指示 2026-10-15）。利用者の行のタスクだけを、この時間帯の分で数えて置いた（10-15〜10-19 に祝日は無い） |

⭐ 利用者は時間帯の外でも、できるかぎり不具合と改善点の報告と裁定を行う。計画は時間帯の内だけを仮定している —— 外で答えが出れば、それを待つタスク（とくに波 B）はそのぶん早まる。

## レーン（タスクグループ）

1 行が 1 つの持ち手である。席は並行に動くセッションで、同時に 5 つまで（調整役の既定）。1 つの席は 1 度に 1 つのタスクだけを持つ。利用者の行のバーは、利用者の時間帯をまたいで長く見える —— 中身は「利用者の時間帯の分」で、バーの全体ではない。

| 行 | 中身 |
|---|---|
| 調整役 | 波ごとの合流と確かめ、台帳の締め、チェックリストの刷り直し、一括の GT-2、push |
| 利用者 | 残りの裁定、聞き取り、OneDrive の停止、1 枚のチェックリスト、正式公開の判断 |
| 席1 | CR-753 → 未検討のトリアージ → 実装待ちの残り → CR-755 → CR-754（＋DFC-2517）→ W4 → W5 → チェックリストの直し |
| 席2 | CR-740 → 罠の束 → DFC-730 → CR-756 → CR-695 |
| 席3 | 工程の強制の道具 → CR-752 → T-064 の呼び方 → 聞き取り分の CR → CR-697 |
| 席4 | CR-758 → 用語集の JSON → 仕様待ちの起草 → CR-757 → 仕様待ちの当て → DFC-2214・2215 |
| 席5 | JDG-2071 の調べ → 再検討 → 規則と検査 → 試験待ち 7 行 → トリアージ分の直し |

薄い箱（ハイライトの箱）は **波 A・B・C** の幅である。波は「1 つのファイルの組に書き手は 1 人」を守るための順で、波 B は波 A の合流と利用者の残りの裁定を、波 C（CR-754）は波 B の合流を待つ（パネルの幅は波 B が足す行の後に測る）。波 B が裁定を待つあいだ、席 1・2・4 は波のファイルに触れない台帳の仕事（トリアージ・実装待ちの残り・罠・用語集・仕様待ちの起草）を先に進める。依存線は「前が終わってから始める」（終了→開始、ずれ 0）だけを使った。

**いちばん長い道**: 利用者の裁定（10-15 21:15 まで）→ 波 B → 波 C → W4 → W5（10-17 19:15）→ 一括の GT-2 → チェックリスト → 直し → 公開の判断。W4・W5 は波の CR と同じファイルを割るので、波 C の後に 1 つの席で順に置いた（`JDG-1479`: W5 は W4 の後）。

## 色

| 色 | 意味 |
|---|---|
| 青 | 起草済みの CR の当て（仕様とコードの体 ＋ 仕様だけを読む試験の体） |
| 緑 | 並行の仕事（道具・調べ・リファクタ・台帳の残り） |
| 薄い灰 | **仮置き** —— 件数がまだ分からない（聞き取り分・トリアージ分・チェックリストの直し） |
| 紫 | 調整役の合流と関門 |
| 橙 | 利用者の手番 |
| 青緑 | AI 連携（一括の GT-2 の後） |
| 赤（星） | 正式公開の判断・計画の終わり |
| 濃い灰 | 済み（CR-751 の適用、02:00〜03:04。統合の枝に在り、一括の GT-2 を待つ） |

マイルストーンは 4 つ: OneDrive を止める・push と Pages の配備・正式公開の判断（`JDG-1740`）・計画の終わり。

## 数の出し方

| 種類 | 時間の出し方 |
|---|---|
| 見積のある CR | **CR の本文の見積 × 0.5**（15 分へ切り上げ）。根拠: CR-743 は見積 13 時間に対し、起草のコミットから仕様の当てまで 4 時間 6 分、コードの体の始めから合わせまで 2 時間 24 分（10-14 20:25→22:49）、計 6.5 時間ほど（コミットの時刻で測った） |
| CR ごとの足し引き | CR-753 は `JDG-2069`（A）で 4.1 節が入るので 2.5 ＋ 4 ＝ 6.5 時間。CR-758 は見本 50 の数え直しに 1 時間を足して 8.5 時間 |
| 見積の無い仕事 | 大きさの段 S ＝ 2 時間・M ＝ 4 時間・L ＝ 8 時間（壁時計の時間）で置いた。T-064 は 479 名を 1 時間 60 名ほどで 8 時間 ＋ 再検討 4 時間 |

| 合流 | CR 1 本につき 15 分。一括の GT-2 は 2 時間（前の巡の試験だけで 468 秒、時間切れの再走を見込む） |
| 台帳の残り | `tools/ledger_metrics.py` の数（10-15 03:44）: 未検討 43・仕様待ち 36・実装待ち 37・試験待ち 9・実測待ち 411。CR-740〜758 が名指す行と聞き取りの行（DFC-2515〜2526）を除いた残りを、仕様待ち 約 19・実装待ち 約 20・試験待ち 7・未検討 40 と数えた |
| 始まり | セッションの仕事は 10-15 04:15（書いた時刻を 15 分へ切り上げ）から。動いている席（聞き取り・JDG-2071 の調べ・工程の道具）は始まりの時刻を測っていないので、実績を書かず計画として置いた |

## 置いた仮定（調整役が確かめた）

- AI 連携は一括の GT-2 の後に回し、正式公開の判断はその完了を待たない（`JDG-1740` の 3 条件は解明・リファクタ・分刻みの日程）
- T-064 の呼び方は仕様の設計の原稿を波 B と同時に触る。合流は調整役が受ける

## スキーマで迷った点

書式はスキーマ（`docs/spec/_source/grs-document.schema.json`）だけを読んで書いた。次の点はスキーマだけでは決められなかった。台帳の行は括弧の中。

1. **始まっていないタスクの `percentComplete`** —— 0 か `null` か（0 と書いた）。（`DFC-2690`）
2. **予定の全体が稼働の時間帯の外にあるタスク** —— 予定の長さが稼働の分で 0 になるとき、マイルストーンの決まりが及ぶか。（`DFC-2691`）
3. **マイルストーンとプロジェクトの開始を稼働の外の瞬間に置いてよいか**。（`DFC-2692`）
4. **`fadeInDays`／`fadeOutDays` が日の単位** —— 数時間のタスクの「確かでない端」を表せない。仮置きは色で表した。（`DFC-2693`）
5. **ハイライトの箱に分の時刻を書いてよいか、上下の行が両端を含むか**。（`DFC-2694`）
6. **ずれ 0 の依存の `lagFormat`**（7 と書いた）。（`DFC-2564`）
7. **`minutesPerWeek`・`daysPerMonth` を暦と揃えるか**（10080 と 30 と書いた）。（`DFC-2568`）
8. **基の暦の `baseCalendarUid`**（`null` か `-1` か）と `Calendar.ordinal` の意味。（`DFC-2562`・`DFC-2560`）
9. **マイルストーンでないタスクの `milestoneGlyph`**（`diamond` と書いた）。（`DFC-2563`）
10. **名前の色の暗いテーマでの見え方**。（`DFC-2695`）
11. **「誰がやるか」は行と担当のどちらで表すか**（席を行にした）。（`DFC-2696`）
12. **`documentStamp.lastEditedBy`・`Project.author` に何を書くか**（公開の文書で個人の名を避けたいとき）。（`DFC-2562`）
13. **24 時間稼働の暦の書き方** —— 1 日 1 本の時間帯 `00:00:00`〜`00:00:00`（`toTime` の 00:00 は 24:00）で全日になるか、「始まりが終わりより前」の決まりに触れて空の時間帯と読まれるか。`defaultFinishTime` は `00:00:00`（24:00）か `23:59:00` か（`23:59:00` と書いた）。（`DFC-2697`）
14. **持ち手ごとの稼働時間を書けない** —— 稼働日は文書の暦 1 つで数え、`Resource.calendarUid` は往復のためだけと言う。利用者の時間帯（平日 06:45〜07:30・21:00〜25:00、休日 09:00〜23:00）を文書に持たせる場所が無いので、利用者の行のバーは時間帯をまたいで長く描かれる。（`DFC-2698`）
