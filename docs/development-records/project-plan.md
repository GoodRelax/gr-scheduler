⭐ **計画の本体は隣の `project-plan.json`（GRS JSON）である。GRS で開いて読む。**本書はその読み方だけを持つ。
⭐ **1 つ前の計画は `previous-plan.json` に残す**（利用者の指示 2026-10-15）。巡ごとに、今の `project-plan.json` を `previous-plan.json` へ名を変えて上書きし、新しい `project-plan.json` と本書を書く。それより前の計画は git の履歴でだけ辿る。

## 前の計画との比べ方

GRS で `project-plan.json` を開くと、1 つ前の計画（07:31 時点）が**点線の輪郭**で重なる（`baselineTasks` に `previous-plan.json` の全タスクを入れ、`isBaselineVisible` を真にした）。重ねの切り替えで消せる。

- 輪郭は **uid が同じタスク**の上に描かれる。同じ仕事は前の計画の uid を引き継ぐ —— 今の 95 タスクのうち 69 が前の計画の uid を持つ（例: 一括の GT-2 は 39、正式公開の判断は 44、T-064 は 15）。新しく出てきた仕事は前の計画の最大の uid（92）の続きから振るので、輪郭は無い
- 前の計画で予定だった仕事の多くが今は済んでいる —— 輪郭（前の予定）と濃い灰のバー（実績）の隔たりが、前倒しや遅れを示す。例: CR-769 は前の計画では 10-16 23:00 からの予定だったが、10-15 16:06 に済んだ
- 前の計画にあって今は無い仕事（CR ごとの合流、DFC-2645 の手写しなど）は、重ねる相手が無いので描かれない。`previous-plan.json` をそのまま開けば見える
- 輪郭は分の位置に描かれる（日に丸まる不具合 `DFC-2765` は 10-15 に直った）

## 行（タスクグループ）

1 行が 1 つの持ち手である。席は並行に動くセッションで、5 つ。1 つの席は 1 度に 1 つのタスクだけを持つ。調整役の合流は短いので届いた順にさばくとし、調整役の行だけは重なってよい。利用者の行のバーは利用者の時間帯をまたいで長く見える —— 中身は時間帯の分で、バーの全体ではない。

| 行 | 中身 |
|---|---|
| 済み（02:00〜07:36） | 前の計画のときに済んでいた 16 件 |
| 済み（07:36〜22:30） | その後に済んだ 23 件 —— CR-740・754〜766・768 の A・B・769・770 の実装、DFC-2765・2309 の直し、計画の更新など |
| 調整役 | CR-771 の合流 → dist の作り直し → vitest 全体と Playwright 全体 → 一括の GT-2 → push → Pages の配備とチェックリストの刷り直し。その後、裁定のあとの CR の合流、全部の合流、2 度目の GT-2 |
| 利用者 | OneDrive の停止（GT-2 の前ならいつでも）、裁定待ち 約 15 問への答え、1 枚のチェックリスト、正式公開の判断 |
| 席1 | CR-771 → 裁定のあとの小さな直し → T-064 の呼び出し形 → 古い STOP → 罠の束 → 実装待ちの残り → チェックリストの直し |
| 席2 | CR-767 の波 1・2 → CR-768 の C → W4 → W5 |
| 席3 | CR-766 の Q1 の改名（新しい CR）→ CR-762 の行の仮想化（Q2 で採るなら）→ edgeOf・NOT_STORED_DUMMY_SIZES・baseChangeCommandOf → 試験待ち → 用語集の JSON → CR-695 |
| 席4 | DFC-2856（新しい CR）→ DFC-2855 → DFC-2646〜2648 → 未検討のトリアージ → その直し → CR-697 |
| 席5 | DFC-2880 → DFC-557 → DFC-2870 → 仕様待ちの残り → DFC-730 → DFC-2214・2215 |

**いちばん長い道**: 裁定（今夜）→ 席1 の直しと片付け → 実装待ちの残り → チェックリストの直し（土 09:00〜13:00）→ 全部の合流 → 2 度目の GT-2（土 16:00）→ W4 → W5（月 00:00）→ 合流と GT-2 → 公開の判断（月 06:45、利用者の朝の時間帯）。

**依存線**は「前が終わってから始める」（終了→開始、ずれ 0）だけを使い、次の線は描かない（利用者の指示 2026-10-15）: 同じ行の中の線（行の並びが順を言う）・もっと長い道で同じ所へ届く線・「全部の合流と台帳の締め」へ集まる線（表の下のコメントが何を待つかを言う）。全 76 本のうち描いているのは 27 本。⚠️ 描かない線は文書の依存にも無いので、遅延診断（`BD-2`）はその先の遅れを出さない。この計画は巡ごとに作り直すので、遅れは次の作り直しで拾う。

## 色

| 色 | 意味 |
|---|---|
| 濃い灰 | 済み（実績の開始と終了を持つ） |
| 青 | CR の当て（仕様とコードの体 ＋ 仕様だけを読む試験の体） |

| 薄い灰 | **仮置き** —— 大きさや要否が裁定次第（裁定のあとの直し・CR-762 の仮想化・トリアージの直し・チェックリストの直し） |

| 橙 | 利用者の手番 |

## 置いた仮定（調整役が確かめる）

- 裁定のあとの仕事・片付け・台帳の残りは、1 度目の GT-2 の後に入り、**2 度目の一括の GT-2** でまとめて確かめる
- 正式公開の判断は、2 度目の GT-2 と **W4・W5 の合流の後**に置いた（`JDG-1740` の 3 条件にリファクタが入るため）。AI 連携は待たない
- OneDrive の停止は前提を持たないので、今夜の利用者の時間帯の始めに置いた（GT-2 の前ならいつでもよい）

## スキーマで迷った点

書式はスキーマ（`docs/spec/_source/grs-document.schema.json`）だけを読んで書いた。次の点はスキーマだけでは決められなかった。台帳の行は括弧の中。

1. **始まっていないタスクの `percentComplete`** —— 0 か `null` か（0 と書いた）。（`DFC-2690`）
2. **予定の全体が稼働の時間帯の外にあるタスク** —— 予定の長さが稼働の分で 0 になるとき、マイルストーンの決まりが及ぶか。（`DFC-2691`）
3. **マイルストーンとプロジェクトの開始を稼働の外の瞬間に置いてよいか**。（`DFC-2692`）
4. **`fadeInDays`／`fadeOutDays` が日の単位** —— 数時間のタスクの「確かでない端」を表せない。仮置きは色で表した。（`DFC-2693`）
5. **ハイライトの箱とコメントの付け根の時刻** —— コメントの付け根は日の列の中央と行の帯の中央（仕様 `LF-15`）、`anchorDate` は `00:00:00` で書く 1 つの日（`WT-8`）だが、スキーマはどちらも言わない。`bodyOffsetPx` の向きと単位も言わない。（`DFC-2694`）
6. **ずれ 0 の依存の `lagFormat`**（7 と書いた）。（`DFC-2564`）
7. **`minutesPerWeek`・`daysPerMonth` を暦と揃えるか**（10080 と 30 と書いた）。（`DFC-2568`）
8. **基の暦の `baseCalendarUid`**（`null` か `-1` か）と `Calendar.ordinal` の意味。（`DFC-2562`・`DFC-2560`）
9. **マイルストーンでないタスクの `milestoneGlyph`**（`diamond` と書いた）。（`DFC-2563`）
10. **名前の色の暗いテーマでの見え方**。（`DFC-2695`）
11. **「誰がやるか」は行と担当のどちらで表すか**（席を行にした）。（`DFC-2696`）
12. **`documentStamp.lastEditedBy`・`Project.author` に何を書くか**（公開の文書で個人の名を避けたいとき）。（`DFC-2562`）
13. **24 時間稼働の暦の書き方** —— 1 本の時間帯 `00:00:00`〜`00:00:00` で全日になるか。`defaultFinishTime` は `00:00:00` か `23:59:00` か（`23:59:00` と書いた）。（`DFC-2697`）
14. **持ち手ごとの稼働時間を書けない** —— 暦は文書に 1 つで、利用者の時間帯を持たせる場所が無い。（`DFC-2698`）
