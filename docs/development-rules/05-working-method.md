# 05 進め方 —— 記録・順番・並行・受け入れ・止まり方

⛔ **8 条の ⑥ と ⑦ は原則としては既にある。** ⚠️ **原則のままでは走らないことを実測しているので、本書は手順として書く。**

---

## 1. ⛔ 止まっても再開できるように記録する

⚠️ **止まる理由は選べない** —— 停電・枠切れ・要約による文脈の消失・単に日をまたぐ。
⭐ **どれも「作業中の頭の中」だけが消える。** ディスクの中身は残る。**だから頭の中をディスクへ落とす。**

### ⭐ 記録は `docs/development-records/` に置く

⛔ **git が答えられることを書かない。** 何を変えたかは `git log` と `git diff` が持つ。
⭐ **記録が持つのは、git が答えられない 3 つだけである:**

```
1. 現在地   いまどのユニットのどの段にいるか（次の一手が読める形で）
2. 状態表   各ユニットが 未着手 / 実装済 / 試験済 / 受入済 のどれか
3. 決めた理由と踏んだ罠   ⭐ 変更要求に載らない、作業中の判断
```

### ⛔ 書き足す時機（**あとでまとめて書かない**）

| いつ | 何を |
|---|---|
| **ユニットの段が 1 つ進んだ直後** | 状態表の 1 マスを書き換える |
| **裁定を受けた／罠を踏んだ／自分で決めた直後** | 1 行足す |
| **危ない操作の前** | 何を壊しうるか、どう戻すかを 1 行 |
| **枠が細ってきたとき** | ⭐ **要約が入って検討事項が消える前に。** 消えてからでは書けない |

⚠️ **「終わってから書く」は失敗する。** ⛔ **実測**: 引継ぎを最後にまとめて書いた回で、古い節が残って次の担当を誤らせた。

### ⭐ 記録は機械が突き合わせる（**腐らせない**）

⛔ **状態表は放っておけば腐る。** ⭐ **機械検査が、記録と実物のズレを落とす:**

```
・その波のユニットが 1 つでも表から漏れていれば落ちる
・表に無いファイルが並んでいれば落ちる
・⬜ 未着手 と書いてあるのにファイルが stub でなければ落ちる
・段が進んだと書いてあるのにファイルが stub のままなら落ちる
```

⚠️ **「未着手」は行数や export では判定していない** —— **stub 生成器が書くはずの全文と 1 バイトでも違うか**で判定する。
⭐ **記録は「波を宣言する」** —— 先頭に `**対象**: \`src/adapter\`` の 1 行を置く。検査はそれを読む。

### ⛔ 止まるときは緑で止まる

⭐ **中断する前に、機械検査と型検査を通しておく。** ⚠️ **赤いまま止めると、次に開いた者が
「自分が壊したのか、前から壊れていたのか」を切り分けるところから始めることになる。**
⭐ **通せないなら、記録に「いまここが赤い。原因はここまで絞れている」と書いてから止まる。**

## 2. ⛔ 実装の順番は依存で決める（**好みで決めない**）

⭐ **順番は既に半分決まっている** —— 層の規則（表 T-061）が依存を内向きだけに限っているので、
**内側の層は外側を待たない。**

```
documentModel → layoutEngine → UseCase → Adapter → Framework
```

### ⭐ 波の中の順番は、継ぎ目と公開エントリで決める

1. **その波が実装する継ぎ目**（表 T-065）**を宣言している側が先** —— 宣言が無ければ実装できない
2. **コンポーネントの公開エントリが先、内部ユニットが後** —— 外から見える形が決まらないと、他が書けない
3. ⛔ **依存の向きに逆らって始めない。** 生煮えのものに依存したコードを書かない（8 条の ⑥）

### ⚠️ 内側から順に作ると、最後の波まで実物が見えない（**実測**）

⛔ **`index.html` が読むのは `single-html-shell.ts` であり、いまそれは中身の無いユニットである。**
**つまり全部そろうまでブラウザには何も出ない。** ⚠️ **[04](04-verification.md) が「緑の試験は動くアプリを意味しない」と言う一方で、
実物を確かめる手段が最後まで存在しないことになる。**

⭐ **だから波の中で、まず 1 本の縦線を通す。** 依存の順を守ったまま、**「画面に何かが出る」最小の集合を先に選ぶ。**
⚠️ **そこから先は、実物を見ながら進められる。** ⛔ **波の全部を書き終えてから初めて起動する、という順番を採らない。**

### ⭐ 縦線のために、次の波へ先に手を出してよい（**利用者の裁定 2026-08-18**）

⛔ **波は「順番」であって「柵」ではない。** ⭐ **縦線を通すのに必要なら、次の波のユニットを先に書いてよい。**

```
許される     縦線に必要な最小限だけを、次の波から先に書く
             ⭐ 例: Adapter を書いている途中で、画面に出すために
                    Framework のシェルを先に動く形にする
許されない   ⛔ 依存の向きに逆らうこと（外側の層に内側が依存する）
             ⛔ 段を飛ばすこと（4. の ✅ を経ずに他が依存する）
```

⚠️ **先に手を出したら、記録に「どの波のどれを、なぜ先にやったか」を書く** ——
**状態表は波ごとのファイルなので、書かないと「その波は未着手」と読まれる。**
⭐ **機械検査が状態表と実物を突き合わせるので、書き忘れれば落ちる。**

## 3. ⭐ インターフェースが決まったら並行してよい

⛔ **「決まった」は「実装が動く」ではない。** ⭐ **並行を許す条件はこれだけである:**

```
公開エントリに、公開する型と署名が書かれ、型検査が通る
```

⚠️ **そこから先、それに依存する側は中身を待たずに書ける** —— 型が契約だからである。
⛔ **中身が未実装のまま依存側の「試験」を緑にしてはならない**（4. を見よ）。

### ⛔ 並行の単位はファイルである。⭐ **隔離の単位は worktree である**（**利用者の裁定 2026-08-23**）

⛔ **同じ作業木で複数の体を走らせない。** ⚠️ **実測（11 体を同じ木で走らせた回）:**

```
各体が npm test と check.sh を何十回も走らせ、互いの編集で数字が動くたびに
「これは自分のか」を調べ直した —— 報告の半分がその説明で埋まった
1 体が共有の scratch/ を rm -rf した
1 体が死に、報告ごと失われた（作業はディスクに残っていたが、何が未達かの申告が消えた）
```

⭐ **実装する体は `isolation: "worktree"` で隔離する。** ⛔ **体には検証をさせない。**

| 誰が | 何を走らせるか |
|---|---|
| 実装する体 | ⛔ **走らせない。** 書いて、**変えた点と、できなかった点**だけを報告する |
| 前に立つ者 | ⭐ **合流点で 1 回だけ** —— `precheck` → `typecheck` → `test` → `layers` → `check.sh` → 実物 |

⚠️ **体に基準の数字を渡さない。** ⛔ **渡すと、走っているあいだに動いて必ず食い違う。**
⭐ **「自分で先に測れ」とだけ言う。**

⛔ **走っている体の途中結果を、確定した数字として報告しない。** ⚠️ **実測**: 型検査を「0 エラー」と
報告した後、まだ生きていた体が書き足して 7 件に戻った。**体が終わったと確定するまで、その領域の数字は言わない。**

### ⛔ 並行の単位はファイルである

⚠️ **同じファイルを 2 人（2 体）で書かない。** 衝突する。
⭐ **実測で効いた形**: 1 体 1 ファイル。集約 6 つを並行させて 1 巡で揃った。
⛔ **効かない形**: 仕様書への適用。**必ず 1 体でやる**（同じ文書を並行に書けば壊れる）。

## 4. ⛔ 試験が通ってから、他所での参照を許す

⭐ **ユニットには段がある。** ⛔ **「受入済」になるまで、他のユニットがそれに依存してはならない。**

```
⬜ 未着手    stub のまま
🔧 実装済    製品コードを書いた。⛔ まだ誰も依存してよくない
🧪 試験済    別の者が docs/spec だけを読んで試験を書いた（04 の 1.）
✅ 受入済    その試験が緑。型検査・層の検査も緑
             ⭐ ここで初めて、他のユニットがこれに依存してよい
```

⚠️ **段を飛ばさない。** ⛔ **「あとで試験を書く」は、依存が積み上がった後では書けなくなる** ——
落ちたときに、どのユニットの欠陥かを切り分けられなくなるからである（8 条の ⑥ の「不具合範囲を局所化し」）。

⭐ **例外は 3. の「型だけ先に決める」だけ** —— 型に依存してよいが、**振る舞いには依存しない。**

## 5. ⭐ 1 巡の形（**まとめ**）

```
1. 記録の「現在地」を読む                     ← 停電から戻ってきてもここから
2. 次のユニットを依存の順に選ぶ                （2.）
3. 公開エントリの型を書く → 型検査が通る       ← ここで並行を解禁（3.）
4. 製品コードを書く                            🔧
5. 別の者が仕様だけを読んで試験を書く           🧪（04 の 1.）
6. 緑にする。型検査・層の検査も通す             ✅ 受入済
7. 記録の状態表を書き換える                     ← 段が進むたび。あとでまとめない
8. 緑のまま止まる                               （1. の最後）
```

## 6. ⛔ 前に立つ者はオーケストレーションに徹する（**利用者の裁定 2026-08-19**）

⛔ **前面のセッションが製品コードと試験を自分で書かない。** ⭐ **書くのはサブエージェントである。**

```
前に立つ者がやること     読む・測る・決める・分ける・検証する・記録する
                         仕様への適用と原稿の移送（⛔ これは 1 体でやる。3. を見よ）
サブエージェントがやること 製品コードを書く／試験を書く／踏査する
```

### ⭐ なぜか（**実測**）

| | |
|---|---|
| **文脈が保つ** | ⚠️ **試験を別の者に書かせても、親の文脈はほとんど減らない**（195 万 → 35k）。⛔ **前に立つ者が自分で書くと、検証に使える文脈が残らない** |
| **04 の 1. がただで手に入る** | ⭐ **書いた者に試験を書かせない**が、分業の副産物として成立する。⚠️ **実測: 仕様だけを読ませた 3 体が、本物の欠陥を 8 件見つけた** —— 型検査も 684 件の試験も 1 件も捕まえていない |
| **並列が効く** | ⭐ 1 体 1 ファイルなら並行できる（3.）。⛔ **同じファイルを 2 体で書かない** |

### ⭐ 仕様への適用は 1 巡にまとめる（**利用者の裁定 2026-08-23**）

⛔ **変更要求ごとに「測る → 書く → 当てる → 検査 → 変更履歴」を回さない。**
⚠️ **実測**: 5 本を 1 本ずつ回して 5 周した。⭐ **閉路が無いことは最初の 1 回で分かっていた。**

```
1. 種を全部集めて induced.py を 1 回      ⭐ 閉路の有無がここで出る
2. 閉路に入る対象を 2 つ以上触るなら、その閉路は 1 つの計画で 1 度に書く（規則 02 の 3.）
3. 閉路に入らない分は、変更要求を全部書いてから、まとめて当てる
4. 検査は最後に 1 回
```

⚠️ **数の予測は変更要求ごとに書く** —— まとめて当てても、外れたのがどれかは分かる必要がある。

### ⛔ それでも前に立つ者が手を動かす場面

```
1. 仕様書への適用と原稿の移送   ⛔ 必ず 1 体（同じ文書を並行に書けば壊れる）
2. 変更要求を書くこと           ⛔ 影響を測った者が書く
3. 分けようがない小さな直し     ⚠️ 1 ファイルの数行。⭐ 迷ったら分ける
```

### ⚠️ 受け取り方（**鵜呑みにしない**）

⛔ **サブエージェントの報告を鵜呑みにしない。** ⭐ **必ず自分で開いて確かめ、検査も自分で走らせる。**
⚠️ **実測: 行番号は 1〜25 行ずれて報告される。逐語の中身は正しいことが多い。**
⛔ **落ちた試験を自分で直さない** —— 取り出し方が怪しいと思ったら**書いた側へ差し戻す。**
⚠️ **下書き（`zz-*.test.ts` など）を残すことがある。終わったら `git status` を見る。**

## 7. ⛔ 5 段のパイプライン（**利用者の裁定 2026-08-26**）

⛔ **前に立つ者が、体の報告を自分の推論の入力にしてはならない。** ⚠️ **実測（2026-08-26）: そうした結果、
存在しない二者択一を利用者に出した。**⭐ **本節はそれを起こさない順序である。手順であって心構えではない。**

```
段 1  前に立つ者が「大雑把に」指示する        ⭐ 詳細を作り込まなくてよい
段 2  ⛔ 体が仕様を読み、実装方針を提案する    ⛔ ここでコードを書かせない
段 3  前に立つ者がその方針の可否を決める      ⛔ 数字と file:line が無い方針を通さない
段 4  実装の体と試験の体を「同時に」走らせる  ⛔ 試験の体は docs/spec だけを読む
段 5  実装が入ってから試験を当て、前に立つ者が最終報告をまとめる
```

### ⛔ 段 2 を飛ばしてはならない

⚠️ **飛ばすと、前に立つ者の思い込みがそのまま体の台本になる。**
⭐ **実測: 段 2 を踏んだ回は、体が台本の誤りを 7 件返した** —— そのうち 5 件は
「仕様に無い」と `src/` の `STOP` コメントが書いていたのに**実際には在った**ものである。
⛔ **`STOP` コメントを根拠に「仕様に無い」と言わない。必ず自分で当たる。**

### ⛔ 段 3 で通してよい方針の条件

```
1. 触る要求・表・行を行 ID で名乗っている
2. file:line が付いている（⚠️ 行番号は 1〜25 ずれる。逐語で確かめる）
3. ⛔ 値を選ぶ提案なら、選択肢ごとの帰結が数で出ている
4. 仕様に行が無いなら、そう申告している（⛔ 発明していない）
```

### ⛔ 波を出す前に commit する（**実測 2026-08-26**）

⛔ **作業木はセッションの開始コミットで切られる。HEAD ではない。**
⚠️ **実測**: 設定値の行を書いて commit せずに波を出したところ、体の木にその行が無く、
⭐ **体は発明を拒んで STOP を残した（正しい判断）。誤っていたのは波の出し方である。**

```
1. commit する
2. その sha を five-stage へ baseCommit として渡す
3. ⭐ 体は `git merge --ff-only <sha>` で治してから始める
```

⭐ **`baseCommit` を渡さなければ `five-stage.js` が拒む。**⛔ **覚えている必要がないようにしてある。**

### ⛔ 段 4 の並行は「実装 ‖ 試験」であって「実装 → 試験」ではない

⚠️ **試験を後から書くと、実装に合わせた期待値になる。**
⭐ **同時に走らせれば、試験の体は実装を見られないので、仕様からしか書けない。**
⛔ **前に立つ者が、自分が動かした値の試験を自分で直してはならない** ——
⚠️ **実測: `S-85` を動かした当人が試験を直し、3 か所のうち 2 か所しか直さず、
しかも直した 1 つは `FR-017` のフォント補正を落としていた。緑がそれを隠した。**

### ⛔ 問う前に、そもそも問ってよいかを見る（**利用者の裁定 2026-08-26**）

```
① 直すときに触るのは 1 コンポーネントの中だけか
② 公開された API（表 T-064 ・ 表 T-065）は動かないか
⇒ 両方「はい」なら `A`〜`C` であることが多い。⛔ **問わずに推奨値で進める**
```

⛔ **`A`〜`C` を巡の途中で問わない。実装と試験を止めない。**
⭐ **推奨値で実装し、`// @provisional PD-n` の印を付け、一覧に溜めて巡の最後か次の先頭でまとめて問う。**
⚠️ **実測 2026-08-26: 1 巡で 14 件の裁定を並べ、そのうち 8 件は `A`〜`C` であった。**
⛔ **問わずに進められたものを問い、その間下流を待たせた。規則 06 は最初からそう書いてあった。**

### ⛔ 利用者へ裁定を問う前に埋める欄（**空欄のまま問わない**）

```
機構      症状ではなく、なぜそうなるかを file:line と数で 1 文
実測      自分の手で走らせた数字（⛔ 体の報告の引き写しは不可）
選択肢    2 つ以上。⛔ それぞれの帰結を数で
推奨      1 つ。根拠は仕様の逐語
覆す費用  規則 06 の分類と、落ちる試験
```

⛔ **「測れなかった」と書くのはよい。⭐ 測っていないことを設計判断のふりにするのが悪い。**

### ⭐ 不具合は台帳で追う

⛔ **利用者が指摘した不具合を、頭の中と引継書だけで追わない。**
⭐ **`docs/development-records/defects.md` に 1 行立て、直るまで消さない。**
⚠️ **「実装済」は試験が緑という意味であって、実物で動いた証拠ではない**（規則 04）。
