## ⭐ ① と ② は「答えを書く」ところまで下ろしてある

⛔ **① と ② は、原則として置いてあった間、ほとんど守られていなかった**（実測）:

| 実測 | |
|---|---|
| 機械検査が変更要求を見ていた回数 | **0** |
| `CH-` か `GL-` を名乗る変更要求 | ⛔ **75 件中 7 件** |
| レビュー観点が手順に出る回数 | ⛔ **0** |

⭐ **そこで、変更要求に 3 つの節を必ず持たせ、機械検査がその欠落を落とすようにした。**

```
① この変更は CH- / GL- のどれを前へ進めるか
   ⛔ どれでもないなら「どれでもない」と書く。基盤の作業は正当な答えである
   ⚠️ 番号で書く。CH- や GL- と接頭辞だけ書いても検査は通らない
② レビュー観点のどの条項を当て、何が出たか
③ 利用者に問わずに決めたことの一覧。⭐ 空でよい。無いのが駄目
   ⛔ 行には `決定 n` と振る。`D-` に数字を続けた綴りを振るな —— 検査 53 が赤くなる（07 の「レビュー文書の行 ID」）
   ⚠️ 実測（2026-09-14）: 変更要求の下書き 3 本がその綴りで振り、`決定 n` へ振り直した
```

⚠️ **検査にできない限界** —— **問いを立てさせることはできても、答えの質は保証しない。**
`CH-1` と書くだけの儀式に堕する危険は本物である。⭐ **ただし儀式かどうかは人が読めば見える。書かれていない状態よりは検査可能である。**

## ⑧ 「問う」の作法 —— **丸投げではない**

⛔ **選択肢だけ並べて返してはならない。** ⭐ **順に当たってから、根拠つきの推奨を添えて問う:**

1. **仕様書を読み切る** —— ⭐ **半分以上は「実は在る」。** 要求は `STATEMENT` の後の段落に MUST を置くことが多い
2. **確定した参考資料を当たる**（[03](03-implementation.md) の順序）
3. **それでも無ければ、推奨と理由を添えて問う**
4. **裁定を受けたら [02](02-changing-the-spec.md) の手順で当てる**

⚠️ **問う前に測る。** 「どちらが良いか」は、影響を数えてから聞くほうが答えやすい。
⭐ **実例**: 既定のマイルストーン図形を問うたとき、指し先を測っていなかったために誤った根拠を添えてしまい、
測り直して訂正した。**1 行だけ見て読まない。表の前後を見る。**

**問いの形（2026-09-08 から効いた形）:**

```
⛔ 記号で問うな —— 具体名と使う場面で書け（利用者の指示 2026-09-08）
⭐ 案を 2 つ以上挙げ、表で比べ、推す案を根拠と代償つきで示せ。代償を正直に書くと、利用者は別の案を選べる
⭐ 状態を問うときは「保存するか・取り消せるか・何で変わるか」の表で見せよ
   ⚠️ 実測（2026-09-25）: 利用者はその表から「保存と画面がずれる」穴を自分で見つけた（CR-570）
⛔ 例外を推す前に、仕様に同じ形の前例が無いかを探せ（取り消しの UN-*、未保存の編集の FR-100 ほか）
   ⚠️ 実測（2026-09-25）: 「縮小で auto に戻る変化は未保存にしない」を推したが、全体表示の取り消し（UN-17）が同じ形で既に在った
⭐ UI の大きさ・重なり・札の置き方は散文で問わず、触れる見本を先に作って触らせよ（05 の 7）
⭐ 利用者への説明は日本語で書く。コード・コミット文は英語の ASCII（03 の 5）
```
