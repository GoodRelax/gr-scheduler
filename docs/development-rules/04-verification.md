# 04 確かめ方 —— 試験・実物・機械検査

⛔ **「通った」は「正しい」ではない。** 本書は、何をもって確かめたと言えるかを定める。

---

## 1. ⛔ 書いた者に、その試験を書かせない

⛔ **ユニットを書いた者が、そのユニットの試験を書いてはならない。**
**実装を読んで書いた試験は、実装の読み違いごと緑になる。**

```
A  製品コードだけを書く。「別の者が仕様から試験する」と伝えられている
   ⭐ だから公開する形を、それだけで意味が通るように作る
B  docs/spec だけを読んで試験を書く。A の本体ロジックは読まない
   （読んでよいのは冒頭の宣言・公開する型・署名まで）
```

- ⭐ **落ちた試験は「手間」ではなく「発見」である**
- ⛔ **期待値をコードに合わせて書き換えてはならない。** 仕様が明確ならコードを直す（その文を引用する）。
  仕様が曖昧ならその件を落とし、**食い違いとして報告する**
- ⭐ **表を指す要求の試験は、表を写した固定データで駆動する**（`docs/development-rules/08-spec-template/spec-writing-rules.md`）
- ⭐ **単体試験が要るとき（3.5 節の表 `UO` のどの行にも当たらない関数）も、書くのは B —— 仕様だけを読む体である。** ⛔ その関数を書いた者が書いてはならない（`JDG-635`）

⚠️ **実測**: 415 件が緑のまま、ある関数が仕様の下限を落としていた（見つけたのは監査で、試験ではない）。
⭐ **仕様から書かせた 2 回の走りは、実装者自身の試験には出せない欠陥を 2 件捕まえた** ——
既に否定されていた古いコメントと、`@purity pure` を名乗りながら引数を書き換えていた関数。
⚠️ **実測（2026-09-14）: `DFC-578`・`DFC-579`・`JDG-72` のアンカー・`HB-6` の特別扱いは、直しを抜いても既存の単体試験が緑のままだった。区別したのは仕様だけを読む体が足した件だけである。**

---

## 2. ⛔ 通るだけの試験は何も証明しない

⭐ **検査・契約・免除は、わざと壊して落ちることを確かめるまで、確かめたことにならない。**

```
1. 期待どおり通ることを見る
2. ⛔ 壊す。落ちることを見る          ← ここまでやって初めて「効いている」
3. 戻す。ファイルが元に戻ったことを確かめる
```

⚠️ **控えを取ったら `ls -la` で存在と大きさを見る。** ⛔ **失敗した `cp` を信じて復元したつもりになり、原稿を壊した実例がある。**

⭐ **原稿から値が届く仕組みの受け入れ試験は「原稿の値を 1 つ変えると試験が落ちるか」とする。**
⚠️ **落ちなければ、その値はどこにも届いていない。**

## 3. ⛔ 緑の試験は「動くアプリ」を意味しない

⚠️ **描画・入出力を触ったときは、開発サーバの実 DOM を見る。** 過去に何度も刺さった:

- **rAF だけの初回描画** → 入力が来るまで白い画面
- ⛔ **文字列の鍵に制御文字が 1 つ混じる** → ブラウザが書き換える → 成果物のハッシュが合わなくなり
  **アプリ全体が止まる。** ⭐ **鍵は ASCII だけ**
- **収める表示のはみ出し**（印とラベルを数えていない）／ヘッダーが日程表の高さを奪う

⭐ **見るもの**: 要素数・色・`data-role` の節点・コンソールとセキュリティ方針の誤り。
⚠️ **プレビュー枠は幅も高さも 0 で冷間起動することがある** —— **そのときの崩れは退行ではない。**
1280×800 にして読み直してから結論を出す。

⛔ **描かれる面を変えた波は、その面を主張する Playwright の件（`tests/system` ほか。6.4）を走らせてから緑と呼べ。** vitest の緑では足りない。
⚠️ **実測（2026-09-14）: 直しの体は vitest だけを回し、組み直したヘルプとツールチップを主張する `tests/system` の 3 件が、通しの e2e まで赤のままだった。**

## 3.6 ⛔ 発見器は 1 つでは足りない

⚠️ **同じ日に、4 つの発見器がそれぞれ**別のもの**を捕まえた。**⛔ **どれ 1 つでも欠けていたら、
その分は見つからなかった。**

| 発見器 | その日に捕まえたもの | ほかの器では捕まらない理由 |
|---|---|---|
| **同型突き合わせ**（`npm run parity`）| 行の帯の床が無く、操作子の下段が次の行へ落ちる | 見本と並べて初めて「違う」と言える |
| **掃引**（`tests/system` を 1 回の起動で回す）| 書き出した絵が畳みに追随しない | ⛔ **見本は書き出しを持たない** |
| **仕様だけを読む体** | 5 日間緑だった表の手写し／前に立つ者が書いた偽の条文 | 実装を読む者は、実装の読み違いごと緑にする |
| ⭐⭐ **人のように通しで押す** | 消す確認が嘘をつく／描いた直後に名前を打てない／設定が内部の綴りで出る ほか 6 件 | ⛔ **どの機械も「使い心地」を問うていない** |

⛔⛔ **その日、parity は 50/50、単体は 6009 件、掃引 23 件、機械検査 32 本が全部緑であった。**
**その状態で、通しで押して回るだけで 6 件出た。**
⇒ ⭐ **巡ごとに、少なくとも 1 度は「人として使う」こと。**⛔ **主張を確かめる作業と混ぜるな** ——
**通しで使い、驚いた所だけを拾い、仕様を引いて「驚きでない」ものを落とす。**

### ⛔ 一致しきった検査は、もう問うていない検査である

⚠️ **`npm run parity` は 25 手で 25/25 に達し、頭打ちになった。**⛔ **それは「欠陥が無い」ではない。**
**手を 50 に増やした（使い切った入口を押す／ピンを 3 つ立てる／畳んだ祖先を持つピン ほか）。**
**50 手すべて一致した** —— ⭐ **が、増やす作業そのものが新しい欠陥を 1 件掘り当てた。**
⇒ ⛔ **突き合わせが全部一致したら、次は手を増やす番である。**

## 3.7 ⛔ 原因は 1 つとは限らない。原因ごとに戻して確かめろ

⚠️ **書き出した絵が畳みに追随しない件は、原因が 2 つあり、それぞれ別の状態を割っていた。**

```
①の 1 行を戻す  → 触らない状態と全開きが割れる（全畳みは正しいまま）
②の 2 行を戻す  → 全畳みだけが割れる（ほかは正しいまま）
```

⛔ **「症状が消えた」で止めるな。**⭐ **直した所を 1 つずつ戻し、どれがどの症状を割っていたかを数で出す。**
⚠️ **1 つ戻して症状が全部戻るなら原因は 1 つである。戻らない症状が在れば、原因はもう 1 つ在る。**

**覚えていなければならない規則は、走らない規則である。**

## 3.9 ⛔ 既知の赤・flaky・現状を固定しただけの試験・XSD（`JDG-641`〜`JDG-645`）

- ⭐ **既知の赤は `tests/known-red.txt` に 1 行 1 DFC で置く**（`DFC-nnn`・試験のファイル・件の名・必要なら `flaky`）。関門（4 節の表 `GT`）は、一覧に無い赤で止まる。一覧に在って緑になった行でも止まる（`flaky` の行を除く）—— 減らし忘れに気づくためである。⭐ **減らすのは調整役、⛔ 増やすのは利用者の OK**（`JDG-641`）。
  ⚠️ 一覧と、それを読む関門の走らせ手（`tools/gate/run-gate.mjs`）は `CR-573` の波 3c が作る。それまでは、報告のたびに既知の赤を名指す。
- ⛔ **flaky を retries で隠さない**（`playwright.config.ts` と vitest の再試行は 0 のまま）。DFC を起こして直すか消す。それまでは一覧に `flaky` と付けて載せる（`JDG-642`）。
- ⛔ **現状を固定しているだけの試験を、一斉に棚卸ししない**（`JDG-31`・`JDG-645`）。修正の途中で赤になったとき、覆う条項があればその条項を引かせ（行 ID か逐語）、条項に従って直す。無ければ消し、消したことを commit に書く。
- ⭐ **MSPDI の XSD（`docs/reference/mspdi/`）を読む試験は、XSD が無いとき、その理由とパスを名乗ってスキップする。** ⛔ 関門は根の作業木で回す —— 関門の走らせ手は、XSD が無ければ止まる。⛔ XSD を repo に入れない（`JDG-644`）。
  ⚠️ スキップの手当ては `CR-573` の波 3c が当てる。それまで、XSD を読む試験は作業木で ENOENT で落ちる（2026-09-26、`b6292bb0` で 11 ファイル）。

### ⭐ 何が何を強制するか

```
型検査        層の規則（Entity と UseCase は DOM ライブラリ抜きでコンパイルされる）
              生成された既定値が、その列の値でないこと

              変更要求が 8 条の ①②⑧ に答えていること

人            答えの質。⛔ ここは機械に下ろせない
```

⛔⛔ **記法が届かない所が 1 つ在り、それは `DFC-367` が立った型そのものである。** `実物確認` の欄は ✅ で始まる約束なので、この印を持てない。⚠️ **`対応方針` が「裁定が要る」（真）、`実物確認` が ✅（これも真）という組を、検査 31 はいまも「前者は古い」と読む。**⇒ **その腕を退役させるか、ステータスで絞るかは、この裁定の外の別の判断である。⛔ 体の独断で決めない。**

### 6.10 ⛔⛔ 出荷ビルドを押すとき、盤面を使い回すと嘘をつく

⛔⛔ **1 つの盤面を作って複数の画素に使い回すな。⭐ 1 押しにつき盤面を 1 つ作り直せ。**
⚠️ **実測**: 同じ画素について、探索子 08 は「`GR-9` が答えた」、探索子 10 は「何も答えなかった」と報告した。
⭐ **1 押し 1 盤面に書き直した探索子 11 は自己整合し、探索子 12 が 3 つの倍率で再現した。**
⇒ **前の押しが残した選択・構え・実績が、次の押しの答えを変える。**

⛔⛔ **`Command Palette` は日程の上に浮いており、その矩形の押しを全部食う。**
⚠️ **実測（既定の窓 1920 × 1080）: `x = 209..595` ／ `y ≒ 100..253`。**
⇒ **その範囲を押す探索子は、⭐ 先に `IC-7` でパレットを下ろせ。**
⛔ **これを知らずに書いた探索子 1 本が、63 画素 × 3 倍率を丸ごと無駄にした** —— **マーカーの上の押しまで「何も無い」と読めた。**

⛔⛔ **掴んだ行（`GR-n`）を答える証人は、`partAt()` でも ポインタの形 でもない。**
⚠️ **実測**: `partAt()` はいちばん外側の `data-role` を返すので、タスクのどの画素でも `Schedule Canvas` である。
⚠️ **`frame-loop.ts` の `POINTER_SHAPE_BY_GRAB` は `GR-1` / `GR-2` / `GR-7` / `GR-8` / `GR-9` / `GR-10` / `GR-11` / `GR-13` / `GR-14` / `GR-16` / `GR-17` / `GR-18` に等しく `null` を与える。**
⇒ ⭐ **効く証人は「その押しが 何を書いたか」である** —— **`Agent API` で文書を読み戻し、どの列が動いたかで行を名指せ。**
⛔ **絵の差分では足りない** —— **複数の行が同じ絵を動かす。**

⭐ **割合を測るときの分母は 溝（track）の長さであって、窓の大きさではない**。
⚠️ **既定の窓 1920 × 1080 で、横の溝は `x=200 w=1702`、縦の溝は `y=85 h=977` である。**
⛔ **窓で割ると、縦の規則が「予測 0.092 対 実測 0.102」となり、守られているものが壊れて見える。**

### 6.11 ⛔⛔ e2e の時間切れは、開発サーバの監視が根の配下を這うことで起きる（`DFC-604`）

⛔⛔ **「`page.goto: Target page, context or browser has been closed`」＋ 30 秒の時間切れを、並行の走行や冷えたサーバの最初の読み込みのせいと読むな。** ⚠️ **その 2 つの読みは、どちらも誤診であった。**
⚠️ **実測（2026-09-16）**: `playwright.config.ts` が起動する `npm run dev` の Vite の監視（chokidar）が、根の配下の `.claude/worktrees`（作業木 144 個、ファイル約 22 万）を起動から約 150 秒這い、その間の応答が最大 31 秒止まった。「browser has been closed」は afterAll が閉じた結果であり、原因ではない。
⇒ ⭐ **`vite.config.ts` の `server.watch.ignored` に `**/.claude/**` を置く。** 直す前は `rows-fixed-with-nothing-holding-them.test.ts` が 187 秒で 1 件落ち、直した後は 32 秒で 12/12、`tests/system` は 120/120 だった。

⛔ **温め（globalSetup で 1 度開く）では防げない** —— 詰まりは「最初の 1 回」ではなく「起動からの経過時間」に縛られる。
⛔ **直す体の作業木で「再現しない」は、原因が根に在るという印である** —— 作業木の中には入れ子の作業木が無い。
⛔⛔ **e2e を回しているあいだ、根で checkout もファイルの書き込みもするな** —— Vite が `page reload` を送り、描画が消えて試験が落ちる（別の作業木の `scratch/` への書き込みでも 44 回起きた）。
⇒ **時間切れの形の赤を見たら、trace でサーバの応答の時刻を読め。** ⚠️ 作業木が溜まれば、監視の外の道具にも同じ重さが出うる —— 溜めたら掃け（OneDrive の中ではフォルダが読み取り専用になり、`git worktree remove` / `prune` が `(y/n)` で止まる。`attrib -R` で外してから消す）。

### 6.12 ⛔⛔ 自分で立てたサーバも `reuseExistingServer` に拾われ、`src/` の直しが 1 つも走行に反映されない（`DFC-160`）

⛔⛔ **「直したのに赤のまま」を、直しが効いていないとすぐに読むな。** ⚠️ **その読みが外れることがある。**
⚠️ **実測（2026-09-16）**: `playwright.config.ts` の `webServer` は `reuseExistingServer: true`。調べもののために `npm run dev -- --port <port>` を先に立て、そのあとで `src/` を直すと、次の `npm run e2e` は自分でサーバを立てず、**直す前のモジュールを配っている古いサーバを採用する**。`DFC-160`（行見出しパネルの隅の入口の刻み）を直したのに、走行は刻みを直す前の `52.0026 / 34.6684 / 17.3342 / 0` のまま読み、「直したのに赤」に見えた。ポートを空けて走らせ直したら、同じ件が 925ms で緑になった。
⇒ ⭐ **`src/` を直す前に立てたサーバは、直したあとに必ず落とすこと。** ⛔ **緑と赤のどちらの読みも、サーバをいつ立てたかを確かめるまで信用しない。**

⚠️ **6.4 には「取り残された成果物を dev サーバが拾う」記録が既に在る（`scratch/` の `.html` が構文エラーを起こす件）が、それとは別の穴である** —— **今回拾われるのは成果物ではなく、自分が立てたままの、直す前の"生きたサーバ"そのものである。**

⛔⛔ **e2e の走行そのものが根の `dist/index.html` を焼き直す** —— `tests/nfr/nfr-004-single-file.test.ts` が走行の中で `npm run build`（`vite build`）を呼び、`vite.config.ts` が埋め込みの CSP を sha256 で計算し直して書き込む。
⇒ ⭐ **利用者が `file://` で試す根の `dist/index.html` は、`e2e` を回すたびに書き換わる。** 「試せる」と言う前に、最後の走行のあとで改めて `npx vite build` を打ち、その sha256 を採ること。
