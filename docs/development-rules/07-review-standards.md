## はじめに

### 目的

本書は、ソフトウェアの成果物（仕様書・設計・コード・テスト）をレビューで確かめる観点を定める。

本書は、レビュアーが参照するレビュー観点の唯一の正（Single Source of Truth）である。

### 適用範囲

- 本書は SW 開発の全般に適用できるように設計されている。特定の業務の分野に限らない。
- 本書は NDD（下の NDD 節）を主な対象として設計した。
- NDD を採らない開発も、本書の観点を手を加えずに使える。

### 使い方

レビュアー（人か AI）は、次の順にレビューする。

1. 下の「構成」の表で、成果物の種類に当たる節を選ぶ。NDD の節の観点は、NDD を採るかにかかわらず、すべての成果物に当たる。
2. 選んだ節の詳細を読み、成果物を確かめる。
3. 「総合レビューチェックリスト」の全行に Verdict（判定: PASS / FAIL / NA）を書く（記入の規則は、チェックリストの節の冒頭が持つ）。
4. 指摘を付録 A の「レビュー指摘の対応」に従って記録し、対応する（重大度は「重大度」の節で決める）。

### 構成

## NDD（Naming Driven Development / 命名駆動開発）

### NDD とは

NDD は、命名を最優先とする AI 連携の SW 開発スタイルである。人は名前に魂を込め、あとを AI に任せる。

**なぜ名前を最優先にするか:**
- プログラミング言語と開発手法の歴史は、人が本質的な仕事だけを受け持つ方向へ進んできた。
- 2026 年以降、AI は高度に進化し、一般的なエンジニアより高い品質で仕様書もコードもテストケースも書くようになった。
- 人に残る本質的な仕事は、何のために、誰のために、何を、どうしたいのかを考え、誤解の無い言葉で AI に指示することである。
- AI（LLM: Large Language Model / 大規模言語モデル）は、言葉をベクトル（意味の近さを表す数の並び）として扱い、指示の言葉の意味から次の言葉を生成する。ベクトルが並ぶ空間では、意味の近い概念ほど近くに位置する。
- 正確な用語は、ベクトル空間の中で概念の位置をはっきり指し、AI の生成の精度を上げる。
- 曖昧な語や揺れた語（1 つの物に 2 つの名前、2 つの物に 1 つの名前）は、ベクトル空間の中で概念の位置をぼかし、AI の作るものをぶれさせる。
- 言葉のいちばん小さな単位は名前である。ゆえに、NDD は名前を最初に、最も厳しく決める。

### NDD の基本の考え方

- NEIM（名は体を表す）: 名前から対象の意味・機能・責務を読み取れる。
- OKPN（1つの名前に1種類の値）: 1 つの名前が 1 種類の値だけを取る。
- OMPV（1つの値に1つの意味）: 1 つの値が 1 つの意味だけを持つ。
- 3 つの考え方の確かめ方と例、用語集、機械が読む原本、図と表、名前の選び方、改名、仕様が決めていない振る舞いの観点は、下の「NDD で重要となるレビュー観点」が持つ。運用は付録 A が持つ。

### NDD で重要となるレビュー観点

本節の観点は、NDD を採らない開発も含め、すべての成果物に当たる。

**NEIM（Name Explaining Its Meaning / 名は体を表す）:**
- 対象: 要求仕様の用語から、変数・関数・クラス・部品・データのキーと値まで、すべての名前
- 名前から対象の意味、機能、責務を読み取れるか
- 名前が、対象と違う意味、機能、責務を表していないか
    - 例: 悪い `"flag": true`（何の旗か名前から読めない） → 良い `"isMilestone": true`
    - 例: 悪い `checkTask()`（調べるだけか、直すのか読めない） → 良い `isTaskValid()`（調べるだけ）と `repairTask()`（直す）
- 細目: 汎用名（`data`, `info`, `tmp`, `obj`）と曖昧な動詞（`process`, `handle`, `manage`）を使っていないか
- 細目: 同じ対象を 1 つの名前で呼んでいるか（`Usr` と `User` を混ぜない）
- 名前が、仕様書の用語集の語と一致しているか
- 設計とコードの命名の規約（品詞・単位・レイヤー別）は、R2 の Naming 節が持つ。

**OKPN/OMPV**
- 対象: 値を取るすべての名前（例: JSON のプロパティ、関数の引数、変数、設定の項目、画面の項目、用語集の用語）。
- **OKPN（One Kind Per Name / 1つの名前に1種類の値）**
    - 1つの名前が1種類の値だけを取っているか
    - 1つの名前が複数の種類の値を取っていないか
    - 例: 悪い `"color": "#c0504d/#b2423f"`（明と暗の 2 値を詰めた） → 良い `"color": {"light": "#c0504d", "dark": "#b2423f"}`
- **OMPV（One Meaning Per Value / 1つの値に1つの意味）**
    - 1つの値が1つの意味だけを持っているか
    - 1つの値が複数の意味を持っていないか（例: -1 や空文字に別の意味を載せていないか）
    - 例: 悪い `"parentId": 0`（0 で「親が無い」） → 良い `parentId` を書かない
- 例外: 参照している規格が名前と値の仕様を定めている場合は、規格の仕様に準拠すること。

**用語集:**
- 必須: 用語集の用語ごとに、人が確かめた記録（例: 人の裁定の ID か、確かめた印）があるか
- 用語集が、1 つの名前に 1 つの意味だけを持たせているか（上の「OKPN/OMPV」）
- 似て非なる概念に、別の名前を付けているか
- 同じ概念を言い換えただけの言葉を、1 つの名前にそろえているか
- 用語集は日英を併記してよい。併記するなら、どちらか一方を正としているか
- 推奨: 英語を正としているか。AI もコードも、英語を土台に動くからである。

**機械が読む原本:**
- 機械が読む原本（JSON、JSON Schema、データベースの表の形）を、付録 A の「NDD の進め方」の「機械が読む原本の決まり」に従って持っているか（必須と推奨の別も付録 A に従う）

**図と表:**
- 図や表を使う場合のトレーサビリティ（要求・図表・実装・テストを ID で辿れること。シーケンス図は、図ごとに、対応する要求と ID で辿れること）は、R1b の「トレーサビリティ」で確かめる。
- 必須: 各コンポーネントの定義（責務と公開面）があるか
- シーケンス図が全ケースを網羅できないなら、仕様を EARS で定め、シーケンス図を基本の動作を理解するための補助にしているか（仕様として参照してよい図は、付録 A の「NDD の進め方」の「文型と図表の使い方」）

**名前の選び方:**
- 名前を、何を指すかに照らした適切さだけで選び、不適切と分かった名前を残していないか（詳しくは付録 A の「名前の選び方と改名」の「名前の選び方」）

**改名:**
- 改名を、付録 A の「名前の選び方と改名」の「改名の手順」のとおりに行っているか

**仕様が決めていない振る舞い（未決の問い）:**
- 仕様を書くときも、仕様に従って作るときも、決まっていない点を黙って決めず、付録 A の「未決の問いの進め方と書き方」のとおりに扱っているか（止まるか仮に決めるか、印と一覧、答えが出た後の閉じ方）

## R1: 要求品質レビュー観点（仕様書の要求と、要求の上位の項目（例: 目的、ユースケース）が対象。文の決まりは仕様書の全章）

### R1a: 要求構造品質

- すべての要求（機能要求と非機能要求）に ID が付与されているか（ID の形は仕様書の決まりに従う。例は付録 A の「ユースケースと要求の書き方の例」）
- 要求ごとに、ID と要求文と親の ID を対で読めるか（形は仕様書の決まりに従う。例: 表）
- ユースケースから導いた要求が、親の ID で、導いた元のユースケースの道（正常に終わる道か拒む道）を指しているか
- 閾値、率、期限の値を、設定の表か JSON に置き、要求文から表の項目名か JSON のキーで指しているか（同じ値を 2 か所に書いていないか）
- テスト不可能な表現（例: 「適切に」「十分に」「高速に」）が残っていないか
- 矛盾する要求が存在しないか（例：同一操作に複数の結果が定義されている）
- ユースケースの正常に終わる道と拒む道のそれぞれを、ID で指せるか（ユースケースの細かい検査は R1c）
- 非機能要求が、テストで合否を判定できる基準を持っているか（例：「200ms以内」「99.9%以上」。数値は、設定の表の項目か JSON のキーで指してよい。数値の無い要求は、観察できる結果で書く）
- エンティティ名・操作名が一貫して使用されているか（同一概念に複数の名前がない）
- 略語・専門用語に定義があるか（用語集の存在）
- 要求の上位の項目（例: 目的、課題、目標）を、仕様書の決まりの形で書いているか。達したかを確かめる項目（例: 目標）を、観察で判定できる文で書いているか
- 用語と名前で、名前から対象の意味・機能・責務を読み取れるか（NEIM）。1 つの名前が 1 種類の値だけを取るか（OKPN）。1 つの値が 1 つの意味だけを持つか（OMPV）

### R1b: 要求表現品質（要求工学的観点）

**文の決まり（仕様書の全章）:**
- 仕様書のすべての章で、「など」「等」を使っていないか（例は「例:」で示す）
- 指示代名詞（例: 「これ」「その」）を使わず、指す物の名前を書いているか（英語の仕様では "it"、"its"、"this"、"these"、"they"、"them"、"their"、"itself" を使わず、"that" と "those" を指示語として使わない。関係代名詞と接続詞の "that" は使ってよい）
- 要求文と命令文のほかの文に主語と動詞があり、動詞が他動詞なら目的語もあるか（目的と課題の動詞句、見出し、表の項目名は文ではないので対象外。要求文は下の「曖昧性の排除」で確かめる）
- 要求文のほかの文で、受動態を使っていないか。否定形を、下の「否定形の扱い」の 2 つの場合にだけ使っているか（要求文は下の「受動態の排除」と「否定形の扱い」で確かめる）

**曖昧性の排除:**
- 曖昧表現（例: 「なるべく早く」「適切に」「必要に応じて」「可能な限り」）が残っていないか
- まだ決まっていない値や表現が、NDD の「仕様が決めていない振る舞い」に従っているか
- 各要求文に主語と動詞があり、動詞が他動詞なら目的語もあるか

**受動態の排除:**
- 受動態（「データが保存されること」）で、責務の所在を曖昧にしていないか。能動態（「システムはデータを DB に保存すること」）で書いているか

**否定形の扱い:**
- 否定形の要求を、代わりの行動の要求で書いているか
    - 例: 悪い「パスワードをログに書かないこと」 → 良い「システムは、パスワードを伏せ字にしてからログに書くこと」
- 否定形を、次の 2 つの場合にだけ使っているか
    - 対象の全体と否定する部分が決まっていて、否定形のほうが分かりやすい（例: 「システムは、管理者のほかの利用者に管理画面を表示しないこと」）
    - テストで、起きないことを確かめる（例: Gherkin の `But`）
- SHALL NOT と SHOULD NOT（`shall not`、`should not`。日本語の仕様では「〜しないこと」「〜しないことが望ましい」）を、上の 2 つの場合にだけ使っているか
- 二重否定（「無効でない場合」）が使われていないか

**異常系・準正常系の網羅:**
- 各機能要求に対して以下の観点が考慮されているか:
  - タイムアウト（外部サービス応答なし）
  - 中断（ユーザーが操作を途中で中止）
  - 同時操作（複数ユーザーが同一リソースを同時変更）
  - 権限不足（認証切れ、権限なし）
  - データ不整合（参照先が存在しない、型不正）
  - リソース枯渇（ディスク満杯、メモリ不足）
- 正常系だけでなく、準正常系（正常だが特殊なケース）と異常系が明示されているか
- 故障でユースケースを終えられなかったときの扱い（例: 途中の状態を残さない）を、非機能要求に書いているか

**仕様の重複・競合の排除（DRY for Specs）:**
- 同じ要求が複数箇所に分散して記述されていないか（分散している場合、どれが正かが曖昧になりdefect の原因）
- 同じことを2度書かない。必要なら唯一の本体を直接参照する
- 異なるセクションの要求間で暗黙の矛盾がないか（例: FR-001の前提条件がFR-015の動作と競合）
- 要求の前後の依存を、要求文の条件（例: EARS の状態（State-driven）の型の「<FR-001 で決めた状態>の間、」）で書いているか（親の ID には書かない）

**完全性の検証:**
- MECE（漏れなくダブりなく）の観点で要求が整理されているか
- ステークホルダーごとの視点（管理者/一般ユーザー/外部システム）で要求の漏れがないか
- 境界条件（最小値、最大値、空、null）が明示されているか

**トレーサビリティ:**
- 上位の目的から要求、設計、実装、テストまでの項目を、ID で双方向に辿れるか（鎖に置く項目と親子の組は、仕様書の決まり（テンプレート）に従う。例は付録 A の「トレーサビリティの鎖の例」）
- 子が親の ID を持ち、親の ID で検索して子を見つけられるか（親の ID を書く所は、仕様書の決まりに従う。例: 表の traces の列、コードのコメント `// Spec:`、シナリオのタグ）
- 親の ID の検索を、ID 全体で一致させているか（例: 語の境で検索し、`FR-001` で `NFR-001` に当てない）
- `// Spec:` を、仕様の振る舞いを実装する所（例: UseCase の公開の関数、コンポーネントの公開面の関数）とテストに書いているか。実装の単位は、仕様の振る舞いを実装する所である。ほかのコードは呼ぶ側の親を受け継ぎ、`// Spec:` は要らない
- 親が子の ID を持っていないか（仕様書の決まりが認める、子を描く図を除く）
- 裁定や決定の ID を、親の ID の代わりにしていないか（裁定や決定の ID は根拠として書く）
- ID を振り直したり、欠番を使い回したりしていないか
- 次の漏れの数が、すべて 0 か
    - 親を持たない、鎖の項目（最上位の項目と、仕様書の決まりが鎖の外とする節は数えない）
    - 子を持たない、要求より上位の項目
    - 実装を持たないか、テストも仕様書の検証方法の一覧の行も持たない末端の要求（子の要求を持たない要求）。仕様書の制限事項の節の本文に要求の ID と見送る理由がある MAY と SHOULD の要求は、漏れの数から除く（要求は要求の章に残す）
    - 実装かテストを持たない、要求を辿る、要求のほかの実装とテストの親（例: 実装仕様）。要求を辿る、要求のほかの親を持つ実装とテストは、親が辿る要求の実装とテストにも数える
- 下位要求をすべて満たせば上位要求を、上位要求をすべて満たせば目的を満たせるか
- どの上位要求にも辿れない下位要求・実装・テストケースが無いか（目的に寄与しない作り込みが無いか）
- 各要求に、検証方法が決まっているか（子の要求を持たない要求は、テストを 1 つ以上持つか、テストの代わりに、検証方法（検査、解析、実演）と検証者を仕様書の検証方法の一覧に持つ。仕様書の制限事項の節の本文に要求の ID と見送る理由がある MAY と SHOULD の要求を除く）

**要求の記法（EARS: Easy Approach to Requirements Syntax）:**
- 要求を EARS の型で書いているか（必須）

| 型 | 英語 | 日本語 |
|:---|:---|:---|
| 常時（Ubiquitous） | `The <system name> shall <system response>.` | `<システム名>は<システムの応答>すること。` |
| イベント（Event-driven） | `When <trigger>, the <system name> shall <system response>.` | `<トリガー>とき、<システム名>は<システムの応答>すること。` |
| 状態（State-driven） | `While <precondition(s)>, the <system name> shall <system response>.` | `<状態>の間、<システム名>は<システムの応答>すること。` |
| 異常（Unwanted Behavior） | `If <trigger>, then the <system name> shall <system response>.` | `もし<トリガー>場合、<システム名>は<システムの応答>すること。` |
| 任意機能（Optional Feature） | `Where <feature is included>, the <system name> shall <system response>.` | `<機能>がある場合、<システム名>は<システムの応答>すること。` |
| 組み合わせ（Complex） | `Where <feature is included>, while <precondition(s)>, when <trigger>, the <system name> shall <system response>.` | `<機能>がある場合、<状態>の間、<トリガー>とき、<システム名>は<システムの応答>すること。` |

- 組み合わせの条件を、Where → While → When の順に置いているか
- If … then（異常）を、望まない振る舞い（拒む道と故障を含む）の要求にだけ使っているか
- Where（任意機能）を、製品の構成（積む機能、動かす前に決める設定の値）にだけ使っているか。設定の値なら、型は `Where the <setting> is <value>,`（日本語の型は `<設定>が<値>の場合、`）である
- While（状態）の `<precondition(s)>` に、動いている間に続く状態を書いているか（ユースケースの前提とは別の物）
- 条件を、EARS の型の表の語だけで書いているか。日本語の条件を示す語で、「とき」をひらがなで書き、「場合」を「もし〜場合」（異常）と「〜がある場合」「〜が〜の場合」（任意機能）にだけ使っているか
- 英語の強さの語と日本語の文末が強さに合っているか: SHALL は `shall`「〜すること」、SHOULD は `should`「〜することが望ましい」、MAY は `may`「〜してもよい」、SHALL NOT は `shall not`「〜しないこと」、SHOULD NOT は `should not`「〜しないことが望ましい」
- 1 つの要求文に、動作（`shall` か強さの語）が 1 つだけか
- 細部を表・式・図で定めた場合、EARS の要求文から、定めた表・式・図を参照しているか（詳しくは付録 A の「NDD の進め方」の「文型と図表の使い方」）

### R1c: ユースケース品質

本節は、ユースケースについてレビュアーが確かめる観点を持つ。ユースケースの欄、見出し、ID の形は、仕様書の決まり（テンプレート）に従う。例は付録 A の「ユースケースと要求の書き方の例」。

**粒度:**
- 1 つのユースケースが、アクターの 1 つの目的（アクターが 1 回の作業で成し遂げたいこと）だけを持つか。目的を成し遂げたら、アクターは作業を終えてよいか
- 1 つのユースケースの中に、ほかの人の判断を待つ所か、アクターが作業をいったん終え、後で続ける所を含めていないか（含むなら分け、分けたユースケースのつながりを示す）
- アクターが目的にしない操作（例: ログイン、手順の中で選ぶための一覧）を、ユースケースにしていないか（ログインは前提に、一覧は機能要求に書く）
- 照会が目的なら（例: 残高を確かめる）、照会をユースケースにしているか
- 人が判断するユースケース（例: 申請を承認するか却下するか決める）を、判断の結果ごとに分けていないか。アクターが手順で判断を伝え、結果にシステムが判断を記録したことを書いているか

**欄と ID:**
- 各ユースケースが、目的、きっかけ、前提、結果、手順、拒む場合を持つか
- 各ユースケースと、正常に終わる道と拒む道のそれぞれを、ID で指せるか
- ユースケースごとに、同じ名前の UseCase が、仕様書のコンポーネントの定義に 1 つあるか（名前の形は仕様書の決まりに従う。接尾辞 `〜UseCase` か `〜Interactor` は付けてよい）
- 各ユースケースが、親の ID で上位の項目（例: 目標）を指しているか

**前提と拒む場合の境:**
- 前提に、手順の中でシステムが確かめない前提だけを書いているか（手順の中でシステムが確かめるなら拒む場合に書く）。前提を、先のユースケースか全体に当てる要求（例: 認証）が保証しているか
- 拒む場合に、システムが業務の規則か入力に照らして拒むことだけを書いているか（故障は非機能要求に書く）。各拒む場合が、応じる手順を示しているか
- 拒まずに別の道で目的を成し遂げる場合（例: 未登録の振込先なら、先に登録を求める）を、ユースケースでなく機能要求に書いているか

**手順の文:**
- 手順に、1 人のアクターが待たずに続ける、システムとのやり取りだけを書いているか。システムの内部の処理を手順にしていないか
- 1 つの手順に、主語が 1 つ、動作が 1 つか
- 画面と操作の手段でなく、アクターから見た意図（例: 伝える、選ぶ）で書いているか
- 条件を手順に書かず、拒む場合に書いているか

**つながりと網羅:**
- 分けたユースケースを、後のユースケースの前提に前のユースケースの ID を書いてつないでいるか（つながりのまとめ方は仕様書の決まりに従う）。つながりをまとめるなら、まとめに入るユースケースが、まとめを親の ID で指しているか
- すべてのユースケースの、正常に終わる道と拒む道のそれぞれに、ユースケーステストのシナリオが 1 つ以上あるか（R6 の「テストケースの記法（Gherkin）」）

## R2: SW設計原則レビュー観点（仕様書のアーキテクチャ・仕様とコードが対象）

### Naming（命名）— 設計とコードの命名規約（MUST・最重要）

- 命名はソフトウェアの主要なインターフェースである。命名は最重要のレビュー項目として扱い、SHOULD ではなく MUST とする。
- 名前の原則は、要求仕様の段階から当たる。
    - 名前から対象の意味・機能・責務を読み取れるか（NEIM）
    - 1 つの名前が 1 種類の値だけを取るか（OKPN）
    - 1 つの値が 1 つの意味だけを持つか（OMPV）
    - 名前を、何を指すかに照らした適切さだけで選んだか
- 本節は、設計とコードの命名の規約（品詞・単位・レイヤー別）を定める。
- コードは意図を叫ぶべきである（Screaming Architecture）。ソフトは言霊——名前が構造と意図を規定する。

**品詞の規約**（`pure` / `semi-pure-immutable` / `semi-pure-mutable` / `non-pure` は純粋性の 4 値。定義は後述の R7 節、注釈規約は R7 の「`@purity` タグ」）**:**

| 対象 | 品詞 | 例 |
|---|---|---|
| クラス・型 | 名詞または名詞句 | `Order`, `CellVoltage` |
| コマンド（`non-pure`。状態を変える） | 動詞 + 目的語 | `cancelOrder` |
| クエリ（`pure` / `semi-pure-immutable`。アクセサ。可変のオブジェクトの getter（`semi-pure-mutable`）も含む） | 名詞句、または `is/has/can`。値を変換する純粋な関数は動詞 + 目的語でよい（UseCase は照会でも動詞句） | `totalPrice`, `isExpired`, `calculateTax` |
| 外部を読む操作（`semi-pure-mutable`） | 動詞 + 目的語 | `readDocument`, `fetchUser` |
| プロパティ | 名詞 | `retryCount` |
| Boolean（変数・関数・プロパティ） | `is/has/can` で始める（`should` は誰の判断か読めないので使わない。判断の結果は `isRetryRequired` のように書く。外部を読んで真偽値を返す関数は、外部を読む操作の行に従って動詞 + 目的語にし（例: `checkFileExists()`）、結果を `is/has/can` の変数で受ける） | `isExpired`, `hasChildren` |
| コレクション（変数・プロパティ） | 複数形 | `orders`, `tasks` |
| イベント | 過去形 | `OrderPlaced`, `CellVoltageExceeded` |

**コマンドとイベントを形で分ける。** コマンドは**今から起こすことの依頼**であり拒否できる。イベントは**既に起きたことの通知**であり拒否できない。`PlaceOrder` と `OrderPlaced` が形で違えば、**受け手が拒否してよいかが名前から読める。** メソッドの品詞は R2 の CQS の分離と対応する。

**副作用が無いことと、呼んで安価であることは別である。** 時刻・乱数・DB/ファイル/NW を読む関数（`semi-pure-mutable`）は、状態を変えず値を返すだけでも**動詞にする。** 名詞にすると遅さと失敗しうることが名前から消え、ループの中で気軽に呼ばれる（R2 の POLA）。`readDocument()` を `document()` に改めてはならない。**判定は R7 の `@purity` タグを元のまま使う** — 新たに分類し直す必要はない。

**単位が固定の量は名前に単位を入れる。** `timeoutMs` / `voltageMv` / `capacityAh`。**単位の取り違えは型検査を通り抜ける。** ただし単位を実行時に持つ値（例: `Quantity { amount, unit }`）は対象外である。単位が名前ではなく値だからである。

**レイヤー別のコンポーネント・クラス名:**

| レイヤー | 品詞 | 例 | 兆候 |
|---|---|---|---|
| Entity | 名詞 | `Order`, `Temperature` | 動詞、`〜Data` / `〜Info` |
| Use Case | **動詞句**（接尾辞を付けるなら `〜UseCase` / `〜Interactor`） | `ConvertUnit`, `PlaceOrder` | **`〜Service`** |
| Adapter | 役割 + 方式 | `PostgresOrderRepository`, `CliPresenter` | 方式だけ（`DbHelper`）、役割だけ（`Manager`） |
| Framework | 名詞句 | `ExpressRouter`（技術名が元の形で現れてよい） | — |

**既定の 4 層を採らない設計では、仕様書のアーキテクチャ方式が定義した層に読み替える**（R2 の CA のとおり層の数は問わない）。読み替えは層の**役割**（何を担う層か）で対応させる。

**Use Case を動詞句にするのは趣味ではない。** `OrderService` は操作をいくつでも抱えられるが、`PlaceOrder` は抱えられない。**命名が R2 の SRP を強制する。** 逆に言えば、名詞化された Use Case は肥大化の予告である。

### SOLID 原則

**SRP（Single Responsibility Principle / 単一責任原則）**
- 各クラス・ユニット・モジュール・コンポーネント・層は、責務を1つだけ持っているか
- 各クラス・ユニット・モジュール・コンポーネント・層が、複数の責務を持っていないか
- 上位の要素（層・コンポーネント・モジュール）の責務を、中に含む要素の責務を並べずに1文で言えるか
    - 例: 悪い `fileHandlers` の責務が「JSON の読み込みと CSV の書き出し」（中の要素を並べただけ） → 良い `documentIo` の責務が「文書をファイルとやり取りする」（1文の要約）
- 責務を表す文から、手順（1 回の操作の途中の段）・範囲（働きが及ぶ先の列挙）・制約（条件・既定・禁止）の句を除いたとき、句が1つだけ残るか
- 句が2つ以上残るとき、片方だけを書き換えさせる出来事を挙げられないか（挙げられれば、別の責務）
    - 例: 悪い「文書を保存し、一覧を画面に描く」（描き方が変わっても保存は変わらない） → 良い「文書を保存する。保存の前に形を検め、保存できなければ理由を返す」（「検め」は手順、「理由を返す」は制約）
    - 例: 悪い `UserService`（認証・プロフィール管理・メール送信） → 良い `Authenticator`・`ProfileEditor`・`MailSender`
- 推奨: 「〜と〜を行う」という名前のクラスや、互いに関係の無いメソッドを並べたクラスは、複数の責務を持ちやすいので避ける

**OCP（Open-Closed Principle / 開放閉鎖原則）**
- 要求か ADR が予想される拡張を名指す所で、拡張のたびに既存コードの変更（特に if/switch 分岐の追加）が要る構造になっていないか
- 拡張点が、パターン（例: ストラテジーパターン、テンプレートメソッドパターン）で設けられているか

**LSP（Liskov Substitution Principle / リスコフ置換原則）**
- サブクラスが親クラスの事前条件を強化・事後条件を弱化していないか
- オーバーライドメソッドが親の契約（例外の種類・戻り値の意味）を変えていないか

**ISP（Interface Segregation Principle / インターフェース分離原則）**
- 実装クラスが使用しないメソッドを持つインターフェースを実装していないか
- 大きなインターフェースを用途別に分割できないか

**DIP（Dependency Inversion Principle / 依存性逆転原則）**
- 上位モジュール（ビジネスロジック）が下位モジュール（DB・外部API）の具象クラスに直接依存していないか
- 依存方向がインターフェース・抽象クラスを経由しているか
- 単体テストで、依存をモック・スタブに差し替えられるか（Testability。純粋な部分の分け方と読み取りの注入は R7）

### ほかの設計原則

**DRY（Don't Repeat Yourself / 繰り返しを避ける）**
- 同一ロジックが複数箇所に複製されていないか
- 1 つの判断・計算・変換（仕様の 1 つの要求が決めること）を、実装の 1 か所だけが持っているか
- 補助関数を書く前に、ほかのコンポーネントの公開面に同じ処理が無いかを探したか
- ほかのコンポーネントの公開されていない関数を、自分の中に写していないか
- マジックナンバー・マジック文字列が散在していないか（定数化されているか）
- 各検証の決まりの原本が 1 つで（例: 値オブジェクト、スキーマ）、ほかの層は原本を呼ぶか原本から作っているか（サーバー側の検証は、クライアント側にあっても省かない）
- GRS での手順（1 か所）: 足した関数・式ごとに、実装する仕様の行 ID を 1 つ名指し、その行 ID と主な語で `src/` を grep した跡を Remark に書く。検査 45（`check-repeated-expressions.py`）の緑は 1 か所の証拠にしない（名前を付け替えた写しが見えない）
- GRS での手順（公開面）: 足した補助関数ごとに、公開の入口の索引 `docs/review/public-entry-index.md`（表 T-064 から生成）を同じ語で grep した跡を Remark に書く。検査 26b の `crossing-names-baseline.txt` に新しい行が要る変更は、公開を飛ばして境界を越えている印である —— 基準線を上げて通さない

**KISS（Keep It Simple, Stupid / シンプルに保つ）**
- 解決策が問題に対して不必要に複雑になっていないか
- 関数の中のブロック（if、for、while、try）の入れ子の深さが 4 以上になっていないか
- 早期リターンで複雑な条件分岐を平坦化できないか

**YAGNI（You Aren't Gonna Need It / 必要になるまで作らない）**
- 現在の要求に存在しない機能が先回りで実装されていないか
- 過度な汎化・抽象化（例: 現時点で1つの具体的ケースしかない抽象クラス）がないか
- 未使用のパラメータ・フラグ・設定値がないか

**最小構成との比較（オッカムの剃刀）**
- 仕様書の設計判断に ADR-000（最小構成との比較）が存在するか（**存在しなければ本項は違反である。内容の巧拙は本項では問わない**）
- 最小の構成が「要求を満たす」ものとして書かれているか（要求を落とした案は最小構成ではない）
- 採用案が最小構成に対して増やした要素が列挙され、各々に増やした理由があるか（理由は、ADR-000 から ID で指す先にあってよい）
- 理由が「規約に従ったため」だけになっていないか（**どの規約がどの要求のために働いたかまで書く**）

**デザインパターン（Design Patterns）**
- メリット: 繰り返し現れる設計の問題に、実績のある解き方を使える。パターンの名前が共通の語になり、設計の意図を短く伝えられる。変わる部分を分けられる
- デメリット: 間接の層が増え、読むコードとテストが増える。問題の無い所で使うと、かえって変更しにくくなる
- パターンを、要求か、文書にある予想される変更が求める時だけ使っているか（KISS・YAGNI。最小構成との比較は ADR-000 の決まりに従う）
- パターンが解く問題を言えるか
- シングルトンを既定にせず、依存を外から渡しているか（DIP）。使うなら理由を書いているか
    - 理由: シングルトンは全体の状態を隠し、テストで差し替えにくい
    - 例: 悪い 関数の中で `Logger.getInstance()` を呼ぶ → 良い `logger` を引数で受け取る
- やりすぎの兆候が無いか
    - 実装が 1 つで、2 つ目の予定が無い抽象
    - 決まった 1 つの振る舞いのための Factory や Strategy の層
    - 解く問題を言えないパターン
- パターンの役割を名前に出すのは、読み手の助けになる時だけか（NEIM）。飾りとして出していないか

**SoC（Separation of Concerns / 関心の分離）**
- UIロジックとビジネスロジックが混在していないか
- データアクセスロジックがビジネスロジック層に漏れていないか
- バリデーション・変換・永続化が同一関数内に混在していないか

**SLAP（Single Level of Abstraction Principle / 単一抽象レベル原則）**
- 1関数内で「高レベルの意図（何をするか）」と「低レベルの実装詳細（どうやるか）」が混在していないか
- 指摘例：HTTP処理とSQL文字列組み立てが同一関数に存在する

**LoD（Law of Demeter / デメテルの法則 / 最小知識の原則）**
- `a.b.c.doSomething()` のようなチェーン呼び出しが多用されていないか（構造への過剰依存）
- オブジェクトが「直接の友人」以外の詳細に依存していないか

**CQS（Command-Query Separation / コマンド・クエリ分離）**
- 状態変更（副作用あり）と値返却を同時に行うメソッドがないか
- 指摘例：`getNextId()` が内部カウンタを変更しながら値を返す

**POLA（Principle of Least Astonishment / 最小驚き原則）**
- 関数・メソッド名から期待される動作と実際の動作が一致しているか
- 隠れた副作用（ログ出力以外の状態変更）が呼び出し元から見えない位置にないか
- Booleanの逆転フラグ（二重否定。例: `isNotInvalid`）がないか

**PIE（Program Intently and Expressively / 意図を明確に表現する）**
- 変数名・関数名が「何をしているか」だけでなく「なぜそうしているか」を表しているか
- コメントが「何をしているか」（コードから明白）ではなく「なぜそうしているか」を説明しているか（詳しくは R3 のコメント）
- 一時変数を使って中間結果に名前を付けることで意図を明確化できる箇所はないか

**CA（Clean Architecture / クリーンアーキテクチャ / レイヤードアーキテクチャ）**
- 依存の方向がドメイン層（内側）に向かっているか（外側から内側への依存のみ許可）
- 依存方向が、仕様書のアーキテクチャ方式のレイヤーに従っているか（Dependency Direction）。依存先が、自分より安定した（変更が少ない）コンポーネントか（SDP）
- ドメインエンティティがフレームワーク・DBの詳細（例: アノテーション）に汚染されていないか
- インフラ層（DB・外部API）の変更がビジネスロジックに波及しない構造になっているか
- **レイヤー仕訳の正しさ**: 層の分類は妥当か？中心に属すべき概念が外周に誤分類されていないか？逆に外周で済むものが中心に引き上げられていないか？「プロジェクトの目的にとって本質か手段か」を基準に判断する。**層の数自体は指摘対象ではない。** 既定の 4 層（Entity/UseCase/Adapter/Framework）で表せない設計は、仕様書のアーキテクチャ方式に層の定義と依存の向きがあれば妥当とする
- **Adapter層の適切さ**: Adapter層が薄すぎて外部依存がドメインに漏洩していないか？ 厚すぎてビジネスロジックがAdapter層に混入していないか？

**コンポーネント境界（CA とは別の軸）**
- 他コンポーネントの内部実装を直接参照していないか（`private/` 配下、`_` 接頭辞、公開エントリを経由しない import）
- 各コンポーネントの公開面が仕様書のコンポーネントの定義に宣言されているか。宣言の無いコンポーネントがないか
- 公開面が内部の実装詳細（内部専用の型・可変状態）を漏らしていないか
- コンポーネント図とクラス図を、アーキテクチャ方式のレイヤーの凡例で色分けしているか
- 仕様書のコンポーネントとドメインモデルの図に、要素の一覧（コンポーネントは名前、責務、公開面、親の ID。ドメインモデルは名前、責務、親の ID）があるか（一覧の形は仕様書の決まりに従う。例は付録 A の「ユースケースと要求の書き方の例」）

**キャッシュ方針（キャッシュを用いる場合）**
- 何をキャッシュするかが仕様書の設計判断（ADR）に記録されているか。暗黙のキャッシュ（メモ化・遅延初期化・ORM の一次キャッシュ・HTTP の中間キャッシュ）が見落とされていないか
- 無効化の契機が**上流の変更に紐づいている**か。時間切れだけに頼っていないか
- 許容する陳腐化が数値または条件で書かれているか（「なるべく新しく」ではない）
- 同時失効時の挙動が決まっているか（多数の要求が一斉に裏へ抜ける経路がないか）

**互換性とバージョン**
- 保存・交換する形式（ファイル・API・メッセージ）がバージョンを持っているか
- 形を変えるとき、互換（値や省略できる要素を足す）と非互換（既存の要素を変える）を区別し、非互換の変更は、読み手がエラーで知れるか、仕様に書いた読み替えで古い形を読めるか
    - 例: 悪い バージョンの無い JSON の要素の意味を黙って変える → 良い `schemaVersion` を上げ、古いバージョンを読んだらエラーコードで知らせる
- 外に出す名前（保存・交換するデータのキー、公開 API の名前）の改名を、非互換の変更として扱っているか（付録 A の「名前の選び方と改名」の「改名の手順」）

**ビルドのバージョン**
- バージョンを、ビルドの仕組みが自動で付けているか（人が手で書き換えていないか）
- バージョンから、元のソースのコミットを辿れるか
- 推奨: ビルドの UTC 日時を、年から秒までバージョンにする（例: `20261024T153045Z`）。バージョンが一意に決まり、バージョンの間の前後もはっきりする
- 推奨: ほかから依存される物（ライブラリ・API）は、互換を表すバージョン（SemVer: `MAJOR.MINOR.PATCH`）も併せて持つ

**Prompt Engineering（AI/LLM連携が有効な場合）**
- 製品のプロンプトテンプレートが、開発用の指示と分けて配置されているか
- 各プロンプトに入出力スキーマ（期待入力の型・期待出力の型）が明記されているか
- プロンプト内の指示に曖昧表現がないか（R1bの曖昧性排除と同じ観点をプロンプトにも適用）
- プロンプトのテスト（入力→期待出力のペア）が存在するか
- プロンプトのバージョン管理方針が定義されているか（モデル変更時の挙動変化への対応）
- ハルシネーション対策（出力の検証ロジック、グラウンディング手法）が設計されているか

## R3: コーディング品質レビュー観点（コード対象）

### エラーハンドリング
- すべての外部I/O（ネットワーク・DB・ファイル）でエラーが捕捉されているか
- エラーが握りつぶされていないか（空のcatch節、`_` での無視）
- エラーメッセージにデバッグに必要な文脈情報が含まれているか
- ユーザーに返すエラーメッセージに内部実装の詳細（スタックトレース・DBエラー）が含まれていないか

### ログと観測
- ログの水準（error / warn / info / debug）を、意味どおりに使い分けているか
- 個人情報と秘密を、ログに出していないか
- 失敗したとき、ログから原因を追える文脈（何を・どの入力で・どこで）が残るか

### 防御的プログラミング
- 外部からの入力（API引数・環境変数・設定ファイル）がすべてバリデーションされているか
- Null/Undefined/空配列のケースが考慮されているか
- 型アサーション（`as Type`）が安全性確認なしに使用されていないか

### 境界とインデックス
- 区間が半開 `[start, end)` で統一されているか。閉区間を用いる箇所は名前で示されているか（例: `endInclusive`）
- 反復と部分列が iterator / slice / range で表されているか。インデックス変数を手で進めていないか
- 端点に `±1` を書いて長さや終端の帳尻を合わせていないか（**帳尻合わせは半開と閉が混ざっている兆候**）

### 資源の生存期間
- 取得した資源が言語の機構（例: `try-with-resources` / `using` / `defer` / `with` / RAII）で解放されているか
- 手で書いた `close()` / `release()` が例外経路で飛ばされる箇所がないか
- 取得と解放が同一の関数内で対になっているか。片方だけが別の階層にある箇所がないか

### 時刻
- 経過時間の計測に壁時計を使っていないか（単調時計を用いているか）
- 保存・交換する時刻が UTC またはオフセット付きか。ローカル時刻が表示以外に使われていないか
- 日付の加減算に固定秒数（例: `86400`）を使っていないか

### Null Trap（null の罠）
- データ要素とは、名前（キー）と、名前が取る値のルールの組をいう（例: JSON のプロパティ、関数の引数）。
- データ要素を省いた場合と値が null の場合の扱いを仕様に定め、実装が仕様に従っているか
- 推奨: 値が無いデータ要素は、データ要素自体を省く
- 推奨: 値が無いデータ要素の値に、null を入れない
- 推奨: 関数の戻り値のように値を省略できない場合は、コーディングする言語が推奨する方式か、判別子つきの共用体で値が無いことを表す
- 理由: null を使うと「値が無い」の書き方が省略と null の 2 つになり、書き手と読み手で null の扱いが食い違う。
    - 例: 悪い `{"taskId": 7, "parentTaskId": null}` → 良い `{"taskId": 7}`（仕様: `parentTaskId` を省いたタスクは最上位のタスク。値が null ならエラー）
    - 例: TypeScript なら `undefined`、または判別子つきの共用体 `{"isTaskFound": false}` ／ `{"isTaskFound": true, "task": {"taskId": 7}}`
- 例外: 参照している規格がデータ要素の仕様を定めている場合は、規格の仕様に準拠すること。

### コメント

長いコメントは、コードを直しても直されずに古くなり、読み手を誤らせるので、有害である。コメントは次の種類に限り、英語で書き、先頭に種類を書く。ほかの種類を使うなら、先にプロジェクトルールに定める（例: ツールが読む指示のコメント、法が求める著作権とライセンスの表記）。複数行のコメントでは、種類を最初の行にだけ書く。人間は AI に翻訳させてもよい。翻訳が大変なほどのコメントは、問題がある証拠である。

| 種類 | 書く形 | 書く時 |
|:---|:---|:---|
| Why | `// Why: <reason>` | コードで語れない理由がある時 |
| Spec | `// Spec: FR-012` | 仕様書にある振る舞いを実装する時と、テストする時。内容は写さない |
| Summary | `// Summary: <EARS>` | 振る舞いが仕様書に無く、コードからも容易に読めない時 |
| Temporary | `// Temporary: <reason>. Until: <condition>.` | 暫定のコードとコメント（仕様が決めていない振る舞いを仮に決めた所は `Provisional`） |
| Unimplemented | `// Unimplemented: OPQ-012` | 仕様が決めていない振る舞いで、止まって人に問うている所。振る舞いは作らない（NDD の「仕様が決めていない振る舞い」） |
| Provisional | `// Provisional: OPQ-012` | 仕様が決めていない振る舞いを、仮に決めて作った所（NDD の「仕様が決めていない振る舞い」） |
| R7 のコメント | `@purity <value>`、`// Section: <name>`、`// Consistency: <unit>` | R7 の `@purity` タグ、構造の分離、収集と処理の分離が定める時 |

**決まり:**
- `Summary` は 1 文とする。2〜3 文なら `Temporary` を付ける。4 文以上なら処理を分ける。要約の本来の置き場は仕様書である
    - 例: 正常・準正常・異常で 3 文
      ```
      // Summary: When the file exists, readDocument shall return the parsed document.
      // If the file is missing, then readDocument shall return {"isDocumentFound": false}.
      // If the file is corrupt, then readDocument shall raise DocumentCorruptError.
      // Temporary: The summary is long. Until: The spec, version xxx, includes the summary.
      ```
- 仕様書を更新したら、`Spec` の ID からコードを追跡して直す
- `Unimplemented` と `Provisional` には、未決の問いの ID を 1 つだけ書く。決まっていないこと、探した所、仮の扱いは未決の問いの一覧に書き、コメントに写さない
- `Unimplemented` と `Provisional` は、止めた所か仮に決めた所の直前に置く。テストにも同じ形で書く。Gherkin のシナリオでは、`#` のコメントで、シナリオのタグの行の直前に書く（例: `# Provisional: OPQ-012`）
- 未決の問いの答えが出たら、コードとテストのコメントの `Unimplemented` か `Provisional` を `Spec` に、ID を仕様の本文の ID に書き換える（例: `// Spec: FR-031`）。Gherkin のシナリオでは、`#` のコメントを消し、要るときは機能要求の ID をタグに足す

**機械で判定する項目（lint）:**
- すべてのコメントが上の種類で始まっているか
- コメントが英語か
- `Spec` の ID が仕様書に実在するか
- `Summary` が 3 文以下で、2 文以上なら `Temporary` があるか
- `Temporary` に `Until:` があるか
- `Unimplemented` と `Provisional` の ID が、未決の問いの一覧に実在するか
- 未決の問いの一覧から消えた ID の `Unimplemented` と `Provisional` が残っていないか
- R7 の `@purity` タグの決まりどおりに、`@purity` タグがあるか

**AI が Yes/No で判定する項目:**
- `Why` は理由を述べているか
    - 例: 良い `// Why: The payment API allows 10 calls per second, so space the calls out`
- `Summary` は要るか。名前・型・本体だけを読んで、正常・準正常・異常の振る舞いを全部言えるなら要らない
- 止まるべき選択（NDD の「仕様が決めていない振る舞い」）に、`Unimplemented` でなく `Provisional` を付けていないか
- コメントは、次のコードの言い換えや仕様書の写しではないか
    - 例: 悪い `// add tax`（次の行は `x = y * 1.1`）→ 良い コメントなしの `priceWithTax = priceWithoutTax * taxMultiplier`
    - 例: 悪い `// Reject an order with no items`（仕様の文の写し）→ 良い `// Spec: FR-012`

## R4: 並行性・状態遷移レビュー観点

### デッドロック
**設計レベル:**
- 複数リソース（例: DB・キャッシュ・ファイル）を同時に使用するフローで、リソースのロックを取得する順序が全パスで共通に定義されているか
- 設計文書に「リソースのロックを取得する順序の制約」が記載されているか
- DBトランザクションの分離レベルと、デッドロック発生可能なアクセスパターンが分析されているか

**コードレベル:**
- ロックのネスト（`lock A` の中で `lock B` を取得するパターン）が複数の取得順序でアクセスされていないか
- DBトランザクション内で外部API呼び出し・長時間処理が行われていないか（長時間ロック保持）
- `SELECT ... FOR UPDATE` を使用する場合、取得順序が一貫しているか

### レースコンディション
**設計レベル:**
- 共有状態への同時アクセスが発生しうるフローが特定され、対策が設計されているか
- Check-Then-Act パターン（「存在確認してから使う」）がアトミック（原子的）に実装できる設計になっているか

**コードレベル（JavaScript/TypeScript向け）:**
- 複数の `await` をまたいで共有状態を読み書きするパターンで競合が発生しないか
  ```
  // Dangerous example
  const count = await getCount();   // Other code may change count here
  await setCount(count + 1);        // Update based on stale count
  ```
- イベントハンドラが並列実行されることでキューやカウンタが不整合になる箇所はないか
- `Promise.all` で並列実行する処理が同一リソースを競合して更新しないか
- DBのRead-Modify-Writeが非アトミックな箇所に楽観ロックまたは悲観ロックが適用されているか

**コードレベル（マルチスレッド言語向け）:**
- 共有変数へのアクセスに適切なロック・アトミック操作・揮発性修飾が行われているか
- スレッドセーフでないコレクション（例: `HashMap`）がマルチスレッド環境で使用されていないか

### グリッチ（状態遷移中の瞬間的な不正状態）
**設計レベル:**
- 仕様書の状態遷移図が実装可能な形で定義されているか（遷移中の中間状態が明示されているか）
- 複数フィールドの同時更新が必要な場合、更新のアトミック性が設計で保証されているか

**コードレベル:**
- 仕様書に定義された状態遷移図と実装コードが一致しているか（無効な状態遷移が存在しないか）
- 複数フィールドを同時に更新する処理がトランザクション外で行われていないか
  ```
  // Dangerous example (intermediate state between order.status and order.completedAt is observable)
  order.status = 'completed';     // Here status is completed but completedAt is null
  order.completedAt = new Date();
  ```
- フロントエンドとバックエンドの状態同期において、部分更新が観測可能な期間が存在しないか
- イベント通知のタイミングが状態変更の「前」か「後」か明確になっているか

### ステートマシン（STM: State Machine）

#### 基本の考え方
- ステートマシンは、振る舞いを「今の状態 × イベント → 次の状態」の表だけで決める仕組みである。表に無い振る舞いを作らない。
- 次の状態は、今の状態とイベント（とガード）だけで決まる。時間やほかのステートマシンの途中の状態に、結果を左右させない。履歴擬似状態は極力避ける（「状態の定義」）。
- 設計の良さは、動作だけでなくテストの数でも測る。表の交点（ガードで分かれる交点は、ガードの枝ごと）の数がテストの数であり、設計者は全交点をテストできる大きさにステートマシンを保つ。
- 任意の 1 つの状態で、1 つのイベントが動かす遷移は多くても 1 つにする。複数のステートマシンがイベントを共有する場合も、イベントディスパッチャの中で同じ規則が当たる。例外は、どの順序で処理しても結果が同じ場合だけである（「複数のステートマシン」）。
- 同じイベントでも、今の状態が違えば、別の遷移を定めてよい（表の交点が別の場合）。
    - 例: `paused` で `PlayPressed` を受けると続きから再生し、`stopped` で受けると先頭から再生する
- 1 つのイベントで 2 つの遷移が動くと、処理の順序で結果が変わるレースコンディション（アトサキ問題）になる（どの順序でも結果が同じ場合を除く）。
- 故障も 1 つのイベントである。設計者は、故障時とフェールセーフの遷移も表に書く。
- 推奨: ステートマシンは、確立されたライブラリで作る。自前で組むと、遷移の漏れや競合の穴が開きやすい。
- 推奨: 自前で組むなら、状態遷移表をデータ（表）としてコードに持ち、1 つの汎用の処理で動かす。仕様の表とコードの表が 1 対 1 に対応し、全交点のテストも表から作れる。
- 次善: 今の状態で分ける `switch` 文（状態ごとに 1 つの case）で書く。網羅の検査（例: enum の `switch` の漏れの検出）が効く言語で使う。
- 非推奨: 遷移を `if` 文の連なりで書く。遷移の漏れや重なりを、読んでもテストしても見つけにくいからである。

#### 命名
- ステートマシンの名前が、次の表に従っているか

| 対象 | 規則 | 例 |
|---|---|---|
| ステートマシン（定義） | `〜StateMachine`（大文字と小文字は表の下） | `ConnectionStateMachine`（型）、`connectionStateMachine`（値） |
| 状態の型（取りうる状態の一覧。状態の総称） | `〜State`（単数形） | `ConnectionState` |
| 今の状態を持つ変数・プロパティ | `current〜State`（単数形。値はいつも 1 つの状態だけなので、コレクションの複数形にしない。型と大文字・小文字だけで分けず、`current` で「今の 1 つ」と示す） | `currentConnectionState` |
| 状態 | 形容詞か分詞（現在分詞・過去分詞） | `idle`, `connecting`, `stopped` |
| イベント | 過去形 | `PowerLost`, `ConnectTimerExpired` |
| ステートマシンの要素（UML の element）と要素の属性の名前（推奨: 自前で組む場合） | UML の用語に合わせる（下の表） | `{ source: "idle", trigger: "ConnectRequested", guard: "isNetworkUp", target: "connecting" }` |
| 状態・イベント・遷移の識別 | 名前で識別し、通し番号を振らない。遷移は、元の頂点（例: 状態・擬似状態）・トリガー（イベント）・ガードの名前の組で識別する。トレーサビリティでは、名前を ID として辿る | 良い `stoppedByFault`、悪い `S3` |

**定義の名の大文字と小文字:** プロジェクトや言語で記法が決まっている場合を除き、定義が型（クラス）なら大文字で始め、値（変数、JSON のキー）なら小文字で始める。状態遷移表の JSON の `name` の値は、コードの定義の名と同じ字にする。型と値の両方があるときにどちらの名に合わせるかは、プロジェクトが決めて表記規約に書く。

**通し番号を振らない理由:** 番号を振ると、状態を途中に足すたびに番号を振り直すことになり、技術的負債になる。

**UML のステートマシンの主な用語**（出典: 付録 B の「出典」の UML 2.5.1 の 13 章 Common Behavior と 14 章 StateMachines）:

| UML の用語 | 意味 |
|---|---|
| `StateMachine` | ステートマシン（定義） |
| `Region` | 領域。状態と遷移の入れ物で、ステートマシンか複合状態が持つ。1 つのステートマシンか 1 つの状態に 2 つ以上の領域があると、並行に動く（直交領域）。直交領域は 1 つのイベントで領域ごとに遷移を動かすので、極力避ける。使うなら、どの順序で処理しても結果が同じ場合に限る（「複数のステートマシン」の、イベントを共有する行） |
| `State` | 状態 |
| `FinalState` | 終了状態 |
| `Pseudostate` | 擬似状態。使ってよい種類は `initial`（初期）・`choice`（動的な分岐）・`junction`（静的な分岐と合流）・`entryPoint` / `exitPoint`（入口と出口）・`terminate`（停止）。<br>以下は非推奨（極力避ける。使う時の決まりは「状態の定義」と「複数のステートマシン」）: `fork`（並行の開始）・`join`（並行の合流）（どちらも直交領域と同じ扱い）・`shallowHistory` / `deepHistory`（履歴） |
| `Transition` | 遷移 |
| `source` / `target` | 遷移の元の頂点 / 先の頂点（Vertex。例: 状態・擬似状態） |
| `trigger` | 遷移を起こすイベントの指定 |
| `guard` | ガード。遷移してよい条件 |
| `effect` | 遷移で行う処理 |
| `entry` / `exit` / `doActivity` | 状態に入る時の処理 / 出る時の処理 / 状態にいる間の処理。`doActivity` は使わず、長く続く仕事は独立したステートマシンか待つ状態として作る（「処理とタイマー」） |
| `Event` | イベント |

#### 状態の定義
- 各状態に1つずつ状態名を定義しているか
- 初期化（電源投入・再起動・復元）のそれぞれで、入る状態が 1 つに決まっているか
- 複数の値の組み合わせで状態を定義していないか
    - 例: 悪い `isLoading` と `hasError` の組み合わせ（両方が真という、ありえない状態ができる） → 良い `currentLoadState` が `loading`・`failed`・`loaded` のどれか1つ
- 1 つの状態が 1 つの意味だけを持っているか
- 1 つの状態に複数の意味を持たせていないか（必要なら、複数の意味を持たせた状態の中に内部状態を作る）
    - 例: 悪い `stopped` が「利用者が止めた」と「故障で止まった」を兼ねる → 良い `stoppedByUser` と `stoppedByFault` に分ける
- 1 つのイベントが 1 つの意味だけを持っているか
- 1 つのイベントに複数の意味を持たせていないか
    - 例: 悪い `Done` が「保存が終わった」と「印刷が終わった」を兼ねる → 良い `SaveCompleted` と `PrintCompleted` に分ける
- 次の状態を、今の状態とイベント（とガード）だけで決めているか（履歴擬似状態を使う遷移を除く）
- UML の履歴擬似状態（`shallowHistory`・`deepHistory`。図では H・H*）を使っていないか
    - 理由: たどった履歴で結果が変わり、仕様とテストが複雑になるので、極力避ける
    - 代わりの方法: 前の状態に依存するなら、前の状態による違いを状態として定義する
    - 使う時: 総合レビューチェックリストの「ステートマシン（履歴擬似状態。状態の定義）」の行の Remark に、避けられない理由を書く（理由があれば PASS、理由が無ければ FAIL）
    - 例: 悪い `paused` から再開するため、前の状態（`playing` か `fastForwarding`）を履歴用の変数に記録する → 良い `pausedFromPlaying` と `pausedFromFastForwarding` に状態を分ける

#### 処理とタイマー
- タイマーを、独立したステートマシンにしているか
- タイマーを、状態の処理（entry・exit・遷移の処理）の中で実装していないか
    - 例: 悪い `connecting` の entry 処理が 5 秒待ってから `timedOut` へ遷移させる → 良い `ConnectTimerStateMachine` がイベント `ConnectTimerExpired` を発生させ、接続のステートマシンが `ConnectTimerExpired` で遷移する
- 状態の処理が待ちを含まず、すぐ終わるか
- 状態の処理の中で、応答・時間・入出力を待っていないか（待つなら、待つ状態を作る）
- `doActivity`（状態にいる間の処理）を使わず、長く続く仕事を、独立したステートマシンか待つ状態として作っているか

#### 複数のステートマシン
- 連携する複数のステートマシンを、コンポーネント（仕様書が公開面を定める単位）ごとに 1 つのイベントディスパッチャで管理し、同期型で動かしているか
    - 注: イベントディスパッチャ（event dispatcher）は、コンポーネントの中でイベントを受け取り、ステートマシンに配る部品である。責務は次の 3 つ。
        - イベントを待ち行列（キュー）で受け、1 つずつ取り出す
        - 取り出したイベントを、イベントを受けるステートマシンに、決まった順で渡す
        - 渡した先の遷移と処理がすべて終わってから、次のイベントを取り出す（UML の run-to-completion: 1 つのイベントの処理を最後まで終えてから次へ進む動き方）
- ほかのコンポーネントのステートマシンへは、非同期のイベントだけで働きかけているか（直接読み書きしていないか。公開面を通る通常の呼び出しは、R2 のコンポーネント境界に従う）
- 遷移の途中に来たイベントが、イベントディスパッチャの待ち行列に入り、遷移が終わってから処理されるか（取りこぼさないか）
- 待ち行列があふれたときの扱い（古いものを捨てる・新しいものを捨てる・異常とする）を決めているか
- 直交領域と `fork`・`join` を極力避けているか（使うなら、どの順序で処理しても結果が同じ場合に限る）
- 1 つのイベントで動く状態遷移が、イベントディスパッチャの中で多くても 1 つか（例外は下の、イベントを共有する行）
- 1 つのイベントで、複数の状態遷移が動いていないか（処理の順序で結果が変わるレースコンディション、アトサキ問題になる。例外は下の、イベントを共有する行）
    - 例: 悪い 表示のステートマシンと記録のステートマシンが、どちらも `PowerLost` で遷移する → 良い 電源のステートマシンだけが `PowerLost` で遷移し、電源の遷移が発生させる `ShutdownStarted` で記録のステートマシンが遷移し、記録の遷移が発生させる `LogClosed` で表示のステートマシンが遷移する（本例では、どのイベントも動かす遷移は 1 つだけ）
- 1 つのイベントを複数のステートマシンで共有すると（コンポーネントをまたぐ場合も同じ）、どの順序で処理しても結果が同じ場合を除き、処理の順序で結果が変わるアトサキ問題が起きる。
- イベントを共有するステートマシンの間に相互作用があるなら、共有するイベントを受けるのは 1 つのステートマシンだけで、受けたステートマシンの遷移が発生させるイベントで、ほかのステートマシンを動かしているか（上の `PowerLost` の例）
- イベントを複数のステートマシンで共有するのは、どの順序で処理しても結果が同じ動作だけか

#### 状態遷移表とテスト
- ステートマシンごとに、状態遷移図（UML）と状態遷移表が組になっているか
- 推奨: 図と表を 1 つの原稿（例: JSON）から生成する（付録 A の「NDD の進め方」の「SSOT の考え方」）。
- 図と表を手で別々に書くなら、どちらか一方を正と決め（付録 A の「NDD の進め方」の「SSOT の考え方」）、図と表の内容（状態・イベント・遷移）が一致し、互いに辿れるか
- ステートマシンの設計で、動作の仕様に加えて、テストケースの数を見積もっているか
- 状態遷移表のすべての交点に、次の状態か、「無視」か「異常」を決めているか
- 状態遷移表に凡例があり、「無視」と「異常」の書き方を定めているか（書き方はプロジェクトごとに決めてよいが、凡例は必須。既定は英語の語のタグ `ignore` と `error`。状態遷移表を JSON で持つなら `ignore` と `error` に限る）
- 同じ状態・同じイベントのガード条件が、互いに重ならず、漏れも無いか
- 表のすべての交点（ガードで分かれる交点は、ガードの枝ごと）で、実装の次の状態が表と一致することをテストで確かめているか
- 推奨: 状態遷移表は、行がイベント、列が今の状態、交点が「次の状態 [ガード] / 処理」と書く（一般に状態より数が多いイベントを行に並べると、表が見やすい）

#### 故障時
- 故障時・不具合の発生時に、ステートマシンがどの状態へ移るかを決めているか
- 故障時・不具合の発生時に、致命的な動作（例: 危険な出力を続ける、止まって戻らない）をしていないか
- フェールセーフが働いたときの状態遷移（入る状態と、入った状態から戻る遷移）を決めているか
- フェールセーフの動作が、2 次被害（例: 急な停止による損傷、データの喪失）を起こさないかを検討しているか
    - 例: 悪い 温度センサが壊れても `heating` のまま加熱を続ける → 良い センサの故障で `stoppedByFault` へ移り、ヒーターを切り、利用者のリセットだけが戻す

## R5: パフォーマンスレビュー観点

### アルゴリズム・データ構造
**設計レベル:**
- パフォーマンス要求（仕様書の非機能要求）を満たすために、重要なアルゴリズムの計算量が分析されているか
- 非機能要求が定めるデータの件数の上限を扱う処理で、O(n²)以上のアルゴリズムが選択されていないか

**コードレベル:**
- ループ内で不変の計算が繰り返し実行されていないか（ループ不変式のループ外出し漏れ）
- 線形探索が使用されている箇所で、MapやSetによるO(1)アクセスに置換可能なものはないか
- ソート済み配列への二分探索適用漏れがないか

### データベース・I/O
**設計レベル:**
- 頻繁にアクセスされるクエリのインデックス設計が考慮されているか
- ページネーション・カーソルが必要な大量データ取得が設計されているか

**コードレベル:**
- N+1クエリ問題が発生していないか（ORMの遅延ロードによるループ内クエリ）
  ```
  // Dangerous example
  const users = await User.findAll();
  for (const user of users) {
    const orders = await user.getOrders(); // Issues N queries
  }
  ```
- `SELECT *` が使用されている箇所で不必要なカラムが取得されていないか
- バルク操作が可能な箇所でループ内単発INSERT/UPDATEが行われていないか
- トランザクション内でネットワークI/Oや長時間処理が行われていないか

### メモリ・リソース
**コードレベル:**
- 大量データをメモリに一括ロードしている箇所でストリーミング処理に変更可能なものはないか
- EventListenerやタイマーの解除漏れがないか（メモリリークの原因）
- 循環参照によるGC不能オブジェクトが生成されていないか
- キャッシュに有効期限・最大サイズが設定されているか
- 資源の使用量（例: CPU 負荷、メモリ使用量、ストレージの摩耗）が、非機能要求の値に収まるか

### ネットワーク・フロントエンド
**コードレベル:**
- 直列化する必要のないAPI呼び出しが `await` で直列化されていないか（`Promise.all` で並列化可能）
- APIレスポンスに不必要なフィールドが含まれていないか（overfetching）
- フロントエンドで不要な再レンダリングが発生していないか（例: React `useEffect` の依存配列の誤設定）
- 遅延ロード・コード分割が適用可能な箇所で静的インポートになっていないか

## R6: テスト品質レビュー観点（仕様書のテスト・テストコード・テスト記録が対象）

- テスト名が「前提条件 → 操作 → 期待結果」または「should + 期待動作」の形で意図を表しているか（テスト名の形は、テストコードのテスト名に当てる。シナリオ名は、下の Gherkin の決まりに従う）
- テストが独立しているか（実行順序依存・テスト間の共有状態がないか）
- 正常系だけでなく境界値・異常系・エッジケースが網羅されているか
- モック・スタブが過剰に使用されて実際の動作を検証できていないテストになっていないか
- フレーキーテスト（タイミング依存・ランダム依存）が含まれていないか
- 子の要求を持たない要求のそれぞれに、確かめるテストが 1 つ以上あるか。テストの代わりに、仕様書の検証方法の一覧に検証方法と検証者があるか（仕様書の制限事項の節の本文に要求の ID と見送る理由がある MAY と SHOULD の要求を除く。コードのテストは、確かめる親の ID（例: 要求、ユースケースの道の ID、実装仕様）をコメントで持つ。例: `// Spec: FR-012`。シナリオは ID をタグで持つ。例: `@FR-012`）
- 人が確かめなければならないテスト（例: 見た目、使い勝手）に、タグ `@manual` を付けているか。`@manual` の無いテストのすべてに、ツールの報告がテスト記録にあるか
- テストの結果を仕様書に書かず、テスト記録（仕様書と別のファイル）に書いているか
- 仕様書が、テストの方針（検証方法の一覧とテスト記録の場所を含む）と、ユースケースを確かめるテストを持つか（置く節は仕様書の決まりに従う。例は付録 A の「ユースケースと要求の書き方の例」）

**テストケースの記法（Gherkin）:**
- ユースケーステストのシナリオを Gherkin の `Given`（前提）／ `When`（操作）／ `Then`（期待結果）で書いているか（続きは `And` ／ `But`）（必須）
- 1 つのシナリオが 1 つの振る舞いだけを確かめているか（`When` が 1 つ）
- シナリオ名の頭に、シナリオの ID があるか（ID の形は仕様書の決まりに従う。例は付録 A の「ユースケースと要求の書き方の例」）
- 各シナリオが、確かめるユースケースの道の ID をタグで 1 つ持つか（タグの形は仕様書の決まりに従う）。確かめる機能要求の ID のタグ（例: `@FR-012`）と `@manual` は、要るときに足す
- すべてのユースケースの、正常に終わる道と拒む道のそれぞれに、シナリオが 1 つ以上あるか
- ユースケースの前提を `Given` に、きっかけと目的を 1 つの `When` に、結果と拒む場合の応答を `Then` に写しているか
- 拒む道のシナリオが、拒む条件に当たる値を `Given` か `When` に書いているか（例: Given 残高は 1,000 円、When 利用者は 2,000 円を送る）
- 自動のテストで、ツールの報告（例: Cucumber の JSON、JUnit の XML）をテスト記録にしているか。`@manual` のテストのテスト記録で、Result が Cucumber の結果の値（passed、failed、skipped、pending、undefined、ambiguous）のどれかか。passed のほかは、Remark に理由があるか

## R7: 純粋性・構造レビュー観点（仕様書のアーキテクチャ・仕様とコードが対象）

関数・クラスを純粋性の軸で分類し、非純粋な作用を計算ロジックから分離することで、テスト容易性と推論可能性を確保する。

**レイヤー軸との関係:** 本節は純粋性軸の規約であり、レイヤー軸（Entity/UseCase/Adapter/Framework、R2 の CA）とは**直交する**。Adapter 層に純粋関数があってよく、Entity 層に可変集約（例: DDD の Aggregate）があってもよい。一方の軸の違反をもう一方の軸の違反として起票しないこと。

### 純粋性の分類

| 分類 | タグ値 | 定義 |
|------|--------|------|
| 純粋 | `pure` | 可変内部状態なし・副作用なし・外部状態を読まない。出力は引数のみで決まる（参照透過） |
| 準純粋-不変 | `semi-pure-immutable` | 副作用はないが**不変値**の外部状態を読む（例: 定数・起動時設定の読み取り）。決定的 |
| 準純粋-可変 | `semi-pure-mutable` | 副作用はないが**可変**の外部状態を読む（時刻・乱数・DB/ファイル/NW 読取）。非決定 |
| 非純粋 | `non-pure` | 可変内部状態を持つ、または副作用がある |

**メソッドの分類:** 不変のオブジェクトのメソッドが読む、オブジェクト自身の項目は、引数と同じに見る。可変のオブジェクトのメソッドで、オブジェクト自身の項目を読むだけのもの（例: getter）は `semi-pure-mutable` とする。名前は、R2 の Naming のクエリの行に従って名詞句でよい。

**非純粋な作用の一覧:** I/O・DB 書込・ログ出力・lock/mutex/semaphore の取得解放・グローバル変数や引数の書き換え・HW/OS/環境変数の変更。例外送出の扱いは R7 の「計算ロジックの純粋性」の「例外の扱い」に従う。

### 計算ロジックの純粋性

ドメインの計算ロジック（業務規則・判断・変換）は `pure` または `semi-pure-immutable` として実装する。非純粋な作用を計算ロジックに混在させず、非純粋な作用を専門に担う関数/ユニットへ分離する。

- 判断（何をするか決める）と実行（実際に作用させる）が同一関数に同居していないか
- 業務規則の中に I/O・ログ出力・ロック取得が埋め込まれていないか

**例外の扱い:** ドメイン不変条件の違反を表す例外（例: 値オブジェクトの検証）は、同一引数に対して同一の例外を送出する限り、計算ロジック側で許容する。I/O 失敗・システム起因の例外（接続断・タイムアウト・資源枯渇）は非純粋側に限る。

### 外部読取の引き上げ

`semi-pure-mutable` の読取（時刻・乱数・DB/ファイル/NW 読取）は関数の先頭で収集し、可能なら引数として注入して `pure` へ引き上げる。

- 関数の内部で現在時刻取得・乱数生成・リポジトリ呼び出しを直接行っていないか
- 引数注入により、注入を受ける関数の単体テストが固定値だけで書けるようになるか

### 収集と処理の分離

**処理の途中で新たな外部読取を行わない。読取は処理開始前に完結させる。**

守るべき不変条件は「全件をメモリに載せること」ではなく、**処理の途中で外部状態が変化しても結果が変わらないこと**である。ストリーミング・ページネーション・早期終了により全件収集が不可能な場合は、**一貫性の単位（チャンク／スナップショット／トランザクション）を明示し、一貫性の単位内で収集→処理の順序を守る**。

- 一貫性の単位が成果物（仕様書の状態遷移の定義か、実装コードのコメント）に明示されているか
- ループの内側で読取と加工が交互に発生し、結果がタイミング依存になっていないか
- 状態遷移では、遷移の条件を読む所と遷移を行う所を分けているか

**R5 の「メモリ・リソース」（大規模データはストリーミング）とは衝突しない。** ストリーミングはチャンクを一貫性の単位とすることで本項を満たす。

### 純粋側クラスの不変性

純粋側のクラスは immutable class / value object / stateless class のいずれかとし、可変状態を持たない。可変状態または副作用メソッドを持てば stateful（非純粋）として扱う。

### `@purity` タグ

すべての関数/メソッドは、関数/メソッドの言語のコメント（例: `//`、`#`、`--`、`/* */`、`"""..."""`）内に `@purity` タグをちょうど 1 つ持つ。値は次の 4 値のいずれか。

```text
@purity pure | semi-pure-immutable | semi-pure-mutable | non-pure
```

`@purity` はコメント内のテキストマーカーであり言語構文ではないため、全言語で機能し grep で検査できる。**純粋も無印にせず明示する**（付け忘れと純粋を区別するため）。4 値はどれも他の値の前方一致にならないので、`grep '@purity semi-pure-mutable'` は `semi-pure-immutable` を拾わない。無印の `grep '@purity semi-pure'` は 2 値の両方を拾う。

**適用除外:**

| 対象 | 理由 |
|------|------|
| テストコード | 検査対象は製品コードの構造である |
| 自動生成コード | 生成器の管轄であり手で維持できない |
| サードパーティのベンダリングコード | 自プロジェクトの設計判断ではない |
| 単一式のラムダ・無名関数 | 注釈が本体より長くなり可読性を損なう |

除外対象を除いた製品コードに対し、タグ付与率は 100% でなければならない。

### 構造の分離

- クラス/ユニット内で、メンバを 純粋 → 準純粋 → 非純粋 の順に並べ、非純粋群の前にセクションコメントを置いているか
- クラスに可変状態と純粋計算を混在させず、純粋ロジックを純粋関数か値オブジェクトへ抽出しているか
- 純粋性でユニットを分割しているか（純粋な core と非純粋な shell を別ファイルに）

### 失敗の表現

計算ロジック側の失敗は、可能であれば戻り値型（Result / Either / Option）で表現する。言語が同等の機構を持たない場合は、R7 の「計算ロジックの純粋性」の「例外の扱い」に従いドメイン例外で代替してよい。

## R8: セキュリティレビュー観点（仕様書・コード対象）

### 秘密情報
- 鍵・トークン・パスワードを、コード・設定ファイル・ログ・エラーメッセージに書いていないか
- 秘密を、環境変数か秘密の保管庫から読んでいるか

### 入力と注入
- 外部から来た値を、SQL・シェルのコマンド・ファイルのパス・HTML に、元のままつないでいないか
- プレースホルダ・エスケープ・許可リストのどれかで守っているか

### 認証と認可
- 認証（誰か）と認可（何をしてよいか）を、分けて確かめているか
- 各処理が、必要な最小の権限だけで動いているか

### 依存と OSS
- 依存パッケージのバージョンを固定しているか（ロックファイル）
- 依存パッケージに既知の脆弱性が無いかを、定期的に確かめているか
- OSS のライセンスが製品の配布の形と両立し、必要な表記（著作権・ライセンス文・NOTICE）を同梱しているか
- コピーレフトのライセンス（例: GPL）が、製品の全体に及ばないかを確かめたか
- GRS での機械: 検査 93 が、ロックファイルが `package.json` の求める版を固定していること・入れた包みがすべて build 専用であること・`src/` が包みを import しないこと（製品に第三者のコードが入らないこと）を見る。ライセンスの表記は検査 27（`tools/generate_license.py --check`）が見る。⚠️ 既知の脆弱性は機械で見ていない（`npm audit` は網が要る）

## 重大度

本節は、レビュアーが指摘に付ける重大度と、重大度ごとに許容される対応とゲート要求を定める。指摘の対応の流れ、記録、再レビューは、付録 A の「レビュー指摘の対応」が持つ。

| 重大度 | 基準に照らすと | 被害で見ると | 許容される対応 | ゲート要求 |
|--------|-----------|-----------|-------------|-----------|
| Critical | （基準に照らす軸では決めない） | - 生命・身体・健康・財産・環境に関する安全が損なわれる<br>- サイバーセキュリティが損なわれる<br>- 法令に反する<br>- 金銭の損害を生む<br>- 権利を侵害する<br>- 不具合で失ったデータや止まったシステムを元に戻すのが困難である | 修正済みのみ | フェーズ遷移には、すべて修正済みであること |
| High | MUST の行が FAIL（Medium に挙げた 2 行を除く） | 機能の目的を果たせない | 修正済み・受容（人の承認が要る） | フェーズ遷移には、すべて修正済みか、人が承認した受容であること |
| Medium | - SHOULD の行が FAIL<br>- 振る舞いに影響しない形の決まりの MUST の行（R1 の「文の決まり（仕様書の全章）」と R3 の「コメント（種類）」の 2 行だけ）が FAIL | 機能の目的は果たせるが、使いにくい、または保守しにくい | 修正済み・据置き・受容 | 全件に対応の記録があること |
| Low | どの行も FAIL でない | - 動作にも保守の手間にも影響しないが、コード、コメントの書き方が不適切である<br>- 一般のユーザーが気付かない、または気付いても許容できる不具合 | 修正済み・据置き・受容 | 全件に対応の記録があること |

重大度は、当たる段階のうち最も高い段階で決める。被害は、不具合が起きた時の被害で見る。機能は、利用者から見た業務の単位（ユースケース）で見る。フェーズ遷移は、次の工程（例: 仕様書の確定、実装の開始、受入）へ進むことをいう。

本表は一般的な目安である。実際の定義とルールは、プロジェクトに合わせて定め、1 か所に書き、レビューの依頼に添える。

プロジェクトの定義とルールがあれば、プロジェクトの定義とルールに従う。決めていない部分は、本節を使う。

## 総合レビューチェックリスト（NDD・R1〜R8・必須）

全レビュー観点（NDD・R1〜R8）を統合した、単体でも使えるチェックシート。キーワードは RFC 2119 に従う（MUST/SHALL=必須、SHOULD=推奨）。

- レビュアーは全行の Verdict（PASS/FAIL/NA）を記入しなければならない（MUST）。
- FAIL には必ず指摘を起票するか、据置きか受容の前の指摘を引き継がなければならない（付録 A の「レビュー指摘の対応」）。
- Verdict が PASS 以外（FAIL/NA）の場合は、Remark に理由を記入しなければならない。
- NA は「非該当」（行の観点を成果物が持たないこと。例: 状態を持たないシステムでの、R4 のステートマシンの行）だけを表す。
- 項目に反する場合は、理由があっても Verdict を FAIL としなければならない。理由は FAIL の指摘の対応（据置きか受容。High の受容は人が承認する）で扱い、対応は付録 A の「レビュー指摘の対応」に従う。FAIL の指摘を修正の無いまま残すときは、次のレビューでも Verdict を FAIL にし、新しい指摘の代わりに、同じ指摘の ID を Remark に書く。
- 全行の記入の例外として、コードを確かめる行は、コードができるまで Verdict を空けておく。
- 仕様書が設計原則の準拠確認の表を持つなら、表には本チェックリストの観点の欄の設計原則を並べ（プロジェクトの性質に応じて原則を足してよい）、レビュアーはレビューのたびに、本チェックリストと同じ決まりで、表の全行に判定と根拠（確かめた所）を書くことが望ましい（SHOULD）。

各行は章と観点の名で本文の詳細セクション（運用は付録 A）に対応し、根拠・例はそちらを参照する。

**純粋性の注釈規約（言語非依存・R7用）:** R7 の「`@purity` タグ」に従う。

## 付録 A: 運用

本付録は、本文の観点を当てるときの運用（指摘の対応、名前の選び方と改名、未決の問いの進め方と書き方、トレーサビリティの鎖の例、ユースケースと要求の書き方の例、NDD の進め方）を持つ。確かめる観点は本文が持つ。

### A.1 レビュー指摘の対応

レビュアーの AI が指摘を起票した後、以下の対応ワークフローを適用する。

重大度の段階と許容される対応は、本文の「重大度」の節が持つ。

#### 対応フロー

1. レビュアーの AI が重大度（Critical / High / Medium / Low）付きで指摘を起票
2. 書き手の AI が各指摘をトリアージし、対応を記録
3. 人がフェーズ遷移前に、全指摘に対応の記録があることを確かめ、High の受容を承認する

#### 記録要求

- 指摘の ID は `RVF-xxx` とする。レビュー報告の列は「ID / 重大度 / チェックリストの行 / 所 / 内容 / 対応 / 状態」とし、置き場はプロジェクトが決める。

| 対応 | 定義 | 使える重大度 | 決める人 | 記録に書くこと | 指摘の状態 |
|:---|:---|:---|:---|:---|:---|
| 修正済み（fixed） | 直し、再レビューで解消を確かめた | すべて | 書き手の AI が直し、レビュアーの AI が確かめる | 直した所 | 閉じる |
| 据置き（deferred） | 直すと決めたが、今のフェーズでは直さない | Medium、Low | 書き手の AI | 理由、残る危険、直す期限 | 開いたまま追いかける。期限までに直せなければ仕分け直す |
| 受容（accepted） | 直さないと決めた | High、Medium、Low（Critical は除く） | Medium と Low は書き手の AI（レビュアーの AI が理由を確かめる）。High は人が承認する | 理由、範囲。High のときは承認した人と見直す条件も書く | 閉じる。High の受容は、見直す条件が満たされたら開き直す |

- 受容した FAIL の行は、次のレビューでは新しい指摘を起こさず、前の指摘の ID（`RVF-xxx`）を Remark に書いて引き継ぐ。受容の理由と範囲が変わらない限り、指摘は閉じたままにする。High の受容は、見直す条件が満たされたら指摘を開き直す。範囲の外に同じ違反が増えたら、新しい指摘を起こす。据置きの指摘がある FAIL の行も、同じく前の指摘の ID を Remark に書いて引き継ぎ、指摘は開いたままにする。

#### 再レビュー時の動作

レビュアーが修正後の再レビューを実施する際:
1. 前回の各指摘を対応記録と照合して検証
2. 「修正済み」の指摘が修正後の成果物で実際に解消されていることを確認
3. 「受容」の指摘を確かめる（Medium と Low は理由を確かめ、High は見直す条件を確かめる。見直す条件が満たされた High の受容は開き直す）
4. 「据置き」の指摘の期限を確かめ、期限を過ぎた指摘を書き手の AI の仕分け直しに回す
5. 更新された件数を含む新しいレビュー報告に検証結果を記録
6. 再レビュー中に発見された新たな指摘は指摘の記録に追加

### A.2 名前の選び方と改名

本節は、NDD の「名前の選び方」と「改名」が確かめる決まりと手順を持つ。

#### 名前の選び方

- 名前は、何を指すかに照らした適切さだけで選ぶ。
- 名前が不適切と分かったら、改名の手間を理由に、不適切な名前を残さない。
    - 例: 悪い「キーを改めると直す所が多いので、意味のずれた名前を残す」 → 良い「意味に合う名前に改め、使う所をすべて直す」
- 理由: 適切に設計された SW なら、AI による改名は比較的容易である。長く使う SW では、不適切な名前が技術的負債になる。
- 改名の影響が大きい場合は、SW のリリースの時期を考えて、直す範囲を検討して決める。

#### 改名の手順

名前は第 1 級の識別子なので、改名は概念の正体を変える。改名の手間の多くは、名前が行き渡った所の直し漏れから生じる。

1. 改名の前に、古い名前で、すべてのファイル（例: 仕様、コード、テスト、JSON）を検索し、使われている所を洗い出す。検索には、用語集の名前（JSON の用語集では `key` と `label`）と、コードの識別子の形（例: camelCase、PascalCase）を使う。
2. 用語集に、古い名前と改名の履歴（いつ、なぜ、どの変更の記録で）を残す。用語集の JSON では `renames[]` の `from`、`version`、`reason`、`basis` に、表の用語集では「改名の履歴」の列に書く。古い名前は、別の用語に使い回さず、使わない言い換え（`avoid`）に重ねて書かない。
3. 外に出す名前（保存・交換するデータのキー、公開 API の名前）の改名は、非互換の変更として扱う（R2 の互換性とバージョン）。形式のバージョンを上げ、古い名前の扱い（新しい名前に読み替えるか、エラーで知らせるか）を、仕様書のデータスキーマの節か API 定義の節に書く。
    - 例: 悪い 保存のキー `dueDate` を `deadline` に改名し、古いファイルが黙って読めなくなる → 良い 形式のバージョンを上げ、古いバージョンの `dueDate` を `deadline` に読み替える扱いを仕様に書く
4. 内部の名前（変数、関数、内部の型）の改名では、すべての場所を直し、古い名前を読む仕組みを作らない。
5. 改名の後に、古い名前で検索する。当たってよいのは、用語集の改名の履歴、古い名前の扱い（仕様、コード、テスト）、変更の記録（変更履歴、変更要求、レビューの指摘、ADR、未決の問い）だけである。

### A.3 未決の問いの進め方と書き方

本節は、NDD の「仕様が決めていない振る舞い（未決の問い）」が確かめる進め方と形（未決の問いの一覧、印、答えが出た後の閉じ方）を持つ。

#### 進め方

- AI は迷っても迷ったと言わず、もっともらしく決めて先へ進む。黙って決めた振る舞いは成果物の中に埋もれ、人は気付かない。
- 仕様を書くときも、仕様に従って作るときも、決まっていない点を黙って決めない。
- 決める前に、仕様、用語集、設計判断（ADR）を、問う語と ID で検索する。答えがあれば、答えに従う。
- 次の選択では、決めずに止まり、人に問う。
    - 取り消しにくい選択: 保存・交換するデータの形式、公開する境目（例: API、コンポーネントの公開面）、入力を受け付けるか拒むかの境、ほかの決まりの正しさが頼る値（例: 設定の表の閾値と上限）、仮の決定の上に積む仮の決定
    - 誤ると被害が大きい振る舞い（安全、サイバーセキュリティ、法令、金銭、権利、復旧が困難な損失）
- ほかの選択では、仮に決めて進み、仮の決定に未決の問いの ID を付ける。
- ただし、仕様書の設計判断の節で AI が決めた判断は、AI が ADR に決定者を AI と書き、未決の問いを足さない（OPQ の ID も書かない）。
- 設計判断の節で AI が決めた判断は、決定者が AI の ADR を検索して見つける。
- 止めた所と仮に決めた所のそれぞれに、未決の問いの一覧の行を足す。

#### 未決の問いの一覧

- 未決の問いの一覧は、仕様書の付録に置く。ID は `OPQ-xxx`。列は「ID / 決まっていないこと / 探した所 / 決める人 / 仮の扱い（推奨と根拠） / 覆したときに直すテスト」。

#### 印

- 仮に決めた仕様の文の末尾に、`（仮: OPQ-xxx）`（英語の仕様では `(provisional: OPQ-xxx)`）を書く。
- 止めた所の文か値の末尾に、`（未決: OPQ-xxx）`（英語の仕様では `(undecided: OPQ-xxx)`）を書く。
- コードとテストの止めた所と仮に決めた所に、R3 のコメント（`Unimplemented`、`Provisional`）を書く（Gherkin のシナリオでは、シナリオのタグの行の直前に `# Unimplemented: OPQ-xxx` か `# Provisional: OPQ-xxx`）。
    - 例: 悪い 仕様が決めていない一覧の並び順を、黙って名前の順にする → 良い 名前の順にする仮の決定の直前に `// Provisional: OPQ-012` を書き、未決の問いの一覧に `OPQ-012` の行を足す

#### 答えが出た後の閉じ方

- 答えを仕様の本文に書く。
- 仕様の文か値の `（仮: OPQ-xxx）` か `（未決: OPQ-xxx）` と、一覧の行を消す。
- 変更履歴には、根拠に未決の問いの ID を書き、変更の列に問いと答えを 1 文ずつ書く。
- コードとテストのコメントの `Unimplemented` か `Provisional` を `Spec` に、ID を仕様の本文の ID に書き換える（例: `// Spec: FR-031`）。
- Gherkin のシナリオでは、`#` のコメントを消し、要るときは機能要求の ID をタグに足す。
- 答えが出た未決の問いの ID を、別の問いに使い回さない。

### A.4 トレーサビリティの鎖の例

本節は、本文の R1b の「トレーサビリティ」が指す鎖の例を 1 つ持つ。鎖に置く項目、親子の組、親の ID を書く所、鎖の外の節は、仕様書の決まり（テンプレート）が定める。

- 鎖（左が親）: 目的 ← 要問 ← 課題 ← 目標 ←（ユースケースの流れ UCF ←）ユースケース ← 要求 ← 設計・詳細仕様・実装・テスト
- 親: 設計・詳細仕様・実装・テストの親は、ユースケースか要求である。実装とテストの親には、実装仕様（IMPS）もなれる。IMPS の traces は、要求を 1 つ以上含める。実装仕様を実装する関数も、実装の単位になる
- 親を持つ項目: 要問からテストまで（目的は最上位の項目で、親を持たない）
- 親の ID を書く所: 表の親の ID の欄か traces の列（検証方法の表では要求の ID の列）、ユースケースの intent の欄の末尾と、UCF と図の見出しの直下の `traces:`、JSON Schema と OpenAPI の `description` の末尾の `traces: <ID>`、`CREATE TABLE` の直前の SQL のコメントの `traces: <ID>`、コードのコメント `// Spec:`、シナリオのタグ。ユースケースの印（`UC-xxx.OK`、`UC-xxx.RJn`）も親の ID になる
- 子を描く図: UCF の図は、描くユースケースの ID を持ってよい
- 子を持つ項目: 目的からユースケースまで（UCF を含む）
- 鎖の外: アーキテクチャ方式の節、ファイル構成の節、設定の表の節

### A.5 ユースケースと要求の書き方の例

本節は、本文の R1、R2、R6 が指す、要求、ユースケース、シナリオ、コンポーネントの一覧、検証方法の一覧の書き方の例を 1 つ持つ。形は、仕様書の決まり（テンプレート）が定める。

- 上位の項目: 要問を疑問文で、課題を動詞句で、目標を、達したかを観察で判定できる平叙文で書く
- 要求の ID と表: 機能要求は `FR-xxx`、非機能要求は `NFR-xxx`。要求を「ID / 要求文 / traces」の表で書き、ユースケースから導いた要求は、表の traces の列でユースケースの印を指す
- 検証方法の一覧: テスト戦略の節の検証方法の表（列: 要求の ID / 検証方法 / 検証者）。テスト戦略の節は、テスト記録の場所も持つ。テストの章は、テスト戦略の節とユースケーステストの節を持つ
- ユースケースの欄: intent（目的）、trigger（きっかけ）、precondition（前提）、postcondition（結果）、steps（手順）、rejection（拒む場合）の 6 つ。中身が無い precondition と rejection は「—」
- 見出し: `UC-<3 桁> <目的語>を<動詞の終止形>（<英語の PascalCase の名前>）`（英語の仕様では `UC-<3 digits> <Verb> <object> (<PascalCaseName>)`）。UseCase は見出しの英語の名前を取り、仕様書のコンポーネントの節に置く
- 印: 正常に終わる道は `UC-xxx.OK`、拒む道は `UC-xxx.RJn`（n は 1 から）。各 rejection は `RJn（手順 m）` の形で、応じる手順を示す
- 親: intent の欄の末尾の `traces:` で、目標か UCF を指す
- つながり: 分けたユースケースは、後のユースケースの precondition に前のユースケースの印を書いてつなぎ、ユースケースの流れ（UCF）にまとめる。UCF に入るユースケースは、`traces:` で UCF を指す
- コンポーネントの一覧: コンポーネントの節の図の要素の一覧表の列は、名前、責務、公開面、traces。ドメインモデルの節は、名前、責務、traces
- シナリオ: シナリオ名の頭に `SCN-xxx`。各シナリオは、確かめるユースケースの印をタグで 1 つ持つ（例: `@UC-010.OK`、`@UC-010.RJ1`）。precondition を `Given` に、trigger と intent を 1 つの `When` に、postcondition と rejection の応答を `Then` に写す

### A.6 NDD の進め方

本節は、NDD の進め方を持つ。NDD の節の観点が指す決まり（機械が読む原本の決まり、JSON のキーの一覧）は、NDD を採るかにかかわらず当たる。確かめる観点は、本文の NDD 節の「NDD で重要となるレビュー観点」が持つ。

#### SSOT の考え方

- 1 つの事実は 1 か所にだけ書き、ほかの所は元の 1 か所から生成するか、元の 1 か所を参照する。以上の決まりを SSOT（Single Source of Truth / 唯一の正）と呼ぶ（R1b の仕様の重複・競合の排除）。
- 写しが食い違うと、AI も人も、どちらが正しいかを判断できない。

#### 人と AI の役割

- 成果物は書き手の AI が書き、書き手と別のセッションのレビュアーの AI が、本書の観点でレビューする。書き手の AI も、本書に合わせて成果物を書く。ゆえに、本書の 1 行が成果物の質を決める。
- 人はレビューの基準（本書）を用意し、AI のレビューの結果、未決の問い、`@manual` を付けたシナリオの選び方、用語集の名前を確かめる。
- 人は、AI が質問にまとめた事項を裁定する。
- 裁定の大半は、目的（何を実現したいか）と、名前の適否（付けた名前で合っているか）である。
- AI も人も、同じ用語集を見て話す（R1a の用語の一貫）。

#### 文型と図表の使い方

- 仕様の書き手（人か AI）は、決まった文型で仕様を書く。
- 要求の文型（EARS）は R1b の「要求の記法（EARS: Easy Approach to Requirements Syntax）」で、ユースケーステストのシナリオの文型（Gherkin）は R6 の「テストケースの記法（Gherkin）」で確かめる。
- 細かな値や条件の組み合わせは表で、計算は式で、振る舞いの流れや構造は図で定めてよい。定めたら、EARS の要求文から、定めた表・式・図を仕様として参照する。
- 文型が決まると、AI は仕様をまっすぐ読み、機械は文型を手がかりに仕様を自動で点検できる。
- クラス図は、要求文や設計の文から、仕様として参照してよい。
- コンポーネント図は、要求文や設計の文から、仕様として参照してよい。各コンポーネントの定義（責務と公開面）は、本文の「NDD で重要となるレビュー観点」の「図と表」で確かめる。
- シーケンス図が全ケースを網羅するなら、要求文から仕様として参照してよい。網羅できない場合は、本文の「NDD で重要となるレビュー観点」の「図と表」で確かめる。

#### 機械が読む原本の決まり

- 推奨: 製品のコードが 10,000 行以下の見込みでも、用語集、ID の登録簿、状態遷移表を、機械が読める JSON で持つ。
- 必須: 製品のコード（テスト、コメント、空行、生成したコードを除く）が 10,000 行を超える見込みなら、用語集、ID の登録簿、状態遷移表を JSON で持つ。言語が 2 つ以上なら、UI の文言も JSON で持つ。
- 用語集、ID の登録簿、状態遷移表を JSON で持つなら、キーは下の「JSON のキーの一覧」に従う。
- 必須: 保存・交換するデータの形式を、JSON Schema で定める（API は OpenAPI でもよい）。データベースの表の形は、表か `CREATE TABLE` で書く（JSON Schema は要らない）。JSON のほかの形式は、形式のスキーマの言語（例: XML は XSD、CSV は列の表）で書く。
- 必須: JSON と表が両方あるなら、JSON を正とし、表を JSON から作る。
- 必須: JSON を仕様書と別のファイルに置き、JSON に当たる表を置く節に、JSON の場所を書く。表を置かない JSON（例: ID の登録簿、UI の文言）は、仕様書の付録に場所を書く。キーは camelCase にする。言語ごとの文は、言語のタグ（BCP 47）をキーにして書き（例: `{ "en": …, "ja": … }`）、`en` を必ず置き、英語を正とする。
- 推奨: JSON で SSOT（上の「SSOT の考え方」）を定め、JSON の SSOT から仕様書用の Mermaid の図、コード、テストケースを生成する。

#### JSON のキーの一覧

- 機械が読める用語集なら、機械が用語の一貫を自動で点検でき、文書や画面に出す用語も、用語集という 1 つの元から生成できる。
- 用語集、ID の登録簿、状態遷移表を JSON で持つときのキーは次のとおり。
    - 用語集（配列 `terms[]`）: 必須のキーは `key`（用語を指す英語の語。camelCase。一意。番号の ID は振らない）、`label`（文書と画面に出す名前。`{en, ja}`）、`definition`（`{en, ja}`）。任意のキーは `avoid`（使わない言い換え）と `renames[]`（改名の履歴）。
    - ID の登録簿（配列 `prefixes[]`）: 必須のキーは `prefix`、`standsFor`（頭文字が表す英語）、`meaning`、`section`（ID を使う節）。任意のキーは無い。
    - 状態遷移表（配列 `stateMachines[]`）: 必須のキーは `name`、`states`（状態名の配列。`initial` を含めない）、`transitions[]`（`source`、`target`、`trigger`。`trigger` は初期の遷移のほかで必須）。任意のキーは `transitions[]` の `guard` と `effect`、`unhandled[]`（遷移の無い状態とイベントの組。`source`、`trigger`、`handling`。`handling` は `ignore` か `error`）。値があるときだけ書く。状態とイベントのすべての組を、`transitions[]` か `unhandled[]` に書く。JSON から作った表の凡例は `ignore` と `error` を示す。JSON を持たないときも、表に全交点と凡例を書く。

## ⛔ GRS のレビュー文書の行 ID は、既存の接頭辞を使ってはならない（MUST NOT）

`docs/review/` の文書は、所見や決定を `| # | … |` の表や
`### D-1.` の見出しで**自分の中だけの連番**を振ることがある。
それ自体は良い —— 1 つの文書の中で読まれる。
⛔ **ただし、登録簿（`docs/spec/_source/row-id-prefixes.json`）に既に在る
接頭辞をそれに使ってはならない（MUST NOT）。**

⚠️ **なぜか** —— 実測 2026-09-13。1 文字の接頭辞は **13 個**あり
（`A` `D` `G` `K` `L` `N` `P` `R` `S` `U` `V` `W` `X`）、**その 13 個すべてが
レビュー／CR 文書でも番号を振り直されている**（`S` は 22 文書、
`U` は 19、`A` は 14）。同じ綴りを 2 つ以上の文書が定義しているものは
**131** あり、`D-3` は **13 文書**が定義していた。
⇒ `PD-` はこれで**生きている仕様の指し先を 3 箇所剥がれ**、
CR-371 と続く CR で 6,500 箇所以上を改名するはめになった。

⭐ **既存の 309 行は直さない**（同裁定）。検査 53 がその 24 の名簿を
**1 つずつ名指しで持ち、走るたびに刷る。**
⛔ だから**新しく `D-1` から振り始める文書は、検査 53 を赤にする。**
それがこの規則の機械である。

### 代わりに何を使うか

```
1. 番号を振らない       —— 箇条書きで足りるならそれが最善
2. 文書固有の接頭辞   —— ファイル名から取る（`A05-1` の形）
3. 素の数字           —— `| # |` の列に `1` `2` `3`。行 ID と読める綴りにしない
```

⭐ **例外は `RVF` だけである** —— 原本の付録 A.1 が指摘の ID に決めた接頭辞で、登録簿に載せ、
レビュー報告の指摘の行にだけ使う（下の「レビュー指摘の置き場（GRS）」）。

⛔ **登録簿に新しい接頭辞を足して逃げてはならない（MUST NOT）** ——
登録簿は**仕様書・台帳・規則の 3 つの木の行 ID** のためのものであり、
レビュー文書の中だけの連番はその 3 つのどれでもない。
