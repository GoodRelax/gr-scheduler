### ⛔ 生成定数に `export` を付けるのは、ほかのファイルが読む写しだけ（JDG-139）

⭐ **利用者の裁定（2026-09-16）** —— 生成器は、ほかのファイルが読む生成定数にだけ `export` を付ける。
⭐ 利用者の問いは「公開する者だけPublicにするもんじゃない？」である。
⚠️ **判定は名前ではなく写しで行う。**
写しとは、定義したファイルと名前の組である。
1 つの名前は、それを使うユニットごとに刷られる（上の注）。
⛔ 名前で数えると、ある写しを誰も読んでいないのに、同じ名前の別の写しが読まれているせいで公開のまま残る。

| 何が | 規則 | 誰が落とすか |
|---|---|---|
| `export` の付いた写し | ほかのファイルが少なくとも 1 つ import している | 検査 30 |
| `export` の無い写し | ほかのファイルが読んでいない | 名前での import は `tsc`。<br>名前空間を文字列の鍵で読む形（`(ns as Record<string, unknown>)['NAME']`）は `tsc` を素通りし、実行時に黙って `undefined` になるので、検査 30 |
| どの写しに `export` を付けるか | `tools/generate_entity_types.py` の一覧に書く。<br>`PUBLISHED_READ_BY_SRC` は `src/` が読む写し、`PUBLISHED_READ_BY_TESTS_ONLY` は試験だけが読む写しである。<br>一覧に無い写しは `export` の無い `const` として刷られる | 一覧が、生成器の刷らない定数を名指せば生成器が止まる。<br>一覧と木の食い違いと、2 つの群の取り違えは検査 30 |

## 2. ⛔ 名前を足すときは、名が体を表すこと

⭐ **必要なら名前を足してよい。** ⛔ **ただし、その識別子の意味と責務が読んで分かること。**

⚠️ **品詞・接頭辞・単位の規約は既にある。書き写さない:**

| 何を決めたいか | どこ |
|---|---|
| クラス・コマンド・クエリ・イベントの品詞 | `R2` の品詞の規約 |
| Boolean は `is` / `has` / `can` / `should` で始める | `R2` |
| コレクションは複数形 | `R2` |
| 単位が固定の量は名前に単位を入れる（`timeoutMs`）| `R2` |
| 層ごとのコンポーネント名（Entity は名詞、UseCase は動詞句 …）| `R2` の層別表 |
| 純粋性の 4 値と `@purity` タグ | `R7` |

### ⭐ 足す前に自問する 3 つ

1. **仕様に同じ概念の名前が既に無いか**（1. に戻る）
2. **その名前は「何であるか」を言っているか、「どう作ったか」を言っていないか** ——
   ⛔ `parsedDataList` ではなく `acceptedTasks`
3. ⚠️ **範囲・限界を含む名前は、境界を含むかどうかが名前から分かるか** ——
   `min` / `max` は**含む**、`begin` / `end` は**終端を含まない**、`first` / `last` は**含む**。
   ⭐ **この 3 組を混ぜない**

⛔ **`data` / `info` / `tmp` / `obj` / `manager` / `helper` / `util` は名前ではない。**

## 3. ⛔ コメントには「なぜ」を書く。「どう動くか」を書かない

⭐ **コードを見れば分かることをコメントに書かない。** ⛔ **コードを見ても分からない意図を書く。**
⚠️ 規約としては `R2.15`（名前・コメントが「何を」でなく「なぜ」を表す）が既に持つ。**以下はこの製品に固有の作法である。**

### 書くべきこと

| | 例 |
|---|---|
| ⭐ **なぜ他の選び方を採らなかったか** | 「行ごとに回すと重ね順で勝者が変わるので、行を外側の繰り返しにしている」 |
| ⭐ **その値・規則を持っている仕様書の行 ID** | 「表 T-266 の `GA-5` の掴み代。値は 表 T-206 の `S-262` / `S-263`」 |
| ⭐ **危険の理由** | 「ここで `null` と `undefined` を同一視すると、一度も完了していないタスクが完了と判定される」 |
| ⛔ **無いもの・未決のもの** | 「⛔ アンカーの 9 点がどの表にも無い。範囲だけを検査し、推測しない」 |

### 書いてはならないこと

- ⛔ **コードの言い換え**（`// i を 1 増やす`）
- ⛔ **仕様の本文の写し** —— **行 ID を書く。** 写すと 2 か所になり、片方が腐る
- ⛔ **値の写し** —— ⚠️ **実例**: 掴み代の注記が `6px` / `15 x 15` / `30 x 20` と数を写しており、
  原稿を変えても古い数を言い続けた。**注記は行 ID を名乗る**
- ⛔ **嘘** —— ⚠️ **実例**: 「これは DOM ではない」と書いたコメントを型検査が拒んだ。
  **注記が事実かどうかは、機械が確かめられる形にしておくほうがよい**

### ⭐ 印の使い分け（仕様書・コード・変更要求で共通）

```
⛔  禁止・欠落・本物の欠陥
⚠️  注意・過去に踏んだ罠
⭐  要点
```

### ⛔ 規約に無いので、ここで定めるもの

| | 規則 |
|---|---|
| **説明変数・要約変数** | ⭐ **複雑な式には名前を付ける。** `if (task.actualFinish !== null && task.percentComplete === 100)` より `const isComplete = …` を挟む。**名前がその式の説明になる** |
| **変数のスコープを縮める** | ⭐ **変数は使う直前で宣言し、寿命を短くする。** 上で宣言して下で使う形は、間の全行が「この変数に触るかもしれない」場所になる |
| **短さより明確さ** | ⛔ **行数を減らすために意味を潰さない。** 三項演算子の入れ子・1 行に詰めた副作用は短いが読めない |

| **意味のある順序を保つ** | ⭐ 仕様の表が持つ順序（印刷順）を、コードの順序にも保つ。⚠️ **実例**: 掴みの優先順を行 ID の数字順に並べ替えると、表の裁定を 3 つ黙って逆にする |
| **無関係の下位問題を抽出する** | ⭐ その関数の主題でない汎用処理は、別の関数へ出す |
| **試験も読み手のために書く** | 詳細は [04](04-verification.md) |

### ⛔ 描いた寸法の境目は、浮動小数の誤差だけを吸収する比べ方で比べる

⭐ **仕様の「以上」「以下」「未満」「超える」「下回る」は、実数の意味である。**
⛔ **描いた寸法（px）どうしの境目の比較は、`>=` や `<` で直に書かず、浮動小数の誤差だけを吸収する共通の比べ方を通すこと（MUST）。**

| | |
|---|---|
| いまどこに在るか | `src/entity/layout-engine/schedule-geometry/schedule-geometry.ts` の `isAtLeastDrawnPx`（許容は同じファイルの `DRAWN_PX_ROUNDING`）。<br>⚠️ **通しているのは 表 T-222 の経路の選択だけである** —— ほかの境目はまだ直に比べており、次の段で当てる |
| 許容の大きさ | 描いた寸法の丸めの誤差を吸収し、画面で意味のある差（1px の何分の 1）を決して飲まない値。<br>⚠️ **測って決めた値ではない** —— 導き方は定数の `WHY:` が持つ |
| ⛔ 使ってはならない所 | 日数・件数・時間（ミリ秒）の比較。<br>境目の近くの値を丸めて寄せる目的（誤差より大きい幅を足すこと） |
| ⛔ 境を越えて使うとき | 同じ関数を写して 2 つ目を作らない。<br>ほかのコンポーネントへ公開するには 表 T-064 の行が、新しいファイルへ移すには 表 T-075 の行が要る（検査 26b / 24）|
| なぜ仕様に書かないか（`JDG-138`）| 浮動小数は実装の都合である。<br>仕様に許容を書くと、以上・以下を使うほかの表すべてに同じ問いが生える。<br>退けた案: 仕様に許容を書く、その 1 か所だけ描く比を掛ける前の日数と設定値で比べる（日数を経路の選択へ運び込むことになり、ほかの場所の同じ問題は残る）、試験を緩める |

⚠️ **実例（`DFC-616`）**: 表示の倍率が描く比（`S-236`）を掛けると、1 日の幅が 2 進で割り切れない値になる。
2 本のバーの間隔を「2 つの辺の絶対位置の差」で求めるので、入口の走りと数学では等しい間隔が 1 ulp 足りず、表 T-222 の `RP-1` ではなく `RP-4` を選んでいた（`tests/integration/schedule-drawing.sws.test.ts` の `SWS-3`）。
