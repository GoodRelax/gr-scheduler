## 2. ⛔ 名前を足すときは、名が体を表すこと

⭐ **必要なら名前を足してよい。** ⛔ **ただし、その識別子の意味と責務が読んで分かること。**

⚠️ **品詞・接頭辞・単位の規約は既にある。書き写さない:**

| 何を決めたいか | どこ |
|---|---|
| クラス・コマンド・クエリ・イベントの品詞 | `R2` の品詞の規約 |
| Boolean は `is` / `has` / `can` / `should` で始める | `R2` |
| コレクションは複数形 | `R2` |
| 単位が固定の量は名前に単位を入れる（`timeoutMs`）| `R2` |
| 層ごとのコンポーネント名（Entity は名詞、UseCase は動詞句 …）| `R2` の層別表 |
| 純粋性の 4 値と `@purity` タグ | `R7` |

### ⭐ 足す前に自問する 3 つ

1. **仕様に同じ概念の名前が既に無いか**（1. に戻る）
2. **その名前は「何であるか」を言っているか、「どう作ったか」を言っていないか** ——
   ⛔ `parsedDataList` ではなく `acceptedTasks`
3. ⚠️ **範囲・限界を含む名前は、境界を含むかどうかが名前から分かるか** ——
   `min` / `max` は**含む**、`begin` / `end` は**終端を含まない**、`first` / `last` は**含む**。
   ⭐ **この 3 組を混ぜない**

⛔ **`data` / `info` / `tmp` / `obj` / `manager` / `helper` / `util` は名前ではない。**

## 3. ⛔ コメントには「なぜ」を書く。「どう動くか」を書かない

⭐ **コードを見れば分かることをコメントに書かない。** ⛔ **コードを見ても分からない意図を書く。**
⚠️ 規約としては `R2.15`（名前・コメントが「何を」でなく「なぜ」を表す）が既に持つ。**以下はこの製品に固有の作法である。**

### 書くべきこと

| | 例 |
|---|---|
| ⭐ **なぜ他の選び方を採らなかったか** | 「行ごとに回すと重ね順で勝者が変わるので、行を外側の繰り返しにしている」 |
| ⭐ **その値・規則を持っている仕様書の行 ID** | 「`GR-9` の掴み代。値は 表 T-206 の `S-93`」 |
| ⭐ **危険の理由** | 「ここで `null` と `undefined` を同一視すると、一度も完了していないタスクが完了と判定される」 |
| ⛔ **無いもの・未決のもの** | 「⛔ アンカーの 9 点がどの表にも無い。範囲だけを検査し、推測しない」 |

### 書いてはならないこと

- ⛔ **コードの言い換え**（`// i を 1 増やす`）
- ⛔ **仕様の本文の写し** —— **行 ID を書く。** 写すと 2 か所になり、片方が腐る
- ⛔ **値の写し** —— ⚠️ **実例**: 掴み代の注記が `6px` / `15 x 15` / `30 x 20` と数を写しており、
  原稿を変えても古い数を言い続けた。**注記は行 ID を名乗る**
- ⛔ **嘘** —— ⚠️ **実例**: 「これは DOM ではない」と書いたコメントを型検査が拒んだ。
  **注記が事実かどうかは、機械が確かめられる形にしておくほうがよい**

### ⭐ 印の使い分け（仕様書・コード・変更要求で共通）

```
⛔  禁止・欠落・本物の欠陥
⚠️  注意・過去に踏んだ罠
⭐  要点
```

## 4. ⭐ 読みやすいコードの常識

⛔ **既に規約が持つものは、ここでは指すだけにする**（`review-standards.md`）:

| 常識 | どこ |
|---|---|
| 繰り返しを避ける／マジックナンバーを定数にする | `R4`（DRY）|
| ネストを 4 段以上にしない／早期 return で平坦にする | `R4`（KISS）|
| 今の要求に無い機能を先回りで作らない | `R4`（YAGNI）|
| 1 つの関数に複数の抽象度を混ぜない | `R4`（SLAP）|
| 関心を分ける（UI と業務、データ取得と業務）| `R4`（SoC）|
| 状態を変える操作と値を返す操作を分ける | `R4`（CQS）|
| チェーン呼び出しで他人の内部に触らない | `R4`（LOD）|
| 驚かせない | `R4`（POLA）|
| エラーを握り潰さない／境界とインデックス／資源の生存期間／時刻 | `R3` |
| アルゴリズムとデータ構造・毎フレームの経路 | `R5` |

### ⛔ 規約に無いので、ここで定めるもの

| | 規則 |
|---|---|
| **説明変数・要約変数** | ⭐ **複雑な式には名前を付ける。** `if (task.actualFinish !== null && task.percentComplete === 100)` より `const isComplete = …` を挟む。**名前がその式の説明になる** |
| **変数のスコープを縮める** | ⭐ **変数は使う直前で宣言し、寿命を短くする。** 上で宣言して下で使う形は、間の全行が「この変数に触るかもしれない」場所になる |
| **短さより明確さ** | ⛔ **行数を減らすために意味を潰さない。** 三項演算子の入れ子・1 行に詰めた副作用は短いが読めない |
| **条件は肯定形で書く** | ⭐ `if (!isNotReady)` を書かない。**否定の否定は読む速度を半分にする** |
| **似た処理は似た形で書く** | ⭐ **並んだコードは、並んで見えるように書く。** 見た目の違いは意味の違いだと読まれる |
| **意味のある順序を保つ** | ⭐ 仕様の表が持つ順序（印刷順）を、コードの順序にも保つ。⚠️ **実例**: 掴みの優先順を行 ID の数字順に並べ替えると、表の裁定を 3 つ黙って逆にする |
| **無関係の下位問題を抽出する** | ⭐ その関数の主題でない汎用処理は、別の関数へ出す |
| **試験も読み手のために書く** | 詳細は [04](04-verification.md) |

## 5. ⛔ コードは英語・ASCII

⭐ **識別子・コメント・文字列・ログ出力を含む。** 世界に公開する前提である。
⚠️ **日本語の仕様書を引くときは行 ID を書く**（`FR-094` / `GR-9` / `S-93`）—— **本文を訳して写さない。**
⚠️ **例外は、日本語そのものを扱う処理**（分類の欄を解析するなど）。**その場合も、なぜ日本語が要るかを書く。**

⛔ **文字列の鍵は ASCII だけにする。** ⚠️ 制御文字が 1 つ混じると、成果物のハッシュが変わって
**アプリ全体が読み込まれなくなる**（[04](04-verification.md)）。
