# 開発の規則 —— 索引

**本フォルダは、この製品の作り方の規則を置く場所である。** コーディングに限らない ——
**何のために作るか**、**仕様をどう変えるか**、**どう確かめるか**を含む。

⛔ **製品が何であるかは書かない。** それは `docs/spec/` が持つ。**本フォルダは作り方だけを持つ。**

---

| **02** | [仕様を変える手順](02-changing-the-spec.md) —— **影響をグラフで測ってから書く**。穴に当たったときの作法 | 本フォルダ（原本）|

### ⛔ なぜ `RS` と `SW` をここへ複製しないか

⭐ **仕様書がその 2 つを「パスで」引いているからである** —— `01-04-requirements.md` と `05-07-design.md`。
⚠️ **複製すると、仕様書が条項番号で引いている文書が 2 部になる。** 2 部あるものは必ずずれる（`R4`）。

⚠️ **移動もしない。** 過去の変更要求・レビュー在庫・引継書が **10 か所以上**でそのパスを引いており、
**過去の記録を書き換えないのが本プロジェクトの規則だからである。**

⭐ **したがって本フォルダは入口であり、正はあちらにある。** ⛔ **条項の中身をここへ書き写してはならない。**

## 2. ⭐ 規則は「置いた場所」で守られ方が変わる（**実測**）

⛔ **重要度ではなく形が守らせる。** 同じ内容でも、置く場所で守られ方が変わることを測った:

```
記憶・技能書        4 セッション連続で飛ばされた
原則として書く      75 件中 7 件しか従っていなかった
仕様書に MUST       それを書いた回の中で 275 か所破られていた
手順として書く      走った
機械検査に載せる    飛ばせない
```

⭐ **だから本フォルダの規則は、可能なものを機械検査へ下ろしてある。** 何が何を強制するかは 04 が持つ。
⚠️ **検査にできない部分は残る** —— 検査は「問いを立てさせる」ことはできても、**答えの質は保証しない。**

---

## 3. ⭐ 規則の読み方

- **⛔** は禁止・違反すると本物の欠陥になるもの
- **⚠️** は注意・過去に実際に踏んだ罠
- **⭐** は要点・そこだけ読めば効くもの

⚠️ **この 3 つの印は仕様書・コード・変更要求でも同じ意味で使う。**
