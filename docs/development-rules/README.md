# 開発の規則 —— 索引

**本フォルダは、この製品の作り方の規則を置く場所である。** コーディングに限らない ——
**何のために作るか**、**仕様をどう変えるか**、**どう確かめるか**を含む。

⛔ **製品が何であるかは書かない。** それは `docs/spec/` が持つ。**本フォルダは作り方だけを持つ。**

## 2. ⭐ 規則は「置いた場所」で守られ方が変わる（**実測**）

⛔ **重要度ではなく形が守らせる。** 同じ内容でも、置く場所で守られ方が変わることを測った:

```
記憶・技能書        4 セッション連続で飛ばされた
原則として書く      75 件中 7 件しか従っていなかった
仕様書に MUST       それを書いた回の中で 275 か所破られていた
手順として書く      走った
機械検査に載せる    飛ばせない
```

⭐ **だから本フォルダの規則は、可能なものを機械検査へ下ろしてある。** 何が何を強制するかは 04 が持つ。

⭐ **本フォルダそのものにも同じ手を当てた** —— ⛔ **「まず規則を読め」を引継書に書くのは「原則」の段であり、75 件中 7 件しか従われなかった段である。** そこで:

```
検査 0   bash .claude/skills/spec-graph-check/check.sh が最初に走らせるもの
         上の表を README.md から読んで刷る（⛔ 写しは作らない）
検査 26  その索引が実物と合っているかを見る
         —— 索引に無い規則ファイル / 解決しないリンク / 欠けた番号で落ちる
```

⚠️ **機械にできないのは「読んだか」である。** ⭐ **できるのは「入口を正しく保ち、作業の最初の命令がそれを目の前に出すこと」** —— 検査 22 が変更要求に対してする割り方と同じである。
⚠️ **検査にできない部分は残る** —— 検査は「問いを立てさせる」ことはできても、**答えの質は保証しない。**

## 3. ⭐ 規則の読み方

- **⛔** は禁止・違反すると本物の欠陥になるもの
- **⚠️** は注意・過去に実際に踏んだ罠
- **⭐** は要点・そこだけ読めば効くもの

⚠️ **この 3 つの印は仕様書・コード・変更要求でも同じ意味で使う。**
