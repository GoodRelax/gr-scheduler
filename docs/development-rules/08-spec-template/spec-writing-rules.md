# 仕様の書き方の規則（GRS）—— StrictDoc の記法と、ANMS v0.36 が持たない決まり

⭐ **仕様書のテンプレートは ANMS v0.36 である**（[`anms-v036-ja.md`](anms-v036-ja.md)、`JDG-3823`）。章・節・ID・鎖・文の決まり・EARS・ユースケース・機械が読む原本・未決の問い・変更履歴は ANMS が持ち、GRS が ANMS をどう当てるかは [`spec-template.md`](spec-template.md) が持つ。⛔ 本書はそれらを書き写さない。
⭐ **本書が持つのは、ANMS が持たない GRS の決まりだけである** —— StrictDoc の Markdown の記法（GRS の要求は StrictDoc の節点で書く、`JDG-3831`）、散文に数を書くとき、履歴を持たないこと、表と図の規則、規則と理由の置き場、GRS の語の決まり、検査の走らせ方。
⛔ **本書と ANMS v0.36 が食い違えば、ANMS v0.36 と `spec-template.md` に従う。**
⚠️ **2026-11-24 まで、本書は旧い 10 章のテンプレートの章ごとの規則を持っていた** —— Cockburn のユースケース、`SWS`・`TC`・`TR` のノード、旧い EARS の日本語の形、ANMS・ANPS-part・ANPS-chapter のファイルの分け方、旧い構成の設計根拠。ANMS v0.36 と重なり食い違うので消した（git の履歴に残る）。今の仕様（まだ旧い形）の節の名前は、`spec-template.md` の 3 節の対応表で読む。

## 1. ノードと地の文

**仕様書は StrictDoc の Markdown で書く。** 見出しがノードの `TITLE` になり、`**Type**:` がノードの型を名指す。

> **本節は「何がノードか」と「各型が持つ欄」だけを持つ。書き下し方と検査の走らせ方は、7 節「ノードの書き下しと検査」にある。**

### 何がノードで、何が地の文か

| 何 | 書き方 |
|---|---|
| **ノード** | 見出しの直後に `**Type**:` を置く。`spec.sgra` が宣言する型（下の「型ごとの欄」） |
| **地の文を直接持つ章・節の見出し** | **`**Type**: SECTION` を置く（MUST）。省略できない** |
| **配下が下位見出しだけの章・節の見出し** | **置かなくてよい。** 省くと行数が減る |
| **地の文** | 何も宣言しない。段落・表・図はそのまま書く |

> **`SECTION` を常に省けると読み違えてはならない。** 省けるのは「その見出しの下に段落・表・図が 1 つも無く、下位の見出しだけがある」場合に限る。**1 例で通ったことは、条件が揃っていたことしか示さない。**

### 型ごとの欄（今の文法 `spec.sgra`）

| `**Type**:` | 必須の欄 | 任意の欄 | 親 | `Role` |
|---|---|---|---|---|
| `SECTION` | （見出しが `TITLE` になる） | — | — | — |
| `GOAL` | `UID` / `STATEMENT` | — | **無し（根）** | — |
| `USE_CASE` | `UID` / `STATEMENT` / `SCENARIO` | `EXTENSIONS` | `GOAL` | `Satisfies` |
| `FUNC_REQ` | `UID` / `STATEMENT` | `ORIGIN` / `RATIONALE` | `USE_CASE` | `Satisfies` |
| `NON_FUNC_REQ` | `UID` / `STATEMENT` | `ORIGIN` / `RATIONALE` | `GOAL` | `Satisfies` |
| `SW_SPEC` | `UID` / `STATEMENT` | `RATIONALE` | `FUNC_REQ` / `NON_FUNC_REQ` | `Satisfies` |
| `USE_CASE_TEST` | `UID` / `GIVEN` / `WHEN` / `THEN` | — | `USE_CASE` ＋ `File` | `Verifies` |
| `SW_SPEC_TEST` | `UID` / `TEST_LEVEL` (※) / `GIVEN` / `WHEN` / `THEN` | — | `SW_SPEC` ＋ `File` | `Verifies` |
| `NON_FUNC_TEST` | `UID` / `GIVEN` / `WHEN` / `THEN` | — | `NON_FUNC_REQ` ＋ `File` | `Verifies` |
| `TEST_RESULT` | `UID` / `RESULT` / `EXECUTED_ON` (※) / `TESTED_VERSION` (※) / `ENVIRONMENT` (※) / `EVIDENCE` | `REMARK` | テスト 3 型のいずれか | `ResultOf` |

**(※) は GRS の文法 `spec.sgra` で必須である。**

**`TITLE` は見出しから来る。`.md` に `**TITLE**:` と書いてはならない（MUST NOT）。**

**値域を持つ欄:**

| 欄 | 値域 |
|---|---|
| `TEST_LEVEL` | `Integration` / `System`（**`Unit` は無い。** 単体テストは仕様書の外で行う） |
| `RESULT` | `PASS` / `CONDITIONAL` / `FAIL` / `SKIP` |

⚠️ **上の型と欄は、旧い 10 章の文法のままである。** ANMS v0.36 の章（目的・分析・要問、ユースケースの 6 つの欄と印、要求の traces、実装仕様 `IMPS`、6.2 のシナリオ）に合わせて型と欄を改めるのは計画の B5・B8 で、文法を改めたら本表を文法から書き直す。⛔ 型と欄の正は文法である —— 本表と文法が食い違えば文法に従う。

## 2. ⛔ 散文に数を書くときは、機械が読み直せる形で書く

⛔ **散文が抱えた数は、書いた席とは別の場所が動いた日に偽になる。** ⚠️ **実測（2026-09-12）**:
「合格条件は `NFR-001` 〜 `NFR-003` が持つ」は**実際には 6 つ**（`NFR-010` `NFR-011` `NFR-013` も
ゲート行が正に取る）、「名簿は 7 本の表が持つ」は**生成器が読むのは 13 本**、
「辺のラベルには、その線が何を表すかだけを書く」は **30 本中 3 本が規則の指し先を運んでいる**。
⭐ **3 件とも、書いた当日から偽か、数日で腐ったかのどちらかである。**

| 書こうとしている数 | どう書くか |
|---|---|
| **表の行数そのもの** | ⭐ **「表 T-nnn の N 件」の形で書く**（`件` ／ `行` ／ `段` ／ `つ`）—— **検査 9 がこの綴りだけを読み、表の行数と突き合わせて赤にする。**⇒ **形を合わせるだけで門になる** |
| 表の**一部**の数（ゲート行だけ、など） | ⛔ **数を書かない。**「表 T-nnn の〜の行が持つ」と**指し先で書く** —— 検査 9 は部分集合を数えられない |
| 別の文書・生成器・コードを数えた数 | ⛔ **数を書かない。**⚠️ **仕様書が写しを引く形（原本と写しの逆転）になる** |
| 日付つきの実測 | ⭐ **書いてよい。**⛔ **ただし「⚠️ 実測（YYYY-MM-DD）」を添えること** —— **記録は腐らない。腐るのは現在形の主張である** |

⛔ **「全数」「員数」「すべて」「だけである」と書いたら、その席は主張をしている。**
⭐ **主張するなら、それを数え直す機械か、指し先のどちらかを必ず添えること。**

## 3. ⛔ 仕様書は理由を持ち、履歴を持たない（CR-375）

⛔ **仕様書に、規則の出どころ（誰が・いつ・どう言ったか）と、覆った履歴を書いてはならない（MUST NOT）。**
覆った文は、生きた規則と読み違えられる。
出どころは、規則の正しさに何も足さない。
⭐ **なぜその仕様にしたのか／しなかったのかは、その要求の `RATIONALE` か表の結びに、理由の文として書くこと（MUST）。**
同じ判断を繰り返さないための記録は、理由の文が担う。

| 書こうとしているもの | どう書くか |
|---|---|
| 「利用者の裁定（日付）」「〜の指示で」 | ⛔ **書かない。**規則だけを書く |
| 利用者の言葉の引用 | ⛔ **書かない。**理由の文に直す。言葉は `docs/development-records/rulings.md` が持つ |
| 「YYYY-MM-DD まで〜と定めていた」「〜を撤回した」 | ⛔ **書かない。**いま正しい規則だけを書く |
| 退けた案 | ⭐ **日付の無い MUST NOT と、その理由**で書く |
| 実測の数 | ⭐ **測り方を 1 句添える。**測り方の無い数は書かず、主張だけを書く。日付は上の表の「日付つきの実測」の行に従う |

⭐ **検査 54 が、原稿に「利用者の裁定 YYYY-MM-DD」の形と「YYYY-MM-DD まで」が残っていないことを数える。**
⚠️ 日付の無い引用や「以前は…」の履歴は検査 54 に見えない —— 書き手がこの節に従うこと。

⭐ **ANMS が仕様書に置くと決めた 2 つは、上の「履歴」ではない** —— 付録 A.3 の未決の問いの一覧（`OPQ-n` の行）と、仮に決めた文と止めた文の末尾の `（仮: OPQ-n）`・`（未決: OPQ-n）`。どちらも今の未決を示し、答えが出たら消す（規則 06 の 3 節）。⚠️ 検査 54 と precheck（検査 41）が `OPQ` を通すように直すのは計画の B2 である。

## 4. レビュー指摘の置き場

> **レビュー指摘はレビュー報告（`docs/review/` の 1 ファイル。指摘 1 件を `RVF-xxx` の 1 行）が持つ。仕様書のノードは一切持たない（MUST NOT）。**

**指摘にはノードに紐づけられないものがある** —— 漏れの指摘（「境界条件が無い」）、文書全体への指摘、コードへの指摘。**紐づけられないものを置ける形は仕様書のノードにはない。**

**書き方は本書ではなく規則 07 の付録 A.1 と「レビュー指摘の置き場（GRS）」が持つ。** ここでは「仕様書は持たない」ことだけを定める。

## 5. 表と図

### 図の規則

> **大きな図は、別ファイルへ出して本文から参照する（MUST）。** 置き場は `_assets/fig-<name>.md` とする。

**大きな図の判定は、図の種類ごとに要素の数で行う（MUST）。**

| 図の種類 | 別ファイルへ出す条件 |
|---|---|
| シーケンス図 | **ライフラインが 5 本以上** |
| クラス図 | **クラスが 5 つ以上** |
| ER 図 | **エンティティが 5 つ以上** |
| 状態遷移図 | **状態が 7 つ以上** |
| 構成図・コンポーネント図・フローチャート | **ノードが 10 個以上** |
| アクティビティ図 | **分岐が 5 つ以上** |

**閾値を変えたら、仕様書の 1.12 Notation（表記規約）に記す（MUST）。**

| # | 規則 |
|:-:|---|
| 1 | **外へ出す条件と置き場は本節冒頭の MUST が持つ** |
| 2 | **外に出したら、前後の地の文も直す（MUST）。**「下の図のとおり」が宙に浮く。**これは機械では検出できない。目で読む** |
| 3 | **`_assets/` の図に `**Grammar**` を宣言してはならない（MUST NOT）。** パス解決で落ちる |
| 4 | 小さな図は本文に置いてよい |

**図が本文に埋まると、その仕様書を読むすべてのエージェントが、毎回その全行を読む。** **図の行数はそのまま固定費になる。**

### 表と図の参照の規則

**細目が表または図で表せるなら、要求は 1 文でそれを指すこと（MUST）。行ごとに要求ノードを作ってはならない（MUST NOT）。**

| 行 ID | 書き方 |
| --- | --- |
| WR-1 | 「〜の判定は表 T-XXX に従うこと。」／「〜を構成するクラスは図 F-XXX に従うこと。」（**番号は例示であり、実在の表や図を指していない**） |
| WR-2 | 「aaa は bbb であること。」「ccc は ddd であること。」…と細目を要求ノードで並べる |

要求ノードは 1 つずつが UID・理由・関係・検証するテストを連れてくる。表で表せる細目をノードに割ると、文書も追跡も重くなるだけで、得るものが無い。

- **番号は席番号とする（MUST）。** 表は `表 T-001`、図は `図 F-001` の形で通し番号を振り、途中の表や図を削っても残りの番号を詰め直してはならない（MUST NOT）。
- **要求の `UID` も席番号とする（MUST）。番号を振り直してはならない（MUST NOT）。** 一度振った `FR-xxx` / `NFR-xxx` / `UC-xxx` / `GL-xxx` は、要求を書き換えても、間の要求を削っても、そのまま保つ。**番号が動くとトレースの鎖が切れ、テストと結果の親子関係が黙って壊れる。** 要求を足すときは既存の最大値の次を使う。
- **番号の順と文書の並び順は別である（MUST）。** 新しい要求は**番号の順ではなく、関連する要求の隣へ置く**。色の要求は色の要求の隣、編集の要求は編集の要求の隣に置き、`FR-031` が `FR-007` の直後に並ぶことを正しいものとする。**同じことを述べる要求が文書の離れた場所に散ってはならない（MUST NOT）** —— 散ると、読む者が全体を読むまで重複と欠落に気づけない。
- **表の第 1 列は行 ID とする（MUST）。** テストが落ちたときに、行 ID がそのまま仕様の 1 行を指せるようにするためである。
- **表を指す要求を検証するテストは、表を写した固定データで駆動すること（SHOULD）。** 行ごとにテストを書くのではなく、1 つのテストが表の全行を回る形にする。
- **推奨を決定として書いてはならない（MUST NOT）。** 出典が「推奨する」までしか述べていないことを、仕様書が「決めた」と書き換えない —— 後から出典に当たった者が、誰がいつ決めたのかを探して見つけられなくなる。**仕様書で決めるなら、決める理由を仕様書が持つこと（MUST）。**

### 規則と理由の置き場

**規則と理由は、それを課す要求が持つこと（MUST）。値の表は値だけを持ち、規則には行 ID で指すこと（MUST）。** 例外は 2 つある —— **その値の範囲そのものの根拠**（「範囲の理由」列）と、**その値の由来の記録**（🔎 を付けた注）である。どちらも値についての記述であって、規則ではない。

⚠️ **値の表の側は検査 12（`.claude/skills/spec-graph-check/style-checks.py`）が機械で止める。** 同じことを文でも持つと写しになるので、ここには置かない。

**同じことを 2 度書きたくなったら、置き場を 1 つ決め、他方は行 ID か `UID` で指すこと（MUST）。指す先の文を書き写してはならない（MUST NOT）** —— 写しは、元を直したときに一緒に腐る。

⚠️ **規則が 2 か所にあると、片方を直したときにもう片方が残り、そこで 2 つの文が食い違う。重複は必ず矛盾に育つ。** **`docs/spec/_assets/tbl-settings.md` の `S-105` が正しい書き方の例である** —— 規則を持たず「派生する色は保存しない方針（§4）に従う」と指すだけで済ませている。

## 7. ノードの書き下しと検査

**本節は、書く中身が決まったあとに引く。** 何がノードかと型ごとの欄は 1 節にある。

### 書き方の規則

> **本表はすべて strictdoc 0.27.1 で実測した（参考 1）。推測は含まない。** 記法の話を測らずに書いてはならない（MUST NOT）。

**記法の規則:**

| # | 規則 | 破ると |
|:-:|---|---|
| 1 | **地の文を直接持つ見出しには `**Type**: SECTION` を宣言する（MUST）** | `Invalid node type: REQUIREMENT` |
| 2 | **配下が下位見出しだけの見出しは宣言しなくてよい。** 省くと行数が減る | ——（省いても通る） |
| 3 | **見出しレベルを飛ばしてはならない（MUST NOT）** | `heading level forward jumps are not allowed` |
| 4 | **欄は 1 行 1 欄で並べる。行継続の `\` を書いてはならない（MUST NOT）** | 最終行に残ると export が止まる。**唯一の失敗形がこれである** |
| 5 | **欄の並びは文法の宣言順に合わせる（MUST）。** `ORIGIN` は `STATEMENT` の後 | `Wrong field order for requirement` |
| 6 | **水平線 `---` を書いてはならない（MUST NOT）。** 章見出しが区切りを兼ねる | ノードの直後だと `Invalid requirement field`。**節の直後だと通ってしまうので原因が分かりにくい** |
| 7 | **`**Relations**:` は本文の欄より後ろ、ノードの末尾に置く（MUST）** | メタデータに隣接させると、整形で空行が入った瞬間に `duplicate field names` |
| 8 | **1 行の欄しか持たない型は、最後の欄を段落として独立させる（MUST）。** `TEST_RESULT` の `EVIDENCE` がこれに当たる | 置き場が無くなり `Relations must directly follow requirement metadata without an empty line` |
| 9 | **関係は `- ` で始まる箇条書きで書き、続く欄は字下げする（MUST）** | 1 行にまとめると `each relation dictionary must contain a mandatory 'Type' key` |
| 10 | **`**SCENARIO**:` `**EXTENSIONS**:` `**Relations**:` のように箇条書きを従える欄名は、その後ろに空行を 1 つ置く（MUST）** | ——（空行なしでも export は通る）。**ただし Prettier が空行を入れるため、置かないと保存のたびに差分が出る** |
| 11 | **`File` 関係の鍵は `Path` である（MUST）。** 使える鍵は `Type` / `Path` / `Element` / `ID` / `Hash` / `Lines` の 6 つ | 他を書くと export が止まる |
| 12 | **親として書いた `UID` は同じ文書の中に実在しなければならない（MUST）** | `references parent requirement which doesn't exist`。**空欄フォームだけを並べた仕様書テンプレートは export できない** |

> **規則 6 と 10 は、規則 7 と組で効く。** どちらも「エディタの自動整形に耐えるか」の規則である。**書いてあっても人は守れない**ので、**仕様書テンプレートそのものを整形の不動点にしておく。**

**欄の値の規則:**

| # | 規則 |
|:-:|---|
| 1 | **`EXECUTED_ON` は UTC の ISO 8601 日時とする（MUST）** —— `2026-08-09T05:32:05Z`。**オフセット表記を使ってはならない（MUST NOT）。** 混ざると文字列比較の順序が実時刻とずれる。**日付だけにしてはならない（MUST NOT）** |
| 2 | **`TESTED_VERSION` は被試験ソフトを一意に特定するものとする（MUST）。** commit SHA を推奨する。タグでもよい |
| 3 | **`EVIDENCE` は後から取り出せるものとする（MUST）。** ログの位置・実行 ID・成果物のパス。**「確認済み」のようなたどれない文字列を書いてはならない（MUST NOT）** |
| 4 | **`TEST_RESULT` の見出しは判定で始める（SHOULD）** —— `[PASS] 語を問い合わせて意味を得る`。トレースツリーの上で判定が読める |
| 5 | **仕様書のノードはレビュー関連の欄を持たない（MUST NOT）。** 前半の「レビュー指摘の置き場」を見よ |

**ノードの書式:**

```markdown
#### 見出しがそのまま TITLE になる

**Type**: [型名]
**UID**: [接頭辞]-001
**[1 行で収まる欄]**: [値]

**[本文の欄]**: [本文]

**[本文の欄]**: [本文]

**Relations**:

- **Type**: `Parent`
  **ID**: `[親の UID]`
  **Role**: `[Satisfies または Verifies または ResultOf]`
- **Type**: `File`
  **Path**: `[テストコードの位置]`
```

**書式が示すのは 4 つである。**

| # | 何 |
|:-:|---|
| 1 | **見出しが `TITLE` になる。** `**TITLE**:` とは書かない |
| 2 | **欄は 1 行 1 欄で並べる。** 行継続の `\` は要らない |
| 3 | **本文の欄は、前後を空行で区切って独立させる** |
| 4 | **`**Relations**:` はノードの末尾に置く。** ラベルの後ろに空行を 1 つ入れ、`- ` の箇条書きで書く |

**型ごとの具体は、今の仕様書のノードが例である。** ⛔ 空欄のフォームを本書に置かない —— 片方だけが更新される。

**文書ヘッダ（H1 の直後に置く）:**

```markdown
# Requirements

**Grammar**: spec.sgra
**UID**: DOC-REQUIREMENTS
**Version**: 0.4
```

**文書ヘッダに独自の欄を書いてはならない（MUST NOT）。** エラーも警告も出さずに消える。**欄の未知はノードでは export を止めるが、文書では黙って捨てられる。**

> **`**Grammar**` / `**UID**` / `**Version**` と H1 の間に何かを挟んではならない（MUST NOT）。** 文書ヘッダを丸ごと失い、文法が適用されなくなる。**Common Block（YAML frontmatter）をファイル先頭に置けないのはこのためであり、同名の `.meta.yaml` へ外出しする。**

⚠️ **ANMS の頭の 3 行（バージョン・テンプレート・変更履歴、`spec-template.md` の 1 節）は、上の文書ヘッダと H1 の間に置けない。** 置き方と、古い `**Version**` の行の扱いは、計画の B9 が組み立ての道具と一緒に決め、`spec-template.md` の 1 節に書く。

### 検査の走らせ方

**export:**

```bash
strictdoc export docs/spec --formats=json --output-dir out/json --no-parallelization
# GRS の検査は check.sh が回す（規則 09）
```

**`--no-parallelization` を必ず付ける（MUST）。** 並列 export が本当のエラーを握り潰す。**出力先を入力フォルダの中に置いてはならない（MUST NOT）** —— UID 重複で止まる。

> **export だけでは記法の検査にならない（実測）。** 「記法の規則」7 番を破った形は、**そのままでは export が通り、整形を 1 回かけた瞬間に落ちる。**
>
> ```text
> 整形前: Total execution time ... 1.47s
> 整形後: Semantic error: duplicate field names in a valid requirement node are not allowed.
> ```
>
> **したがって記法の検査は「複製する → 整形をかける → export する」の順で行う（MUST）。** 原本を整形してはならない（MUST NOT）—— 利用者の書いた表の桁揃えまで変わる。

⭐ **GRS の仕様の検査は `bash .claude/skills/spec-graph-check/check.sh` が持つ**（規則 09）。export はその一部である。
