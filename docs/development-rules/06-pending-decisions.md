# 06 裁定待ちの扱い —— 待たずに進める範囲を、可逆コストで決める

⛔ **裁定は利用者にしか下せない。** ⚠️ **だが、裁定が下るまで手が止まると、待ち時間がそのまま遅れになる。**
⭐ **そこで「覆したときに何を払うか」で線を引く。** 安く覆せるものは**推奨値で進め、後でまとめて裁定する。**

---

## 0. ⛔ 利用者の裁定が要るものと、要らないもの（`JDG-3590`）

⭐ **正本は [reduce-owner-rulings-study.md の 9 節](https://github.com/GoodRelax/Sandbox/blob/54ad86d/Analisys/reduce-owner-rulings-study.md)である。** 各チームはこの節を参照し、本文を打ち直さない。本節はその要点を gr-scheduler の言葉で書く。
⭐ **本節は「裁定が要るか」を決める。** 2 節以降は、裁定を待つか、進めながら受けるかを決める。

### 0.1 要るものと要らないもの

| 種類 | 当たるもの | 裁定 | 進め方 |
|---|---|---|---|
| **UI** | アプリを使う人の目に見えるもの、手で触れるもの —— 配置・大きさ・色・線幅・余白、画面の言葉、操作と待ち時間、画面に出る初期値、印刷と書き出しの見た目 | ⛔ **要る** | 0.3 の道で作る。⭐ 作業は止めない |
| **外部との約束** | 保存・交換するファイルの形式、公開する API（表 T-064・表 T-065、MCP のツール名と引数）、外に見える名前、受け入れる入力と拒む入力の境目。⭐ **用語集の語はここに入る** | ⛔ **要る** | 2 節の `D`〜`F` と同じく待つ |
| **日程** | 次のマイルストーンの見込みが 1 日以上遅れる、またはクリティカルパスの残りが 20% 以上延びる | ⛔ **要る** | PMO が遅延診断と計画で測る。BOSS は何を先にし、何を後に回すかを問う |
| **コンテキスト** | 1 つの仕事が 1 本のセッションで終わらないと見込まれる | ⛔ **要る** | BOSS が始める前に見積もり、順番とモデルを問う |
| **週間の使用量** | 週間の使用量の残りが 20% を切る | ⛔ **要る** | 測り方は未定である。BOSS が使用量の表示を見て問う |
| **上のどれにも当たらず、基準で答えが決まる選択** | 関数の分け方、内部の層の切り方、内部の名前、試験の書き方、重複の消し方 | ✅ **要らない** | AI が決める。⛔ 決めた行に、根拠にした [07](07-review-standards.md) の観点の名前と MUST・SHOULD を書く |
| **上のどれにも当たらず、基準で答えが決まらない選択** | 2 つ以上の案が基準を通り、基準がどちらとも言わない選択 | ⭐ **1 問だけ** | 個々の選択ではなく、基準の追加を問う |

⭐ **「基準で答えが決まる」は次の 2 つのどちらかである**: [07](07-review-standards.md) の総合レビューチェックリストの MUST をすべて通す案が 1 つだけある。または、複数の案が MUST を通り、SHOULD と設計原則にも合う案が 1 つだけある。
⭐ 基準で答えが決まる選択は、一覧に載せない。基準で答えが決まらない選択の個々の値は、基準の追加の答えを待つあいだ、2 節の分類で進める。

### 0.2 判定の順番

```
1. 既存の裁定・仕様・用語集で答えが決まっているか   決まっていれば問わずに従い、元の JDG を書く（1 節の引き方）
2. UI に当たるか                                 当たれば裁定が要る
3. 外部との約束に当たるか                         当たれば裁定が要る
4. 日程・コンテキストのしきい値を超えるか           超えれば裁定が要る
5. 基準で答えが 1 つに決まるか                    決まれば AI が決める。決まらなければ基準の追加を 1 問だけ問う
⛔ 裁定が要る種類に 1 つでも当たれば、裁定が要る
```

### 0.3 UI の道

```
1. 推奨値で作る（分類は 2 節の A か C）
2. 印 // @provisional PND-n を付け、一覧に行を足す（3 節）
3. 触れる見本を利用者に見せる（05 の「UI の数は触れる見本で決める」）
4. 裁定で確定し、印を消す（3 節）
⭐ 作業は止めない
```

### 0.4 委任の安全策（`T1`〜`T5` を全部入れる）

| 策 | 誰が | 何をする |
|---|---|---|
| **T1. 負債の週報** | PMO が毎週、BOSS 経由で利用者へ | 基準線・暫定の印の数・既知の赤・関数の大きさの超過・マジックナンバーを 1 表にし、先週との差を出す |
| **T2. 分類を別の者が確かめる** | 決めた者とは別のサブエージェント | AI が決めた行を読み、0.1 の「要る」の種類に当たらないかを見る。⛔ 疑いがあれば裁定へ戻す |
| **T3. 覆った率で委任を縮める** | BOSS | AI が決め、後で利用者が覆した選択を種類ごとに数える。覆った率が線を超えた種類は、「要る」側へ移す案を利用者に問う。⚠️ **線の値 10% はまだ裁定されていない** —— 最初の集計を出すときに、値も一緒に問う |
| **T4. 負債の定義表** | BOSS | 何を負債とみなすかの表を作り、利用者の裁定を 1 回取る。表に無い種類に気づいたら、検査に下ろす案を GQA の 1 問として出す |
| **T5. 定期の独立レビュー** | BOSS が週 1 回起こす独立レビュー | [07](07-review-standards.md) の `R1`〜`R8` で見る |

⭐ BOSS は調整役であり、PMO は BOSS の下で計画を持つ子セッションである。

## 1. ⛔ リストに載せる前に、必ず引く

⚠️ **実測**: 「裁定が要る」と判断した 3 件のうち **2 件は既に答えが在った** ——
曜日の番号は交換相手の正典（`docs/reference/mspdi/`）、削除の連鎖は 表 T-050 の `CD-1`。

```
0. grep -n "<問おうとしている言葉>" docs/development-records/rulings.md
                                 ⛔ 裁定の唯一の置き場である。利用者は既に裁いていることが多い
1. docs/spec を読み切る          ⭐ 半分以上は「実は在る」
2. docs/reference/ を当たる       交換相手とアクセシビリティの正典
3. studies/ を当たる（03-ui-naming → 08-poc の順）
4. ⛔ それでも無ければ、初めて裁定待ちである
```

⛔ **未読を裁定待ちにしてはならない。** ⭐ **それは利用者の時間を、こちらの手抜きで使うことである。**
⛔ **同じ裁定を二度問うな** —— 利用者の言葉「これまでも同じ裁定を繰り返している。 何とかしてくれ。非効率すぎ」（`JDG-02`）。0 の grep は、問うときだけでなく、見本やコードに規則を入れるときにも打つ（2026-09-19、`JDG-05` が既に持つ規則を、grep せずに見本へ実装した）。

⛔ **裁定が「守られていない」と見えたら、まず言葉が 2 通りに読めることを疑え。** ⭐ **利用者の読みが常に正である ⇒ 仕様の言葉のほうを直す。**

```
⚠️ 実測（2026-09-08）: 利用者「タスクのダミーは1日とする。 だから = は1日」 ＝ 開始日 = 終了日 は 1 日
   設計表「実績の右端 ＝ 開始日 ＋ 長さ（稼働日）」       ＝ 開始日 = 終了日 は 0 日
   ⇒ サブエージェントは設計表を読んで「穴は無い」と結論し、前に立つ者はそれを受け入れ、利用者に同じ裁定をもう一度問うた
```

## 2. ⭐ 可逆コストで 8 つに分ける

### ⛔ まずこの 2 問を引く

```
① 直すときに触るのは 1 コンポーネントの中だけか
② 公開された API（表 T-064 のメンバと 表 T-065 の継ぎ目）は動かないか
```

⭐ **両方が「はい」なら、それは変えやすい。推奨値で進め、あとでまとめて問う。**
⚠️ **そのために Clean Architecture と SRP でコンポーネントを切っている** —— **切った意味を使わなければ切っていないのと同じである。**

⛔ **この 2 問は十分条件ではない。** ⚠️ **下の「実測に基づく注意」が反例を持つ** ——
仕様のグラフで他の表の連鎖規則に縛られていれば、コンポーネントが 1 つでも `D`〜`H` である。
⭐ **順序はこうである**: ①② で箩をかけ、**残ったものだけ `impact.py` でグラフを見る。**

### ⛔ 前に立つ者への縛り

```
⛔ `A`〜`C` を巡の途中で利用者に問わない。推奨値で実装し、印を付け、一覧に溜める
⛔ 実装と試験を止めない。止めてよいのは `D`〜`H` だけである
⭐ 問うのは巡の最後か、次の巡の先頭である（3b）
```

⚠️ **実測: 1 巡で 14 件の裁定を並べ、そのうち 8 件は `A`〜`C` であった。**
⛔ **問わずに進められたものを問い、その間下流が待った。**

⭐ **利用者の常設の許し（2026-09-22、`JDG-321` ②）**: **分類 `G` に当たるものでも、仕様の自己矛盾を変更要求で直すだけなら、問わずに進めてよい。** ⛔ どの 2 文が食い違い、どちらへ揃えたかを変更要求に書け。

### ✅ 推奨値で進めてよい（**リストに載せ、印を付けて先へ行く**）

| | 何が未決か | 覆したときの実費 |
|---|---|---|
| **A** | **原稿（`_source/`）にあり、生成でコードへ届く値のうち、UI に当たらないもの** | ⭐ **1 セル ＋ `npm run gen` ＋ その値を読む試験** |
| **B** | **純関数の内部。観測できる振る舞いは仕様が固定している** —— 「どう計算するか」だけが未決 | ⭐ **1 関数 ＋ その試験** |

### ⭐ 推奨値で作り、裁定で確定する（**UI。0.3 の道で進め、作業は止めない**）

⭐ **`JDG-3590` で、`A` と `C` のうち UI に当たるものをこの表へ移した。** ⛔ 裁定は要る。
⭐ 一覧の分類の欄は `A`・`C` のまま書く —— 検査 25 がこの 2 字に印を求める。見本を見せて問う時は、上の縛りのとおり巡の最後か次の巡の先頭である。

| | 何が未決か | 覆したときの実費 |
|---|---|---|
| **A** | **原稿（`_source/`）にあり、生成でコードへ届く UI の値** —— 線幅・色・待ち時間・寸法 | ⭐ **1 セル ＋ `npm run gen` ＋ その値を読む試験** |
| **C** | **表示だけの選択で、保存形に痕跡が残らないもの** | ⭐ **描く側 1 か所** |

### ⛔ 待つ（**推奨で走ってはならない**）

| | 何が未決か | なぜ待つか |
|---|---|---|
| **D** | **文書または `MSPDI` に保存・交換される値** | ⛔ **覆すと移行が要る。** 保存済みの文書が壊れるか、往復が合わなくなる |
| **E** | **公開署名・継ぎ目（表 T-064 / T-065）を決めるもの** | ⛔ **他ユニットがそれに対して書かれ、その試験ごと無効になる** |
| **F** | **入力を受理するか拒むかの境界** | ⛔ **時間の非対称性。** 緩く受理した文書は既に手元にある。後で厳しくしても回収できない |
| **G** | **他の規則の正しさの論証が乗っている値** —— しきい値・上限・不変条件 | ⛔ **覆すと論証が再開する。** 値の裁定が設計の裁定になる |
| **H** | ⛔ **暫定の上に暫定を積むこと** | ⛔ **覆すコストが掛け算になる。例外なく禁止** |

### ⚠️ 実測に基づく注意

- ⚠️ **`1 ファイルで完結するか」では線を引けない。** ゴミ日付の扱いは 1 ファイルの話に見えて、**別の表の連鎖規則に縛られていた**
- ⚠️ **「ただの値」が設計の裁定だった例がある** —— ある寸法が 2px だと**どの倍率でも図形が消え**、案を 4 つ並べて絵を描いたら 2 案が消えた（`G` の実例）
- ⭐ **`D` の窓はいま最も安い** —— **利用者の文書がまだ 1 つも存在しない。** ⚠️ **初回リリース後、`D` の線は硬くなる**

## 3. ⛔ 手順

```
1. docs/development-records/pending-decisions.md に 1 行足す
     PD 番号 / 何が未決か / 推奨と根拠 / 分類(A〜H) / 波 / 触る行 ID /
     覆したとき落ちる試験 / 状態(未裁定 or 裁定済)
2. A〜C なら推奨で実装し、その場所に印を付ける
     // @provisional PND-7
   ⛔ D〜H なら実装しない。⭐ 進める部分だけ先に進める
3. 裁定を受けたら
     値やロジックを直す → 「覆したとき落ちる試験」を回す → 印を消す
     → 行の状態を 裁定済 にする（⛔ 行は消さない。記録である）
```

⭐ **「覆したとき落ちる試験」を先に書いておくのが要点である** ——
⚠️ **書いていないと、裁定が下りたときに「どこを直せば済むか」を作業ごと探し直すことになる。**

## 3b. ⛔ 裁定は巡の先頭で取る

⛔ **裁定はクリティカルパスである。** ⚠️ **実測**: ある巡で裁定を後半まで持ち越したところ、
**下流の実装が全部そこで待った。** ⭐ **引継書と、狙った `grep` 数本があれば、先頭 30 分で問える。**

```
1. 引継書が挙げる未裁定を読む
2. ⛔ 1 の作法（仕様 → docs/reference/ → studies/）を、狙った grep で当てる
   ⭐ 通読ではない。「本当に未決か」を確かめるだけである
3. 問う
4. ⭐ 答えを待つあいだ、裁定に依らない仕事を進める
```

⚠️ **2 を飛ばすな** —— 実測で 8 件のうち 2 件は既に答えが在り、**うち 1 件は 3 か所で決着済みであった。**
⛔ **一覧に「未裁定」と書いてあることは、未決である証明ではない。**

## 4. ⭐ 裁定の返し方（**利用者の手間を最小にする**）

```
A〜C   ⭐ まとめて承認できる形で出す（推奨と根拠が並んでいる）
       ⭐ UI の A・C には触れる見本を添える（0.3）
D〜H   ⛔ 1 件ずつ。根拠つきの推奨を添えて問う（規則 01 の ⑧）
```

⚠️ **`A〜C` でも「推奨がそのまま通る」とは限らない。** ⭐ **通らなかったときの実費が小さいから先へ進める**のであって、
**当たると見込んでいるからではない。**

## 5. ⛔ 波を閉じる条件

```
✅ 波は、A〜C の未裁定が残っていても閉じてよい
⛔ D〜H の未裁定が 1 件でもあれば閉じられない
```

⚠️ **理由**: `D〜H` は覆せない側なので、**閉じた後に裁定が来ても直せない。**
⭐ `A〜C` は覆せるので、**次の波と並行して裁定を受けられる。**

## 6. ⭐ 機械が見るもの（検査 25）

```
・@provisional の印とリストが双方向に一致すること
   ⛔ 印だけあって行が無い → 忘れられた暫定
   ⛔ 未裁定の行なのに印が無い → 直したのに記録が古い
・行が分類(A〜H)と波を宣言していること
・⛔ D〜H に分類された行に @provisional の印が在ったら落とす
   （待つべきものを実装している）
・⛔ 状態表が全部 ✅ の波に、その波の未裁定 D〜H が残っていたら落とす
・⛔ 裁定済 の行に @provisional の印が残っていたら落とす
   ⭐ これで印の一生が閉じた —— 未裁定の A〜C は持たねばならず、
     D〜H は持てず、裁定済 も持てない
   ⚠️ 足すまで、裁定済 の行は両方向とも無検査であった ——
     実測: この検査を足した時点で、13 か所（12 PD）が 4 ファイルに残ったまま、検査は緑であった
```

⚠️ **機械にできないこと** —— **分類そのものの正しさ。** ⭐ `A` と書いた行が本当に `A` かは人が読む。
⛔ **だから分類の根拠を 1 行書く**（「原稿の `S-nnn` にあり、生成で届く」など）。

## 7. ⛔ `rulings.md` の行の状態の欄

| 状態 | いつ書くか |
|---|---|
| `指示 —— change-request/CR-<n>-*.md が当てる` | ⭐ 起草した変更要求が当てる裁定（`JDG-600`・`JDG-601`・`JDG-603` の形） |
| `未着地` | 誰もまだ起草していない裁定だけ |
| `適用済` | 着地先の欄が、検査 43 の読める ID かファイル（`docs/spec`・`src` ほか）を名指すとき。⚠️ `.claude/` の道は読まれない |

⛔ **検査 43 は `未着地` の字面を数え、基準線を超えれば赤にする** —— 否定文の中の字面も数える（2026-09-21、「①〜③は未着地ではない」と書いた行が数えられた）。
⇒ **状態の欄に `未着地` の字面は、その意味のときにしか書くな。** 起草した変更要求の行を `未着地` と書くと、基準線を上げることになる（2026-09-26、`CR-572` の起草で 17 → 22）。
