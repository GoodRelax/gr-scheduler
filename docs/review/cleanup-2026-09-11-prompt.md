## 6. 判定 — 5 つの箱

**掃除の中心はここである。⛔ 問う順を変えるな。**

```
問い 0 ── そもそも要るか？ ───────────── いいえ → 消す（箱 A）
   │ はい
問い 1 ── 要求か、自称か？ ────── 自称 → 消す（箱 A）
   │ 要求
   ├── 製品が満たすこと → docs/spec（箱 B）
   └── 作り手が守ること → docs/development-rules（箱 C）
   │ どちらでもない
問い 2 ── コードを読んでも分からない「なぜ」か？ → 製品コードのコメント（箱 D）
   │ いいえ
問い 3 ── どれでもない ──────────────── 保留して報告（箱 E。⛔ 消すな）
```

⛔ **「仕様書に書けるか？」から問うな。**そこから入ると書く前提になり、そもそも要らないものが仕様書かコードへ配られる。
⛔ **箱 C へ移すべきものを見つけても、自分で移すな**（第 11 節）—— **報告せよ。**

### 6-1. 問い 0 — そもそも要るか（ここで消えるものがいちばん多い）

**1 つでも「はい」なら消す。**

| | 問い | 意味 |
|---|---|---|
| ① | **原本が他所にあるか** | Git ／ 台帳 ／ 仕様書 ／ 生成元。⇒ ここに在るのは写しである |
| ② | **機械が同じことを言えるか** | 型 ／ 検査 ／ 生成 |
| ③ | **コードが自明に語っているか** | 名前で言えることを言い直していないか。⛔ ひどい名前をコメントで補うな —— **名前を直せ** |
| ④ | **その文を消しても、次の人は同じ間違いをしないか** | 機械が止めるなら消してよい。⛔ 止めないなら残す |
| ⑤ | **それは「自称」か** | 「この実装は〜を満たしている」という申告 → 6-2 |

**実例:**

| 実物 | どれで消えるか |
|---|---|
| `2026-09-10 まで「…」と定めていた` | ① —— 仕様書の撤回記録と Git が持つ |
| `実測（2026-09-10、出荷ビルド）: 6 × 16.002px` | ① —— 台帳の `実物確認` 欄が原本 |
| `` `FR-011` は「両端を動かさないこと（MUST）」と定めている `` | ① —— **指し先 1 語だけ残せ** |
| `/** 名前を返す。 */ function nameOf()` | ③ —— 名前が言っている |
| `負の値は AT-39 が禁じている` の隣に `if (n < 0) refuse()` | ②③ |

⛔ **例外 1 つ**: `@purity pure` は ② に見えるが、判定する機械がまだ無い（裁定 4）。**作るまで消すな。**

**要求と自称の見分け:**

| | 例 | 行き先 |

### 6-3. 問い 2 — 製品コードのコメントに何を残すか

⛔ **この節が裁くのは「コメントの文」であって、コードではない。**「この行は要るか」ではなく **「この文は要るか」と問え。**

**「コード」は 2 つある。⛔ 混ぜて数えるな**（利用者の裁定 2026-09-11）:

| | 実測 2026-09-11 | 扱い |
|---|---|---|
| **製品コード** `src/` | 68 本 ／ 76,506 行、うち **コメント 48,736 行（63.7%）** | **本節。ここが的である** |
| テストコード `tests/` | 227 本 ／ 191,702 行、うち コメント 59,912 行（31.3%） | 6-4。役割が違うので規則も違う |

⚠️ **製品コードは 3 行に 2 行がコメントである。この巡でいちばん重い数はこれである。**

**判定は 2 段。漏れなく重なりなく 3 つに分かれる:**

| その文は | コードを読めば | 押せば | 行き先 |
|---|---|---|---|
| **何をしているか**（WHAT） | 分かる | — | **書かない（箱 A）**。名前で言えるなら**名前を直せ** |
| **何を満たすか**（約束） | 分からない | 分かる | **仕様書（箱 B／C）** |
| **なぜそう書いたか**（WHY） | 分からない | 分からない | **コメント（箱 D）** |

**Readable Code 第 5 章が「書け」と言うもの** —— 要点は 1 つ、**コメントの目的は書き手が何を考えていたかを読み手に伝えることである**:

| 書くもの | この製品の実例 |
|---|---|
| **採らなかった道とその理由** | 「`ScheduleGeometry` から読むと `LR-3` の閉路になる」 |
| **読み手が抱く疑問への先回り** | 「`Math.max` にしたのは、`null` が来ると `undefined` が伝播して黙って消えるから」 |
| **罠の告知**（触ると壊れる／遅い／順序に依存する） | 「ここで早期に返すと、下の分岐が到達不能になる」／「ここに `const` を置くと初期化前に読む」 |
| **なぜその値なのか**（根拠） | 値そのものは仕様書が原本。書くのは根拠だけ |
| 欠陥の自覚（`TODO` ／ `FIXME`） | ⚠️ この製品では台帳が担う。二重に書くな |
| 全体像・要約（この塊は何のためか） | ファイル頭の 2〜3 行。中身の言い直しは書くな |

**仕様書とコメントの違い:**

| | 仕様書 `docs/spec` | コメント `src/` |
|---|---|---|
| 誰に向けた文か | 製品の外 —— **利用者** | **次にこの関数を書き換える人だけ** |
| 何を言うか | **何を満たすか**（WHAT） | **なぜそう書いたか**（WHY） |
| 確かめ方 | **押せば分かる** | **押しても分からない** |
| 変わる時 | 要求が変わったとき | 実装を書き換えたとき |
| **腐ったら誰が気づくか** | 利用者が押して気づく | ⚠️ **誰も気づかない** |
| **原本か** | **原本である** | **原本ではない** |

**最後の 2 行が、この掃除の理由そのものである。**コメントは**腐っても誰も気づかない唯一の場所**であり、しかも原本ではない。⇒ **だから最小限にせよ。**

**消すもの:**

| 消す文 | なぜ | どこへ |
|---|---|---|
| `function nameOf()` の上の「名前を返す」 | コードを読めば分かる（WHAT） | どこへも。消す |
| ひどい名前を補うコメント | 松葉杖 | **名前を直せ** |
| 「この関数は純粋である」 | 自称（6-2） | どこへも。消す |
| 「`FR-011` は『両端を動かさないこと』と定めている」 | 原本は仕様書 | **指し先 1 語だけ残す** |
| 「`S-93` は 30px である」 | 原本は生成元 | `_source/settings.json` |
| 「2026-09-10 まで別の値だった」 | 原本は Git | Git ／ 仕様書の撤回記録 |
| 「D-408 で見つかった」 | 原本は台帳 | 台帳 |

**写しは、直す人が全部を見つけない限り必ず腐る。**実装の理由にはその経路が無い —— コード行が消えれば文も一緒に消える。実測: 仕様の逐語引用は `src/` に 2,118 行、`tests/` に 4,912 行。

⚠️ **ただしコメントの理由も腐る。**「2 か所に書くと必ず離れる」と書いた隣で実物は 4 か所である（`FR-093`）。**箱 D に入れる前に、その理由が今も真かを確かめよ。**

### 6-4. テストコード（`tests/`）は規則が違う

⛔ **製品コードの規則をそのまま当てるな。**試験の仕事は**どの条項を押さえているかを名指すこと**だからである。赤くなった試験を見た人が、まず知りたいのは「どの条項が破れたか」である。

| コメントの中身 | 判定 | 実測 `tests/` |
|---|---|---:|
| **指し先**（`` `FR-011` ``） | ⛔ **消すな。**消すと、赤が何を守っていたのか誰にも分からない | 4,685 行 |
| 何を押したか（手順が自明でないときの 1 行） | 残す | 散文の中 |
| **条項の逐語引用** | 消す。指し先だけ残せ | **4,912 行** |
| 台帳の番号 | 消す | 1,008 行 |
| 撤回の記録・日付つき実測 | 消す | 108 行 |
| `@purity` の印 | 消すな（裁定 4） | 440 行 |

⛔ **試験のコメントの嘘は、製品コードより悪い** —— 製品コードの嘘は押せば露見することがあるが、**試験のコメントの嘘は試験が緑のまま居座る。**引用した条項が変わっても、その試験は別のことを確かめたまま緑を出し続ける。
実在する: 検査 39 が数える保持 718 件のうち **367 件（51.1%）は試験の主張ではなくコメントだけ**である。

⛔ **順を守れ** —— **裁定 3 を済ませてから `tests/` のコメントに手を付けよ。**逆にすると、消した分だけ保持が落ちて検査 39 が赤くなる。

### 6-5. 問い 3 — どれでもない → 保留して報告

⛔ **判断がつかないものを消すな。**報告の形は「ファイル ／ 行 ／ その文 ／ 迷った理由」。**前に立つ者が裁く。**

## 13. 作法・検査の走らせ方・報告

### 作法

- **赤を先に出せ**（規則 04）。**手ごとにコミットせよ** —— ⛔ 週を 1 コミットに混ぜるな
- ⛔ **コミットの前に毎回、個人情報の点検を行い、実測した数を報告してから**コミットすること
- ⛔ **コミットメッセージに attribution を書くな**
- ⛔ **一時ファイルはセッションの scratchpad へ。このリポジトリの外のファイルを書き換えるな**（読むのはよい）
- ⛔ **コードとスクリプトは英語・ASCII で書く**（日本語の仕様書・記録は例外。逐語の引用も例外）

### 検査の走らせ方 —— ⛔ トークンを溶かすな

検査は**別プロセス**で走り、あなたのコンテキストに入るのは標準出力だけである。既定はこう打つ:

```bash
bash .claude/skills/spec-graph-check/check.sh > /dev/null 2>&1; echo "exit=$?"
```

⚠️ 実測: `check.sh` は **37 秒**、読む量 354 ファイル / 18.0 MB、出力 240 行 / 21 KB。⇒ **出力を丸ごと受け取ると 1 回で数千トークン溶ける。**落ちたときだけ該当節を `grep` で取り出せ。

| 門 | 所要 | 打ち方 |
|---|---|---|
| `npx tsc --noEmit` | 数秒 | 誤りの数だけ数える |
| `npx vitest run` | 21.7 秒 | 末尾 3 行だけ |
| `check.sh` | 37 秒 | 上のとおり |
| `npm run layers` ／ `npm run parity` | 数秒〜数十秒 | 末尾 2〜3 行 |
| `npx playwright test` | **8 分 17 秒** | ⚠️ **週の最後に 1 度だけ** |

### 報告の形（手ごと・週ごと）

1. **実測値** —— 何行消し、何行増えたか。第 12 節の数がどう動いたか
2. **箱ごとの内訳** —— 消した分を、問い 0 のどの下位問いで消したか。**保留に回した数も必ず報告せよ**
3. **門の終了コード** —— `tsc` / `vitest` / `check.sh` / `layers` / `parity`
4. **意図して動かした基準線** —— どれを、いくつからいくつへ、なぜ
5. **このプロンプトのどこが間違っていたか** —— ⛔ 見つからなかったなら「測っていない」と書け

### タグ付けの依頼

⛔ **あなたは `git tag` を打てない**（`gr-scheduler` の git 例外に `tag` は含まれない）。各週の終わりに、門が緑になり、コミット＆Push を済ませたら、利用者に次を渡して依頼すること。

```bash
git tag -a After-Cleanup-W1 -m "After week 1 of the cleanup: the instruments" && git push origin After-Cleanup-W1
```

巡の始まりには `Before-Cleanup` が打たれている。⇒ 成果は 1 行で出る:

```bash
git diff Before-Cleanup..After-Cleanup-W2 --stat
```

⚠️ **依頼の際は第 12 節の「掃除の前後の数」を添えること。**「終わりました」だけでは、成果が測れたことにならない。
