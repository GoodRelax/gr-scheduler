# src/ のコメント規則（裁定 17・18、利用者の裁定 2026-09-13）

⛔ **`src/` のコメントは、本書の第 3 節の形だけを書く。** 第 6-3 節（[`cleanup-2026-09-11-prompt.md`](cleanup-2026-09-11-prompt.md)）と裁定 16 が本書と食い違うときは、本書に従う。
⭐ 根拠: 命名と SSOT を徹底したので、仕様書とコードを見れば分かることが大半になった。多いコメントは腐り、この巡の実測でも事実でない文が 100 件以上見つかった。

## 1. 文字

**ASCII の印字可能文字（0x20〜0x7E）だけ。** 日本語も、⭐ ⛔ ⚠️ などの記号も書かない。

## 2. 密度

| 項目 | 定め |
|---|---|
| 密度 | コメント行 ÷（コード行 ＋ コメント行） |
| コメント行 | コメントの文字を含む行。**行末コメント（`code // Spec: GR-21`）も 1 行と数える**。`/**`・` *`・` */` だけの行も数える |
| 数えない行 | コメントが `@purity` のタグだけの行 |
| 生成領域 | `<generated -- do not edit by hand>` から `</generated>` までは、コードにもコメントにも数えない |
| 上限 | **木全体で 10% 以下。** 加えて、**コード 100 行以上のファイルはファイルごとにも 10% 以下** |

## 3. 書いてよい形（これ以外は書かない）

⭐ **種類は規則 07 の R3「コメント」と、規則 03 の 3 節の「GRS の種類」が決める**（2026-11-24、計画 `studies/82-anms-ndd-apply-plan/README.md` の B1）。本節は形・置き場・行数の上限を決める。

| 形 | 書く場所 | 上限 | 書いてよい条件 |
|---|---|---|---|
| `// Spec: FR-013` ／ `// Spec: FR-013, T-021` | 仕様の振る舞いを実装する所（UseCase の公開の関数、コンポーネントの公開面の関数、実装仕様を実装する関数）の定義の直上と、テスト | 1 行 | その定義かテストが実装・試験する仕様の本文の行。関係する行を並べた目録にしない。`JDG`・`DFC`・`CR`・`OPQ` を書かない |
| `// Why: <採らなかった道と理由>` | 該当する行の直上 | 2 行 | 理由が仕様書にもコードにも無い |
| `// Summary: <EARS の 1 文>` | 定義の直上 | 1 文（2〜3 文なら `Temporary` を付ける） | 振る舞いが仕様書に無く、コードからも容易に読めない |
| `// Temporary: <reason>. Until: <condition>.` | 該当する行の直上 | 2 行 | 暫定のコード。仕様からわざと外れている所は、理由に台帳の `DFC-n` を書く |
| `// Unimplemented: OPQ-n` | 止めた所の直前 | 1 行 | 規則 06 で止めて問う問い（分類 `D`〜`I`）。振る舞いを作らない |
| `// Provisional: OPQ-n` | 仮に決めた所の直前 | 1 行 | 規則 06 で仮に決めて進む問い（分類 `A`〜`C`） |
| `// Trap: <何をすると何が壊れるか>` | 壊れる行の直上 | 2 行 | 型・試験・機械検査のどれも止めない壊れ方がある |
| `// Step: <1 つの手順>` | `tests/` に限る。`it`／`test` の本体の中 | 1 行（1 つの試験に 3 行まで） | 押し方の順が自明でない。条文の文言を書かない（JDG-62） |
| `/** @purity pure */` | 関数の直上 | 1 行 | 裁定 4 |
| `// Section: <name>` ／ `// Consistency: <unit>` | 規則 07 の R7 が定める所 | 1 行 | 構造の分離、収集と処理の分離 |
| ファイル頭: `// File: <Name>: <役割>` ＋ `@unit` ／ `@component` ／ `@publishes` ／ `@seam` | ファイルの先頭 | 5 行（`@seam` は継ぎ目ごとに 1 行） | 各ファイル 1 か所 |
| ツールの指示（`// eslint-disable-next-line <rule> -- <reason>` ほか） | ツールが求める所 | 1 行 | ツールが読む。理由を書く |
| 生成領域の出どころの見出し | ファイルの先頭 | 検査 21 が求める最小 | 生成領域を持つファイル |

⭐ `Spec` の行と `@purity` の行が並ぶときは、`// Spec: ...` を上に、`/** @purity ... */` を定義の直前に置く。
⛔ **`Unimplemented` と `Provisional` は、仕様の付録 A.3 の未決の問いの一覧の行と必ず結ぶ**（規則 06）。ID を 1 つだけ書き、中身はコメントに写さない。⛔ 一覧に行が無ければ書かない。先に行を起こす。

### 古い形から新しい種類へ（移る間だけ両方が木に在る）

| 2026-11-24 までの形 | 新しい種類 |
|---|---|
| `// see FR-013` | `// Spec: FR-013`。ただし仕様の振る舞いを実装する所とテストだけ。ほかの所の `see` は消す。`JDG`・`DFC`・`CR` を指す `see` は消すか、`Why`・`Temporary` の理由に直す |
| `// WHY:` | `// Why:` |
| `// TRAP:` | `// Trap:` |
| `// STOP: ... Looked in ...` ＋ `// @provisional PND-n`（分類 `A`〜`C`） | `// Provisional: OPQ-n`（`Looked in` の中身は一覧の「探した所」の列へ） |
| `// STOP: ... (PND-n)`（分類 `D`〜`H` で、コードが既に選んでいる） | `// Provisional: OPQ-n`。一覧の行は「決める人」を持ち主にして開いたままにする（規則 06 の 3 節） |
| 止めて作っていない所 | `// Unimplemented: OPQ-n` |
| `// DEVIATION: spec says ...; here ... (DFC-n)` | `// Temporary: spec says ...; here ... (DFC-n). Until: DFC-n is fixed.` |
| `// STEP:` | `// Step:` |
| ファイル頭の役割の行（種類なし） | `// File: <Name>: <役割>` |

⛔ **移る間も、新しく書くコメントは新しい種類で書く。** 検査 55 は、移しが済むまで新旧の両方を通す（計画の B2）。

## 4. 書かないもの

| # | 書かないもの | 分かる場所 |
|---|---|---|
| 1 | 第 3 節の形以外で仕様の行 ID を書くこと | `Spec` の行、生成物、試験の名前 |
| 2 | 仕様の文の言い換え（MUST・値・順序・語） | 仕様書 |
| 3 | 次の宣言や式が言っていること | 名前と型 |
| 4 | 機械が保証していること（層の規則、純粋性、値の範囲） | 検査・`tsc`・生成物の検査 |
| 5 | 他のファイルや関数についての記述。⭐ 例外: `Trap` の中で「同時に変える相手」を名指すこと | `grep` |
| 6 | 数・日付・人・経緯・測定値 | Git と台帳 |
| 7 | 見出し・強調・区切り線 | ― |

## 5. 予算に収まらない罠は、コードで守る

⛔ **密度の上限に収まらない `Trap` は、コメントで残さない。** 必須のメンバーにする、型を狭める、表明を置くなどで**コードが止める形**に直す。
⭐ **直すのは後でまとめて行う。** 掃除の巡ではコードを変えず、その罠を [`defects.md`](../development-records/defects.md) に行として起こし、コメントは消す。

## 6. 数値リテラル

⛔ マジックナンバーは禁止である。見つけたら [`magic-numbers.md`](../development-records/magic-numbers.md) の作業表で扱い、コメントで説明しない。
