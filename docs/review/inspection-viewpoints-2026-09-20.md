# 進捗妥当性検査 / ProgressValidation — 観点表（CR 前の草案）

2026-09-20（2026-09-23 に用語を差し替え）。利用者との対話で決めたもの。**CR にはまだしていない。**
⚠️ **本書は `遅延診断 / Delay Diagnostics` の下位にある**（`progress-check-2026-09-23.md` の 1 節）。
⚠️ ファイル名は旧名のままである。CR のときに読み替えること。

## 1. 何のための機能か

チェックアイコンを押すと、いま開いている文書の**辻褄の合わない箇所**を数え上げて一覧に出す。
一覧から順に該当箇所へ移動でき、修正候補を出して、利用者が OK したら GRS が直す。
**修正は 1 つずつ**行う。レポートとして書き出せる（外部の XML を直す側の作業に使う）。

⭐ **検査するのは GRS の文書モデルであって、`MSPDI` の XML ではない**（利用者の裁定）。
XML にしか無い値は判定に使えない。3 節がその線引きを持つ。

## 2. 「おかしい」の定義

> **その文書だけを読んで、両立しない 2 つの事実が読み取れる状態（内部矛盾）**

この定義から外れるもの:

| 外すもの | 理由 |
| --- | --- |
| 遅れ・進み | 予定と実績の差であって矛盾ではない。**GRS が見せたいのはむしろこれ** |
| 予定が過去のまま更新されていない | 正常。予定を動かしてよいのは公式に計画を修正した時だけ（利用者の裁定） |
| 計画そのものの良し悪し | 矛盾ではない。別の話 |
| ボトルネック | 矛盾ではない。**本機能の次に別機能として入れる想定** |

## 3. 用語

| 概念 | 日 | 英（コード） | 意味 |
| --- | --- | --- | --- |
| 機能全体 | 遅延診断 | `Delay Diagnostics` | チェックアイコンが走らせるもの |
| 本書が持つ段 | 進捗妥当性検査 | `ProgressValidation` | その中の、辻褄を見る段 |
| 見つかった 1 件 | 指摘 | `finding` | 一覧の 1 行、移動の 1 停留所 |
| 強い段 | **矛盾** | `contradiction` | 両立しない。必ずどちらかが誤り |
| 弱い段 | **疑義** | `suspicion` | 両立はするが、ありそうにない。人が判ずる |

⛔ **`Error` / `Warning` を使わない** —— 取り込み時の検証（`FR-023`）が文書を**拒む**仕組みを
GRS は既に持っており（`Refusal` / `InvariantRefusal`、`05-07-design.md` の 表 T-220 の `IV-*`）、
**あちらが本物の error である**。あちらは「開けない」、本機能は「開けるが辻褄が合わない」。
同じ語を当てると 2 つが混ざる。

## 4. GRS のモデルで判定できるか

`_assets/fig-erd-detail.md` の `AT-*` で確認した。

**持っている**（判定できる）:
`Task` の `uid` / `wbsParentUid` / `wbsOrder` / `start` / `finish` / `milestone` / `deadline` /
`actualStart` / `stop` / `actualFinish` / `resume` / `resumeValid` / `percentComplete`、
`Dependency` の `predecessorUid` / `linkType` / `lag` / `lagFormat`、
`Project.statusDate`、`Calendar` の一式、`BaselineTask` の `start` / `finish` / `milestone`。

**持っていない**（判定できない）:

| 無いもの | それで落ちる観点 |
| --- | --- |
| 工数・コスト（`Work` / `Cost` / `ActualWork` / `ActualCost` / `Remaining*`） | 工数加重の進捗、親子の工数合計、`Work = Actual + Remaining` |
| `Duration` | 期間と稼働時間の一致。GRS では `start`〜`finish` から解くので、そもそも食い違えない |
| `PercentWorkComplete` | 進捗率 2 種の食い違い |
| `Summary` フラグ | 不要。**GRS の親子は `Task.wbsParentUid` の 1 本**。子を持つ `Task` が親である |
| `OutlineLevel` / `OutlineNumber` / `WBS` 文字列 | 3 者の食い違い。取り込み時に `wbsParentUid` へ畳まれる |
| `TotalSlack` / `FreeSlack` / `Early*` / `Late*` / `Critical` | 余裕とクリティカルの食い違い |
| `BCWS` / `BCWP` / `ACWP` / `*Variance` | 出来高の食い違い |
| `Assignment` の工数・単位 | 割り当ての合計と `Task` の食い違い、過負荷 |

⚠️ これらは `carry` / `carryElements` の中に**値としては残っている**が、
**`carry` を解釈して判定してはならない** —— `carry` は往復のための預かり物であり、
読み解き始めると「モデルに無い列を暗黙のモデルにする」ことになる。

⭐ **むしろ好都合な面がある** —— `TotalSlack` や `Critical` は XML の値を信じずに
**GRS が依存と暦から計算し直す**ことになる。それはそのまま**ボトルネック検出の土台**になる。

## 6. 判定の基準

### 6.1 完了をどう判ずるか

⭐ **完了の判定は `actualFinish` の有無で行う（利用者の裁定 2026-09-20）。**
`percentComplete` は**消化率**であって完了度ではない。ゆえに次の 2 つは正常であり、指摘にしない。

| 状態 | 読み方 |
| --- | --- |
| `percentComplete` が 100 なのに `actualFinish` が無い | 予定した分を使い切ったが、まだ終わっていない（予定より多くの時間を使っている） |
| `actualFinish` があるのに `percentComplete` が 100 未満 | 予定した分を使い切る前に終わった（予定より早く終わった） |

⚠️ **CR のときに 表 T-019a（`planActualState`）と 表 T-021b（`isDelayed`）の判定と突き合わせること**
—— 既に完了を判ずる箇所があるなら、そちらと同じ 1 本を使う。2 か所に置けば必ず離れる。

### 6.2 依存の向きの式

`Dependency.linkType` は `0` = FF / `1` = FS / `2` = SF / `3` = SS（`AT-46`）。`lag` を織り込む。

| linkType | 名 | 満たすべき式 |
| --- | --- | --- |
| 1 | FS | 後続の `start` ≥ 先行の `finish` + `lag` |
| 3 | SS | 後続の `start` ≥ 先行の `start` + `lag` |
| 0 | FF | 後続の `finish` ≥ 先行の `finish` + `lag` |
| 2 | SF | 後続の `finish` ≥ 先行の `start` + `lag` |

⭐ これに反する状態とは、**画面に依存の矢印が描かれているのに、帯の位置がその矢印と逆を向いている**
ということである。見た人は矢印の意味を読み取れない。ゆえに矛盾とする（`SC-22`）。
同じ式を `actualStart` / `actualFinish` に当てたものが `SC-23` であり、
そちらは部分着手・前倒し着手で**現場では普通に起きる**ので疑義どまりとする。

### 6.3 親子の集約

親の値は子から決まる。⭐ **実績だけは条件が 1 つ増える。**

| 対象 | 親が持つべき値 |
| --- | --- |
| `start` | 子の最も早い `start` |
| `finish` | 子の最も遅い `finish` |
| `actualStart` | 子の最も早い `actualStart`。子が 1 つも着手していなければ持たないこと |
| `actualFinish` | **子が全部完了しているときだけ**、子の最も遅い `actualFinish`。1 つでも未完了なら持たないこと |

### 6.4 マイルストーンが子を持つとき（`SC-6`）

⚠️ **依存と WBS の親子を取り違えないこと** —— つながりは 2 種類あり、`SC-6` が見るのは後者だけである。

| | 列 | 形 | 判ずる行 |
| --- | --- | --- | --- |
| 依存 | `Dependency.predecessorUid` | 横のつながり。矢印で描かれる | `SC-21` |
| WBS の親子 | `Task.wbsParentUid` | 縦の入れ子。行が字下げされる | `SC-6` |

「機構設計・I/F 設計・xx 設計が終わったら『設計完了』」は**依存**であり、正常である（`SC-21` の対象）。
`SC-6` が指すのは、その 3 つが `wbsParentUid` で『設計完了』を**親として指している**形である。
束ねる親は期間を持つはずなのに、点（◆）として描かれることになる。

正しい形は、束ねる親を別に置き、マイルストーンをその**末尾の子**に並べたものである。

⭐ **疑義とする** —— 両立しない訳ではなく、画面が読みにくくなるだけなので、断定しない。
⭐ **告げるときの言葉は「この行を束ねる上位タスクが無い」とする** —— 利用者に伝わるのはこちらである。
⛔ **検出の条件をその言葉に合わせてはならない** —— 上位タスクが無い行は他にいくらでもあり
（根の直下に平たく並べた文書は全部そうなる）、数え上げが鈍る。**検出は「子を持つマイルストーン」のままとする。**
⚠️ 修正候補は「束ねる親を新しく作り、マイルストーンをその末尾の子へ移す」。
`Task` を 1 つ新規に作るので、`IV-6`（どの `Task` もちょうど 1 つの `TaskGroupMember` から指される）を満たす必要がある。

## 9. 画面と修正の振る舞い（CR で書き下す）

1. **1 件直すと、件数が 1 より多く減る。** 一覧は毎回作り直すこと。「7 件 → OK → 4 件」が普通に起きる。
   逆に**新しい指摘が生まれる**こともある（親を子に合わせたら、その親の親がずれる）。
2. **自動で直せるものを先に片づけると、選ばせる件数が目に見えて減る。** 修正の型を一覧に出す。
3. **実績を書き換える修正には印を付ける。** 実績は記録であり、整えると「解決した」のか
   「隠した」のか分からなくなる。取り消しは `EditHistory` が持つ。
4. **修正候補の並びは「実績・派生を直す案 → 予定を動かす案」の順**とする ——
   予定を動かしてよいのは公式に計画を修正した時だけ、という利用者の方針に沿わせる。
5. **レポート出力** —— 外部の XML を直す作業に使うので、指摘ごとに
   タスクの名前・`uid`・段・観点・いまの値を持つこと。

## 10. 本機能では扱わないと決めたもの

| 事柄 | 理由 |
| --- | --- |
| `OutlineLevel` / `OutlineNumber` / `WBS` の 3 者の食い違い | GRS のモデルに無い。**取り込みの路の検査**であって本機能ではない |
| 対になる `.ja.xml` と `.en.xml` の食い違い | サンプル資料の品質の話であって、製品の機能ではない |
| 工数・コスト・出来高の整合 | 4 節のとおりモデルに無い |
