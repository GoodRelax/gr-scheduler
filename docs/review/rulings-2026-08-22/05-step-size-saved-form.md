## 2. 課題 —— **仕様の文言と実装が、36% 違う形を測っている**

`FR-031`（`01-04-requirements.md:1557`、逐語）:

```
1 段の大きさは、その段の保存形を UTF-8 で符号化した長さ（バイト）で測ること（MUST）
```

**実装**（`document-change-plan.ts`）:

```ts
function stepSize(document: Document): number {
  return utf8Length(JSON.stringify(document))     // 詰めた形
}
```

**保存形**（`json-codec.ts`）:

```ts
return JSON.stringify(document, null, 1) + '\n'   // 1 スペース字下げ ＋ 改行
```

**起動テンプレートで測った実測**:

```
詰めた形   655,969 バイト
保存形     895,286 バイト     ← 36.48% 大きい
```

⛔ **したがって合計メモリの予算は、仕様の文言より約 36% 緩く効いています。**

### 2.1 ⛔ そして「保存形」は仕様のどこにも定義されていない

⚠️ **同じ語を持つ行は 表 T-024 に 1 つあります** ——「`IO-5` | localStorage | **保存 / 復旧** | 自動保存とクラッシュ復旧」。
⭐ **そして自動保存を行うコードは `jsonFromDocument` を呼びます**（＝ 字下げのある形）。
⛔ **`JSON.stringify(document)`（詰めた形）は、製品のどこにも保存されません。数えるためだけに存在します。**

## 3. ⭐ 意図の証拠 —— **`git` が答えを持っていた**

⚠️ **この文は誰かが昔に書いたものではありません。** `CR-182` のコミット（`6d9043b`「Say what the numbers mean and how much is measured」、2026-08-18）が**足した**ものです。

⛔ **そして同じコミットが、実装の 1 行を書き換えています**:

```
-  return JSON.stringify(document).length
+  return utf8Length(JSON.stringify(document))
+ function utf8Length(text: string): number {
```

⭐ **書き手が直していたのは「文字数 → バイト数」です。**
⭐ **`JSON.stringify(document)`（詰めた形）は、そのまま手つかずで残されています。**

⚠️ **つまり「保存形」は「直列化した形」という一般語として書かれ、
どの直列化かを選ぶ意図は無かった、と読むのが最も自然です。**

⛔ **これは決定的ではありません** —— 書き手が字下げに気づかなかっただけかもしれません。
⭐ **しかし「実装が仕様に反している」より「仕様の語が曖昧だった」ほうが、証拠に合います。**

## 4. ⛔ 直せない理由（**層の壁**）

⭐ **素直な直し方は「`jsonFromDocument` で測る」です。** ⛔ **できません。**

```
stepSize      は UseCase（ApplyDocumentChange）に居る
jsonFromDocument は Adapter（DocumentCodec）に居る
LR-1          依存は内向きだけ。UseCase から Adapter は呼べない
```

⚠️ **図 F-013 〜 F-017 にも `ApplyDocumentChange → DocumentCodec` の辺はありません。**

## 6. 推奨 —— **A。⛔ ただし条件を 1 つ付ける**

⭐ **推奨: A —— 仕様の文言を「詰めた `GRS JSON`」と明示し、実装は動かさない。**

**根拠**:

1. ⭐ **`git` の証拠**（§3）—— 文と実装は**同じコミット**で書かれ、書き手は符号化（文字→バイト）を直し、直列化には触れていない。**曖昧な語を後から厳しく読み直すより、書き手が何を決めたかに従うほうが正確である**
2. ⭐ **層の壁を越えない** —— B・B′・C はいずれも `PI-8` か `DocumentCodec` を動かす。**36% の緩さのために公開署名を動かすのは釣り合わない**
3. ⭐ **いま誰にも見えていない** —— `S-95` が噛み始めるのは、およそ **1.3MB を超える文書**からである。⚠️ **起動テンプレート（1000 タスク）でも 50 段で 32.8MB、64MB に届かない**
4. ⭐ **`FR-031` の目的は「際限なく積まないこと」であり、36% の精度は目的に対して十分である**

⛔ **付ける条件**: **「詰めた形」と書くと同時に、`S-95` の 🔎 を外さないこと。**
⚠️ **`S-95` の 64MB は由来の無い値です。** ⭐ **測る形を緩いほうに固定するなら、上限そのものを選び直せる状態を保つべきです。**

### ⚠️ A を推さない立場も強い（**正直に書く**）

⛔ **`FR-031` の RATIONALE は「文字数で測ると上限が 3 倍に緩む」を理由に MUST を置いています。**
⭐ **同じ論法をこの 36% に当てれば、B′ が正しいことになります。**
⚠️ **私が A を推すのは「36% は 3 倍ではない」という程度の差と、公開署名を動かす代償との釣り合いによります。** ⛔ **この釣り合いの判断は、私のものではなく利用者のものです。**
