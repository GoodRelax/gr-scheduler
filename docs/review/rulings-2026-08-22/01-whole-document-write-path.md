# 裁定 01 —— 文書まるごとを現在値にする道（`replaceDocument`）

**日付**: 2026-08-22 ／ **仕様**: 0.85 ／ **分類**: **D ／ E ／ F ／ G**（6 問。⛔ **どれも推奨で走れない**）
**止まるもの**: ⛔ **ファイルを開く・自動保存から戻る・起動時の文書・取り込み**（6 呼び手すべて）
**止まらないもの**: いま動いている編集・ズーム・取り消し（⚠️ **ただし取り消しは規約違反の道を通っている**）

⚠️ **本書は調査と提案の記録である。仕様ではない。** ⛔ **本書は仕様のオブジェクトを 1 つも動かしていない。**

---

## 1. ユースケース

### 1.1 いちばん普通の場面

> 作成者が日程を 30 分編集した。同僚から `.grs.json` が届いたので開く。
> `OP-3` により「置き換える／合流させる／重ねる」を問われ、**置き換える**を選ぶ。

起きなければならないことは、仕様がはっきり書いています。

| | 逐語 | どこ |
|---|---|---|
| 捨てる前に問う | 「**置き換えを選んだときは、捨てる前に確認を求めること（MUST）。** 黙って捨ててはならない（MUST NOT）」 | `OP-4`（`01-04-requirements.md:3179`）|
| 履歴は消える | 「取り消しの履歴は引き継がない（`LM-9` と同じ理由）」 | 同上 |
| 置き換え自体は戻せない | 「⚠️ **置き換え（`OP-3`）は対象外** —— 取り消しの履歴を引き継がないので戻せない」 | `UN-6`（`:1575`）|

⛔ **いまこれは 1 つも起きません。** 押しても何も起きない、ではなく、**そもそも押せません。**

### 1.2 同じ形の場面が、あと 5 つある

仕様書自身が 6 つを数えています（`A-appendix.md:101`、逐語）:

```
⛔ 取り消し・やり直し・取り込み・自動保存からの復帰・OP-3 の置き換え・起動時の文書の 6 つが、
   計算した文書を現在値にする手段を持っていなかった
```

⛔ **6 つとも、履歴と刻印の扱いが違います。** それが本裁定の芯です。

### 1.3 いま実際に起きていること（⚠️ **規約違反が 1 つ動いている**）

`Ctrl+Z` は動きますが、**唯一の書き込み経路を迂回しています。** コードが自分でそう告白しています:

```
⛔ NOT THROUGH THE ONE WRITE PATH ... the pair is replaced here -- and MS-1 of table T-042
   calls that the second entrance it forbids.
```

⭐ **実害は測れています** —— **取り消しは `WS-7` を通らないので通知が出ません。** 仕様書自身が別件でそれを欠陥と診断しています（`A-appendix.md:110`）:「**`AG-6` の「まだ受け取っていない変更だけを通知する」の違反である。**」

## 2. 課題 —— **仕様は答えを持っている。ただし 3 つの成果物が食い違っている**

### 2.1 ⭐ 部品グラフは、答えを完全に描いていた

`docs/spec/_source/components.json` は 図 F-013 〜 F-017 の原稿です。**辺を数えました**（自分で走らせた実測）:

```
ApplyDocumentChange へ 入る 辺（＝ 呼ぶ側）
   InputCommandTranslator  → one operation     画面
   AgentApiEndpoint        → same operation    API
   FileGateway             → intake            ⭐ ファイルを開く
   AutosaveGateway         → restore           自動保存からの復帰

ApplyDocumentChange から 出る 辺（＝ 呼ばれる側）
   → EditDocument          validate + update   命令の道
   → ImportDocument        intake              取り込みの道
   → UndoEdit              step back           ⭐ 取り消し
   → RedoEdit              step forward        ⭐ やり直し
   → DocumentStamp         advance + stamp
   → EditHistory           push one step
   → NotifyChangeWatchers  what was confirmed

UndoEdit / RedoEdit へ入る辺は、この 2 本だけ
```

⭐ **`UndoEdit` は「呼び手」ではなく「呼ばれる側」です。**
⭐ **`replaceDocument` の「外で組み立てた文書」の「外」とは、`ApplyDocumentChange` の外 —— つまり `ImportDocument` / `UndoEdit` / `RedoEdit` のことです。**

⛔ **この読みは、純粋性からも裏が取れます。**

```
表 T-064 の前文  「純粋性を添えていないメンバは pure である」   （05-07-design.md:324）
PI-11 / PI-12    | UndoEdit | undoEdit |  ／  | RedoEdit | redoEdit |   ← 印が無い
表 T-075         | UF-20 | undo-edit.ts | pure |  ／  | UF-21 | redo-edit.ts | pure |
```

⛔ **純粋関数は文書を据え付けられません。** ⭐ **据え付けるのは `non-pure` な `replaceDocument` だけです。**

### 2.2 ⛔ ところが、3 つの成果物が食い違っている

| | 何と言っているか | どこ |
|---|---|---|
| **(1) 部品グラフ** | `ApplyDocumentChange` が `UndoEdit` を**呼ぶ**（step back）| `_source/components.json`、図 F-014 |
| **(2) `CR-196`（利用者の裁定）** | 取り消し・やり直しは `replaceDocument` の**呼び手**である | `CR-196` の §0① と §4 |
| **(3) いまのコード** | シェルが `undoEdit` を呼び、**自分で**対を置き換える | `frame-loop.ts` の `carryOutAction` |

⛔ **`LR-3` は「層の中の呼び出しを非巡回に保つこと（MUST）」と定めるので、(1) と (2) は両立しません。**
⭐ **どちらかが誤りであり、誤っているほうを直す必要があります。** それが本裁定の第 1 の問いです。

### 2.3 「段は 表 T-067」が、まるごと差し替える道に当たらない

表 T-067 の 7 段は**命令の列で書く道**のために書かれています。まるごと差し替える道に当てると 4 段が答えを持ちません。

| 段 | 命令の道 | ⛔ まるごと差し替えるとき |
|---|---|---|
| `WS-1` 刻印を照合 | 読んだ刻印と現在の刻印を比べる | ⛔ **何と比べるのか。** 入ってくる文書の刻印は**定義により**現在のものと違い、素直に読むと**あらゆる差し替えが拒否される** |
| `WS-2` 書ける時機か | 身振り中・入力確定前・通知配布中は拒否 | ⚠️ `AG-9` の主語は `Agent API` である。画面からの差し替えに掛かるかが書かれていない |
| `WS-3` 命令を検証し組み立てる | `editDocument` が組み立てる | ⛔ **組み立てるものが無い。** 代わりの段が書かれていない。⭐ **ただしグラフは答えを持つ** —— `ImportDocument` / `UndoEdit` / `RedoEdit` がこの位置に立つ |
| `WS-4` 履歴に 1 段積む | 表 T-027 の対象なら積む | ⛔ **表 T-027 の 17 行に、取り消し・やり直し・復帰・起動・置き換えの行が 1 つも無い。** 素直に読むと**取り消しが自分の歩いている履歴に段を積む** |
| `WS-5` 刻印を進める | 「必ず更新する」 | ⛔ **`FR-063` が逆を書いている** ——「取り消しは以前の文書を**刻印ごと復元する**」 |
| `WS-6` 差し替える | 1 つの参照の置き換え（MUST）| ⭐ **そのまま効く** |
| `WS-7` 通知を配る | 差し替えの後（MUST）| ⭐ 効く。⚠️ ただし `WS-5` が判定を作らないなら誰が作るのか |

### 2.4 ⛔ 仕様は 2 つの呼び手を**操作の名前でだけ**区別している

```
置き換え（ファイルを開く）  → 履歴は消える（OP-4 / UN-6 / LM-9 が 3 回書いている）
取り消し（1 段戻る）        → 履歴は残らねばならない
```

⛔ **後者はどこにも直接書かれていません。** `FR-031` の「取り消した編集を**やり直せるようにすること**」から含意でしか出ません。
⚠️ **この非対称そのものが証拠です** —— 仕様は「消す」ときだけ明文で書き、「残す」ときは書いていない。

⛔ **そして区別は 1 度もメンバに届きません。** 表 T-064 の前文がそう定めています（`:325`）:

```
本表は名前と、それが何を担うかだけを持つ。引数・戻り値は src/ の公開エントリが持ち、
境界値は Chapter 6.1 が持つ
```

⭐ **裁定は「引数をどうするか」の形では降ってきません。** 降ってくるのは**規則**であり、`src/` が署名を合わせます。

## 4. 推奨 —— **(f)**

⭐ **推奨: (f)** —— **1 つの公開メンバが「どの呼び手か」を受け取り、対応する純粋コンポーネントへ問い、履歴・刻印・段の扱いを経路の中で適用する。**

**根拠**:

1. ⭐ **仕様自身の部品グラフが、既にこの形を描いている。** `ApplyDocumentChange` から `ImportDocument` / `UndoEdit` / `RedoEdit` へ辺が出ており、`UndoEdit` へ入る辺は他に 1 本も無い。**(f) は新しい設計ではなく、描かれていた設計の実装である**
2. ⭐ **純粋性が裏づける。** `undoEdit` は `pure`（表 T-064 の既定と表 T-075 の両方）。**純粋関数は据え付けられないので、据え付ける側が問うしかない**
3. ⭐ **`CP-8` の「唯一の経路」を字義どおり満たす唯一の案**（(a) と (e) は経路を通るが規則は通らない。(d) は経路を通らない）
4. ⭐ **新しい語を作らない** —— `CR-196` が退けた形を避けられる
5. ⭐ **機械検査に下ろせる** —— 6 値が仕様の行 ID なら、検査 26b と同じ形で「6 つとも扱いが書かれているか」を見られる

⛔ **代償を正直に**: **表 T-067 に列を 1 つ足すか、小表を 1 つ立てる必要があります。** ⚠️ 表 T-067 は閉路（`AG-11 ↔ AG-2 ↔ AG-6 ↔ FR-063 ↔ WS-5`）を持つので、**1 つの変更要求で一括に書く必要があります**（規則 02 の 3.）。

### ⚠️ (a) を推さなかった理由

**(a) は 0 行で済みます。** ⛔ **それでも推しません** —— **`OP-4` は MUST であり、(a) はそれを検査不能にします。**
⚠️ **今日この回で、まさにそういう欠陥を 3 件出しました**（`S-95` の単位・`Esc` の中断・`FR-048`）。**3 件とも「呼び手が正しくやるはず」に頼っていた箇所です。**
