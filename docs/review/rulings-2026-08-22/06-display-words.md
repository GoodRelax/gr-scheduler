## 2. 課題

`PD-160` は「`CR-194` が原稿・生成器・成果物を作り、172 語の枠が空のまま在る」と記録しています。
⛔ **私は当初、これを「利用者が 172 語を決めれば直る」と説明しました。それは誤りでした。**

### ⛔ 決定的な事実 —— **`display-words.json` を読むコードが 1 行も無い**

```
$ grep -rn "display-words" src/ --include=*.ts
src/adapter/screen-renderer/screen-renderer.ts:136:   * as `_source/display-words.json`; `display-words.json` beside this file is
                                                        ↑ 注記の中で名前に触れているだけ
```

⛔ **取り込んでいる `.ts` は 1 つもありません。**
⭐ **つまり、いま 172 語を全部埋めても、画面は 1 文字も変わりません。**

`CR-194` は原稿・生成器・成果物（`npm run gen:check` が守っている）まで作りましたが、
⛔ **それを画面へ配る側（`CR-194` の項目 9〜14）が当てられていません。**

⚠️ **`CR-194` 自身がその受け入れ試験を定義していました** ——
「⭐ 原稿の値を 1 つ変えると試験が落ちるか。**落ちなければ、その値はどこにも届いていない**」。
⛔ **その試験も書かれていません。**

## 3. ⭐ 結論 —— **これは裁定ではなく、未完了の作業である**

⛔ **利用者に 172 語を尋ねるのは、順序が逆です。**

```
いま尋ねると    利用者が 344 個の文字列（172 語 × 2 言語）を決める
                → どのコードもそれを読まない
                → 画面は IC-1 のまま
```

⭐ **先にやるべきは、語を配る道を通すことです。それは裁定を要しません** ——
**表 T-075 の `UF-60` の行が、そのメンバを既に命じているからです。**

⚠️ **規則 01 の ⑧ は「問う前に仕様を読み切れ。半分以上は実は在る」と定めています。** ⭐ **今回もそうでした。**

## 4. ⭐ 尋ねる形を変えると、決める量が 1/3 になる

道が通った後で尋ねるとしても、**172 語を一度に尋ねる必要はありません。**

### 4.1 いま画面に出ている語だけなら 53 語

```
App Header        IC-1 〜 IC-22    22 語（文書 4 / 履歴 2 / 表示 11 / AI 3 / 補助 2）
Command Palette   IC-23 〜 IC-62   31 語（置く 17 / 揃える 2 / 表示 6 / カーソル 6）
                                   ────
                                   53 語 × 2 言語 = 106 個
```

⭐ **残りの 119 語は、通知・確認・プロパティパネルなど、いま画面に出ていない場所のものです。**

### 4.2 ⭐ そして、多くは既に決まった名前がある

⚠️ **`previous-project-result/03-ui-naming/` は前プロジェクトの確定文書であり、
規則 06 の 1. が「載せる前に必ず引くこと」と定めている参照先です。**

⭐ **したがって尋ね方は「172 語を発明してください」ではなく、
「この 53 語の候補を確認・訂正してください」になります。**
⛔ **候補には必ず出典を添えること** —— 利用者は**引用を確認**するのであって、**発明を受け入れる**のではありません。

⚠️ **⛔ 候補を原稿へ書き込むのは私ではありません。** 語を `_source/` へ入れるのは確定名の新設であり、**利用者の裁定を経てからです。**

## 6. 推奨 —— **A →（C ＋ D）。⛔ B と E は採らない**

⭐ **推奨**:

```
1. A  配る道を通す（裁定不要。表 T-075 の UF-60 が既に命じている）
      ⭐ 併せて CR-194 の受け入れ試験を書く ——
        「原稿の語を 1 つ変えると落ちる試験」。落ちなければ届いていない
2. C+D いま画面に出る 53 語を、出典つきの候補として並べ、確認・訂正してもらう
```

**根拠**:

1. ⭐ **A は裁定ではない** —— 表 T-075 の `UF-60` の行が既にそのメンバを命じており、**決めることが何も無い**
2. ⭐ **A をやらずに尋ねると、利用者の判断が捨てられる** —— どのコードも読まないから
3. ⭐ **C は「読める画面」までの距離を 1/3 にする** —— 106 個で `FR-038` の MUST が画面上で満たされる
4. ⭐ **D は規則 06 の 1. そのもの** ——「載せる前に必ず引く。⛔ 未読を裁定待ちにしてはならない。それは利用者の時間を、こちらの手抜きで使うことである」
5. ⛔ **E を退ける理由**: **見た目が良くなると、未完了であることが見えなくなります。** ⚠️ `IC-1` という表示は醜いが、**正直**です
