# 裁定 03 —— 開く道で、誰も持っていない 3 つ

**日付**: 2026-08-22 ／ **仕様**: 0.85 ／ **分類**: **F ＋ D ＋ E**（⛔ **3 つとも推奨で走れない**）
**止まるもの**: ⛔ **ファイルを開く・保存する**
**止まらないもの**: いま動いているもの全部

⚠️ **本書は調査と提案の記録である。仕様ではない。**

---

## 1. ユースケース

> 作成者が `Ctrl+O` を押し、同僚から届いた `plan.xml`（MSPDI）を選ぶ。

**この 1 回で、誰も持っていない 3 つに全部ぶつかります。**

```
A  これは GRS JSON か MSPDI か —— 誰が決めるのか
B  「この文書は MSPDI から開いた」を誰が覚えているのか（Ctrl+S が何を書くかがこれで決まる）
C  未保存の編集を捨ててよいかを問い、その答えを誰がどう受け取るのか
```

⭐ **コーデックは両方とも完全に書かれています**（`documentFromJson` / `documentFromMspdi`、読み書き 4 本とも ✅ 受入済）。⛔ **繋げないのは、この 3 つに持ち主が無いからです。**

---

## 2. 課題

### 2.1 ⛔ A —— 形式の判別器が、どの表にも無い

`OP-1`（`01-04-requirements.md:3176`）:

```
| OP-1 | 受け付ける形式 | GRS JSON と MSPDI XML（表 T-024 の IO-1 / IO-2） |
```

⛔ **両方受け付けると書いてあるのに、どちらかを決める者がいません。**

- **`FileGateway` は明文で断っています**（`file-gateway.ts`）:「It does not know what a schedule is… **A gateway that sniffed the format would hold a fourth authority nobody wrote down**」
- **`openDocumentFile` は文字列までしか返しません**:「⚠️ The text as the bytes encode it. **No format has been guessed**」
- **`ImportFormat = 'grsJson' | 'mspdi'` は `importDocument` の引数**であり、⛔ **産む者がいません**
- ⚠️ **ファイル選択に型の絞り込みも掛けていません**（`@provisional PD-104`「どの表も拡張子も MIME 型も持たない」）ので、**ファイル名からも推測できません**

### 2.2 ⚠️ B —— 半分は既に持ち主がいる（**私の当初の読みは誤りだった**）

⭐ **「どのファイルに立っているか」は持ち主が決まっています**:

```
| CP-28 | Framework | FileSystemAccessFileStore | FileStore の実装。ファイルのハンドルを保持する | FR-060 |
| IF-3  | FileStore | FileGateway（CP-22） | FileSystemAccessFileStore（CP-28） |
         ファイルの読み書き。ハンドルは実装が保持する（FR-060） |
```

⛔ **持ち主が無いのは「どの形式で開いたか」だけです。**
⚠️ **そしてそれは `Ctrl+S` の意味を決めます。** 表 T-227 の RATIONALE がそう書いています:

```
表 T-036 の SK-11（保存する）が MSPDI から開いた文書に対して何をするかも、ここで決まる
```

⛔ **`Document` に形式の列はありません。** ⛔ **`src/` のどこにも保持されていません。**

### 2.3 ⛔ C —— 確認の答えの返り道が無い（**3 つのファイルが同じ STOP を書いている**）

**問う義務は 2 つあります:**

| | 逐語 | どこ |
|---|---|---|
| `OP-4` | 「**置き換えを選んだときは、捨てる前に確認を求めること（MUST）。** 黙って捨ててはならない（MUST NOT）」 | `01-04-requirements.md:3179` |
| `DI-4` | 「**同じとみなせない相手へ書き出そうとするときは、上書きしてよいかを問うこと（MUST）**」 | 表 T-227 |

**在るもの・無いもの**:

```
⭐ 問いの 形 は在る        Confirmation 型（manner / text / items）と ScreenView.confirmation
⛔ 画面は描いていない       dom-screen-surface.ts の STOP:「⛔ ONE MEMBER IS NOT DRAWN: view.confirmation」
⛔ 押す入口が無い           表 T-109 に確認の 2 択の行が無く、表 T-103 に名前も無い
⛔ 答えの返り道が無い       notices.ts の STOP:「⚠️ STILL OPEN AFTER TABLE T-227.
                            CR-197 added DI-4, which is a fourth place that asks, and closed nothing
                            about how the answer comes back」
```

⚠️ **さらに実装側にも穴があります** —— `file-store.ts` の契約は「相手を読み、`askToWriteOver` を問い、`true` のときだけ書く」と定めるのに、**実装は 1 度も呼びません**（`grep -c askToWriteOver` → **0**）。⛔ **`DI-4` の MUST は、シェルが答えを用意できても到達しません。**

## 3. 対応案 —— **3 つは 1 つの塊として決める**

⚠️ **1 つずつ決めると噛み合いません。** ⭐ **A の答えが B の置き場を決め、B の置き場が C の呼び手を決めます。**

| # | 形 | ⭐ 利点 | ⛔ 代償 |
|---|---|---|---|
| **1** | **開く道を丸ごと持つ新しいコンポーネントを立てる** | ⭐ 1 か所が「この文書はどこから来たか」に答える | ⛔ **1 つのコンポーネントに 5 つの仕事**（`R2.2` が「〜と〜を行う」を MUST 違反と名指す形）。⛔ **コンポーネント 38・ユニット 71 の刷った数が動き、図が 2 枚再生成される。** ⛔ **C は閉じない** |
| **2** ⭐ | **既存のコンポーネントに 1 メンバずつ配る** | ⭐ **数が 1 つも動かない。** ⭐ A は `DocumentCodec`（`PI-20`）へ、B はシェル（`LY-5` が現在値の持ち主と定める）へ、C は 表 T-109 に行を 1 つ | ⚠️ **表 T-064・表 T-109・表 T-024a に 1 行ずつ足す。** 3 つの表を触る |
| **3** | **シェルが 3 つとも持つ** | ⭐ `LY-5` に素直。⭐ 表を 1 行も触らない | ⛔ **判別は「受理するか拒むかの境界」（分類 F）であり、公開されないシェルの中に隠れる。** ⛔ **C は閉じない**（答えは `ScreenPart.entry` を通るしかなく、それは 表 T-109 の行である）|
| **4** | **2 と同じ。ただし C の答えは継ぎ目から返す**（`ScreenSurface` に第 4 のメンバ）| ⭐ 表 T-109 を触らない | ⛔ **表 T-065 の MUST と正面衝突** ——「点がどの入口の上かは、その入口を描いた側が答えること」。⛔ **継ぎ目の行は他ユニットの試験ごと無効にする** |

---

## 4. 推奨 —— **案 2。ただし A の書き方に 1 つ罠がある**

⭐ **推奨: 案 2 —— 既存のコンポーネントに 1 メンバずつ配る。**

```
A  形式の判別   → DocumentCodec（CP-20）が 1 メンバ公開する。表 T-024a に行を 1 つ（OP-12）
B  開いた形式   → シェルが持つ（LY-5「現在値を保持するのはこの層だけである」）
C  確認の答え   → 表 T-109 に確認の 2 択の行を足し、既存の入口の道（ScreenPart.entry）で返す
```

**根拠**:

1. ⭐ **刷った数が 1 つも動かない** —— コンポーネント 38・ユニット 71・図 2 枚がそのまま
2. ⭐ **A は「受理するか拒むかの境界」なので、公開された場所に置く必要がある**（分類 F）。⛔ 案 3 はそれをシェルの中に隠す
3. ⭐ **C は 表 T-109 の行としてしか返せない** —— 表 T-065 の MUST が「点がどの入口の上かは、**その入口を描いた側が答えること**」と定めるので、答えの道は既にある入口の道と同じである。⛔ 案 4 はその MUST に衝突する
4. ⭐ **B はシェルが持つのが `LY-5` そのもの** —— 「現在値を保持するのはこの層だけである」

### ⛔ A の書き方に罠がある（**反論が見つけた。私も確認した**）

⚠️ **「解析して決める」と素直に書くと、`FR-023` の MUST NOT を破ります。**

```
FR-023: 先頭の BOM は受け入れ、捨てること（MUST）。BOM があることを理由に拒んではならない（MUST NOT）
```

⛔ **BOM 付きの `GRS JSON`（Excel やメモ帳が吐く）を「JSON として解析できないから MSPDI だ」と読むと、
   XML の誤りとして拒まれます。** ⚠️ **人は「JSON なのに XML のエラーが出る」画面を見ることになります。**

⭐ **したがって行の文言は「解析する前に BOM を捨てる」ことを先に言う必要があります。** ⛔ **順序が規則の一部です。**

## 5. ⛔ 裁定が要る 3 問

| # | 問い | 推奨 | 根拠 | 分類 |
|---|---|---|---|:---:|
| **Q1** | **形式を何で決めるか**（拡張子か、中身か、両方試すか）| **BOM を捨てた後の先頭の非空白文字で決める。** `{` なら `GRS JSON`、`<` なら MSPDI、どちらでもなければ拒む | ⭐ 拡張子は当てにできない（`PD-104` が「どの表も拡張子も MIME 型も持たない」と記録）。⭐ 「両方試す」は、壊れた JSON を MSPDI の誤りとして見せる。⛔ **`FR-023` の BOM の MUST NOT を先に満たす順序で書くこと** | **F** |
| **Q2** | **「どの形式で開いたか」をどこが持つか。`Ctrl+S` は MSPDI で開いた文書に何を書くか** | **シェルが持つ。`Ctrl+S` は開いた形式へ書き戻す**（往復が閉じる）| ⭐ 表 T-227 の RATIONALE が「`SK-11` が MSPDI から開いた文書に何をするかも、ここで決まる」と書き、⭐ `FR-060` は「往復が 1 つのファイルで閉じる」ことを望んでいる。⛔ **ただし MSPDI は無損失ではない**ので、**書き戻すと `FR-021` の往復が崩れる。裁定が要るのはここである** | **D** |
| **Q3** | **確認の 2 択を、表 T-109 の行として足すか** | **足す。** 名前は表 T-103 の作法に従い、答えは既存の入口の道で返す | ⭐ 表 T-065 の MUST が答えの道を 1 本に定めている。⛔ 3 つのファイルの STOP はこれ 1 つで閉じる | **E** |

⚠️ **`Q2` が本当の難所です。** ⛔ **MSPDI へ書き戻すと `FR-021`（無損失の往復）が崩れます** —— 拡張領域に載らない列があるためです。⭐ **代案は「MSPDI から開いても `Ctrl+S` は `GRS JSON` で保存し、MSPDI は書き出し（`FR-096`）でだけ出す」** です。**どちらを採るかで、人の期待が変わります。**
