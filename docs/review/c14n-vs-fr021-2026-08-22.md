# Canonical XML は `FR-021` の 4 つを覆うか —— 突き合わせの記録

**日付**: 2026-08-22 ／ **版**: 仕様 0.75 ／ **波**: W4
**きっかけ**: `CR-198` の第 7 節が「`FR-021` の 4 つと Canonical XML の突き合わせは済んでいない」と開けたまま閉じた。
`SWS-6`（`docs/spec/05-07-design.md:835`）は利用者の裁定 `D10` をそのまま置いたものであり、規格が要求を覆うことの確認ではない。

⚠️ **本書は調査の記録である。仕様ではない。** ⛔ **本書は仕様のオブジェクトを 1 つも動かしていない。**
⭐ **裁定は本書では下さない。** 案と根拠を並べ、第 4 節で問う。

## 0. 何をどう確かめたか

⭐ **原文は保存していない。** `docs/reference/w3c/` は空のままである（実体の保存は外部からの取得に当たるので、利用者に断る前にやらない。第 4 節の `Q7`）。

| 何 | どこ | いつの版 |
| --- | --- | --- |
| Canonical XML 1.0 | `https://www.w3.org/TR/xml-c14n10/` | W3C Recommendation 15 March 2001（`This version` は `.../TR/2001/REC-xml-c14n-20010315`）|
| Canonical XML 1.1 | `https://www.w3.org/TR/xml-c14n11/` | W3C Recommendation 2 May 2008（`This version` は `.../TR/2008/REC-xml-c14n11-20080502/`）|

**本書が置くのは「どの節がそう言っているか」を確かめられる最小限である**（節番号 ＋ 原文 1 文 ＋ URL）。

## 1. 4 項目の突き合わせ

⭐ **結論を先に置く。覆うのは 2 つ、覆わないのが 1 つ、半分だけ覆うのが 1 つである。**

| `FR-021` の項目 | C14N が覆うか | 原文の該当箇所（節番号 ＋ 逐語）| 覆わないなら何が要るか |
| --- | --- | --- | --- |
| ① 属性の並び | ⭐ **覆う** | 2.2 節 —— `An element's attribute nodes are sorted lexicographically with namespace URI as the primary key and local name as the secondary key`。3.3 節の例が `<e3 name="elem3" id="elem3" />` を `<e3 id="elem3" name="elem3"></e3>` にする | —— |
| ② 要素の間の空白と改行 | ⛔ **覆わない** | 2.1 節 —— `All whitespace within the root document element MUST be preserved`。3.2 節の `Demonstrates` が `Retain all whitespace between consecutive start tags, clean or dirty` と書く | ⛔ **補う規則が要る。** 第 4 節の `Q2` |
| ③ 自己終了タグの綴り方 | ⭐ **覆う** | 1.1 節の変更一覧 —— `Empty elements are converted to start-end tag pairs`。3.3 節の例が `<e1   />` を `<e1></e1>` にする | —— |
| ④ 名前空間の接頭辞 | ⚠️ **半分だけ覆う** | ⛔ 接頭辞そのもの: 2.3 節 —— `The namespace prefix used in the QName MUST be the same one which appeared in the input document.` 4.4 節の題が `No Namespace Prefix Rewriting`。⭐ 余分な宣言: 4.6 節 —— `Unnecessary namespace declarations are not made in the canonical form.` | ⛔ **接頭辞の側に補う規則が要る。** 第 4 節の `Q3` |

### ② を「覆わない」と判定した根拠（**読み違えではない**）

⚠️ **C14N が空白を正規化するのは 2 か所だけである。** 1.1 節の変更一覧が
`Whitespace outside of the document element and within start and end tags is normalized` と書き、
**すぐ次の行で** `All whitespace in character content is retained` と書いている。
⛔ **要素の間の空白は前者ではなく後者である。**

⭐ **これが `FR-021` に効く道筋は 1 本である。** `FR-021` が比べるのは
**取り込んだ元のファイルと、本ソフトウェアが書き出したファイル**であり、**書き手が 2 人いる。**
**元のファイルの字下げは相手のもので、書き出す側の字下げは本ソフトウェアのものである。**
⛔ **C14N は両方をそのまま保存するので、字下げが 1 文字でも違えば正規形が違う。**

⭐ **補える根拠は、交換相手の正典が持っている**（`docs/reference/mspdi/mspdi_pj12.xsd`。実測）。

```
mixed="true" を持つ複合型      0 件
xsd:sequence                   94 件
xsd:choice                      4 件
xsd:all                         4 件
```

⚠️ **つまり MSPDI に混在内容（mixed content）は 1 つも無い。**
⭐ **子に要素を持つ要素の、空白だけの文字ノードは、交換相手の型定義において意味を持たない。**
⛔ **葉の要素の中の空白は別である**（`<Name>  </Name>` は値である）—— **落としてよいのは「要素の子を持つ要素」の側だけである。**

### ④ を「半分」と判定した根拠

⭐ **C14N は余分な宣言を削る**（4.6 節）—— 親と同じ値で `xmlns` を刷り直している子要素からは消える。
⛔ **しかし接頭辞そのものは書き換えない。** 2.3 節が `MUST` でそう定めており、4.4 節が丸ごとその理由に充てられている。

⚠️ **4.4 節が挙げる「書き換えると壊れる」理由は 1 つである** —— 原文の言い方で
`an XPath expression in an attribute value or element content can reference a namespace prefix`。
⭐ **その危険は MSPDI には無い。** 実測（`mspdi_pj12.xsd`）。

```
xsd:attribute の宣言          0 件   ← 属性を 1 つも宣言していない
xsd:anyAttribute              0 件
xsd:QName / ID / IDREF /
  NOTATION / ENTITY の型       0 件
実際に使われている単純型       boolean 77 / integer 59 / dateTime 50 / string 46 /
                               float 36 / duration 35 / decimal 26 / time 6
```

⛔ **接頭辞を参照しうる型が 1 つも無い。** ⭐ **だから 4.4 節の禁止理由は MSPDI に当たらず、
「比べる前に接頭辞を潰す」規則を上に足しても、規格が守ろうとしたものを壊さない。**

⚠️ **代案として Exclusive XML Canonicalization を当たったが、これは答えにならない。**
同 3 節が `The data model, processing, input parameters, and output data for Exclusive XML Canonicalization are the same as for Canonical XML [XML-C14N] with the following exceptions` と書き、
**その例外は 2 つである** —— ① 祖先の `xml:` 属性を写さないこと、② `InclusiveNamespaces PrefixList` と、目に見えて使われている接頭辞だけを刷ること。
⛔ **接頭辞の書き換えは、こちらにも無い。**

### ⚠️ ① は MSPDI では空振りに近い。**ただし完全な空振りではない**

⭐ **XSD が属性を 1 つも宣言していない**（上の実測）ので、スキーマに従うかぎり並べ替える属性が無い。
⛔ **しかし実ファイルには属性が出る。** 交換相手の公式文書（`docs/reference/mspdi/learn-docs/project-xml-data-interchange/b408000-b417fff-elements.md`）が
`<b408015 DurationFormat="7">PT40H0M0S</b408015>` を実例として載せている ——
**この `b408015` は XSD に無い拡張の要素であり、属性を持つ。**
⭐ **本ソフトウェアはこれを解釈しないので、表 T-053 の `DF-2` により `carryElements` へ原形のまま入る。**
⚠️ **持ち回った属性を書き戻すときの並びは、①の対象である。**

### ⛔ 見つけた第 5 の揺れ —— `FR-021` が挙げていない。**C14N も覆わない**

⭐ **C14N は文字列を型として解釈しない。** 1.3 節が範囲外だと明言している ——
`application-specific rules such as those governing unimportant whitespace and equivalent data`。

⚠️ **交換相手の型は、同じ値を別々に綴れる。**

| 型 | 同じ値の別の綴り | 実ファイルの綴り（`learn-docs` の実例）|
| --- | --- | --- |
| `xsd:boolean` | `1` ／ `true` | `<Summary>1</Summary>` `<Critical>1</Critical>` |
| `xsd:duration` | `PT40H0M0S` ／ `PT40H` | `PT40H0M0S`（`b408015` の実例）|
| `xsd:float` / `xsd:decimal` | `1.0` ／ `1` ／ `1E0` | —— |
| `xsd:dateTime` | 秒の桁・オフセットの有無 | —— |

⛔ **これは本ソフトウェアで実際に起こる。** `docs/spec/_source/erd.json` の実測。

```
列の出自   GRS 57 / Own 43 / Consume 19 / Carry 19
Own の型   文字列 12・日時 10・整数 9・真偽 6・日付 2・その他 4
```

⭐ **`Own` は「取り込んでそのまま書き戻す」ものだが、文書は文字列ではなく型付きの値として持っている。**
⛔ **したがって書き出すときの綴りは本ソフトウェアが決めており、元の綴りではない。**
⚠️ **原形のまま持ち回るのは `Carry` の 19 列だけである。**
⭐ **つまり 43 ＋ 19 ＝ 62 列が、C14N を当てても一致しないことがありうる。**

⛔ **これは `SWS-6` を直しても閉じない。** `FR-021` の側で揺れを 1 つ足すか、`Own` の持ち方を変えるかの裁定である（第 4 節の `Q4`）。

### ⚠️ 名前空間 URI そのものが 2 通りある（**参考。本調査の射程外だが C14N に直に効く**）

```
mspdi_pj12.xsd:21   targetNamespace="http://schemas.microsoft.com/project/2007"
learn-docs の実例    xmlns="http://schemas.microsoft.com/project"        11 件
                     xmlns="http://schemas.microsoft.com/project/2007"    1 件（スキーマの引用そのもの）
```

⛔ **C14N は名前空間 URI を文字どおり比べる。** ⭐ **本ソフトウェアは、読んだ URI をそのまま書き戻すほかない。**
⚠️ **どちらが実ファイルに出るかは本調査では確かめていない**（手元に MSPDI の実ファイルが 1 つも無い）。

## 2. 1.0 と 1.1 の差は `FR-021` に効くか

⭐ **効かない。** ⛔ **ただし「差が無い」のではなく、「差が出る経路を本ソフトウェアが通らない」である。**

### 2.1 機械で比べた（**節見出しで切り、文字列の一致を取った**）

| 節 | 1.0 と 1.1 |
| --- | --- |
| 2.2 文書順（属性・名前空間の並べ替え）| ⭐ **完全一致** |
| 3.2 内容の中の空白 | ⭐ **完全一致** |
| 3.3 開始タグと終了タグ | ⭐ **完全一致** |
| 4.1 〜 4.7（宣言なし・文字モデル・外側の空白・接頭辞を書き換えない・並び・余分な宣言・既定名前空間）| ⭐ **完全一致** |
| 2.1 データモデル | ⚠️ 差は 1 語（`document type declaration (DTD)` が `document type declaration` になった）|
| 2.3 処理モデル | ⚠️ 差は 1 文の言い換え（既定名前空間ノードの局所名を `xmlns` として刷る、の書き方）|
| 4.8 属性を名前空間 URI で並べる | ⚠️ 差は 1 語（`Namespaces in XML` が `Namespaces in XML 1.0` になった）|
| 1.3 限界 | ⚠️ 差は 1 句（`Attributes of type ID` が `Attributes of type ID, other than the xml:id attribute` になった）|
| 2.4 文書の部分集合 | ⛔ **ここだけが本物の差**（1.0 は 2,212 字、1.1 は 5,674 字）|
| 3.8 文書の部分集合と `xml:` 属性 | ⛔ **1.1 にしか無い** |

⭐ **1.1 が足したものは、1.1 自身の `Abstract` が 1 文で言っている** ——
`Canonical XML Version 1.1 is a revision to Canonical XML Version 1.0 to address issues related to inheritance of attributes in the XML namespace when canonicalizing document subsets`。

⛔ **`when canonicalizing document subsets` が全部を決めている。**
⭐ **`FR-021` が比べるのは 2 つの文書の全体であって、部分集合ではない。** ⚠️ **だから差の出る経路を通らない。**

### 2.2 `xml:base` / `xml:lang` を MSPDI が使うかの実測

```
mspdi_pj12.xsd（3,906 行）を検索
  xml:lang   0 件
  xml:base   0 件
  xml:space  0 件
  xml:id     0 件
  xsd:attribute の宣言   0 件
  xsd:anyAttribute       0 件
learn-docs（390 ファイル）を検索
  xml:lang / xml:base    0 件
```

⛔ **交換相手は `xml:` 名前空間の属性を 1 つも使わない。** ⚠️ **属性の宣言も属性のワイルドカードも無いので、
スキーマに従うかぎり `xml:` 属性は出てこない**（⭐ **スキーマに従わない実ファイルはありうる。そこは覆えない**）。

⭐ **したがって 1.0 と 1.1 のどちらを採っても、`FR-021` の 4 つに差は出ない。**

### 2.3 それでも版を明記すべき理由

⛔ **差が無いことは「どちらでもよい」を意味しない。** ⭐ **第 0 節で見たとおり、`SWS-6` が貼っている URL はいま 1.1 を返す。**
⚠️ **仕様書が黙っているあいだ、読んだ者が手に取る版は、その日の W3C の振り替え次第である。**

## 3. SVG / PNG の側（`PD-161`）

### 3.1 SVG —— **使える部分と、足りない部分**

`FR-080`（`docs/spec/01-04-requirements.md:3083`）が挙げる揺れは 3 つである。

| `FR-080` の揺れ | C14N が覆うか | 根拠 |
| --- | --- | --- |
| 属性の並び | ⭐ **覆う。しかも MSPDI と違い、ここでは大きく効く** | 2.2 節（第 1 節の ①）。⭐ SVG は属性で絵を書く形式なので、並べ替えの利きが `FR-021` の場合と正反対である |
| 小数の桁 | ⛔ **覆わない** | 1.3 節が `equivalent data` を範囲外と明言。⭐ `10.0` と `10` は別の文字列のまま残る |
| 空白の入れ方 | ⛔ **覆わない** | 2.1 節と 3.2 節（第 1 節の ②）|

⭐ **第 1 節の ③（自己終了タグ）も、`FR-080` は挙げていないが同じように効く** —— C14N は `<rect .../>` を `<rect ...></rect>` にする。
⚠️ **PNG では C14N は 1 つも覆わない。** ⛔ **PNG は XML ではないので、規格の射程の外である。**

⭐ **いまの実装の実測**（`src/adapter/image-exporter/image-exporter.ts`。⚠️ **裁定が下るまで触っていない**）。

```
組み立て方        文字列の連結（+ と .join('')）。⭐ 要素の間に空白を入れていない
XML 宣言          出していない
名前空間          根の <svg xmlns="http://www.w3.org/2000/svg" ...> だけ。接頭辞を使っていない
自己終了タグ       使っている（<rect .../>）
座標の桁          Math.round(value * 100) / 100 —— 0.01 px の格子
                  ⛔ 同じ関数が image-exporter.ts:221 と svg-renderer.ts:102 の 2 か所にある
比の桁            ⛔ 丸めない（ratioText が toString() をそのまま返す）
```

⚠️ **つまり「空白の入れ方」は、いま揺れていない。** ⛔ **しかしそれは実装がそうしているだけで、仕様に規則が無い。**
⭐ **書き方を変えた者が、黙って `WY-2` を落とせる状態である。**

### 3.2 ⛔ 「出力の精度」と「比較の精度」—— **前の回の見立てを 1 つ正す**

前の回は「`WY-2` は文字列一致を求め、`WY-3` は緩い一致を許すので衝突する」と書いた。
⭐ **`WY-2` と `WY-3` は、そもそも別のものを比べている。**

```
WY-2   同じ JSON を、同じ基準環境で読み、全体表示してから書き出したもの同士
       ⭐ 比べているのは「書き出しの経路が決定的か」である
       ⛔ 桁数の問題ではない。桁が何桁でも、決定的なら一致する

WY-3   画面の外接矩形に比を掛けた値  対  書き出した SVG / PNG の中の外接矩形
       ⭐ 比べているのは「2 つの表現の幾何が合うか」である
       ⛔ こちらは縮める順が両側で違うので、端数が必ず出る
```

⚠️ **だから「絵が飛び飛びになるか、0.01px で落ちるか」の二択ではない。**
⭐ **`WY-2` に要るのは決定性であり、`WY-3` に要るのは許容差である。**

⛔ **ただし `WY-2` には別の穴が開いている** —— **「同じ」の相手が書かれていない。**
2 回書き出したもの同士なのか、版元に置いた見本と比べるのかで、要求の重さが変わる。
**見本と比べるなら、浮動小数の再現性が機械や版に跨がって効いてくる。**

### 3.3 案（**3 本。⛔ 決めない**）

| 案 | 出力の精度 | 比較の精度 | 長所 | 短所 |
| --- | --- | --- | --- | --- |
| **A**（いまの延長）| 座標を 0.01 px に丸めて書く | `WY-2` は C14N 後の文字列一致。`WY-3` は両側を同じ格子へ落としてから比べ、1 px 未満を含めない | ⭐ **実装を動かさない。** 0.01 px は 1600 px 幅で 16 万分の 1 であり、絵に出ない | ⚠️ 「1 px 未満」の境（ちょうど 1.0 px）を決める必要がある |
| **B** | 座標を整数 px で書く | 完全一致 | しきい値の裁定が要らない | ⛔ **1600 px 幅で 1 px の量子化。細い線・矢羽根の角度・実績バーの端が崩れる。** `FR-094` の寸法が壊れる。**推奨しない** |
| **C** | 丸めずに書く | 判定器が両側を同じ格子へ落としてから比べる | ⭐ 絵が最良。**丸めが「判定器の規則」に純化し、`FR-080` の「両側へ同じ丸めを当てる」という文言と素直に一致する** | ⚠️ `0.30000000000000004` のような綴りが出る。ファイルが太り、`WY-2` の一致が浮動小数の再現性に寄りかかる |

⭐ **推奨は `A`。** 理由は 2 つある。

1. ⭐ **いまが `A` である。** `A` から `C` へは判定器だけを直せば移れるが、`C` から `A` へは出力を変えることになる
2. ⭐ **0.01 px は、`S-81` の 1600 px 幅に対して見えない差である。** `B` のように絵を壊さず、`C` のように綴りを膨らませない

### 3.4 PNG の側（**⛔ ここが一番薄い**）

⭐ **いまの実装は `canvas.toBlob` に `image/png` を渡して作っている**（`src/framework/canvas-rasterizer/canvas-rasterizer.ts:356`）。

```
⛔ PNG のバイト列は、同じ画素からでも一致しない
   zlib の段・フィルタの選び方・チャンクの並び・tIME や tEXt の有無が符号器ごとに違う
⛔ 画素そのものも、描画エンジンが違えば違う（アンチエイリアス・字の形）
⚠️ 表 T-025 の MC-6 が定める基準環境は 1920 × 1080 / 全画面 / 拡大率 100% であり、
   ⛔ 描画エンジンとその版を固定していない
```

| 案 | 何を比べるか | 長所 | 短所 |
| --- | --- | --- | --- |
| **P1** | ⭐ **復号したあとの RGBA の画素列**（ファイルのバイト列ではない）| 符号器の差を全部落とせる | ⚠️ 描画エンジンの差は残る |
| **P2** | PNG を `WY-2` の対象から外し、SVG だけで判定する | 判定が 1 本になる | ⛔ `IO-4` が判定されないまま残る |
| **P3** | 画素の一致に許容差を置く（チャネル差が n 以下）| エンジンを跨げる | ⛔ **許容差そのものが `G` の裁定になる。暫定の上に暫定を積む**（規則 06 の `H`）|

⭐ **推奨は `P1`、ならびに `MC-6` へ描画エンジンとその版を足すこと。**
⛔ **エンジンを固定しないまま `P1` を採ると、`WY-2` は基準環境の定義が緩いぶんだけ落ちる。**
⚠️ **固定できないなら `P3` が要る** —— ⛔ **そのときは `H`（暫定の上に暫定）に触れるので、先に `MC-6` を裁くほうが安い。**

### 3.5 ⭐ `PD-161` は 1 行に 2 つの裁定が入っている

```
出力の桁（座標を何桁で書くか）
  ⭐ SVG / PNG は書出のみ（表 T-024 の IO-3 と IO-4）。文書にも MSPDI にも保存されない
  ⭐ 覆したときの実費は「原稿の 1 セル ＋ npm run gen ＋ その値を読む試験」

  ⛔ WY-3 の合否が直に乗る。覆すと「合格」としていた判定が全部組み直しになる
```
