# ボトルネック検出 — 設計メモ（CR 前の草案）

2026-09-20。利用者との対話で決めたもの。**CR にはまだしていない。**
点検機能（`inspection-viewpoints-2026-09-20.md`）の**次**に入れる機能。

## 1. 何を出す機能か

計画に対して遅れているとき、**その遅れを生んだ場所**を名指しする。
並列に走る系列があるので、**ボトルネックは複数出る**。

⭐ **ボトルネックは「遅れている当人」ではない** —— 先行が遅れたせいで遅れている行は**巻き添え**であり、
名指すべきはその大もとである。

## 2. 既存の遅れ判定では足りない

`01-04-requirements.md` の 表 T-021b（`DL-1`〜`DL-3`）は、3 行とも**終点が基準日**であり、
表 T-021 の `PM-4` は**完了したものを遅れとしない**。

⛔ **ところがボトルネックの大半は「もう終わったが、遅れて終わったタスク」である。**
下流を押し出した張本人なのに、既存の遅れ判定では 1 日も数えられない。
ゆえに**別の量が要る**。表 T-021b は画面の遅れの印として残し、本機能は本書の量を使う。

## 3. 定義 — 遅れを 3 つに分ける

| 日 | 英（コード） | 意味 |
| --- | --- | --- |
| 持ち込まれた遅れ | `inheritedDelayDays` | 先行が遅れたせいで最早開始が後ろへずれた分。**巻き添え** |
| 自分で生んだ遅れ | `selfDelayDays` | その最早開始から数えて、自分の計画期間を超えた分。**発生源** |
| 押し出し日数 | `pushOutDays` | 自分で生んだ遅れのうち、後続の余裕に吸収されず**終端まで届いた**分 |
| 見込み終了 | `projectedFinish` | 実際にはいつ終わるか（5.1） |

> ⭐ **ボトルネック ＝ 押し出し日数が大きいタスク**

⛔ **「遅れた量」で並べてはならない** —— 自分で生んだ遅れが 10 日あっても、
後続に 10 日の余裕があれば下流には何も起きない。それはボトルネックではない。
逆に 2 日しか生んでいなくても、余裕ゼロの連鎖の上にあれば終端を 2 日押す。
**押した量で並べる。**

日数はすべて**稼働日**で数える（暦は `FR-054`）。

## 4. 決まったこと（利用者の裁定 2026-09-20）

| 論点 | 裁定 |
| --- | --- |
| 着手済み・未完のタスクの見込み終了 | **`max(finish, 基準日)` のみ。**消化率からの外挿も、打ち込む列の追加もしない |
| 計画期間をどこから採るか | **いまの計画（`finish` − `start`）。**`BaselineTask` は参考にとどめ、判定には使わない |
| 余裕をどこから採るか | **GRS が依存と暦から計算し直す。**取り込んだ値を信じない |
| 資源のボトルネック（制約資源） | **出さない。**工数はどうせ入力されない |
| 構造のボトルネック（合流点・連鎖長） | **一旦不要。**別機能として後で考える |

### 4.1 この裁定が生む性質（意図されたもの）

⭐ **`percentComplete` を一切使わない** —— 見込み終了が `max(finish, 基準日)` なので、
消化率が入っていなくても本機能は動く。**進捗を入力しない現場でも結果が出る。**

⭐ **着手済み・未完のタスクの遅れは、基準日とともに毎日伸びる** ——
「今日いちばん遅れているのはこれです」と毎日示せる。
利用者はこれを**進捗を入力させる圧**として使う意図である。

⭐ **計画を見直すと遅れが消える** —— いまの計画に対して測るので、これは正しい振る舞いである。
`FR` 側の方針（**予定を動かしてよいのは公式に計画を修正した時だけ**）と噛み合っており、
2 つは組で守らねばならない。⛔ **片方だけを崩すと、予定をこっそり動かして遅れを消せてしまう。**

## 5. 手順（4 パス）

### 5.1 パス 1 — 見込み終了を置く

| 状態 | `projectedFinish` |
| --- | --- |
| 完了（`actualFinish` を持つ） | `actualFinish` |
| 着手済み・未完 | `max(finish, 基準日)` |
| 未着手 | 最早開始 ＋ 計画期間 |

⭐ **未着手のタスクの最早開始は `max(依存から決まる最早開始, 基準日)` とする** ——
基準日を過ぎても着手していないのだから、少なくとも基準日までは始まっていない。
表 T-021b の `DL-2` と同じ読みである。

⚠️ 基準日（`Project.statusDate`）が無いときは本機能を走らせない（`FR-046` が遅れの判定について定めるのと同じ）。

### 5.2 パス 2 — 依存グラフを前向きに再計算する

`linkType` と `lag`（点検メモ 6.2 の式）と暦はそのままに、日付だけ実績・見込みへ差し替えて前向きに流す。
各タスクについて「実際にはこうなる終了日」が出る。

### 5.3 パス 3 — 帰属

```
inheritedDelayDays(T) = max(0, 最早開始(T) − start(T))
selfDelayDays(T)      = max(0, projectedFinish(T) − (最早開始(T) + 計画期間(T)))
```

`selfDelayDays > 0` のタスクだけが**発生源候補**である。ここで巻き添えが全部落ちる。

### 5.4 パス 4 — 終端まで押し出す

終端 ＝ **後続を持たないタスク**と**マイルストーン**。
終端ごとに後ろ向きに辿り、発生源の寄与を配る。経路の途中に余裕があればそこで吸収され、配られない。

配られた日数の合計が、そのタスクの `pushOutDays` である。

## 6. 出力

終端ごとに出す。

```
◆ 設計完了     12 日押し出し  ← B が 8 日 / F が 4 日
◆ 調達完了      5 日押し出し  ← K が 5 日
◆ 試験完了      0 日          ← 遅れは全部余裕に吸収された
```

一覧は `pushOutDays` の合計の降順。添えるのは「届く終端の数」。

⭐ **並列な系列を特別扱いする仕組みが要らない** —— 並列な系列は別の終端へ向かうので、
終端ごとに別の発生源が出る。合流していれば同じ発生源が複数の終端に現れ、合計が大きくなって上位に来る。

## 7. 点検との順序

⭐ **本機能は、点検が通っていることを前提とする。**

| 残っていると | 何が壊れるか |
| --- | --- |
| `SC-1`（依存の輪） | 前向き計算が止まる |
| `SC-22`（予定が依存の向きに反する） | 余裕が負になり、押し出しの計算が壊れる |
| `SC-15` / `SC-17`（親子の集約） | 親の行に出る押し出し日数が嘘になる |

**点検 → ボトルネック**の順序を、仕様に書き下すこと。

## 8. 本機能では扱わないもの

| 事柄 | 理由 |
| --- | --- |
| 資源のボトルネック（制約資源） | `Assignment` が `taskUid` と `resourceUid` しか持たず、工数も単位も無い。どうせ入力されない |
| 合流点・余裕ゼロの連鎖長（構造のボトルネック） | 「遅れの原因」ではなく「これから詰まりそうな場所」。別機能 |
| `BaselineTask` との比較 | 参考にとどめる。見直した計画に対して刈り取る |
| 消化率（`percentComplete`）からの見込みの外挿 | 4 節の裁定 |
