## 1. 層の草案 — 何を層としているか（`LAY`）

### 1-1. 層の定義（4 層。`LAY:36`–`41` の表を全数写す）

| 層 | 置くもの | 純粋性 | 出典 |
|---|---|---|---|
| **entity** | 文書モデル（保存される事実）／時間↔座標マッピング／マルチバーのレイアウト（段割当・行高）／整列ソルバ／LOD セレクタ／依存線ルータ／予実差分・イナズマ線の頂点／`Fit` の算出 | すべて `pure` または `semi-pure-a` | `LAY:38` |
| **use case（操作層）** | コマンド実行（原子的・1 呼び出し = Undo 1 段）／基準版の照合／`revision` の更新／Undo・Redo 履歴／取込検証／変更理由の追記／変更の通知 | 履歴と `revision` は `non-pure`。照合と検証は `pure` | `LAY:39` |
| **adapter** | UI アダプタ（入力 → コマンド、幾何 → 画面）／機械向けの口（既定は非公開）／SVG 直列化／JSON・MSPDI コーデック／ファイル入出力ゲートウェイ／自動保存ゲートウェイ | SVG 直列化とコーデックは `pure`。ゲートウェイと 2 つの口は `non-pure` | `LAY:40` |
| **framework** | ブラウザ・DOM／File System Access API／localStorage・IndexedDB／単一 `.html` のシェル | すべて `non-pure` | `LAY:41` |

**層は 4 つ**（自分で数えた: 表の行 `LAY:38`–`41`）。**既定の 4 層名（Entity / UseCase / Adapter / Framework）をそのまま採っている**（`RS:487` の既定と同名）。

### 2-1. `R2.1` Naming の下位規約（**MUST・最重要**。`RS:57`–`95`）

**「命名はソフトウェアの主要なインターフェースである。命名は最重要のレビュー項目として扱い、SHOULD ではなく MUST とする」**（`RS:59`）。

**品詞の規約（`RS:69`–`76`。全 6 行を写す）**:

| 対象 | 品詞 | 例 | 出典 |
|---|---|---|---|
| クラス・型 | 名詞または名詞句 | `Order`, `CellVoltage` | `RS:71` |
| **コマンド**（`non-pure`。状態を変える） | **動詞 + 目的語** | `cancelOrder` | `RS:72` |
| **クエリ**（`pure` / `semi-pure-a`） | **名詞句、または `is/has/can`** | `totalPrice`, `isExpired` | `RS:73` |
| **外部を読む操作**（`semi-pure-b`） | **動詞 + 目的語** | `readDocument`, `fetchUser` | `RS:74` |
| プロパティ | 名詞（Boolean とコレクションは上記に従う） | `retryCount`, `orders` | `RS:75` |
| **イベント** | **過去形** | `OrderPlaced`, `CellVoltageExceeded` | `RS:76` |

- **コマンドとイベントを形で分ける。** コマンドは依頼であり**拒否できる**。イベントは通知であり**拒否できない**。`PlaceOrder` と `OrderPlaced` が形で違えば、**受け手が拒否してよいかが名前から読める**（`RS:78`）。
- **副作用が無いことと、呼んで安価であることは別。** `semi-pure-b` は**動詞にする**。名詞にすると遅さと失敗しうることが名前から消える（R2.14 POLA）。**`readDocument()` を `document()` に改めてはならない。判定は R7 の `@purity` タグをそのまま使う**（`RS:80`）。
- **単位が固定の量は名前に単位を入れる**（`timeoutMs` / `voltageMv` / `capacityAh`）。**単位の取り違えは型検査を通り抜ける。** ただし単位を実行時に持つ値（`Quantity { amount, unit }`）は対象外（`RS:82`）。

**レイヤー別のコンポーネント・クラス名（`RS:86`–`91`。全 4 行）**:

| レイヤー | 品詞 | 例 | **兆候（違反のサイン）** | 出典 |
|---|---|---|---|---|
| Entity | 名詞 | `Order`, `Temperature` | 動詞、**`〜Data` / `〜Info`** | `RS:88` |
| Use Case | **動詞句**（接尾辞を付けるなら `〜UseCase` / `〜Interactor`） | `ConvertUnit`, `PlaceOrder` | **`〜Service`** | `RS:89` |
| Adapter | **役割 + 方式** | `PostgresOrderRepository`, `CliPresenter` | 方式だけ（`DbHelper`）、役割だけ（`Manager`） | `RS:90` |
| Framework | 名詞句 | `ExpressRouter`（技術名がそのまま現れてよい） | — | `RS:91` |

- **既定の 4 層を採らない設計では、Ch5.1 が定義した層に読み替える。読み替えは層の役割で対応させる**（`RS:93`）。
- **Use Case を動詞句にするのは趣味ではない。** `OrderService` は操作をいくつでも抱えられるが `PlaceOrder` は抱えられない。**命名が R2.2（SRP）を強制する。名詞化された Use Case は肥大化の予告**（`RS:95`）。

## 3. `R7`（純粋性・構造）— 条項番号つき全数（**10 条**）

**対象**: 仕様書 **Ch5-6**・コード（`RS:336`）。
**冒頭の直交宣言**（`RS:340`）: 「**本節は純粋性軸の規約であり、レイヤー軸（Entity/UseCase/Adapter/Framework、R2.16 CA）とは直交する。Adapter 層に純粋関数があってよく、Entity 層に可変集約（DDD の Aggregate 等）があってもよい。一方の軸の違反をもう一方の軸の違反として起票しないこと。**」

**自分で数えた**: `R7` は **10 条**（`RS:508`–`517`）。**MUST 5 条（R7.1 / R7.2 / R7.4 / R7.5 / R7.6）／ SHOULD 5 条（R7.3 / R7.7 / R7.8 / R7.9 / R7.10）**。

| ID | Level | 主題 | 要求 | 出典（表） | 詳細節 |
|---|:---:|---|---|---|---|
| **R7.1** | **MUST** | 純粋性の分類 | 各関数／メソッドを `pure` / `semi-pure-a`（**不変値**の読取）/ `semi-pure-b`（**可変・非決定**の読取）/ `non-pure`（可変状態か副作用）に分類 | `RS:508` | `RS:342`–`351` |
| **R7.2** | **MUST** | **計算ロジックの純粋性** | **ドメインの計算ロジック（業務規則・判断・変換）は `pure` または `semi-pure-a`。** 非純粋な作用を混在させず専門の関数／ユニットへ分離。**レイヤー軸（R2.16）とは直交。** ドメイン不変条件違反の例外は計算ロジック側で許容、**I/O・システム起因の例外は非純粋側に限る** | `RS:509` | `RS:353`–`360` |
| R7.3 | SHOULD | **外部読取の引き上げ** | `semi-pure-b` の読取（**時刻・乱数・DB/ファイル/NW 読取**）を**関数の先頭で収集**し、可能なら**引数注入して `pure` へ引き上げる** | `RS:510` | `RS:362`–`367` |
| **R7.4** | **MUST** | 収集と処理の分離 | **処理の途中で新たな外部読取を行わない**（読取は処理開始前に完結）。全件収集が不可能な場合は**一貫性の単位（チャンク／スナップショット／トランザクション）を明示**し、その単位内で収集→処理の順序を守る | `RS:511` | `RS:369`–`378` |
| **R7.5** | **MUST** | 純粋側クラスの不変性 | 純粋側のクラスは **immutable class / value object / stateless class** として可変状態を持たない。可変状態か副作用メソッドを持てば **stateful（非純粋）** として扱う | `RS:512` | `RS:380`–`382` |
| **R7.6** | **MUST** | **`@purity` タグ** | すべての関数／メソッドに **`@purity` タグをコメント内にちょうど 1 つ**。**無印を許さない**（grep で検査可能）。除外: **テストコード・自動生成コード・サードパーティ・単一式のラムダ** | `RS:513` | `RS:384`–`403` |
| R7.7 | SHOULD | メンバの並び | クラス／ユニット内でメンバを **純粋 → 準純粋 → 非純粋の順**に並べ、**非純粋群の前にセクションコメント**を置く | `RS:514` | `RS:407` |
| R7.8 | SHOULD | 混在の禁止 | クラスに可変状態と純粋計算を混在させず、**純粋ロジックは純粋関数か値オブジェクトへ抽出** | `RS:515` | `RS:408` |
| R7.9 | SHOULD | ユニット分割 | **純粋性でユニットを分割**（純粋な core と非純粋な shell を**別ファイル**に） | `RS:516` | `RS:409` |
| R7.10 | SHOULD | 失敗の表現 | 計算ロジック側の失敗を**戻り値型（Result / Either / Option）**で表現。同等の機構を持たない言語ではドメイン例外で代替してよい | `RS:517` | `RS:411`–`413` |

### 3-1. 純粋性の 4 値（`RS:344`–`349`。定義を全数写す）

| 分類 | タグ値 | 定義 | 出典 |
|---|---|---|---|
| 純粋 | `pure` | 可変内部状態なし・副作用なし・**外部状態を読まない**。出力は引数のみで決まる（参照透過） | `RS:346` |
| 準純粋-a | `semi-pure-a` | 副作用はないが**不変値**の外部状態を読む（定数・起動時設定の読み取り等）。**決定的** | `RS:347` |
| 準純粋-b | `semi-pure-b` | 副作用はないが**可変・非決定**の外部状態を読む（**時刻・乱数・DB/ファイル/NW 読取**） | `RS:348` |
| 非純粋 | `non-pure` | 可変内部状態を持つ、または副作用がある | `RS:349` |

**非純粋な作用の一覧**（`RS:351`。自分で数えた **6 種**）: I/O ／ DB 書込 ／ ログ出力 ／ lock・mutex・semaphore の取得解放 ／ グローバル変数や引数の書き換え ／ HW・OS・環境変数の変更。**例外送出の扱いは R7.2 に従う。**

### 3-2. `@purity` タグの機械検査（`RS:384`–`403`）

| 事項 | 内容 | 出典 |
|---|---|---|
| 記法 | `@purity pure \| semi-pure-a \| semi-pure-b \| non-pure` をコメント内に書く | `RS:389` |
| なぜテキストマーカーか | **言語構文ではないため全言語で機能し grep で検査できる** | `RS:392` |
| なぜ純粋も明示するか | **付け忘れと純粋を区別するため** | `RS:392` |
| 4 値を全部実在させる理由 | `grep '@purity semi-pure-a'` が**前方一致で `semi-pure-b` を拾う事故**を防ぐ | `RS:392` |
| 除外 4 種 | テストコード（検査対象は製品コードの構造）／自動生成コード（生成器の管轄）／サードパーティのベンダリング（自プロジェクトの判断ではない）／**単一式のラムダ・無名関数**（注釈が本体より長くなる） | `RS:396`–`401` |
| **数値ゲート** | **除外を除いた製品コードのタグ付与率 `purity_tag_coverage_pct` は 100% でなければならない** | `RS:403` |

### 3-3. `R7.4` が要求する「一貫性の単位」（`RS:369`–`378`）

- 守るべき不変条件は「全件をメモリに載せること」**ではなく**、**処理の途中で外部状態が変化しても結果が変わらないこと**である（`RS:373`）。
- **一貫性の単位が成果物（仕様書 Ch5.5 または実装コードのコメント）に明示されているか**（`RS:375`）。
- **R5.3（大規模データはストリーミング）とは衝突しない。** ストリーミングは**チャンクを一貫性の単位とする**ことで本項を満たす（`RS:378`）。

### 4-2. Clean Architecture を採ると発生する具体的な義務（箇条）

1. **Ch5.1 に層の定義と依存の向きを書く**（`R2.16` MUST・`RS:487`）。**層の数は自由**だが、**定義が無ければ違反**。`LAY:36`–`43` の表と図がそのまま材料になる。
2. **中心がフレームワーク／DB に汚染されないこと**（`RS:171`–`173`）。**entity が `document`・File System Access API・localStorage の型に触れない**こと。
3. **Adapter 層の厚みを測られる** —— 「薄すぎて外部依存がドメインに漏洩していないか／厚すぎてビジネスロジックが Adapter に混入していないか」（`RS:175`）。
4. **層仕訳の正しさは「このプロジェクトの目的にとって本質か手段か」で判断される**（`RS:174`）。**`LAY:25`–`26` の問い（レイアウト・LOD・配線は画面の都合か中心の価値か）は、この判定基準そのものである。**
5. **命名がレイヤーで縛られる**（`R2.1` MUST・`RS:88`–`91`）。**Use Case は動詞句**（`〜Service` は違反の兆候）、**Entity は名詞**（`〜Data` / `〜Info` は兆候）、**Adapter は役割 + 方式**（`Manager` / `DbHelper` は兆候）。**`LAY:39` の「コマンド実行」「基準版の照合」は動詞句であり、この規約と整合する**（実装名は未定 ＝ **未検証**）。
6. **Ch5.6 に ADR-000 を書く**（`R2.18` MUST）。**3 点必須** —— ①要求を満たす最小の構成（要求を落とした案は最小構成ではない）②増やした要素の列挙 ③各々を増やした理由（**「規約に従ったため」だけでは足りない。どの規約がどの要求のために働いたかまで書く**）（`RS:139`–`141` / `LAY:169`–`171`）。
7. **Ch5.3 に公開面を宣言する**（`R2.19` MUST）。**コンポーネントが 1 つの設計では NA とし Remark に理由を書く**（`RS:490`）。
8. **キャッシュを持つなら Ch5.6 に ADR を足す**（`R2.20` MUST）。⚠️ **「暗黙のキャッシュ（メモ化・遅延初期化）が見落とされていないか」と明記されている**（`RS:183`）。**`T-13` の「寸法をフレーム先頭で 1 回読んでキャッシュ」（`LAY:115` / `PERF:321`）はこの暗黙のキャッシュに当たる。** 4 点（何を／無効化の契機／許容する陳腐化／同時失効時の挙動）を書かないと違反になる。**未検証** —— 前資産にこの ADR は無い。
9. **entity 配下に `non-pure` があれば `R7.2` 違反**（`RS:509`）。`LAY:147` はこれを**ディレクトリ単位で機械検査できる**と書く。
10. **`@purity` タグ付与率 100%**（`R7.6` MUST・`RS:403`）。`LAY:148` は「タグの grep で数えられる」と書く。
11. **一貫性の単位を明示する**（`R7.4` MUST・`RS:375`）。**描画フレームでは「フレームの先頭で寸法を 1 回読む」= フレームが一貫性の単位**になる（`LAY:109` / `PERF:321` から導かれる。⚠️ **この対応づけは本書の解釈であり、原文にこの語は無い ＝ 未検証**）。
12. **純粋な core と非純粋な shell を別ファイルにする**（`R7.9` SHOULD・`RS:516`）。**ディレクトリ構成に効くが、構成そのものは未決**（`ENT:89`）。
13. **軸を混ぜて起票しない** —— `R7`（純粋性軸）と `R2.16`（レイヤー軸）は**直交**（`RS:340`）。`R2.19`（コンポーネント境界）も `R2.16` とは**別の軸**（`RS:490`）。**`LAY:141`–`143` はこの直交宣言に寄りかかって「adapter に純粋なものがある」を正当化している。**
14. **`R5.1`（Ch4.2 の NFR を満たす計算量）と `R5.3`（キャッシュに上限 TTL/サイズ・メモリリークなし）は別に見られる**（`RS:501`, `RS:503`）。**`R2.20` は正しさ、`R5.3` は資源** —— 同じキャッシュを 2 条項が別の観点で見る（`RS:491`）。
