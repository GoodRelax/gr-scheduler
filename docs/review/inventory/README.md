# 在庫表 — 仕様書を書くために原典を全数調査した記録

**これは仕様書ではない。** 仕様書は `docs/spec/` である。**食い違ったら仕様書が勝つ。**

本ディレクトリは、**引き継いだ資産（`previous-project-result/`）と交換相手のスキーマを全数調査した結果**である。
`change-request/` の各 CR は、ここを根拠にして書かれている。**CR の判定を辿るにはここを読む。**

⚠️ **鮮度に注意。** ここは調査した時点の写しであり、**仕様書の変更に追随しない。**
数や行番号を引くときは、**その場で `docs/spec` を数え直すこと。**

## 何が入っているか

| 群 | 枚 | 中身 |
|---|--:|---|
| `E01` 〜 `E11` | 11 | **データモデルの全列**（3,380 行 / 559 列）。エンティティ群ごとに原典を全文読んだもの |
| `A01` 〜 `A10` | 10 | 引継書の資産地図に**載っていなかった約 6,000 行**の走査。`A01` が `Agent API` の決定 95 件を持つ |

| `U1` 〜 `U4` | 4 | **UI 名 429 語 × 用語辞書**の突き合わせ。`U4` が辞書に足す行を裁定した |

| `Y1` `Y2` `Y3` | 3 | **依存のグラフと閉路の解析、および反映済みの変更の検算。** `Y3` は反映が作った欠陥を 10 件見つけた |
| `Z01` | 2 | **機械抽出した 559 列**（`.json` と `.md`）。手写しではなくパーサで取った |

## 読むときの順序

1. **`Z01-extracted-columns.md`** —— エンティティごとの列数の一覧。全体の大きさが分かる
2. **`E01`〜`E11`** —— 列の詳細を引く必要が出たとき
3. **`Y2` / `Y3`** —— 仕様書を変更する前に。**閉路と、過去に壊れた型**が書いてある
4. **`X1` / `X2`** —— `CR-114` がどの文をなぜ除いたかを辿るとき

## 作り方

すべて**サブエージェントに原典を全文読ませて**書かせ、**別のエージェントに突き合わせさせた**ものである。
**数の主張はそれぞれが自分で数えている。** ただし ——

⚠️ **エージェントの報告を鵜呑みにしてはならない。** 実際に次が起きた。

- 複数のエージェントが `CR-104`（`Task.milestone` の列を持つ）を知らず、**「列は持たない」と繰り返した**
- 「システムは」の出現数が **CR 本文 210 / `X3` 215 / `Y1` 214 / 実測 178** と全部食い違った
  （同時編集で動いていたため。**反映の直前に数え直すのが唯一の正解**）

**数の主張は自分で数え直し、理由の主張は原文に当たること。**
