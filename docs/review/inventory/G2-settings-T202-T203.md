## 3. 判定不能と、境界が破れる場所

**11 件。重い順に並べた。**

### 1. `FR-063` が新しい規則と正面から矛盾する（担当 23 鍵の全部に掛かる）

`docs/spec/01-04-requirements.md:3111`（`FR-063`）は現にこう書いている。

> **版数を上げるのは、文書に保存される値を変える更新すべてとすること（MUST）。**……⚠️ **ズーム・スクロール・パン・`Dual Cursor` の位置・パネル幅と、表 T-202 が持つ表示の切り替えは文書に保存される**（表 T-202 / T-203）**ので版数を上げる。取り消しの対象外であることとは別である。**

**名指しされているのが、まさに本書の担当範囲そのものである。** 新しい規則を採ると、`FR-063` は 23 鍵のうち少なくとも 21 鍵について逆の答えを出す。しかも `FR-063` は版数の判定基準を「`tbl-settings.md` の各表のうち ⛔ と 🅿 が付いていない行」＝**保存するかどうか**に結びつけており、新しい規則の「日程のデータが変わったか」とは**判定軸そのものが違う**。**`FR-063` の書き換えなしにこの 2 群は成立しない。**
`FR-063` は理由も書いている ——「**取り消しは「人が戻したい編集か」、版数は「読んだものが古くなったか」を判定しており、目的が違う**」。新しい規則はここに**第 3 の軸**（日程のデータが変わったか）を持ち込むので、3 本の軸の関係を書き直す必要がある（→ 11）。
出典: `REQ:3111` / `SET:37`（⛔ と 🅿 の意味）

### 2. `importSeq`（`S-71`）は表示でも書式でもなく、しかも既に二重定義になっている

**(a) 群の誤り**: `importSeq` は表 T-202「**表示の切り替えと文書全体の書式**」にいるが、切り替えでも書式でもない。`FR-049:2513` 自身が「**値そのものを持つ行（積む向き・文字サイズ・取込の連番・デュアルカーソルの 2 日付）も対象外**」と書き、この表の趣旨から外れることを認めている。用途は `TaskOrigin.lastSeenImportSeq` との突き合わせによる「外部マスタから消えた候補」の導出であり（`ERD:475-479`）、`MG-13` は「**他に前回を知る手段が無い**」と書く。これは規則が schedule 側に置いた「**出自**」である。

**(b) 既に別の表が引き取っている**: `docs/spec/_assets/tbl-datamodel.md`（**作業ツリーでは削除済み**。HEAD 版の 75 行 `NR-45`）はこう書いている ——「**列を足した。** `TaskOrigin.lastSeenImportSeq` は「最後に届いた取り込みの通し番号」だが、**比べる相手の通し番号がどこにも無かった。** 由来の文書は文書全体の設定として持っていたが、**設定値ではなく文書の構造なので本書が持つ**」。同 182 行 `DM-120` は `Project.importSeq` を表 T-307（`Project` の列）に置いている。**つまり仕様書側は既に「設定値ではない」と判断済みで、`SET:134` の `S-71` が消し忘れである。**
⚠️ ただし `E04-project.md:59` は逆に「**`documentSettings`（文書設定）側。`Project` の列ではない**」と結論しており、**在庫調査どうしも割れている**。どちらが正かは本書では決められない（`DM` を全文読んでいない）。**判定不能なのは置き場所であって、群ではない** —— どちらに置いても出自であることは変わらないので、**群は schedule で確定できる。**

**(c) 具体的な壊れ方**: 仮に `importSeq` を documentSettings 側に残すと、`MG-12`（`REQ:2675`）が「**設定の項目ごとに問うてはならない（MUST NOT）。`documentSettings` 全体へ一括して適用する**」と定めているため、合流で相手の設定を選んだ瞬間に**相手の取込連番が丸ごと入り込み、自分の `TaskOrigin.lastSeenImportSeq`（schedule 側・タスクごと）と体系が合わなくなる。** `MG-11`（前回届いて今回届かなかったタスクの検出）が黙って誤った一覧を出す。**版数を上げない群に置くと、上げない編集で schedule 側の導出が壊れる。**
出典: `SET:134` / `REQ:2513,2674,2675` / `ERD:475-479,1616` / `DM(HEAD):75,182` ↔ `E04:59`

### 3. `scrollGroupId`（`S-78`）— 2 つの群が独立に検証できなくなる唯一の鍵

群の割り当て自体は迷わない（スクロール位置＝見せ方＝documentSettings）。**破れるのは「群が閉じている」という前提のほうである。**

- 値は `TaskGroup.id` への**弱い FK**（`SET:154`「⚠️ 整数ではない」／`DOCSET:307`）。
- `TaskGroup` の追加・削除は取り消しの対象（`UN-14`、`REQ:1513`）で、schedule 側＝**版数を上げる**編集である。
- したがって **documentSettings 側を 1 文字も触っていないのに、schedule 側の編集だけで `S-78` の値が無効になる。** `OP-10`（`REQ:2888`）が「存在しない id なら全体表示の位置にする（MUST）」と受け止めるので事故にはならないが、**「版数を上げない群の値は、版数を上げた編集の影響を受けない」とは言えなくなる。**
- 帰結: **documentSettings だけを取り出して検証する検査は書けない。** `S-78` の妥当性は schedule 側の `TaskGroup` 集合を見ないと判定できない。担当 23 鍵で自己完結していないのはこの 1 鍵だけである（`scrollDate` は日付が絶対値なので参照先が要らない）。
- 設計側への含意: **「見せ方だけを別文書に切り出して交換する」用途を想定するなら、`S-78` は交換できない。**そこまで想定するのかどうかが原典から確かめられない（**未検証**）。
出典: `SET:154` / `REQ:1513,2888` / `DOCSET:307,333-334`

### 4. `dualCursor`（`S-65`）— **判定不能**

**原典が両側の性質を与えている。**

| 側 | 根拠 | 出典 |
|---|---|---|
| schedule 寄り（注記に近い） | 「任意の縦線を 2 本立て、**その間の日数を測る**」。**2 本の日付を文書が持つ**理由は「**持たないと測った日数が再現しない**」——**人が意図して置いた値**であり、ズーム倍率のような操作の副産物ではない | `REQ:2469` / `SET:128` |
