# 何をどこに書くか —— 書きすぎを切り分ける提案

⛔ **これは提案であり、裁定を受けていない。** 本書のどの行も規則ではない。
規則にするなら `docs/development-rules/` へ移し、機械の検査を添えることになる。

⭐ **測ったのは 2026-09-10、commit `fb4038e` の木である。** すべての数に方法を添えた。
方法が気に入らないなら数を採り直せる —— それが本書がいちばん守りたい作法である。

---

## 0. この提案が下げようとしている費用

利用者の申し立ては 2 つある。逐語で置く。

> 仕様書、および、コードのコメントに無駄が多い。仕様書に記載すべきこと、コードに記載すべきこと、記載すべきでないことを挙げよ。

> GRS は .md と .ts が主なのに、不具合修正や、俺の指摘対応に膨大な時間がかかる。

⭐⭐ **後者が本題である。**「美しくない」ではなく「1 件直すのが高い」。
だから本書は、饒舌を減らすことではなく、**1 件直すときに回らねばならない場所の数を減らすこと**を目的にする。

#### なぜ無駄なのか —— 4 つの観点

**（a）『リーダブルコード』の観点 —— コードが自明に語ることを繰り返している**

⭐ **この規則はもう書いてある。** `docs/development-rules/03-implementation.md` の第 3 節が、
コメントには「なぜ」を書き「どう動くか」を書かない、という見出しを掲げ、
書いてはならないものとして コードの言い換え・**仕様の本文の写し**・**値の写し**・嘘 を並べている。
⛔ 同節は、写せば 2 か所になり片方が腐る、とその理由まで書いている（同ファイル 第 3 節「書いてはならないこと」）。

⛔⛔ **規則が在るのに守られていない。** 実測 1.4 のとおり `src` のコメント字数の 2.8 % しか逐語ではなく、
残りは規則が想定していなかった形 ——「原稿を写す」ではなく「原稿を英語で敷衍する」—— で嵩んでいる。
⚠️ これは**名前で言えることをコメントで言っている**の変種である: 行 ID `GR-17` が既に一意な名前なのに、
その行の趣旨を毎回 10 行で言い直している。

**（b）二重管理 —— 指し示すのと書き写すのは別である**

⭐ **指し示し（`表 T-023d の GR-17`）は二重管理ではない。** 原稿が動けば指し先の中身が動くだけで、指す側は無傷である。
⛔ **書き写し（逐語 40 字）は二重管理である。** 原稿が動くと、写しは**古い規則を主張し続ける**。
実測 1.3 のとおり、551 条項が 2 か所以上に立っている。

**（c）腐り方 —— 何が真でなくなったときに黙って嘘になるか**

| 書いたもの | 何が動くと嘘になるか | 誰が気づくか |
|---|---|---|
| 逐語の引用 | 原稿の語が変わる | **検査 42**（ただし「無い文の引用」だけ） |
| 数の写し（`30px` など） | 表の値が変わる | ⛔ 誰も気づかない |
| 「いま N 件ある」式の数 | 表に 1 行増える | ⛔ 誰も気づかない |
| 撤回の記録（前はこう書いていた） | ⭐ 決して嘘にならない | —— |
| 実測の記録（この日こう測った） | ⭐ 決して嘘にならない | —— |
| 指し先（行 ID） | 行 ID が消える | 検査 6・7（原稿の中だけ） |

⚠️ **最後の 2 つは腐らない。だから消してよい。**
「その日そう測った」は永久に真であり、永久に**今の判断には効かない**。それは台帳と Git の仕事である。

**（d）⭐⭐ 編集の伝播 —— その 1 文を直すと、ほかに何か所直さねばならないか**

⛔⛔ **これが 1 件の費用の正体である。**
`.claude/skills/spec-graph-check/quoted-source-baseline.txt` の頭注が、この現象を自分で記録している:
2026-09-09 / 09-10 の掴みシロの裁定が着地した日、**15 件のコメントが一日で偽の引用に変わった。
どれも書かれた時点では捏造ではなかった。** 表の行に列が 1 つ増えただけである。

⇒ **写しの数 ＝ 1 件あたりの編集コスト。** 実測 1.3 の分布がそのまま費用の分布である。

## 3. ⚠️⚠️ 消してよい饒舌と、機械が支えている饒舌

⛔ **一律に「冗長だから消せ」と言うと、動いている検査が落ちる。** 境目を引く。

### 3.1 境目の引き方（1 行）

> **その散文を消したとき、いずれかの検査の数が悪化するか。悪化するなら機械が支えている。悪化しないなら消してよい。**

方法: 3 つの検査の本体を読み、**どの木のどの行を読んでいるか**を確かめた（読んだのは
`check-quoted-source.py` の `TREES` / `find_unsourced`、
`check-must-clause-coverage.py` の `FILES` / `load_test_corpus` / `held_length`、
`check-ruling-landed.py` の `judge` / `named_places`）。

### 3.2 表 —— 何を消すと、どの検査がどう動くか

| 消すもの | 検査 42（引用の出所） | 検査 39（MUST の逐語保持） | 検査 43（裁定の着地） | 判定 |
|---|---|---|---|---|
| `src` の `「」` 引用 | ⭐ **下がる**（良い方向。基準線も下げる） | 無関係（`tests` しか読まない） | 無関係（下記 3.3） | **消してよい** |
| `src` の撤回の記録 | ⭐ 下がることが多い（廃れた文の引用は「出所なし」に数えられている） | 無関係 | 無関係 | **消してよい** |
| `src` の実測・欠陥番号 | 無関係 | 無関係 | 無関係 | **消してよい** |
| `src` の `@purity` | 無関係 | 無関係 | 無関係 | **裁定が要る**（3.4） |
| `tests` の**コメント**にある MUST の逐語 | 下がる | ⛔⛔ **983 → 1,358 に悪化する** | 無関係 | **消すな。式に移せ**（4.1） |
| `tests` の撤回の記録 | 下がる | ⭐ 悪化しない（廃れた条項は今の原稿に無い） | 無関係 | **消してよい** |
| `docs/spec` の A.3 Changelog | 無関係 | 無関係（読まれていない） | 無関係 | 検査 38 が版番号だけ読む。**裁定が要る** |
| `docs/development-records/rulings.md` の逐語 | 無関係 | 無関係 | ⛔ **落ちる** | **消すな** |

### 3.3 ⭐ `src` の逐語は機械に支えられていない —— 確かめた

検査 43 は、裁定の逐語を **`docs/spec` 全体 ＋ その行の 着地先 欄が名指したファイル**から探す
（`judge()` の `haystacks = spec + named_places(...)`、`named_places` は **着地先 欄だけ**を読む）。
`docs/development-records/rulings.md` の 適用済 行の 着地先 欄を全部読んだところ、
**`src/` のファイルを名指した行は 1 つも無い**（名指しは `docs/spec` の要求・表、
`docs/development-rules/05-working-method.md`、`docs/development-records/handoff.md`、本書＝`rulings.md` のみ）。
⇒ **`src` から逐語を消しても検査 43 は落ちない。**

検査 42 は**引用の存在を求めていない。存在する引用の出所を求めている**（`count > held` で落ちる）。
⇒ **引用を消せば数は下がる。**現在 470（`src` 128 / `tests` 342）、基準線 471。

### 3.4 ⚠️ 機械が支えていないが、支えられるもの

`docs/development-rules/07-review-standards.md` の `R7.6`（MUST）は、
すべての関数がコメント内に `@purity` をちょうど 1 つ持つことを求め、**その理由に「grep で検査できる」ことを挙げている。**
⛔⛔ **誰も grep していない。** `tools/` と `.claude/skills/` を `purity` で検索したが、
読むのは原稿の表（`audit-ch5.py`）と、雛形を**書く**生成器（`generate_unit_tree.py`）だけである。

実測: `src` に `@purity` は 1,228 個（うち `pure` が 692）、関数の概数は 1,177
（`function` 宣言 1,021 ＋ アロー定数 47 ＋ メソッド概数 109）。

⇒ **選択肢は 2 つしかない。**
① 20 行の検査を書いて、1,228 行を「機械が支えている饒舌」に変える。
② `R7.6` を退けて、1,228 行を消す。
⛔ **どちらもせずに残すのは、規則が守られているかを誰も知らない状態である。**

## 4. ⭐⭐ 検査そのものを疑う

⚠️ **機械が支えているからといって正しいとは限らない。** 根拠を添えて 2 点。

### 4.1 検査 39 は「コメントに貼れば通る」

方法: 検査 39 の判定（`TRY_LENS = (120, 90, 60, 40, 28)` の後方一致）をそのまま再現し、
`tests/` の探索対象を **コメント行だけ**の側と **コメント以外だけ**の側の 2 つに割って、
どちらが条項を保持しているかを数えた。

| 条項の在り処 | 数 | 割合 |
|---|---|---|
| 試験の**コード**だけが持つ（表題・期待値・文言） | 238 | 14.0 % |
| 両方が持つ | 105 | 6.2 % |
| ⛔⛔ **コメントだけが持つ** | **375** | 22.0 % |
| どこも持たない（＝基準線 983） | 983 | 57.8 % |

⛔⛔ **「保持されている」718 条項のうち 375（52.2 %）は、何も表明しないコメントが持っているだけである。**

**実例。** `FR-092` 系の条項「…と（MUST）。内部の綴りや識別子をそのまま出してはならない（MUST NOT）」は
`tests/contract/display-words.contract.test.ts:287`、`tests/system/measured-sweep.test.ts:3626`、
`tests/unit/uf-64.test.ts:323` / `:1217` に在るが、**いずれもコメントである**
（`measured-sweep.test.ts:3676` には文字列があるが 24 字で、検査 39 の下限 28 字に届かない）。

⇒ ⭐ **提案: 検査 39 を、コメント行を除いた本文だけで数えるように直す。**
そのとき基準線は 983 → 1,358 に上がる（借金の計上であって、悪化ではない）。
⛔ **上げずに直すと、この検査は「散文を貼れば返せる借金」を数え続ける。**
⇒ そのうえで、375 条項を 1 つずつ `it(...)` の表題か期待値の文言へ移す。行数は増えず、検査は正直になる。

### 4.2 検査 42 は正確さを見るが、量を見ない

検査 42 は**出所の無い引用**を数える。⭐ これは正しい検査である（`D-339` の再発を止める）。
⛔ **ただし「引用が多すぎる」は測らない。** 引用を 2 倍にしても、全部が原稿に在れば緑のままである。
⇒ 実測 1.4 の 6,731 件（`src` 2,063 ／ `tests` 4,668）は、この検査から見れば無風である。
⭐ **提案: 基準線を「下げてよい」だけでなく「毎巡下げる」ものとして扱う。**
471 → 470 で止まっているのは、下げる作業に誰も割り当てられていないからである。

**確かめたこと**
