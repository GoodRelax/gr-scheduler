## 1. 用語の体系

⛔ **「点検 / inspection」「進捗検査 / Progress Check」という語は使わない。**

```
遅延診断 / Delay Diagnostics（機能）
  +-- 進捗妥当性検査 / ProgressValidation
  |     指摘 / finding
  |       +-- 記載漏れ / Omission      … マーカーを操作しない
  |       +-- 矛盾 / Contradiction     … 紫、形状 ?
  |       +-- 疑義 / Suspicion         … マーカーを操作しない
  +-- ボトルネック検出 / BottleneckDetection
        +-- 遅延 / Delay               … 黄、形状 !（診断の前から付いている）
        +-- ボトルネック経路 / BottleneckPath … ピンク、形状 !!
        +-- ボトルネック / Bottleneck  … 赤、形状 炎
```

⭐ **炎は「ここで炎上している／消火してくれ」の意。**
⭐ **紫（?）は矛盾だけの色ではない** —— 「**この行の数字は信用できない**」の色である（5.3）。
⭐ **赤とピンクは色だけで区別させない** —— 形状（炎 と `!!`）でも分かれる。
⛔ 綴りは `Suspicion`（`suspicision` ではない）。

### 2.1 背景

> 日程表は遅れを示すが、**その遅れがどこで生まれたのかは示さない。**
> 遅れている行を並べても、その多くは先行の遅れに巻き込まれた行であり、
> 手を付けるべき行はその中の少数である。
> 読み手 —— **エグゼクティブや AI** —— は、どれが原因でどれが巻き添えかを、
> 依存と WBS を自分で辿って判断せねばならず、支援の差し向け先を誤る。
> さらに、実績が入力されていない箇所があると、遅れの像そのものが歪む。

⭐ **読み手を書いておくこと** —— 後から「もっと詳しく出そう」という要求が来たときに、
**数手の掘り下げで届くことが要件である**と突き返せる。

### 2.2 ゴール

> 基準日の時点で、**遅延の発生源（ボトルネック）**を、
> 畳まれた画面から掘り下げる操作だけで特定できること。
> 遅れている行のうち、**対処すべき行がどれかを、読み手が判断せずに受け取れる**こと。

### 2.3 エグゼクティブの言葉

⭐ **機能の目的そのものなので、言葉ごと仕様に引くこと。**

> 助けてやりたいが、進捗が見えない。
> 進捗を正しく入力しろ。**紫のマーカーが付いたタスクを無くせ。**
> そしたらボトルネックのやつから対処する。

## 4. 進捗妥当性検査

## 5.1 暗黙の親子（`wbsParentUid` が明記されていないとき）

⚠️ **問題** —— 行（`TaskGroup`）を詰めて描くので、`Task.wbsParentUid` が書かれないまま残る。
Lv1 の行に「フェーズ1 / MS1 / フェーズ2 / MS2」が並び、Lv2 の行に複数のタスクが並んだとき、
**どの Lv2 タスクがどの Lv1 のバーに紐づくかが決まらない。**

⛔ **同じ行のバーは時間的に重なりうる。**区間の列として扱ってはならない。

### 導出の規則

**候補 ＝ 親の行のバーのうち、期間を持ち、子を両端で包含するもの。**

```
親.start ≤ 子.start  かつ  子.finish ≤ 親.finish
```

⛔ **`start` だけで判定してはならない（MUST NOT）** —— 親は子を覆うのだから、両端で見る。

| 候補の数 | 扱い |
| --- | --- |
| ちょうど 1 | **自動で確定する** |
| 0 | 親入力機能へ |
| 2 以上 | 親入力機能へ |

⛔ **候補が 2 以上のとき、狭い方を親と決めてはならない（MUST NOT）** ——
親どうしが交差しているとき、どちらが親かは**作成者の意図でしか決まらない。**
幾何に根拠が無い。⚠️ 「最も狭い包含を親とする」案は**誤りとして退けた**（2026-09-23）。

⛔ **マイルストーンを親にしてはならない（MUST NOT）** —— `SC-6` と同じ原則。点は中身を持てない。
ゆえに**縦（親子）＝ 期間を持つバー**、**横（マイルストーン）＝ 依存**に割れる。

### 親入力機能

自動で決まらない子を、別画面で 1 件ずつ選ばせる。

| 子 | 親候補 |
| --- | --- |
| bb設計 | ( ) AA設計 ／ (レ) BB設計 ／ ( ) CC設計 |

**候補の並び** —— ① 包含する親 → ② 一部でも重なる親 → ③ 最も近い親（終点・始点が近い順）。
⭐ **並べるだけで、自動では選ばない。**

### 親確認機能

あるタスクにカーソルを当てると、**親タスクの文字が赤太字に変わる。**
⭐ **導出で確定した親が正しいかを、利用者が検算できる唯一の手段である。**

### 導出した親は保存しない

書き込むと、行を動かしたときに古い親が残って腐る。
代わりに進捗妥当性検査が「**親が明記されていない n 件**」を出し、
**修正候補として「この親子を確定する」を提示する**（1 つずつ。4.2 の仕組みに乗る）。
⚠️ `MSPDI` へ書き出すときに親子が要るので、この出口は必要である。

## 5.2 マイルストーンの先行と達成

⛔ **マイルストーンの先行を幾何で推論してはならない** ——
マイルストーンより前に終わるタスクは無数にあり、どれが達成条件かは作成者の意図で決まる…
**という理由で入力させる案は退けた。**下の規則が曖昧さなく一意に決まるからである。

### 先行の導出

**当該マイルストーンの先行 ＝ 次の 2 つの和。**

| | 中身 |
| --- | --- |
| (a) | 当該マイルストーンより**完了日が前**の、**同一階層**のタスク |
| (b) | **1 階層下**のタスクのうち、**当該マイルストーンと同一階層のタスクとの親子関係が決まっていない**もので、当該マイルストーンより完了日が前のもの |

⭐ **(b) が要** —— これがあるので、**Lv1 にマイルストーンしか書かないプロジェクト**でも
Lv2 の実タスクが直に先行になる。(a) が空でも機能する。
⭐ **(b) の除外条件が二重計上を防ぐ** —— フェーズとその子を両方数えない。
⭐ **1 階層下で止める** —— Lv3 は Lv2 に親があるので自動的に落ちる。

**4 つの決め事（利用者の裁定 2026-09-23）:**

| | 決め事 | 理由 |
| --- | --- | --- |
| 1 | **「完了日が前」は予定（`finish`）で判ずる** | 実績で判ずると、⛔ **遅れるたびに先行の顔ぶれが変わり、診断結果が揺れる** |
| 2 | (b) の「親子関係が決まっていない」は、**導出で決まったものも除く** | ⛔ 明記だけを見ると二重計上が戻る |
| 3 | **直前のマイルストーンより後に完了するものに限り、マイルストーンどうしを依存で繋ぐ**（MS1 → MS2） | ⛔ 限らないと MS1 の先行が MS2 にも重複し、**経路が太って読めなくなる。**繋げば押し出しは MS1 経由で届き、結果は同じまま経路が細くなる |
| 4 | **自動で置く**（選ばせない） | 規則が一意に決まるうえ、先行は数が多く、手で選ばせるのは非現実的。⭐ 導出であることを示し、直せるようにする（明記 > 導出） |

### 達成の導出

> **マイルストーンの達成は、先行から導出する。**
> 先行が全部完了 → 達成日 ＝ 先行の最も遅い `actualFinish`
> 1 つでも未完了 → 未達成
> ⭐ 手で入れた `actualFinish` があればそちらが優先（**明記 > 導出**。親と同じ原則）

これが効くところ:

1. ⭐ **`SC-21`（マイルストーンが達成済みなのに先行に未完了がある）が構造的に起きなくなる** ——
   矛盾を検出するのではなく、**発生させない。**
2. **マイルストーンに実績を入力しなくてよくなる**（「どうせ入力しない」という現実に合う）。
3. マイルストーンの遅れが、先行の遅れから自動で出る。

⭐ **先行を 1 つも持たないマイルストーンは紫とする** ——
何も出ないと、読み手は「順調」と読む。5.3 の「信用できない」に当たる。

## 5.3 壁の整理 —— 止まる軸で分ける

⭐ **壁は 1 種類ではない。止める軸が 2 本あり、効き方が逆である。**

| 軸 | 原因 | 何が止まるか |
| --- | --- | --- |
| **横（依存）** | 矛盾を持つタスク | 前向き計算が止まる → **その下流が解析不能** |
| **縦（親子）** | 親が導出できない／一意でない、先行を持たないマイルストーン | 集約が止まる → **押し出し日数が祖先へ上がらない** |

⭐ **縦の壁があっても、そのタスク自身の遅れと依存の押し出しは計算できる** ——
止まるのはピンクの経路が祖先へ伸びることだけである。

レポートは壁ごとに **種別 ／ 原因のタスク ／ 止まった範囲の件数** を出す。

### 紫の意味を広げる（裁定 2026-09-23）

⭐ **紫（?）は「矛盾」の色ではなく、「この行の数字は信用できない」の色とする。**

| 紫が出る行 | 理由 |
| --- | --- |
| 矛盾を持つ行 | その行の値が両立していない |
| 横の壁の下流 | 解析していない。黄が無くても健全とは言えない |
| 縦の壁を配下に持つ祖先 | 配下の遅れが上がってきていない |
| 先行を持たないマイルストーン | 診断できない |

⚠️ **縦の壁がいちばん危ない** —— 畳まれた祖先に何も出ないと、読み手は「配下は健全」と読む。
⛔ **それではユースケースの掘り下げが成立しない。**

⭐ 形状 `?` は「**分からない**」の意なので、この一般化の方が言葉に合う。
種別（矛盾／解析不能）の区別はレポート側で付ける。
⭐ **読み手の行動は変わらない** —— 「紫を無くせ、そしたらボトルネックから対処する」。

## 7. 出口は 2 つ

| 出口 | 読み手 | 中身 |
| --- | --- | --- |
| 画面のマーカー | 人 | 6 節の 4 色。Fit → 掘る |

記載漏れ・矛盾・疑義・ボトルネックの全種別を乗せる。**

## 8. CR 起票時にやること

1. 3 本のメモを **1 本の CR** に束ねる。
2. 接頭辞を登録簿（`_source/row-id-prefixes.json`）から採り、行 ID を確定する。
3. 課題／ゴール／ユースケースに**別項**を立てる（2 節・3 節）。
4. **関連要求の RATIONALE に次を残すこと（MUST）** ——
   見込み終了を `max(finish, 基準日)` としたので**実績を入力していない行は自動的に遅れて見える**、
   これは**設計した効果**である、と。
   ⛔ 書かないと、後の読み手が「未入力を遅れ扱いするのは欠陥だ」と読む。
   ⚠️ 価値の欄には入れない（ほかに比べて薄いため）。
5. **計画を見直すと遅れが消える**性質は、「予定を動かしてよいのは公式に計画を修正した時だけ」
   という方針と**組で守る**こと。⛔ 片方だけ崩すと、予定をこっそり動かして遅れを消せる。
6. 進捗マーカーのデータの持ち場を調べる（6 節）。
