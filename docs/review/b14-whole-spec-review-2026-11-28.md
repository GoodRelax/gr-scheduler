## Scope and method

- In scope: chapters 2 to 11 and the appendix of the specification (`docs/spec/`), the manuscripts in `docs/spec/_source/`, `src/`, `tests/`, the test records and the build output `dist/index.html`.
- ⚠️ Out of scope for now: chapter 1 (`docs/spec/spec-ch1-3.md`, "Chapter 1. Foundation"). It waits the owner's BGQA10 round 4; its review follows when B5 lands that round.
- Four read-only Opus reviewers split the 99 checklist rows: spec structure and design (NDD, R1 structure, use cases, traceability, R2 spec side, R6 records), requirement text (R1 wording, EARS, R5 spec side), code design (R2 code, R7, table T-740) and code quality (R3, R4, R5, R6 tests, R8). Each counted mechanically where it could (the commands are in its notes) and read samples for the rest. The B14 seat checked one or two claims of each reviewer against the tree, merged the two rows two reviewers judged (CA: the code side FAIL wins; R5 algorithm: both PASS) and merged one duplicate finding (an empty catch, now `RVF-57`).
- A finding is one pattern (a checklist row and one root cause) with its count, not one instance.
- Severity follows rule 07 "重大度": a FAILed MUST row is High, except the rows "文の決まり（仕様書の全章）" and "コメント（種類）", which are Medium; a FAILed SHOULD row is Medium. No finding is Critical.
- Handling: every High row waits the owner's answer in `studies/82-anms-ndd-apply-plan/goodrelax-qa-b14-review.md` (BGQA14; the "BGQA14" column names its table line). The Medium and Low rows are deferred by the seat with a due date (appendix A.1 lets the writer defer them). The `DFC` rows for the work open after the owner answers, so that an accepted row opens no work.
