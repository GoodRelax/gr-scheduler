# Agent Interface 要求（ドラフト 18 件）

- 日付: 2026-08-02
- 根拠: `ai-cowork-trial-findings-ja.md`（実測）
- **これは提案である。決定ではない。** 採否は次期が判断する。
- 番号 `A-n` は**このドラフト内だけの通し番号**。次期は自分の体系で振り直す（`handover/README.md` §0-4）。

---

## 0. 一行の要求

> **GRS は、人間が UI で行える編集・確認・出力を、AI が API で行えること。**

「AI 向けの別機能」を作るのではない。**同じ 1 つの文書に、口が 2 つ付く**という話である。

---

## 1. 基本

### A-1. GRS Agent API を第一級のインターフェースとして持つ

GRS は、人間向け UI と**同格**の機械向けインターフェース **GRS Agent API** を持つ。
単一 `.html` の中で、**呼び出せる入口を 1 つ**公開する。
**入口の名前は `globalThis.grSchedulerAgentApi`。既定では公開しない**（`OPEN-ITEMS-ja.md` 決定-4）。
**エージェントが起動するときは起動側がフラグで、人間が起動したときは画面での有効化で公開する。**

- **由来**: `file://` 直開きでは、AI が GRS に触れる経路は
  「ページ内で処理を実行する」か「ディスク上のファイル経由」の 2 つしかない。
  前者を成立させるには、**画面を模倣操作させるのではなく、名前の付いた関数を呼ばせる**必要がある。
- **効果**: 将来サーバを立てたとき、サーバ側の窓口は**この関数群の薄い包み**で済む（`A-16`）。
- **非目標**: AI 推論を製品に組み込むことではない。GRS は AI を持たない（`user-order.md` の方針どおり）。

### A-8. インターフェース版数を持ち、破壊的変更で上げる

GRS Agent API は semver の版数を持ち、**AI は最初に版数を読む**。
非互換な変更では major を上げる。

- **由来**: AI は「今つながっている GRS が自分の知っている版か」を判定できないと、
  古い前提で書き込む。トライアルでは版数を最初から載せ、事故は起きていない。

### A-9. 例外を投げず、結果を値で返す

失敗は投げるのではなく、**受理されたか / 受理されなかった理由 / 現在の文書**を返す。

- **由来**: 自動化側に例外の文字列を解釈させると、失敗の分類が実装依存になる。
  トライアルの拒否 6 回は、すべて**構造化された拒否**として返り、そのまま再試行に使えた。

## 2. 文書

### A-2. 文書に単調増加の `revision` を持つ

文書は、**あらゆる更新で 1 ずつ増える整数**を持つ。
併せて **誰が最後に書いたか** と **いつ書いたか** を持つ。

- **由来**: 実測で 1 セッション `revision` 104 に達し、
  「相手が触ったか」「どこまで読んだか」「自分の前提が古くないか」の 3 つが
  **この整数 1 個だけで**判定できた。
- **注意**: `documentSettings` に入れない。
  設定値は「同じ JSON から同じ絵を得るためのもの」であり（`02-data-model/grs-document-settings-ja.md` §2）、
  `revision` は**絵に影響しない**。トップレベルの別の入れ物に置く（`agent-interface-spec-ja.md` §2）。
- **決定（2026-08-02）**: **保存した JSON に含める。** ただし `revision` / `lastEditedBy` / `updatedAt` の 3 つだけで、
  **`agentApiVersion` は入れない**（`OPEN-ITEMS-ja.md` 決定-3）。

### A-6. 読み出しは不変のコピーを返す

文書の読み出しは、**内部状態への参照ではなく凍結された複製**を返す。

- **由来**: 既存の Undo 設計が**不変更新のスナップショット**を前提にしている
  （`07-plan-actual/handover-plan-actual-decisions-ja.md` §8）。
  外へ生の参照を出すと、その前提が崩れる。

## 3. 書き込み

### A-3. 書き込みは基準版を照合できる

書き込み側は「**どの `revision` を読んで書いているか**」を申告できる。
食い違えば GRS は**書き込みを拒否し、現在の文書を返す**。

- **由来**: **1 セッションで 6 回発火した。** 人間がコメントを書くのと AI が書き込むのは、実際に**同時更新**になる。
- **効果**: 壊れた中間状態が 1 度も発生しなかった。
- **名前**: この方式は**業界では optimistic locking（楽観ロック）と呼ばれる**が、本プロジェクトでは
  **`BaseRevisionCheck` / 基準版の照合**と呼ぶ（`OPEN-ITEMS-ja.md` 決定-6）。
  **何もロックしていない**うえ、「楽観」＝衝突がめったに起きないという見込みが**実測で外れている**ためである。
- **併記**: 申告を省略した書き込みも受け付ける（人間の UI 操作は常に最新を見ているため）。
  **省略できることと、AI が省略してよいことは別である。** AI は常に申告する。

### A-4. 書き込みは UI と同じ履歴に載り、人間が取り消せる

API 経由の変更は、**UI 操作と同じ Undo / Redo の履歴**を通る。
API 専用の履歴を作らない。1 回の呼び出しは **Undo 1 段**にまとめる。

- **由来**: AI は間違える。実測で **AI は 1 セッションに 7 回、自分の誤りを訂正した**
  （`ai-cowork-trial-findings-ja.md` §4）。うち 2 件は取り返しのつかない損害だった。
  **人間が取り消せることは、共同編集の前提条件である。**
- **既存の正に従う**: 方式は `07-plan-actual/handover-plan-actual-decisions-ja.md` §8（不変更新スナップショット）。
  **新しい Undo を設計しない。**
- **状態**: トライアルでは実装したが**押されなかった**（同 §5）。**未検証の要求である。**

### A-5. 一括の書き込みは原子的である

複数の変更をまとめて渡せる。**途中で 1 つでも拒否されたら、全部を元に戻す。**
半端に適用された文書を残さない。

- **由来**: 日程の変更は「タスクを動かす」「依存を張り直す」「行を移す」が
  **セットで初めて意味を持つ**ことが多い。片方だけ通ると、通知（`NEXT-STEPS-ja.md` 2-5）で
  説明できない状態になる。

### A-7. GRS Agent API は UI の防御を迂回しない

API 経由でも、UI と**同じ検証・同じ制限**を通る。

| 迂回してはならないもの | 既存の正 |
|---|---|
| 取込データの厳格な検証（信頼できない入力として扱う） | `user-order.md` 62 / `05-security-a11y/security-design.md` §3 |
| `innerHTML` 直挿しの禁止・XXE の無効化 | 同 |
| 透かしのパスワード照合（生パスワードを保存しない） | `user-order.md` 62 の該当項 |
| 将来の編集権限（`TaskGroup` ごとの公開/編集可否） | `user-order.md` 65-2 |

- **由来**: 機械向けのインターフェースは、**攻撃面としては UI と同じ重さ**を持つ。
  「AI が呼ぶのだから安全」という前提を置かない。

## 4. 監視

### A-10. 監視は revision スコープである

「**私が最後に読んだ `revision` より後の変更だけ**」を通知する。
「今どうなっているか」を返すだけの監視にしない。

- **由来**: **実地でビジーループを踏んだ。**
  処理済みの状態で即座に起き、監視を張り直すたびに即終了する
  （`ai-cowork-trial-findings-ja.md` §3-1）。`sinceRevision` を必須にして直した。
- **効果**: AI が落ちて復帰しても、`sinceRevision` から追いつける
  （**未検証** — `ai-cowork-trial-findings-ja.md` §5）。

### A-11. 起こす条件は「相手が何かした」である

監視は**手番や特定の操作に縛らない**。
「自分以外の書き手が、指定の `revision` より後に何かを確定した」で起こす。

- **由来**: 最小版では「手番が来たら起こす」で足りたが、
  実寸版では**人間が編集せずに話しかける**ことがあり、それでも AI は起きる必要があった。
  条件を一般化して解決した。

## 5. 会話と変更の理由

### A-12. 画面上で AI と会話でき、**変更の理由は文書に残る**（**決定済み**）

**2 つに分ける。**

| | 何か | 保存 |
|---|---|---|
| **チャット欄** | 日程表を見ながらの実行時のやり取り。指示・確認 | **しない** |
| **`changeLog`** | どの `revision` で・誰が・**なぜ**変えたか | **する** |

狙いは「日付をドラッグする代わりに**言葉で日程を動かす**」ことである。
例（ユーザー提示）: 「**もっと検証の期間を長くして**」「**設計と検証は途中から並行にできるでしょ？**」

- **由来**: **AI の説明量は人間の入力量の 84 倍だった**（14,452 字 対 173 字）。
  この量を別の窓へ出すと、人間は編集対象と説明を往復することになる。
  実測では、**なぜその日程にしたか**と**前言の訂正 7 件**が、すべて文書の上に残った。
- **設計の含意**: 説明の置き場所が**編集の邪魔をしてはならない**。畳めること・流れること。
- **なぜ会話を丸ごと保存しないか**（ユーザー判断）: トライアルの会話を見返すと、
  残す価値があったのは「なぜその手か」と「前言の訂正」だけで、**感想と雑談には無かった**。
  丸ごと保存すると**価値の薄いものが日程表に同梱され、プライバシーの懸念だけが残る**。
- **効果**: 変更 1 回につき 1 件なので**変更回数で自然に有界**。上限の設計が要らない。
- **代償**: **何も変更しなかったときの発言は残らない。** 意図して受け入れた。
- **範囲**: **MVP に入れる**（`OPEN-ITEMS-ja.md` 決定-2）。

## 6. 投入と出力

### A-13. 起動時に文書を埋め込める

単一 `.html` は、**起動時に読み込む文書の入れ口**（`embeddedDocumentHolder`）を最初から持つ。
エージェントはその入れ口を置換した複製を作ることで、**サーバなしで**
「GRS ＋ 文書」の 1 ファイル（**埋込文書つき GRS**）を生成できる。
**入れ口が運ぶのは文書だけであり、API の有効化は運ばない**（`OPEN-ITEMS-ja.md` 決定-4・決着-6 M2）。
**原本は読み取り専用として扱い、複製の名前は ASCII のみとする**（`agent-interface-spec-ja.md` §5-1・§5-1-2）。

- **由来（実測 2026-08-02）**: `file://` で開いたページは、**別のローカルファイルを取得できない**。
  兄弟ファイルへの `fetch` は `TypeError: Failed to fetch`、`XMLHttpRequest` は network error で、
  **どちらも拒否された**（`OPEN-ITEMS-ja.md` 決着-2）。
  `location.search` 自体は読めるので、**パラメータは受け取れるが中身を取りに行けない**。
  したがって **URL にパスを付ける方式は `file://` では成立しない**。
- **規約**: 注入する文字列の中の `<` を、JSON の Unicode エスケープ `\u003c` へ置き換える。
  しないと `</script>` の混入で HTML そのものが壊れる。
- **併記**: `http(s)` で配信する場合に限り、URL パラメータで**同一オリジンの相対パス**を読ませてよい。
  絶対 URL・スキーム付き・上位ディレクトリへの脱出は拒否する。

### A-14. 出力は値で返す

画面出力（`user-order.md` 58）と各形式の書き出しは、
**ダウンロードのダイアログを出さずに文字列や blob を返す**関数を持つ。

- **由来**: AI が「日程を確認して図を出す」には、人間向けの保存ダイアログが邪魔になる。
- **既存の正に従う**: 出力寸法・文字サイズ・倍率は `documentSettings` の値を使う
  （`02-data-model/grs-document-settings-ja.md`）。**API で別系統の設定を持たない。**

### A-15. 描画は純粋関数に保つ。成果物は当面 単一 `.html` だけ（**決定済み**）

**描画は DOM 非依存の純粋関数とする**（`document` に触らず SVG 文字列を返す）。
**ビルド成果物は当面 単一 `.html` のみ**とし、ライブラリ／CLI は出さない。

| 出力 | 中身 | 必要性 |
|---|---|---|
| 単一 `.html` | 全インライン・オフライン動作（**現行のまま**） | **必須**（`user-order.md`） |
| ライブラリ | ドメイン＋描画。`document` に触らず文字列を返す | **当面 出さない** |
| CLI | 変換・描画の薄い CLI | **当面 出さない** |

- **理由（ユーザー判断 2026-08-02）**: **純粋関数のほうが作りやすい。意図しない競合が起こらないから。**
- **成果物を絞る理由**: 決着-4 で **AI は `file://` のままブラウザ経由で全部できる**と分かり、
  「ブラウザ抜きで」の動機が薄れた。**純粋性さえ保てば、必要になった日に足せる。**
- **所在**: 判断するのは `NEXT-STEPS-ja.md` **ステップ 3**（`09-architecture/` は
  モジュール構成・技術スタックを**意図的な空白**にしている。**ここを埋めるのは次期**）。
- **注意**: 単一 `.html` の制約と矛盾しない（成果物が増えるだけで、アプリの動作条件は変わらない）。

## 7. 規約

### A-16. 将来のサーバ／機械連携は、この API の薄い包みにする

サーバを立てたときの機械向けの窓口は、**`A-1` の関数群と 1 対 1**にする。

- **由来**: `file://` では**ライブの共同編集は原理的に成立しない**
  （2 つのビューアが状態を共有できない）。
  したがって `user-order.md` 65-1 の共同編集は**サーバを前提とする**。
  そのとき窓口を作り直さずに済むかどうかは、**今この関数群を素直に決められるかで決まる。**
- **併記**: `A-3` の基準版の照合と `A-10` の revision スコープ監視は、
  **そのまま多人数編集の土台になる。** 2 者で成立した規約を人数だけ増やす形になる。

### A-17. 非 ASCII のデータをシェル引数に載せない

CLI を作る場合、**タスク名・行名・注記などの非 ASCII 文字列を引数で渡さない。**
ファイル・標準入力・HTTP ボディのいずれかを使う。

- **由来**: **実地で文字化けした。** Windows のコンソールのコードページが、
  プロセスに届く前にバイト列を壊す（`ai-cowork-trial-findings-ja.md` §3-2）。
  盤面の描画は無事だったので、**アプリ側では検出できない種類の事故**である。

### A-18. 呼び出しの粒度を粗くする

**1 回の呼び出しで「読んで・書いて・次に待つべき点を返す」**。
素直な CRUD を並べない。

- **由来**: 応答の遅さの主因は推論時間ではなく**往復回数**だった。
  5 往復を 3 往復にまとめて体感が変わった（`ai-cowork-trial-findings-ja.md` §3-3）。

| A-3 基準版の照合 | **6 回発火**・壊れた状態 0 件 | **実測** |

| A-12 会話と `changeLog` | 必要性は文字数比 **1 : 84** で実測／範囲は**ユーザー判断で決定**（決定-2） | **実測＋決定** |
| A-13 文書の埋め込み（経路） | `file://` からの `fetch` / `XHR` が**両方とも拒否されることを実測**（決着-2。2 エンジンで一致） | **実測** |
| A-13 文書の埋め込み（エスケープ規約） | **対照実験**: エスケープ無しでは JSON が壊れ、**内容が本文へ漏れた**（決着-5） | **実測**（Chromium 1228） |

| A-15 純粋な描画 | **ユーザー判断で決定**（`OPEN-ITEMS-ja.md` 決定-1） | **決定済み** |
| A-17 シェル引数 | **文字化けを実地で踏んだ** | **実測** |
| A-18 粒度 | 5 往復 → 3 往復 | **実測** |
| A-6 / A-7 / A-8 / A-9 / A-16 | 設計上の要請。トライアルで反証されていない | **提案** |

> **「実測」と「提案」を混ぜないこと。** 推測を断定で書くことが、
> `handover/` が防ごうとしている失敗である（`handover/README.md` §0-3）。
