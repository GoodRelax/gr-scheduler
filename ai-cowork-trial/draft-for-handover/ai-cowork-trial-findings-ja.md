# AI 共同編集トライアル — 実測と所見

- 日付: 2026-08-02
- 場所: `ai-cowork-trial/`（最小版）／ `ai-cowork-trial/shogi/`（実寸版）
- **この文書は事実の記録である。設計の決定はしない。** 提案は `agent-interface-requirements-ja.md`。

---

## 0. 何を確かめたかったか

**「人間と AI が、同じ 1 つの文書を、同時に見ながら編集できるか」**の一点である。
GRS でやりたいのは日程表の共同編集だが、日程表そのものを作ってから確かめると、
**うまくいかなかったときに原因が「共同編集の仕組み」なのか「日程表の実装」なのか分からない。**
そこで題材を切り離し、**共同編集の仕組みだけ**を裸で作った。

| 試作 | 題材 | 何を足したか |
|---|---|---|
| 最小版 | 3×3 の盤 | 共有状態・基準版の照合・SSE 通知・待機プロセス |
| 実寸版 | 9×9 の盤・持ち駒・棋譜 | **アプリ内チャット**・**Undo**・**ルールをサーバに一元化** |

**題材は共同編集の検証用であって、GRS の機能ではない。** 以下、題材の内容には立ち入らない。

## 1. 実測（実寸版・1 セッション）

サーバの最終状態から機械的に数えた値である。

| 指標 | 値 | 内訳 |
|---|--:|---|
| 最終 `revision` | **104** | 盤面の更新 **62** ＋ 会話の投稿 **42**。**両方が同じ 1 本の連番を進める** |
| 盤面の更新 | 62 | 着手 61 ＋ 終局宣言 1 |
| 会話 | 42 通 | **人間 9 通 / AI 33 通** |
| 会話の文字数 | 14,625 字 | **人間 173 字 / AI 14,452 字**。比 **1 : 84** |
| 基準版の照合による拒否 | **6 回** | 人間の投稿と AI の書き込みが同時更新になり、`baseRevision` 不一致で拒否 → 読み直して再送 |
| AI が自分の誤りを訂正した回数 | **7 回** | §4 に全数 |
| 開発チャットを経由した回数 | **0 回** | 手番の受け渡しは全て待機プロセスで行った |

**会話の文字数比 1 : 84 は設計に効く。** 説明する側（AI）の出力量は、
指示する側（人間）の 2 桁上になる。**説明の置き場所が編集の邪魔をしてはならない。**

## 2. 成立した仕組み

### 2-1. 単調増加する `revision` 1 本で全てを判定できた

盤面の更新と会話の投稿を**同じ連番**に載せた。これで次の 3 つが整数 1 個で片づいた。

- 相手が触ったか（`revision` が進んだか）
- どこまで自分は読んだか（`sinceRevision`）
- 自分の書き込みが古い前提に立っていないか（`baseRevision` の一致）

### 2-2. 基準版の照合は飾りではなく、6 回実際に効いた

**人間がチャットを打つのと AI が書き込むのが、実際に何度も同時更新になった。**
そのたびサーバが `baseRevision` の不一致を検出して**書き込みを拒否し、現在の文書を返した**。
AI は読み直して再送した。**壊れた状態は 1 度も発生していない。**

> 同時更新は「起こるかもしれない」ではなく **1 セッションで 6 回起きた**。
> 人間と AI が同じ文書に書く以上、**この仕組み無しでは成立しない。**

### 2-3. 手番の受け渡しに、開発チャットは要らなかった

AI 側は「相手が確定するまで終了しないプロセス」を走らせ、
**そのプロセスが終わることで自分が起きる**形にした。
61 手と 42 通を、**開発チャットを一度も経由せずに**回している。

**重要なのは通知の向きである。** 画面を光らせるのは push（SSE）だが、
**AI を動かしたのは push ではなく「ブロックして待つプロセス」だった。**

### 2-4. 確定の瞬間が 1 点に定まっていること

最小版では「マスを選ぶ」と「確定する」を分け、**確定を押すまでサーバへ何も送らない**ようにした。
実測で、選択・取消・選び直しを繰り返しても `revision` は動かなかった。

**これで「人間の編集が終わった時刻」が曖昧でなくなる。**
実寸版では移動先クリックが確定点なので、ボタンは置いていない。

## 3. 踏んだ不具合と対処（**ここが一番の収穫**）

### 3-1. 監視が revision スコープでないとビジーループになる

**症状**: 終局を検知して待機プロセスが終了 → AI が起きる → また待機を張る → **即座に終了** → 無限ループ。

**原因**: 待機の条件が「**今の状態**を見て判定する」だったため、
**既に処理済みの状態でも起きてしまう**。

**対処**: `--since <最後に読んだ revision>` を必須にし、
**それ以下の revision では絶対に起こさない**ようにした。修正後、終局済みの盤面では
3 秒待って正常にタイムアウトすることを実測で確認した。

> **規約**: 監視は「**私が最後に読んだ revision より後の変更だけ通知しろ**」でなければならない。
> 「今どうなっているか」を返す監視は、再武装のたびに空振りする。

### 3-2. 日本語をシェル引数で渡すと壊れる（Windows）

**症状**: AI が投稿した日本語のメッセージが、画面上で全て文字化けした。

**切り分け**: 盤面の漢字は正常に出ていた。**ページ側の問題ではない。**
コンソールのコードページが、コマンドに渡る前にバイト列を壊していた。

**対処**: AI が**発言する内容は UTF-8 のファイルに書いてから**送る経路に変えた。
ASCII だけのコマンドは引数で渡してよい。

> **規約**: **AI が製品へ渡す非 ASCII のデータを、シェル引数に載せてはならない。**
> ファイル・標準入力・HTTP ボディのいずれかを使う。
> GRS では**タスク名・行名・注記**が全て該当する。CLI を作るなら設計時点の判断である。

### 3-3. API の粒度が体感速度を決めていた

**症状**: 1 手あたりの応答が遅い。

**切り分け**: 遅さの主因は推論時間ではなく**往復回数**だった。
1 手ごとに「起床 → 状態を読む → 着手を送る → 発言を送る → 待機を張り直す」の **5 往復**が固定で発生していた。

**対処**: 「**書いて・喋って・次の待機点の revision を返す**」を 1 回にまとめ、**3 往復**にした。

> **規約**: `getDocument` → `applyCommands` → `exportSvg` と 3 回叩かせる素直な CRUD は遅い。
> **1 回の呼び出しで「読んで・書いて・次に待つべき点を返す」**設計にする。

## 4. AI が自分の誤りを訂正した 7 件

**共同編集の相手としての AI は、間違える。** 重要なのは
**間違いが同じ文書の上に残り、誰の発言かが分かること**である。全数を挙げる。

| # | 何を誤ったか | 種類 |
|:--:|---|---|
| 1 | 手順を「A を先」と書いたが、正しくは「B を先」だった | 手順の誤り |
| 2 | 「今すぐこう指す」と書いたが、支える駒が無く成立しなかった | 前提の欠落 |
| 3 | **相手の駒の利きを見落とし、駒をただ取られた** | 致命的な見落とし |
| 4 | 「これが一番痛い」と 2 回書いた脅威が、**そもそも成立しなかった** | 存在しない脅威 |
| 5 | 「次はこう受ける」と予告した手が、**指すと駒をただ取られる**手だった | 予告の撤回 |
| 6 | 逃げ場を列挙したとき、**1 マス数え落としていた** | 数え上げの漏れ |
| 7 | **自分の駒で自分の退路を塞いだ袋小路**へ逃げ込み、大駒を失った | #3 と同型 |

**#3 と #7 は同じ間違い方である。** 相手の駒の利きは 1 マスずつ数えるのに、
**自分の駒が自分の邪魔をしていることを見落とす。**

> **GRS への含意**: AI が日程を動かすなら、同じ種類の誤りが必ず出る
> （「他行との衝突は見るが、自分が今動かした結果できた制約を見ない」）。
> だから **AI の変更は人間が取り消せなければならない**（`A-4`）し、
> **なぜそうしたかが文書の上に残らなければならない**（`A-12`）。
> 上の 7 件は、**すべて盤の上のチャットに残っていて、あとから読み返せる。**

## 5. 確かめられなかったこと

**やっていないことを、やったように書かない。**

| 項目 | 状態 |
|---|---|
| **Undo（待った）** | **実装済み・未検証。** 両者の手を 1 本の履歴スタックに載せ、画面にボタンも出したが、**このセッションでは一度も押されなかった** |
| `file://` 直開きでの動作 | **決着済み**（§7）。残るのは「**人間が開いている画面**に外から入れるか」だけで、これは拡張が未接続のため測れず |
| 多人数 | **未実施。** 2 者・認証なし・localhost 限定でしか動かしていない |
| 同時更新の自動調停 | **未実装。** 「後勝ちを禁止し、読み直して再試行」しかしていない |
| 長時間・大文書 | **未計測。** 文書は小さく、セッションは 1 時間程度 |
| AI 側の復帰 | **未検証。** 待機プロセスは**セッションが終わると一緒に死ぬ**。取りこぼしなく追いつけるかは `sinceRevision` の設計上そうなるはず、というだけ |

## 7. `file://` の実測（2026-08-02 追測）

**測定環境は 2 系統ある。** §7 と §7-1 は **Microsoft Edge 151（Chromium）/ Windows 11** で
`ai-cowork-trial/file-protocol-probe.html` を `file://` で直接開いて人が操作した。
§7-2 は **Playwright の Chromium 1228** で外部から自動操作した
（`node ai-cowork-trial/file-protocol-automation-probe.mjs`）。**素の Chrome では未測定。**

| 測ったこと | 実測値 | 何が決まったか |
|---|---|---|
| `window.isSecureContext` | **`true`** | `file://` は secure context である |
| `showSaveFilePicker` / `showOpenFilePicker` / `showDirectoryPicker` | **すべて `function`** | ファイル保存の仕組みが存在する |
| `showSaveFilePicker()` を呼ぶ | **`AbortError`（利用者がキャンセル）** | **ダイアログは開く。** オリジンで拒否されるなら `SecurityError` になるはずで、ならなかった |
| 兄弟ファイルへの `fetch` | **`TypeError: Failed to fetch`** | **URL パラメータで文書を読ませる方式は `file://` では不可** |
| 同じファイルへの `XMLHttpRequest` | **network error** | 同上（別の方法でも同じ） |
| `location.search` | **読める** | パラメータは受け取れる。**中身を取りに行けないだけ** |
| 同名で 2 回ダウンロード | 1 回目 `grs-file-probe.json` / 2 回目 **`grs-file-probe (1).json`** | **保存先は聞かれず既定フォルダ。名前は尊重されるが上書きされない** |

### 7-1. 2 回目の追測 — 往復は実際に閉じた

1 回目では「ダイアログが開く」ところまでしか見ていなかったので、書き戻しまで通した。

| 測ったこと | 実測値 |
|---|---|
| ハンドルを取って書き込む | **成功** |
| **同じハンドルへの 2 回目の書き込み** | **成功。ダイアログは出なかった** |
| 同一セッション内の `queryPermission` | **尋ねる前から `granted`** |
| ハンドルを IndexedDB に入れて**リロード** | **残っていた** |
| リロード直後の権限 | **`prompt` に戻る** → `requestPermission` で **`granted`** → 書き込み成功 |
| 復帰ダイアログの選択肢 | 「この時間を許可する」「アクセスするたびに確認する」「許可しない」。**「常に許可」が無い** |
| 既存ファイルを開いて書き戻す | **129 バイト読取 → 196 バイト書戻し、成功** |
| **ディスク側** | **ファイルは 1 本だけ。同じパスに上書きされ、` (1)` は作られていない** |

**設計への影響は 3 つある。**

1. **往復は 1 本のパスで閉じる。** 「AI が書く → 人間が開いて編集 → **同じファイルへ上書き** → AI が読み直す」が
   **実測で成立した**。測る前は「使えないかもしれない」側に賭けていた部分である。
2. **同じ「ファイルを書き出す」でも、経路が違えば挙動が正反対だった。**
   ダウンロードは上書きされず ` (1)` が増える。保存の仕組みは同じ場所を上書きする。
   **「編集中のファイル」を持つなら後者しかない。**
3. **代償は起動ごとの 1 クリック。** リロードで権限が `prompt` に戻り、
   `file://` の復帰ダイアログには「常に許可」が無いので、**この 1 クリックは省けない。**
   起動時に「編集中のファイルへのアクセスを復帰しますか」を出す設計になる。

### 7-2. 3 回目の追測 — 外部からの操作と、エスケープ規約の対照実験

Playwright の Chromium で `file://` のページを開き、**外部プロセスから**中を操作した。
再現は `node ai-cowork-trial/file-protocol-automation-probe.mjs`。

| 測ったこと | 実測値 |
|---|---|
| `file://` への遷移 | **成功** |
| ページ内から見た `location.protocol` / `origin` | **`file:` / `file://`**（本物の file オリジン） |
| **外部からページ内の関数を呼ぶ** | **成功。** `applyCommands` 相当が `{accepted:true, revision:1}` を返した |
| その呼び出しが画面を変えたか | **変わった** |
| `file://` のページのスクリーンショット | **取得できた** |
| 兄弟ファイルの `fetch`（別エンジンでの再確認） | **BLOCKED** — Edge と同じ |

**これで、当初やりたかったことは `file://` のまま全部できることになった** —
AI が GRS を起動し、API を呼び、画面を見て、書き出す。サーバも拡張も要らない。

> ⚠️ **測ったのは「AI が自分で開いたブラウザ」である。**
> **人間が開いている画面**に外から入れるかは別の測定であり、**7-4 で成立を確認した。**

**そして、エスケープ規約を対照実験で確かめた。**
タスク名に `</script>`・`<b>bold</b>`・`&`・日本語を入れた同じ payload を、
**エスケープ有りと無しの両方**で注入して読み比べた。

| | エスケープ **有り** | エスケープ **無し** |
|---|---|---|
| 起動時に読めたか | **読めた** | **読めない** |
| 往復の同一性 | **完全一致** | — |
| 失敗の中身 | — | `Unterminated string in JSON at position 76` |
| **ページ本文への漏れ** | 無し | **`bold` が本文に出た** |

**規約は経験則ではなく必須だった。** しかも失敗の仕方が悪い。
`</script>` が早期にタグを閉じ、**残りが HTML として解釈されて本文に出る。**
つまり**埋め込みはテンプレート処理であり、エスケープを怠れば注入が成立する**
（`user-order.md` 62 と同じ土俵）。

### 7-3. 4 回目の追測 — 公開は止められるのか、止めたあと戻せるのか

再現は `node ai-cowork-trial/agent-api-exposure-probe.mjs`。
測定用のページは **GRS ではなく最小の代役**（インターフェースはモジュール内、入れ口は `null`）。

| 測ったこと | 実測値 |
|---|---|
| 何もしないときの公開点 | **`undefined`** |
| `agent` を含むグローバル名の全数 | **`ondragenter` / `originAgentCluster` の 2 つだけ**（ブラウザ標準。漏れは無い） |
| 起動側が起動前にフラグを置いたとき | **公開された**（呼び出し成功） |
| そのとき**入れ口**は | **`null` のまま** |
| そのとき**ディスク上のファイル**は | **バイト数不変＝無改変** |
| `file://` の URL に付けたクエリ | **届いた**（`"?agentApi=1"`、値 `"1"`） |
| **名前を消したあとの、渡し済みの参照** | **動き続けた** |

**3 つ分かった。** ① モジュール内に置く限り外から名前で辿れない ② **有効化はファイルを変えずにできる**
③ **一度渡した参照は取り返せない**。③は「あとで切れるから安全」という設計を禁じる。

### 7-4. 5 回目の追測 — **人間が開いている画面**に外から入る

前回の残件（外から入れるのは AI 自身が開いた画面だけか）を閉じた測定である。

**人間が** Edge をデバッグポート付き・使い捨てプロファイルで起動し、`file://` のページを開き、
**`わたしは人間だ` と入力し、有効化ボタンは押していない**状態から、外部プロセスが接続した。
再現は `cowork-live-probe.html` を開いた状態で `node ai-cowork-trial/cowork-live-attach.mjs`。

| 測ったこと | 実測値 |
|---|---|
| 人間が起動したブラウザへの接続 | **成功**（タブ 3 枚） |
| 掴んだページの `protocol` / `origin` | **`file:` / `file://`** |
| **人間が打った文字を外から読む** | **読めた**（`"わたしは人間だ"`） |
| **有効化の前**に API へ届くか | **届かない**（`undefined` / `TypeError`） |
| **有効化の後** | **届いた** |
| 正しい `baseRevision` での書き込み | **受理。`revision 1 → 2`。人間の画面のテキストが実際に変わった** |
| 古い `baseRevision` での書き込み | **拒否**（`stale-base-revision` ＋ 期待した版 ＋ 現在の文書） |

**分かったこと。** **人間の画面に外から入れる。** ただし**起動時にデバッグポートを開けていること**が前提で、
これは後から付けられない。**関門は二重**（起動時のフラグと画面での有効化）で、**後者が無ければ前者だけでは届かない。**
**基準版の照合はこの経路でもそのまま働いた。**

> ⚠️ **ブラウザ拡張の経路は最後まで測れていない**（拡張が未接続のままだった）。
> ただし「入れるか」の答えは本測定で出ている。

### 7-5. 6 回目の追測 — `file://` の保管庫は 1 つしかない

起動順序（どれを開くか）を決める前に、**自動保存がどこに置かれるのか**を確かめた。
再現は `node ai-cowork-trial/startup-storage-probe.mjs`。

| 測ったこと | 実測値 |
|---|---|
| `file://` で localStorage は使えるか | **使える**（`location.origin` は `file://`） |
| **同じフォルダの別ファイル**から見えるか | **見える** |
| **別フォルダのファイル**から見えるか | **見える** |
| IndexedDB も同じか | **同じ**（別フォルダが書いた値を読めた） |
| **ブラウザを完全に落として再起動**したら | **残っていた** |

**分かったこと。** **ローカルファイルはパスに関係なく 1 つの保管庫を共有する。**
つまり **GRS の複製どうしが自動保存を奪い合う**し、**任意のローカル HTML ページが日程を読める。**
前者は「鍵を文書ごとに分ける」で解け、**後者は `file://` である限り解けない**
（`http(s)` で配信すれば本物のオリジンになり消える）。

**この 1 回の測定で、起動順序より先にキー設計が決まった。**
測らずに決めていたら、**2 窓同時のときに黙って上書きし合う**設計になっていた。
