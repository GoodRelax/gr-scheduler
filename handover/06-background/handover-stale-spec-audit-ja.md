## 3. 凍結資産どうしの不整合（**今回発見**）

### 3-1. 【訂正】フィールドキーの記法差は**設計どおり**。真の衝突は 1 点だけ

> ⚠️ **本項は初版の誤りを訂正したもの**。初版は「snake_case と camelCase が食い違っている」と書いたが、**これは規則どおり**だった。

`glossary.md` §2「識別子の導出規則」に**面ごとの記法**が定められている:

| 面 | 記法 | 例 |
|---|---|---|
| JSON 文書のプロパティ名 | **camelCase** | `fadeInDays` |
| i18n キー・**プロパティパネルの項目名** | **snake_case** | `fade_in_days` |

したがって `PROP-L1-002` の `start_date`（プロパティパネルの項目名）と `40-data-format` の `startDate`（JSON）は**同じ概念の別の面**であり、矛盾ではない。対応表は `glossary.md` §10 にある。

**真の衝突は「予定日付の名前」1 点**:

| 系統 | 予定 | 実績 | 出典 |
|---|---|---|---|
| 現行 JSON | `startDate` / `endDate` | `actualStart` / `actualEnd` | `schema.json` |
| **用語集の確定目標（D-9）** | **`planStart` / `planEnd`** | `actualStart` / `actualEnd` | `glossary.md` §12 D-9（改名予定） |
| **今回の GRS モデル** | **`start` / `finish`** | `actualStart` / `actualFinish` | `grs-native-erd-ja.md` |

**D-9 の確定理由**: 実績が `actualStart`/`actualEnd` と明示されるのに、予定が `startDate`/`endDate` では**非対称**。だから `planStart`/`planEnd` にする、という判断（ユーザー確定済み）。

**今回の設計はこれを覆している**（MSPDI の `Start`/`Finish` に合わせたため）。しかも `refactor-gui-data-separation-ja.md` は**この衝突を事前に指摘**していた:

> 「MSP は `Start`/`Finish` + `ActualStart`/`ActualFinish`。これは非対称で、まさに直前 (D-9) で却下した形。**MSP 準拠は D-9 を覆す**。→ 推奨は『MSP の意味と被覆に準拠しつつ、**内部の命名は対称に保ち**…』」

→ **決着済み**: `../03-ui-naming/handover-ui-parts-ja.md` §5-1（予定 = `start`/`finish`、実績 = `actualStart`/`actualFinish`）。

### 3-2. ID 生成規則が二重定義

`15-classification-sections` **SECT-L2-002** は「複製された行・アイテム・依存線は**すべて新規 ID を持つ**」とし、`DATA-JSON-003/004/005` の ID 生成に委ねている。一方、今回の設計は **UID を PK とし、高水位で単調増加採番・GRS 生まれは照合対象外**という規則を確定した。

> **引継ぎへの含意**: **ID 生成は今回の規則に一本化**する（`grs-native-erd-ja.md` §5.3）。複製時は「GRS 生まれ扱いで新規採番」となり、SECT-L2-002 の意図（原本に影響しない）は満たされる。

## 4. 次期で**統合が必要**な論点（矛盾ではないが未整理）

### 4-1. 【訂正】「セクション」は**既に廃止済み**。残る論点は TaskGroup との対応づけ

> ⚠️ **本項も初版の誤りを訂正**。初版は「分類 / セクション / 行 の 3 概念が未整理」と書いたが、**セクションは廃止済み**だった。

`glossary.md` §7 の冒頭:

> **Section の概念は廃止した (D-3/4/5 確定)**。行のまとまり・畳み・並べ替え・表示切替は、最上位の分類 (activity major category) が担う。分類は 3 層に一本化し、`Activity` を接頭辞に付ける。旧語 (section / classification / track / detail) はすべて廃止する。

現行の確定モデル（3 概念）:

| 語 | 意味 |
|---|---|
| **activity major/middle/minor category** | 分類の 3 層。**最上位が畳み・並べ替え・表示切替の単位**（旧 section を兼ねる） |
| **row**（行） | 見出しパネルの 1 項目と、対応するキャンバスの帯（ribbon） |
| **lane**（レーン） | 行の中でアイテムが重ならないように積まれる段（`laneIndex`） |

**今回の設計との対応**（＝これが残る論点）:

| 現行（確定済み） | 今回の設計 | 差 |
|---|---|---|
| 分類 3 層 ＋ row | **`TaskGroup`（入れ子 ≤Lv5）** | **今回は層数を 3 固定から ≤5 へ一般化**。row と分類ノードを 1 つの再帰構造に統合した |
| `laneIndex` | **`TaskGroupMember.stack_order`** | 同概念。名前が違うだけ |

→ **同じものを別名で呼んでいる**。Step 2 で用語を一本化する。

### 4-2. 「ぬるサク UI」の要求が要求文に落ちていない

最優先ポイント（ユーザー明言）だが、`.sdoc` の NFR は数値目標（60fps・初期表示 1.5s）に留まる。**何をすると遅くなるか**という実装知が要求に紐づいていない。

> **引継ぎへの含意**: Step 4（性能・実装ノート）で**「効いた手／踏んだ罠」を独立文書化**し、`user-order.md` からも参照する。
