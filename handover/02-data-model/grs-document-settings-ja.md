## 1. 保存するかどうかの判定 — 検査 1 つで決まる

```
その値を変えたとき、画面の表示 または 出力（SVG / PNG）が変わるか

  変わる    →  documentSettings に入れる（JSON に書く）
  変わらない →  入れない（読む人の環境。localStorage に置くか、製品の定数にする）
```

**判断ではなく検査である。** 迷う余地が無く、CI で機械的に検証できる（§8）。

> **なぜこの基準か**: 「**JSON を読んだらいつでも同じ結果を表示し、同じ結果を PNG / SVG に出力する**」
> がこのツールの中心的な要求だから（`user-order.md` 項 57）。
> 画面と出力は**同じ 1 組の設定から描く**。出力用に別の設定を持つと WYSIWYG（最優先事項 5）が壊れる。

---

## 2. 方針 — **常に全項目を書き出す**（確定 2026-07-31・ユーザー判断）

```
JSON には、既定値から変えていない項目も含めて 全項目を書く
```

**採らなかった案**: 既定値から変わったものだけ書く（疎な上書き）。

| | 常に全項目（採用） | 疎な上書き（不採用） |
|---|---|---|
| 同じ JSON → 同じ出力 | **明示的に保証される** | 既定値の解決規則に依存する |
| 実装 | 欠けた項目の分岐が要らない | 既定値の解決が要る |
| 差分レビュー | **何が効いているか一目で分かる** | 書かれていない項目の意味が読めない |
| 次期が既定値を改善したとき | **古い文書には届かない**（凍結される） | 古い文書にも届く |

**凍結は代償ではなく目的である。** 「同じ JSON からいつでも同じ出力」を成立させるには、
作成時点の値が固定されている必要がある。**だからこそ、凍結する価値が無い項目
（画面にも出力にも出ないもの）は入れない**（§5）。

### 4-2. 画面の状態 — **2026-07-31 に「保存しない」から移した**

| キー | 型 | 意味 |
|---|---|---|
| `themePreference` | `'light'` / `'dark'` | 明暗テーマ |
| **`themeHue`** | 0〜359 | **テーマの色相**（予定・実績・行の帯・地の色がここから決まる） |
| **`themeMonochrome`** | 真偽 | **モノクロにするか**（既定 `false`） |
| `zoomX` / `zoomY` | 数値 | 横 / 縦のズーム倍率 |
| `scrollDate` | 日付 | 表示の左端が指す日付 |
| `scrollRowUid` | 行の識別子 | 表示の上端が指す行 |
| `leftPaneWidth` | px | Row Title Panel の幅 |
| `propertyPanelWidth` | px | Properties Panel の幅 |

**なぜ移したか**: **「人に見せたい場所」を文書が持てないと WYSIWYG が成立しない**（ユーザー判断）。
全体を見たい人は `Fit` ボタンを押せばよい。

> **スクロール位置は px で持たない。** ズームや画面幅が変わった瞬間に別の場所を指すため、
> **日付 ＋ 行の識別子**で持つ。`Comment` の位置が同じ規則を採っている（`user-order.md` 項 44）。

> ⚠️ **`fontScale` と同じ注意が `themePreference` にも要る。** 保存値は**初期値**であって、
> **読む人は変更できること**。WCAG 1.4.4（文字サイズ）と 1.4.3（コントラスト）は
> 強制されないことを要求する。**変更したら文書の編集になる**（保存される）。

**`themeHue` / `themeMonochrome` を保存する理由** — **確定 2026-08-01**

**色のテーマはプロジェクトのテーマカラーである**（ユーザー判断）。
どの色でこの日程表を見せるかは**作った人の決めごと**であって、読む人の環境ではない。
`themePreference`（明暗）と同じ枠に入る。

**派生する色は保存しない。** 地の彩度と、色相ごとの明度の寄せ幅は、
**`themeHue` と `themePreference` から contrast 規則で解いて求める**（下記）。
解いた結果を保存すると、規則を直したときに古い値が残って**規則と絵が食い違う**。

```
保存する    themeHue / themeMonochrome / themePreference
解いて出す  地の彩度 ／ 予定・実績・輪郭線の明度の寄せ幅
規則        「色相ごとに、contrast 規則が壊れる寸前まで濃い地色」
```

> **色相によって解が違う。** 黄の明度 46% は青の 46% よりずっと明るいので、
> 青（§2-6 の確定色）用の明度をそのまま 10 色相へ当てられない。
> **必要最小の寄せだけを掛ける**ので、確定済みの青は寄せ幅 0 で無傷になる。
> 実測は `../08-poc/poc-integrated.html` の「色と縁取り」タブ（40 通りで不合格 0）。

| 予定の端点の掴み代 | バーの上下に 6px | **WCAG 2.5.5（ターゲットサイズ）は「読む人が操作できるか」を問う。** 手が震える人・タッチ操作の人には大きな掴み代が要る。文書が強制してよい値ではない |
| 実績の端点の掴み代 | 実績バーの帯 | 同上 |
| フェード掴み点の当たり判定 | 15 × 15px | 同上 |
| ダミーの実績線の当たり判定 | 30 × 20px | 同上 |

**端末の資源に属する** — 出典は同書 §8。

| 値 | 既定 | 保存しない理由 |
|---|--:|---|
| Undo の回数 | 50 | 動いている端末のメモリ予算。**履歴自体を保存しない**と確定済みなのに、回数だけ文書が指定するのは筋が通らない |
| Undo の合計メモリ上限 | — | 同上 |

**操作の速さであって結果ではない** — `../08-poc/poc-integrated.html` の `SPEC` で ⛔ を付けた 3 項目。

| キー | 既定 | 保存しない理由 |
|---|--:|---|
| `zoomStep` | ×1.1 | 1 ノッチで何倍動くかは**入力装置**（ホイール / トラックパッド）に依存する。**結果の絵は変わらない** |
| `zoomMin` | 0.02 | 同上。倍率そのものは保存する（§4-2）ので再現性は損なわれない |
| `zoomMax` | 64 | 同上 |

### 5-2. 別枠 — `localStorage` に置く

**`language`（`ja` / `en`）**

**絵が変わらないから保存しない。** 多言語の対象はメニューやパネルの文字（項 21）で、
**日程表の出力には含まれない**。タスク名・行名は**データ**であって翻訳対象ではない。

保存すると、日本語で作った文書を英語の利用者が開いたときに**メニューまで日本語になる**。
項 21 の「どの言語で開くかは読む人の環境」と正面から衝突する。

> **`localStorage` が読めないときはブラウザの言語設定に従う。** `file://` で開くと
> `localStorage` を拒否するブラウザがある。自動保存（項 60）も同じ依存を持つ既知のリスクだが、
> `language` には必ずフォールバックを持たせる。

### 5-3. 別枠 — 保存も `localStorage` もしない

**透かし（`watermark`）** — **WYSIWYG に対する唯一の意図的な例外**。

透かしは「Web 会議で秘密の日程を撮影されたときの**証跡**」（項 55）である。
証跡として意味があるのは「**誰がいつ画面に出していたか**」なので、
**開いた人の名前と日時で描かれるのが正しい**。作者の名前が焼き付いて他人の画面に出るのは、
証跡としては**誤り**である。

```
ユーザー名   localStorage（その人の環境設定）
日時         実行時に生成（RFC 3339 UTC・項 55-1）
hideHash     .html に埋め込み（項 55-3）。文書には持たない
```

## 6. 範囲は他の設定に追随する

§3 の「下限 / 上限」列には**他のキーが現れる**。設定できる範囲は固定ではない。

**相互に縛り合う対が 3 組ある。**

```
dependencyWidth      ↔  stackGap          stackGap ≧ dependencyWidth x 2 ／ dependencyWidth ≦ stackGap ÷ 2
thinStrokeMin ↔  thinStrokeMax    互いが互いの上限・下限
zoomMin       ↔  zoomMax          同上（ただし両方とも保存しない）
```

**片方を動かすともう片方の範囲が動く。** UI で編集させるときは**毎回両方の範囲を引き直す**こと。
片方だけ検証する実装は必ず矛盾した組を通す。

**縦の下限は 1 か所だけに置く**（`../03-ui-naming/handover-ui-detail-spec-ja.md` §4-10-3）。
予定と実績の両方をクランプすると、下限に当たった側だけが止まって**比率が仕様から外れる**。

**実際に触れる**: `../08-poc/poc-integrated.html` の「設定・プロパティ」パネル。全項目を個別に変えられ、
範囲は他の設定に追随して引き直される。範囲外の値も入力できる（何が壊れるかを見るため）が赤で示す。

## 7. 本日線は保存しない — 確定 2026-07-31

**`todayLineVisible` を `documentSettings` から外した。**

**理由**: 本日線の位置は**実行時のシステム日付**なので、保存すると
「**同じ JSON → 同じ表示**」が**明日には破れる**。この 1 項目のためだけに例外を作ることになる。

**代わりにカーソルを使う**（ユーザー判断）。

## 8. 自動保存と往復の検査

### 8-1. 自動保存 — 暇なときに、まとめて 1 回

**変更のたびに書いてはならない。** 段階 7 の PoC で **10000 タスクを 1 回描くのに 147〜202ms**
かかった（`../08-poc/POC-RESULTS-ja.md` §D-2）。文書を JSON 化して `localStorage` に書くコストは
これと同等以上とみてよく、**60fps の予算 16.7ms を 10 倍以上超える**。
スクロール中に割り込ませれば必ずフレームを落とす。

```
変更が起きるたびに  requestIdleCallback(保存, { timeout: 5000 })  を予約し直す

  暇になったら保存する          ブラウザに聞く。固定の秒数を当てずっぽうで決めない
  暇が来なくても 5 秒で保存する  スクロールし続けると idle が永久に来ないため
  予約し直すので連続操作は 1 回に畳まれる
```

- **`timeout` は 5000ms**（確定 2026-07-31・ユーザー判断）。
- **帰結**: クラッシュ時に**最大 5 秒ぶんの編集が失われる**。承知の上の判断である。
- `requestIdleCallback` が無い環境では `setTimeout` へ落とす。

> **書き込みが重いなら秒数をいじっても解決しない。** 次を実測すること。
>
> | 測ること | 判定 |
> |---|---|
> | 1000 タスクの文書を JSON 化して `localStorage` に書く時間 | **16.7ms を超えるか** |
>
> 超えるなら、**書き込みを分割する**か、**表示状態を本体と別キーに分けて小さく書く**。

### 8-2. JSON 往復の検査 — CI に入れる

**`documentSettings` は MSPDI に出ない**ので、**項 56（MSPDI 往復無損失）は影響を受けない**。
スクロールしても MSPDI の往復は 1 バイトも変わらない。

決めが要るのは **JSON 往復のテストの書き方**である。JSON には `documentSettings` が入るので、
「開く → 書き出す → バイト一致」というテストを書くと、**スクロールしただけで落ちる**。

| # | 検査 | なぜ |
|:--:|---|---|
| 1 | **データ部**（Task / TaskGroup / TaskGroupMember / 依存 / 注記 / Carry）を**完全一致**で比較する | ここが壊れたら文書が壊れている |
| 2 | `documentSettings` は**比較対象から外す**。代わりに **SVG 出力の一致**で再現性を見る | 表示状態は変わってよい。**再現するかどうか**が要件（項 57） |
| 3 | `documentSettings` に**全項目が書かれている**ことを検査する | §2 の方針。欠けたら「同じ JSON → 同じ出力」が保証できない |
| 4 | 各項目が **§3 の範囲内**にあることを検査する | 範囲は他の設定に追随する（§6）。範囲外の組は描画を壊す |
| 5 | **保存しない 8 項目が JSON に現れない**ことを検査する | §5 の分類が守られていることの機械的な確認 |
| 6 | **保存しないと分類した値を変えて、SVG 出力が変わらない**ことを検査する | §1 の判定基準そのものの検証。**分類の誤りを機械が見つける** |

> 検査 6 が要である。§1 を「判断」ではなく「検査」にしたのは、**分類の誤りを人のレビューに頼らない**ため。
