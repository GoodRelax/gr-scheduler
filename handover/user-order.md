# ユーザーオーダー

> **この文書について**
> 前プロジェクト（gr-scheduler 第1次）の知見を織り込んだ**次期開発の入力**である。

## 何を作りたい？

1つの `.html` でブラウザだけで動作する**日程表作成ツール**。
パワポで日程表を書く作業とほとんど同じ操作感でありながら、成果物は画像ではなく **JSON / MSPDI XML** の構造化データを持つ。

## それはどうして？

- パワポや Excel で日程表を書くのは非効率。
- 既存の日程管理ツールは使いにくい。
- 調査した既存ツールはいずれも **1 行に複数のマイルストーンやタスクを入れられない**ため、**1 対象＝1 行＝全フェーズを 1 枚で俯瞰**する日程表を表現できない。（ツール比較の調査記録は前プロジェクトのリポジトリにある。特定製品の評価を含むため本フォルダには入れていない）

## アイテム（タスク / マイルストーン）

10. 既定の**タスク形状**（`shapeKind`）を提供すること。

    | 表記 | 名前 | 上下の幅 |
    |---|---|:--:|
    | `===` | 矩形（`rectangle`） | **あり** |
    | `>===>` | 矢羽根（`chevron`） | **あり** |
    | `--->` | 矢印（`arrow`） | なし |
    | `*----*` | 端点スパン（`endpointSpan`） | なし |
    | 〇 △ ▽ □ ☆ 五角形 六角形 | マイルストーン（`milestone = true`） | なし |

    - **実績は予定と同じ形状で描く。** 予定が矢羽根なら実績も矢羽根。実績だけ四角にしない。
    - **上下に幅があるタスク形状は実績を内側に重ね、幅がない矢印 / 端点スパンは実績を下にずらす。
      マイルストーンは実績日の位置へ横にずらす**（確定 2026-08-01）。
      詳細は `07-plan-actual/handover-plan-actual-decisions-ja.md` §2-2。
    - ※両端を縦棒で示す細線（`|---|`）は**廃止**した。`*----*`（端に点を打つ）に置き換える。
11. **（欠番）** ~~絵文字~~ — **取り下げ**。「やらないこと」へ移した。
12. アイコンは**枠の色と塗りつぶしの色を個別に**選択できること。
13. **線の太さ**（細/中/太）を選べること。※色だけに頼らない識別手段として必須。
14. **（欠番）** ~~アイコンのインポート（SVG / PNG）~~ — **取り下げ**。「やらないこと」へ移した。
15. マイルストーンやタスクを**コピー&ペースト**できること。
16. アイコンの移動に連動してプロパティが自動で変わること。
17. マイルストーンやタスクの内部または付近に、**その `Task` の名称（`name`）**を表記できること。
    - ※**略称は廃止**した。MSPDI に `Name` と `Notes` しかないため、**テキスト列を増やさない**方針にした（項 20）。
    - **表示上限は全角 12 文字 / 半角 24 文字相当**。超えたら半角 `...` で打ち切り、**ツールチップで全文**を出すこと。

    - 位置は **9 点アンカー ＋ 左詰め/中央/右詰め**で指定する。**既定は自動配置**で、人が動かしたときだけ指定が残る。
    - ※ピクセル座標では持たない。縦横独立ズームでずれるため。

## プロパティ

19. `Task` にプロパティを設定できること。
20. プロパティは以下を含むこと。**編集画面の項目名は英語固定**（項 22）。

    | 項目名（英語・確定） | 日本語 | 備考 | MSPDI |
    |---|---|---|---|
    | `name` | 名称 | | `Task/Name` |
    | `notes` | 備考 | **説明と備考は 1 つに統合**する（下記） | `Task/Notes` |
    | `start` / `finish` | 開始日 / 終了日 | **予定**の日付 | `Task/Start` `Task/Finish` |
    | `actualStart` | 実績開始日 | | `Task/ActualStart` |
    | **`actualDuration`** | **実績期間** | **実績バーの長さそのもの**（稼働日数）。右端は `actualStart` ＋ これ | `Task/ActualDuration` |
    | `actualFinish` | 実績終了日 | **完了したときだけ入る**。同じ `Task` が持つ（別アイテムにしない） | `Task/ActualFinish` |
    | **`resume`** | **再開予定日** | 中断したときだけ入る | `Task/Resume` |
    | **`resumeValid`** | **再開可否** | `false` = 再開日未定の中断（＝中止） | `Task/ResumeValid` |
    | **`percentComplete`** | **完了率** | **整数・0 以上**（通常 0〜100）。`actualDuration ÷ 予定期間` から算出して格納する | `Task/PercentComplete` |
    | `deadline` | 期限 | 「この日までに終える」独立マーカー。終了日とは別 | `Task/Deadline` |
    | **`shapeKind`** | **タスク形状** | 項 10 | **無い** → JSON のみ |
    | `strokeColor` / `fillColor` / `lineWeight` | 線色 / 塗り色 / 線の太さ | | **無い** → JSON のみ |
    | `nameAnchor` / `nameAlign` | 名称アンカー / 名称の揃え | 9 点アンカー ＋ 整列 | **無い** → JSON のみ |
    | `fadeInDays` / `fadeOutDays` | フェードイン日数 / フェードアウト日数 | バー端をぼかして日付の曖昧さを表す | **無い** → **拡張領域（唯一）** |
    | `wbs_parent_uid` | WBS の親 | 軸A。階層の深さはここから導出する（LOD に使う） | `Task/OutlineLevel` へ導出 |
    | （表示のみ） | 担当者 | **`Assignment` → `Resource.name` から導出して表示**（自由入力欄は持たない） | `Resource/Name` |

    > **`stop`（中断日）は保存しない。** 中断したときの実績バーの右端と同じ値なので、
    > MSPDI へ書き出すときに算出する（`Task/Stop`）。
    > **`progressStatus` と `importance` は廃止した**（用語節）。
    > **拡張領域を使うのは `fadeInDays` / `fadeOutDays` の 2 つだけ**になった。

    > **`fullName` / `description` / `remarks` の 3 語をやめる**。MSPDI 側は `Name` と `Notes` の 2 つしかないため、
    > **`name` ＋ `notes` に寄せる**。テキスト列を 5 つ持つと往復で必ず溢れる。
    >
    > **MSPDI に無い項目をどこへ置くか**は複数案を比較して結論を出した。
    > → 別紙 `02-data-model/handover-property-mspdi-mapping-ja.md`（全項目の対応表・3 案の比較・推奨案）

21. プロパティは**多国語対応**すること。
    - 対象言語は **en / ja の 2 言語**とする（それ以上は広げない）。
    - 表示言語の項目名は **`language`**（値 `ja` / `en`）。※「ロケール」は位置を連想させるので使わない（項 66）。
      **どの言語で開くかは読む人の環境**であり、文書には保存しない（別紙 `02-data-model/grs-native-erd-ja.md` §5.7-1）。
    - 文字コードは **UTF-8・BOM なし**。JSON は RFC 8259 が BOM の付加を禁じている。MSPDI XML も UTF-8・BOM なしで `<?xml version="1.0" encoding="UTF-8"?>` を出す。
    - ※ブラウザの File API は既定で BOM を付けない。**何もしなければ正しい**。「Excel 互換のため BOM を付ける」実装を入れてはならない（MSPDI が壊れる）。
22. プロパティ編集時の**項目名は英語表記**とすること。

## 行と階層

26. `Task` を分類する**水平線**（Group Grid Lines）を引けること。
27. **`TaskGroup` は階層を持てること**（大分類 > 中分類 > 対象 のように入れ子にする）。
    - **推奨 3 段、最大 5 段**。「大/中/小」という専用語は持たず、**深さで表す**。
    - 階層の単位で**畳み・並べ替え・表示/非表示**ができること。
    - ※前プロジェクトにあった「セクション」という別概念は**廃止**した。`TaskGroup` の階層がその役割を兼ねる。
    - **画面左（Row Title Panel）で階層を移動したら、元データ（MSPDI）の階層にも反映されること。**
      階層も親も移動する。**ただし `UID` は保持**する（相手ツールで新規タスクにならないため）。
    - 一方、**バーを別の行へ移す操作（マルチバー化）は元データを変えない**こと。**この非対称が要**。
    - 器（行）の既定名・生成規則は別紙 `02-data-model/grs-data-model-ja.md` §7.1-1、
      移動時の追随規則は同 §7.1-2 が正。
28. 非表示にした `TaskGroup` は、**親の**小タブ（Hidden Group Tab）で再表示できること。
    - 畳み/展開は**エディタのツリーと同じ操作体系**とする: **全展開 / 全畳み / 子を全展開 / 子を全畳み / 自分を畳む**。
    - 非表示が増えても**水平線の幅を太くしない**。
29. **Row Title Panel**（`TaskGroup` の見出し）を Schedule Canvas の**左側**に表示できること。
30. **1 行（1 `TaskGroup`）の中で時間が重なる `Task` は自動で縦に積む**こと。規則は次のとおり。
    1. **重なり判定は描画上の占有幅**で行う（日付だけでなく、**はみ出すラベルの幅も占有に含める**）。
    2. **積む順序は決定的**とする: `milestone` を優先 → `start` 昇順 → `finish` 降順 → `uid` 昇順。
       ※決定的でないと再描画のたびに段が入れ替わる。
    3. 各 `Task` を、**その段の既存 `Task` と重ならない最も浅い段**へ置く（貪欲割当）。
    4. **最上段にマイルストーン**を置く（下のタスク群から上のマイルストーンへ依存線が立ち上る構図）。
    5. 積む向き（上/下）は**文書全体**で選べること。既定は上。
    6. **人が `stackOrder` を指定したらそれを優先**する（`null` = 自動）。
    7. **積み順（`stackOrder`）に機能上の上限は設けない。必要なだけ広げる。**
       暴走を止める安全弁として十分に大きい上限を持ち、通常運用では到達しない値にする。
       到達したら人に知らせる（項 61 と同じ考え方）。
       ※**「最終段を再利用する」（重なりを許して同じ段に押し込む）挙動は廃止した。**
       マルチバーが本ツール最大の差別化である以上、勝手に重ねてはならない。
    8. **行の帯高は積み順の数で決まる**（積みが増えた行は下の行を押し下げる）。行高固定を前提にしてはならない。
31. `Task` の位置を**揃えられる**こと。**縦と横で仕組みが違う**。
    - **縦（同じ高さに揃える）は自動**。項 30 の段割当の結果として、同時に始まるタスク・同種のマイルストーンが同じ段に来る。
    - **横（同じ日付に揃える）は Command Palette の整列コマンド**で人が実行する。

## 時間軸・ズーム

32. **Time Ruler**（Schedule Canvas 上端の目盛り）に、**表示中の期間の**年 / 月 / 日 / 曜日を表示できること。
    - ※`App Header` とは**別物**。`Time Ruler` は横スクロール・横ズームに追従し、縦スクロールでは動かない。
33. 拡大縮小で `Time Ruler` の粒度が**自動で切り替わる**こと。**閾値は 1 日あたりの表示幅（px/day）で決める**。
    **4 段階**に分ける（確定 2026-08-01）。しきい値は境目の数だけ **3 本**。

    | px/day | 粒度 | 段数 | しきい値のキー |
    |---|---|---|---|
    | 1 未満 | 年のみ | 1 | — |
    | 1 以上 4 未満 | 年 ＋ 月 | 2 | `rulerTierPxPerDayMonth` = 1 |
    | 4 以上 14 未満 | 年 ＋ 月 ＋ **週**（月曜日の日付） | 3 | `rulerTierPxPerDayWeek` = 4 |
    | 14 以上 | 年 ＋ 月 ＋ 日 ＋ 曜日 | 4 | `rulerTierPxPerDayDay` = 14 |
    - **単調であること**（拡大すると細かくなる一方。粗くなる逆転を起こさない）。
    - 日・曜日の段はラベルが重なるため、**N 日ごとに間引く**（N は幅から決める）。
34. 拡大縮小で**年単位から日単位まで**表示できること。
35. **縦方向のみ / 横方向のみ**の拡大ができること（異方性ズーム）。
36. 拡大縮小によって**表示する `Task` が自動的に増減**すること。
    - 判定は **WBS の階層の深さ**（`wbs_parent_uid` から導出。MSPDI の `Task/OutlineLevel` に対応）。
      **縮小すると深い階層のタスクから順に消える**。
      ※`importance`（重要度）という専用の属性は**廃止した**。人が付ける値が要らなくなる。
      判定では深さを **5 で頭打ち**にしてよい（6 段以上は実務でほぼ無い）。
      ただし**書き戻す値は頭打ちにしない**（階層が壊れる。`07-plan-actual/...` §5-2）。
    - **縮小したのに表示が増える逆転を起こさない**（閾値はズームに対し単調）。
    - `TaskGroup` の階層（軸B）も縦ズームで畳まれる（深いほうから順に親へ集約）。**軸A とは別の仕組み**。
37. **マウスとキーボードの割当**は次のとおり。※**素のホイールはスクロール**。前プロジェクトで「素のホイール＝ズームは違和感がある」と判断して変更した結果を採る。
    | 操作 | 動作 |
    |---|---|
    | ホイール（修飾なし） | 縦スクロール |
    | **Ctrl**（Cmd）＋ ホイール | **両軸ズーム**（ポインタ中心） |
    | **Shift** ＋ ホイール | 時間軸（横）のみズーム |
    | **Alt** ＋ ホイール | 行軸（縦）のみズーム |
    | **Ctrl+Shift** ＋ ホイール | 横スクロール |
    | **キャンバスの背景をドラッグ** / **Ctrl** ＋ ドラッグ / 中ボタンドラッグ | パン |
    - ズームは**ポインタ位置を中心**とし、カーソル下の日付・行が動かないこと。
    - **背景の上での素の左ドラッグはパンである**（改訂 2026-08-01）。**アイテムの上での素の左ドラッグはパンではない**（アイテムを動かす操作）。
      掴む対象があるかどうかで分けるので、「アイテムを掴んだつもりで日程表が動く」事故は起きない。
    - パンは**等倍**。ポインタが動いた距離だけ日程表が動く（倍率を掛けない）。
38. 拡大したら上下左右にスクロールできること。**マウス操作だけでも**スクロールできること。
39. **稼働日/非稼働日**（土日・祝日）を区別して表示できること。

> **全機能のキーボードショートカットとマウス操作の一覧**は別紙
> `03-ui-naming/handover-ui-detail-spec-ja.md` §5 にある（前プロジェクトの Help に実在したものだけを採録）。

## カーソル

**まず種類。3 つあり、役割が違う。総称は `Cursors`（カーソル）。**

42. **Guide Cursor**: ポインタに追従する補助線。上記 4 モードから選べること。

## 予定と実績

50. 予定と実績を表示/管理できること。
    - **同じ `Task` が実績を持つ**方式とする。予定と実績を別アイテム・別行にはしない。
    - **実績バーの両端は人が置いた日付**であり、勝手には動かない。

      ```
      左端 = actualStart
      右端 = actualStart + actualDuration      稼働日で加算
      ```

    - **完了率（`percentComplete`）は日付から算出して格納する。** 人が直接入力する値ではない。

      ```
      percentComplete = round( actualDuration ÷ (finish − start) x 100 )
      ```

    - 状態は **4 つ**。これから外れる入力はできないようにする。
      **各状態の判別（どの列に何が入るか）は `07-plan-actual/handover-plan-actual-decisions-ja.md` §1-3 の表に従う。**

    - **完了にしても実績バーの右端は 1 日も動かない**（`actualFinish` に右端の日付がそのまま入る）。
    - 「中止」（もう再開しない）は**中断・再開日未定と同じもの**。専用の概念を作らない。
    - **基準日を動かしても、バー・日付・完了率のどれも動かない。**
      基準日で動くのはイナズマ線と遅れ判定だけ。
    - **状態を変える入口は実績バーの右端の外側に出る Progress Marker**（進捗マーカー）。
      クリックで 未完了 → 完了 → 中断 → 未完了 と巡る。
    - 詳細は別紙 **`07-plan-actual/handover-plan-actual-decisions-ja.md`**（この領域の正）。
51. **予定のみ / 実績のみ / 両方**の表示を切り替えられること。
    - `[予定]` `[実績]` の**独立した 2 トグル**で表す。**両方 OFF は作らせない**（バーが 1 本も出ない画面は故障に見える）。
52. **（欠番）** ~~予実の描き方を重ね表示 / 上下分離表示で切り替える~~ — **廃止**。
    - 分離が必要だったのは「予実を両方表示すると実績の端点を掴めない」ためだったが、
      **予定バーの高さを実績バーより大きくすれば幾何的に解決する**ので、モードで解く必要がなくなった。
    - **重ね順は背面から前面へ「予定 → 実績 → 進捗マーカー → 名称ラベル」**とする。名称ラベルが最前面。
      実績バーがラベルを覆ってはならない。進捗マーカーは**不透明な下地**を持ち、予定バーの上に出る。
    - **例外**: 幅がないタスク形状（矢印 / 端点スパン）は内側に収められないので、
      **そのタスク形状だけ実績を下にずらす**（局所的な分離）。文書全体のモードではない。
    - **マイルストーンは下ではなく、実績日の位置へ横にずらす**（確定 2026-08-01）。
      上下の中心は予定と同じで、占有する縦幅は ◇ 1 つぶん。
53. 実績表示のとき**イナズマ線**（Progress Line）を引けること（どこがボトルネックか可視化）。
    **頂点の規則は 1 文**。**動いているべき日を過ぎているものだけ、その日に頂点を打つ。**

    **状態ごとの頂点は `07-plan-actual/handover-plan-actual-decisions-ja.md` §4-1 の表に従う。**

    - **頂点は段ごとに分けて計算する**（確定 2026-07-30）。**同じ段に複数の `Task` があるときは、最も遅れた頂点（最も左）が勝つ。**
      行ごとに 1 頂点ではない。段は画面上の高さが違うので、丸めるとどのタスクを指しているか読めなくなる。
    - **イナズマ線は途切れさせない**（確定 2026-08-01）。上端から下端まで 1 本の折れ線で描き、
      **頂点のない段は基準日の位置を通す**（完了だけの段・中断で再開日未定だけの段・まだ動く日が来ていない段）。
      ※ 旧規則は「最も進んだ頂点が勝つ」だったが、それでは**行内に致命的に遅れたタスクがあっても隠れて**しまい、
      本項の目的（ボトルネックの可視化）と矛盾する。マルチバーは本ツール最大の差別化なので、
      1 行に複数タスクが載るのが標準である。
    - **完了したタスクを尖らせない**のは意図的な判断である。
      日本のイナズマ線の作図慣行は「完了なら右端に点を打つ」だが、
      そのまま実装すると**完了したタスクが左へ尖って「遅れている」ように見える**。
    - **基準日の縦線は常時表示にしない**（項 43 のまま）。遅れは Progress Marker と遅れの日数が示す。
    - 詳細は別紙 `07-plan-actual/handover-plan-actual-decisions-ja.md` §4。
54. **変更前の予定をグレーで表示**し、計画の変更を可視化できること。
    - 変更前の予定は**別ファイル**として読み込んで重ねる。

## 透かし

55. 日程表に**透かし**（Watermark）を入れられること（Web 会議で秘密の日程を撮影されたときの証跡）。
    0. **透かしの設定は文書に保存しない。開いた人の名前と日時で描く。**
       証跡として意味があるのは「**誰がいつ画面に出していたか**」なので、作者の名前が他人の画面に出るのは誤り。
       ユーザー名は読む人の環境設定、日時は実行時に生成、パスワードのハッシュは `.html` 埋め込み。
    1. 透かしにはユーザー名と日時を入れること。
       - 日時は **RFC 3339 / ISO 8601 の UTC 形式 `YYYY-MM-DDThh:mm:ssZ`**（末尾 `Z` = UTC）で書くこと。
       - ※ MSPDI 内部の日付は**タイムゾーンを持たないローカル時刻** `YYYY-MM-DDThh:mm:ss` なので**別扱い**。混同しないこと。
    2. ギリギリ見えるくらいの薄さで、画面全体に斜め方向へ複数入れること。
    3. 表示/非表示を切り替えできること。**非表示にするにはパスワードの入力を求める**こと。
       - 照合は **SHA-256 のハッシュ比較**で行い、**生パスワードはコード・モデル・出力（HTML / JSON）に一切保存しない**。
       - **既定パスワードは `GoodRelax`**。その SHA-256（16 進）を定数として `.html` に埋め込む。
       - ⚠️ **クライアント単体の単一 HTML なので、これは弱い抑止（soft deterrent）にとどまる。** DOM / HTML を直接編集すれば透かしは除去できる。暗号的な強制はできない。サーバー配備時は必ず変更する。

## 作り方の原則

66. **各種命名は名は体を表すこと**（ソフトは言霊）。

（掴み点は §3、ラベルは §6、Progress Marker は §2-4）。

### 決着した仕様

1. **掴み点（選択点）の定義**
   - **名称ラベル / 担当ラベル**: 掴み点は**そのラベルの中心**。編集と移動のみでサイズ変更はしないため、これで足りる。
   - **予定のバー**: **左右の端**＝開始日 / 終了日。**左上の角**＝フェードイン、**右下の角**＝フェードアウト
     （矩形と矢羽根のみ）。本体を掴むと平行移動。
   - **実績のバー**: **左端**＝`actualStart`、**右端**＝`actualDuration`（置いた日付から稼働日数を算出）。
   - **掴み代は見た目より大きくとる。** 予定の端点は予定バーの上下にはみ出させ、実績の帯を避ける。
     **予定の高さ > 実績の高さ**なので、上下の縁を狙えば予定、真ん中を狙えば実績が掴める。
2. **担当・進捗の表示**
   - 書式は **`{担当} : {完了率 %} [タスク名]`**。
   - **担当と完了率は「予定タスクの左端」を基準に、バーの外側左へ右揃えで連結**する。
   - **名称ラベルの配置**は次の順に決める。**考え方は「ラベルを表示しても形状が見える / 触れる」。**

     ```
     1. タスクの幅に収まる            → 中に書く
     2. 収まらない                    → まず 全角12 / 半角24 で打ち切る（項 17）
     3. 打ち切っても収まらない        → 右に出す
     4. 右に出すと他と干渉する        → タスクを上下にずらす（積み順は必要なだけ広げる）
     ```

   - 担当・完了率は**個別に表示/非表示**を切り替えられること。
   - フォントサイズは**タスク高の 80%。下限 12px でクランプ**する（縦ズームを縮めたときに読めなくなるため）。
     **下限を割るなら文字を縮めず、描画する Outline のレベルを減らす。**
   - **ラベル幅は概算する**（全角 2・半角 1 の単位数 × フォントサイズ）。**実測もキャッシュもしない**
     （実測は重く、キャッシュは古い値が残る事故を招く）。
3. **予実が重なって編集できない場合の解決**
   - **高さの差で解く。** 予定バーを実績バーより高く描き、上下に露出した帯で予定を掴む。
     ~~上下分離表示~~ は**廃止**した（項 52）。
   - **例外**: 幅がないタスク形状（矢印 / 端点スパン）だけ、**実績を下にずらす**（局所的な分離）。
     **マイルストーンは実績日の位置へ横にずらす**（確定 2026-08-01）。
   - 状態は **Progress Marker**（進捗マーカー）で示す。`(✓)` 完了 / `( \ )` 中断 / `(!)` 遅れ /
     `( )` 未完了（選択時のみ）。**色だけで区別してはならない**（WCAG 1.4.1）。**形が意味を担う**。
     `(!)` の判定は 3 条件（`07-plan-actual/handover-plan-actual-decisions-ja.md` §2-4。確定 2026-08-01）。
   - 掴めない端点は**薄く描き、理由をツールチップで示す**こと。無反応だと故障に見える。
4. **レイアウトの計算順序**（循環を切る）

   ```
   1. 依存関係から「最小間隔の制約」を作る   経路は引かない
   2. ラベルの占有幅を概算する
   3. 積み順の割当                          1 と 2 を占有幅の入力にする → 位置が確定
   4. 依存線の経路を引く                    位置は確定済みなので 1 回で決まる
   ```

   **「依存線が必要とする余地」と「依存線の経路そのもの」を分ける**のが要点。
   再計算が要らず 1 パスで終わる。**依存線とラベルの干渉は計算しない**（やりすぎでバグの元）。
5. **PoC を先に回す**
   - 上記のようにポイントとなる UI は、**実装前に PoC を回してユーザーと認識合わせを行う**こと。
   - PoC では **UI と性能を同時に測る**こと。予実 2 系統 ＋ 担当 ＋ 完了率ラベル ＋ Progress Marker は
     **1 アイテムあたりの DOM ノード数が最も増える構成**で、ぬるサクの最大のリスクである。
   - PoC 項目の全数は `07-plan-actual/handover-plan-actual-decisions-ja.md` §13。
     特に **行の高さ**（矢印 / 端点スパンで実績を下にずらすと積み順の数と掛け算になる）と
     **低ズームでの収束**（ラベルが相対的に大きくなる）を実測する。
