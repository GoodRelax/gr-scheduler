## 0. この設計が解いた問題

前プロジェクトは「予定 = `start`/`finish`、実績 = `actualStart`/`actualFinish`、進捗 = `progressRatio`」という
3 項目のモデルだったが、**進行中のタスクで実績バーの右端をどこに描くかが未定義**だった。

そこから出発し、次の順に検討して**MSPDI の要素をそのまま使うモデル**に着地した。

```
案1  右端 = actualStart + 率 x 予定期間      率から位置を導出する
案2  右端 = 基準日                          経過をそのまま描く
案3  右端 = 案1 の分母を基準日まで伸ばす
到達点モデル       右端は人が置く日付。率は導出値
MSPDI 準拠モデル   実績の期間を ActualDuration で持つ。新しい語を作らない  ← 確定
```

**却下理由**（同じ検討を繰り返さないため）:

| 案 | 却下理由 |
|---|---|
| 案 2 | 進行中のバーが全て基準日で終わるため、**遅れが描けない**。「予定 7/1–7/20 を 7/10 時点で 25%」なら実績線は 7/5 で止まっていなければならない |
| 案 3 | 率を上げていないのに基準日が進むだけで前線が伸びる。**放置したタスクほど進んで見える**（予定 7/1–7/10・90% を放置すると前線が 7/23 → 8/19 と 27 日進む） |
| 案 1 | 率が 1 以下である以上、**進行中に予定終了日を越えられない**。「見積もりが甘くて予定より長くかかっている」を描けない |
| 到達点モデル | 方向は正しいが `actualThrough` という**新語が必要**だった。MSPDI の `ActualDuration` で足りる |

## 1. 実績と進捗のデータモデル

### 1-1. 保存する項目

| GRS | MSPDI | 型 | 意味 |
|---|---|---|---|
| `start` / `finish` | `Start` / `Finish` | 日付 | 予定 |
| `actualStart` | `ActualStart` | 日付 | 実績開始 |
| **`actualDuration`** | **`ActualDuration`** | **稼働日数** | **実績の期間。実績バーの長さそのもの** |
| `actualFinish` | `ActualFinish` | 日付 | 実際に終わった日（完了時のみ） |
| `resume` | `Resume` | 日付 | 残りの部分が再開する予定日（中断時のみ） |
| `resumeValid` | `ResumeValid` | 真偽 | 再開できるか |
| `percentComplete` | `PercentComplete` | 整数 | 完了率。日付から算出して格納する |
| `deadline` | `Deadline` | 日付 | 期限 |
| `milestone` | `Milestone` | 真偽 | マイルストーンか |
| `wbs_parent_uid` | （`OutlineLevel` へ導出） | UID | WBS の親。**軸A。階層はこれが持つ**（既存の確定） |

**実績バーの右端は保存しない。** 描画時に導出する。

```
実績バーの右端 = actualStart + actualDuration     稼働日で加算
```

`stop`（中断した日）も保存しない。中断したときの右端と同じ値なので、export 時に算出する（§10-1）。

**解説書の原文**（この設計の根拠）:

```
ActualDuration  The span of actual working time for a task so far, based on the scheduled
                duration and current remaining work or percent complete. Actual duration can
                be calculated in two ways, either based on percent complete or remaining duration.
Stop            For a Task, Stop is the date that represents the end of the actual portion of a task.
Resume          For a Task, Resume is the date the remaining portion of a task is scheduled to resume.
ResumeValid     Indicates whether the task can be resumed.
PercentComplete The percentage of the task duration completed.
ActualFinish    For a Task, ActualFinish is the date and time that a task actually finished.
OutlineLevel    The number that indicates the level of a task in the project outline hierarchy.
```

**重要**: `Resume` は「最後に再開した日」ではなく「**残りがいつから始まる予定か**」。過去の記録ではなく未来の予定である。

### 1-2. 中断は 1 回しか記録できない — XSD で確認

`Stop` / `Resume` / `ResumeValid` はいずれも **Min 0 / Max 1**。MSPDI は**中断の履歴を持たない**。
常に「今の境界」1 つだけを持つ。したがって:

- 2 回目に中断すると、記録は新しい境界に置き換わる（1 回目は残らない）
- `ActualFinish` が入ると残りの部分が無くなるので `Resume` は意味を失う
- **完了したらバーは 1 本になる**

`TimephasedData` は `maxOccurs="unbounded"` だが、中身は `Type` の列挙が示すとおり
**工数・原価・完了率の時間配分**であって、バーの分割区間を表す構造ではない。

> **GRS も同じ制約に倣う。** 分割区間のリストを持たない。持てば往復で必ず落ちる。

### 1-3. 5 状態の判別（拡張領域を 1 枠も使わない）

| 状態 | `actualStart` | `actualDuration` | `actualFinish` | `resume` | `resumeValid` | `Stop`（export） |
|---|---|---|---|---|---|---|
| 未着手 | 空 | 空 | 空 | 空 | — | 書かない |
| 進行中 | あり | あり | 空 | 空 | true | 書かない |
| **中断・再開予定あり** | あり | あり | 空 | **日付** | true | **書く** |
| **中断・再開日未定** | あり | あり | 空 | 空 | **false** | **書く** |
| 完了 | あり | あり | **あり** | 空 | false | 書かない |

`Stop` は保存項目ではなく export 時に算出する値だが、状態との対応を見失わないようここにも並べる。
書き出しの規則は §10-1 が正で、本表と同じ内容である。

> **状態は 5 つ、Progress Marker の記号は 4 つ。混同しないこと。**
> マーカーは 未着手＋進行中 → `( )`、中断 2 種 → `( \ )` に畳むので、
> **5 状態 → 3 記号 ＋ 導出の `(!)`（遅れ）** になる（§2-4）。
> かつて本節の見出しが「4 状態」だったのは、この記号の数と取り違えたためである。

- 完了と「中断・再開日未定」は **`actualFinish` の有無**で一意に分かれる。
- 「中止」（もう再開しない）は**中断・再開日未定と同じもの**。専用の概念を作らない。
- **遅れ**は状態ではなく導出。上の 5 状態のどれとも並ばない。判定は 3 条件あり、**正は §2-4** である
  （`finish` を過ぎている / 未着手のまま `start` を過ぎている / 中断のまま `resume` を過ぎている）。

### 1-4. 完了率の計算

```
percentComplete = round( actualDuration ÷ (finish − start) x 100 )      いずれも稼働日
```

- **格納する**（導出結果をデータとして保持する）。日付を編集したら再計算する。
- 分母は**予定の期間**。`Duration` と同じ。`actualStart` が `start` より後でも分母は変わらない。
- **完了したら 100 とする**（`ActualFinish` があって 100 未満は MS Project では矛盾するため）。
- **完了タスクの MSPDI export は次のとおり — 確定 2026-07-30**:

  ```
  RemainingDuration   0 を書く
  ActualFinish        実際に終わった日を書く
  PercentComplete     要素そのものを書かない（空欄にする）
  ```

  **なぜ `PercentComplete` を書かないか**: `ActualFinish` があり `RemainingDuration` が 0 なら、
  完了は**その 2 つで一意に決まる**。冗長な `PercentComplete` を併記すると、
  100 超を丸めない方針（下記）と MS Project の意味論が衝突する場面をわざわざ作ることになる。
  **書かなければ衝突しない。** 相手は残りの 2 要素から完了を復元できる。
- 単位は `DurationFormat` に従う。XSD の列挙に **`7=d`（日）/ `8=ed`（経過日）** があり、
  既存の確定規則「元の値の書式を踏襲する」がそのまま効く。

**型は「整数・0 以上」— 確定 2026-07-30**

```
percentComplete : 整数、0 以上。上限を型に持たせない
通常は 0〜100。実績が予定期間を超えると 100 を超える
```

**「0〜100」と書いてはならない。** そう読んだ実装者は必ずバリデーションかクランプを書き、
「予定 10 日の仕事に 15 日かかった」という業務上の事実を消してしまう。

**100 を超える場合の扱い（暫定。実機確認 §12-2 で見直す）**

XSD は `type="xsd:integer"` で**制約ファセットを持たない**。解説書にも範囲の記述がない。
つまり `<PercentComplete>150</PercentComplete>` は**妥当な XML になる**。

```
内部・JSON・MSPDI export とも、算出した値をそのまま出す。頭打ちにしない
拡張領域は使わない
```

**頭打ちにしない理由**: 「予定 10 日の仕事に 15 日かかった」は**業務上の事実**であり、
100 に丸めるとその事実が消える。スキーマが禁じていない以上、まず素直に出して相手の反応を見る。

**残るリスク**: MS Project が 100 超をどう扱うかは**未確認**（取込時に 100 へ丸める / 拒否する / そのまま受け入れる）。
意味論としては「期間のうち完了した割合」なので 100 超は MS Project の考え方と食い違う。
**§12-2 の実機確認で決着させる。** 丸められると分かったら、そのときに頭打ちへ変える。

超過分を拡張領域に載せる必要はない。**日付から常に再計算できる**冗長情報だからである。

> **`Duration` についての訂正**: 「実績が長引けば `Duration` 自体が伸びる」という説明は不正確だった。
> **時間が経つだけでは何も動かない。** 人が実績の期間を増やして入力したときにだけ、
> 恒等式を保つために `Duration` が改訂される。
> なお恒等式 `Duration = ActualDuration + RemainingDuration` は**前プロジェクトの文書（§3-3）の記述**であり、
> **上流の解説書では確認できていない**。
>
> **MS Project がプロジェクト管理として成立するのは `Baseline` を別に凍結して持つから**である
> （`Baseline` 要素は MSPDI に実在し、当初の `Duration` / `Start` / `Finish` を保持する）。
> 比較対象は `Baseline` であって現在の `Duration` ではない。
> GRS も同じ構造を持つ（`user-order.md` 項 54「変更前の予定は**別ファイル**として読み込んで重ねる」）。
> そして GRS は日程を人が決める（スケジューラを作らない）ので `finish` を自動で動かさない。
> **実績が予定終了日を越える状態が普通に起きる。これは設計として正しい。**

### 1-5. マイルストーンの扱い

| | 予定の期間 | `actualDuration` | `percentComplete` |
|---|---|---|---|
| タスク | `finish − start` | 0 以上 | 0 以上の連続値（通常 0〜100） |
| **マイルストーン** | **0** | **0** | **0 か 100 のみ** |

マイルストーンには実績の端点も進捗の掴み点も無い。**点そのものを掴んで移動する**。
0 除算を避けること（予定の期間が 0 のとき、完了なら 100、そうでなければ 0）。

## 2. 描画

### 2-1. 実績バー

```
左端 = actualStart                       人が置く日付
右端 = actualStart + actualDuration      人が右端を置いた結果として actualDuration が決まる
```

- **完了を押しても右端は 1 日も動かない**（`actualFinish` に右端の日付がそのまま入る）。
- **基準日を動かしても、バー・日付・完了率のどれも動かない。** 基準日で動くのは
  イナズマ線と遅れ判定だけ。
- 完了したときだけ、右端に**実線の縦キャップ**を描く（`ActualFinish` という確定日であることを示す）。
  キャップが無ければ実績部分の終わりである。

### 2-2. タスク形状（`shapeKind`）— 5 種

| 表記 | 英語 | 上下の幅 | 実績の置き方 | フェード掴み点 |
|---|---|:--:|---|:--:|
| `===` | `rectangle` | **あり** | 予定の内側に重ねる | あり |
| `>===>` | `chevron` | **あり** | 予定の内側に重ねる | あり |
| `--->` | `arrow` | なし | **予定の下にずらす** | なし |
| `*----*` | `endpointSpan` | なし | **予定の下にずらす** | なし |
| ◇ ほか | `milestone`（`Task.milestone = true`） | なし | **実績日の位置へ横にずらす** | なし |

**規則は 2 本**:

```
1. 実績の形状 = 予定の形状                        ← 2026-07-30 追加

2. 上下に幅がある形状（rectangle / chevron）  → 実績を内側に重ねる ＋ フェードあり
   幅がない形状（arrow / endpointSpan）       → 実績を下にずらす ＋ フェードなし
   マイルストーン                              → 実績日の位置へ横にずらす ＋ フェードなし
```

#### マイルストーンの実績は横にずらす — **確定 2026-08-01**

```
予定 ◇   中心が start（= finish）    輪郭で描く
実績 ◇   中心が actualFinish         塗りで描く。予定より一回り小さい
上下の中心は同じ。占有する縦幅は ◇ 1 つぶん
```

| | 旧（2026-07-30） | 新（2026-08-01） |
|---|---|---|
| 実績の位置 | 予定の**真下** | **実績日**（横にずれる） |
| 上下の中心 | 予定とずれる | **予定と同じ** |
| 占有する縦幅 | ◇ 2 つぶん | **◇ 1 つぶん** |

**なぜ変えたか**

1. **マイルストーンの実績は「いつ起きたか」であって「どこまで進んだか」ではない**（§1-5:
   実績の端点も進捗の掴み点も持たず、`percentComplete` は 0 か 100 のみ）。
   縦に積んでも遅れは読めないが、**横にずらせば遅れが日数として見える**。
2. **縦に 2 つ積むと 1 行が高くなりすぎる。** PoC の実測で、
   マイルストーンを含む段は 59px、それ以外の段は 22px を占めていた。
   ◇ 4 つで全体の高さの 38% を食い、**`Fit` が画面に収まらない原因になっていた**。
   1 つぶんに収めると 4 段で 104px 減る。
3. **「同じ形状で描く」（§2-2-1）はそのまま満たす。** どちらも ◇ である。

**実績日が無いとき（未完了）は実績 ◇ を描かない。** マイルストーンは 0 か 100 しかないので、
描くか描かないかの 2 値でよい。

#### 2-2-1. 実績は予定と同じ形状で描く — **確定 2026-07-30**

**予定が矢羽根なら実績も矢羽根、予定が矢印なら実績も矢印、予定がマイルストーンなら実績もマイルストーン。**
実績だけを四角で描いてはならない。

**理由**: 実績だけ形が変わると**強い違和感が出る**。予定と実績は同じ 1 つの作業の 2 つの側面であって、
別種のものではない。形を変えると「別のものが乗っている」ように見える。

実績は**同じ形状を小さく描く**（高さが予定より低い）。色は §2-6 の規則で分ける。

**縮める比率は `actualOfPlan`（実績の縦幅 ÷ 予定の縦幅）1 つだけ** — **確定 2026-08-01**

```
実績の縦幅 = 予定の縦幅 × actualOfPlan
```

**すべてのタスク形状に同じ比率を掛ける。マイルストーンも例外ではない。**

| タスク形状 | 予定 | 実績 | 比率 |
|---|--:|--:|--:|
| 矩形 | 28.0px | 20.4px | 0.73 |
| マイルストーン | 42.0px | 30.7px | 0.73 |

（`actualOfPlan = 0.73` / `basePlanHeight = 28` / `shapeHeightOf.milestone = 1.5` のときの値）

> ⚠️ **`0.73` 自体に設計上の導出は無い。** 寸法を 1 か所へ統合する前に基準としたページが
> 描いていた **22 : 16** をそのまま採った値である（`../02-data-model/grs-document-settings-ja.md` §3 の注記）。
> **規則は「比が 1 つであること」であって、その比が 0.73 であることではない。** 次期は選び直してよい。

マイルストーンは予定 ◇ 自体が矩形より大きい（`shapeHeightOf.milestone` 倍）ので、
実績 ◇ の絶対値も大きくなる。**比率が同じであることが規則**であり、絶対値を揃えるのではない。
形状ごとに別の比率を持たせない（設定値が増え、どれが効いているか読めなくなる）。

**角度も予定と実績で同じにする** — **確定 2026-08-01**

矢羽根の切り欠きは、**予定側の横長に `actualOfPlan` を掛けた値**で実績側を描く。

```
実績側の切り欠きの横長 = 予定側の切り欠きの横長 × actualOfPlan
```

**なぜこれで角度が揃うか**: 切り欠きの傾きは「横長 ÷（高さ ÷ 2）」で決まる。
実績の高さは予定の `actualOfPlan` 倍なので、横長にも同じ倍率を掛ければ比が保たれ、角度が一致する。

**なぜ規則として書く必要があるか**: 切り欠きは
`min(幅 × chevronNotchOfWidth, 高さ × chevronNotchOfHeight)` で頭打ちする。
**高さの側で決まっている間は自動的に `actualOfPlan` 倍になる**ので角度は勝手に揃うが、
**幅の側で頭打ちになった瞬間に崩れる**。予定と実績は幅も高さも違うため、
頭打ちに入るズーム倍率が別々に来るからである。

| | 高さで決まる（既定ズーム） | 幅で頭打ち（低ズーム・縦拡大） |
|---|--:|--:|
| 予定の角度 | 42.0° | 26.6° |
| 実績の角度 | 42.0° | 22.3° |

**切り欠きとフェードインは別物である。** 切り欠きは矢羽根の**形状の描き方**で、日数を持たない。
フェードイン（`fadeInDays`）は**日数のデータ**で、バー端をぼかして日付の曖昧さを表す
（`../03-ui-naming/handover-ui-detail-spec-ja.md` §4-1。矩形と矢羽根の**両方**が持つ）。
**フェードインの日数は予定と実績で同じ値を使う**（予実で変えると管理できない）。
上の倍率は描画時の切り欠きだけに掛かり、日数のデータには一切触れない。

#### 2-2-2. マイルストーンの形状は `milestoneGlyph` で持つ — **確定 2026-07-30**

`shapeKind` に**マイルストーンという値がある。その詳細（〇 六角形 五角形 ◇ □ ☆ △ ▽）はグリフを見る**、という 2 段構えにする。

```
TaskVisual.shapeKind        'rectangle' | 'chevron' | 'arrow' | 'endpointSpan' | 'milestone'   5 値
TaskVisual.milestoneGlyph   'circle' | 'hexagon' | 'pentagon' | 'diamond'
                          | 'square' | 'star' | 'triangleUp' | 'triangleDown'   8 値
                          既定は 'diamond'。shapeKind = 'milestone' のときだけ見る
```

**値の並びは面積の大きい順である** — 確定。同じ外接円に内接させたときの面積で並べる。

| 順 | 形状 | 英名 | 面積（R = 1） |
|:--:|:--:|---|--:|
| 1 | 〇 | `circle` | 3.142 |
| 2 | 六角形 | `hexagon` | 2.598 |
| 3 | 五角形 | `pentagon` | 2.378 |
| 4 | ◇ | `diamond` | 2.000 |
| 5 | □ | `square` | 2.000 |
| 6 | ☆ | `star` | 1.323 |
| 7 | △ | `triangleUp` | 1.299 |
| 8 | ▽ | `triangleDown` | 1.299 |

- **◇ と □ は同面積**（◇ は □ を 45° 回したもの）。既定の ◇ を先に置く。**△ と ▽ も同面積**で、上向きを先に置く。
- **☆ と △ の差は 1.8% しかなく、`starInnerOfOuter` に依存する**（既定 0.45。範囲 0.2〜0.8 で、0.2 なら ☆ が最小になる）。
  **既定値での順で固定する**。設定を変えても並びは変えない。
- 面積順にする理由: パレットで**大きいものから小さいものへ**並び、選ぶときに視覚的な大小と一致する。

**不変条件**: `shapeKind = 'milestone'` ⇔ **`Task.milestone = true`**。**権威は `Task.milestone` 側**であり、
`shapeKind` は読み込み時にそれに従属して決まる。人が別々に設定できるようにしない。

**なぜ権威を `Task.milestone` に置くか**: **そちらが export される側**だから。
食い違ったときに往復で失われるのは `shapeKind` ではなく `Task.milestone` の側であり、
相手ツールから見た「マイルストーンかどうか」が壊れる。

**MSPDI の事実**（正本 XSD ＋ 上流解説書で確認）:

| 要素 | 型 | 定義文 |
|---|---|---|
| **`Task/Milestone`** | `xsd:boolean` | "Whether the task is a milestone." ← **判定はこれ** |
| `Task/Type` | 整数 0/1/2 | "The type of task. Values are: 0=Fixed Units, 1=Fixed Duration, 2=Fixed Work" |
| `PredecessorLink/Type` | 整数 0-3 | "The link type. Values are 0=FF, 1=FS, 2=SF and 3=SS" |

**`Type` でマイルストーンを判定してはならない。** MSPDI には同名の `Type` が 3 つあり、どれも別の意味である。

**形状・グリフに相当する要素は MSPDI に 1 つも無い**（全要素名を走査済み。近いのは `HideBar` だけ）。
したがって **`milestoneGlyph` は GRS 専用・非 export**、`TaskVisual` に置く。

- **縦棒で端を示す細線は廃止**。`*----*`（端に点を打つ）に置き換える。
- 予定バーの高さ > 実績バーの高さ とし、**上下に露出した帯で予定を掴む**。
- **実績を下にずらす 2 タスク形状（`arrow` / `endpointSpan`）は、実績ぶんの高さを常に確保する**
  （表示を切り替えても行の高さが動かない。既存の確定 Q-C と同じ考え方）。行が高くなるので **PoC で実測する**（§13）。
  **マイルストーンは実績を横にずらすので確保は要らない**（占有する縦幅は ◇ 1 つぶん。§2-2。確定 2026-08-01）。

### 2-3. 上下分離表示は廃止

`user-order.md` 項 52 の「重ね表示 / 上下分離表示の切替」と `[分離]` トグルを**廃止する**。

**廃止できる理由**: 分離が必要だったのは「予実を両方表示すると実績の端点を掴めない」ためだった。
**予定の高さを実績より大きくすれば幾何的に解決する**ので、モードで解く必要がなくなった。

**例外**: 幅のない 2 タスク形状（`arrow` / `endpointSpan`）は内側に収められないため、
**そのタスク形状だけ実績を下にずらす**（局所的な分離）。文書全体のモードではなく、タスク形状ごとの描き方である。
**マイルストーンは下ではなく、実績日の位置へ横にずらす**（§2-2。確定 2026-08-01）。

`[予定]` `[実績]` の 2 トグルは残す（表示の絞り込みとして有効。両方 OFF は作らせない）。

### 2-4. Progress Marker（進捗マーカー）

実績バーの右端の**外側**に描く。

> ⚠️ **2026-07-30 変更**: 「**固定ピクセルサイズ**」をやめ、**文字サイズから導く**ことにした。
> 理由と数値は §2-4-1。以前の版を読んでいる場合は §2-4-1 を正とすること。

| 記号 | 意味 | 表示条件 |
|---|---|---|
| **`(✓)`** | 完了 | `actualFinish` が入っている。常時。**他のどの判定よりも優先する** |
| **`(!)`** | 遅れ | 未完了かつ下の 3 つのいずれか。常時 |
| **`( \ )`** | 中断 | 中断していて `(!)` に当たらない。常時。斜線は**左上から右下**（`( / )` ではない） |
| **`( )`** | 未完了 | 上のどれにも当たらない。**選択したときだけ薄く**表示 |

**`(!)` を出す 3 条件** — **確定 2026-08-01**

```
1. finish < 基準日                                 期限を過ぎている
2. 未着手          かつ  start  < 基準日            着手予定を過ぎている
3. 中断・再開予定あり  かつ  resume < 基準日            再開予定を過ぎている
```

**規則は 1 文**: **動いているべき日を過ぎたのに動いていなければ `(!)`。**

条件 2・3 の判定日は、**イナズマ線が頂点を打つ日と同じ日**である（§4-1）。
同じ「動いているべき日」を、イナズマ線は線の形で、マーカーは記号で示している。
2 つの表示が別々の日を見ていると、線は遅れているのにマーカーは何も言わない、という食い違いが起きる。

**中断・再開日未定**（`resumeValid = false`）は条件 3 に当たらない。
再開予定日そのものが無いので「過ぎている」と言えないためで、
イナズマ線が頂点を打たないこと（§4-1）と同じ理由である。ただし条件 1 には当たりうる。

- **クリックで 3 状態を巡る**: 未完了 → 完了 → 中断 → 未完了。
  **`(!)` はこの巡回に入らない。** 遅れは日付から導出される結果であって、人が選ぶ状態ではない。
- **記号は SVG で描く**（フォントの字形に依存しない）。
- **全体を非表示にするトグル**を用意する（記号が増えて見にくいときのため）。
  状態は **`documentSettings.progressMarkerVisible`**（既定 `true`）に保存する。MSPDI へは書かない（§5-4）。
  格納先の根拠は `../02-data-model/grs-native-erd-ja.md` §5.7。
- **不透明な下地を持つ**。予定バーに重なっても読める。色に依存せず形が意味を担う（WCAG 1.4.11 / 項 25）。
- 実績バーの右端から**固定 4px** 離す。端点の掴み代と重ならない最小距離であり、それ以上離さない。
- **占有幅に含める。** 含めないとマルチバー行で右隣のタスクと重なる。

**なぜ固定サイズか**: 低ズームでバーが潰れても、記号は同じ大きさで残る。
`98%` と `100%` が同一ピクセルに落ちても、記号の有無で必ず分かれる。

**却下した符号化**:

| 案 | 却下理由 |
|---|---|
| ハッチング（斜線塗り） | ある描画ライブラリ 1 本の**公式アクセシビリティ文書を読んだ**だけで、実機検証も複数製品の突合もしていない（製品名は中立化で消したので**再検証不能**）。その文書が「パターン塗りと破線は視覚的に混乱させ、一部の利用者にはかえってアクセシブルでなくなり得る」と警告。低ズームで潰れる |
| 中抜きで完了を表す | 作図慣行で**中抜き＝未着手**の意味が定着している |
| 取り消し線 | 作図慣行で**取り消し線＝キャンセル**の意味が定着している |
| 三角＋`!` | **システムエラーの通知に見える**。遅れを伝えるには強すぎる |
| 色だけ | 項 25（色だけで状態を伝えない）／ WCAG 1.4.1 違反 |

### 2-4-1. マーカーの大きさは文字サイズから導く — **確定 2026-07-30**

**基準の環境を 1 つ決め、そこから寸法の下限を引く。**

```
基準  画面 1920 x 1080 / ブラウザ全画面 / 拡大率 100% / ヘッダー領域の縦 50px
```

| 量 | 下限 | 根拠 |
|---|--:|---|
| **フォントサイズ** | **12px** | 和文がこれを割ると読めない（**🔎 出典なし**。下記） |
| 実績バー ＋ α の縦幅 | **16px** | 16 × 0.8 = 12.8px なので 12px のフォントが収まる |
| **マーカー** | **16px** | **実績バーに追随する**。注釈が本体より大きくならない |
| 予定バーの上下間隔（段の間隔） | **12px** | 依存線が 1 本通る幅 |

**下限を割る文字サイズが必要になったら、マーカーや文字をさらに縮めるのではなく、
グループ LOD（軸B・`TaskGroup`）の深さを 1 つ減らす。** — **軸を確定 2026-08-02（ユーザー判断）**

> ⚠️ **軸A ではない。** 旧版は「描画する `Outline` のレベルを 1 つ減らす」と書いていたが、
> **`Outline` は軸A（WBS）で、その LOD は幅（`zoomX`）で駆動する**。
> **引き金であるフォント下限は縦（`zoomY`）の話**なので、軸A を減らしても行は高くならず、
> 深いタスクが消えるだけで**フォント下限は解消しない**（因果が閉じない）。
>
> **軸B の深さを 1 つ減らすと行数が減り、残った行の高さが増える**のでフォントが下限を上回る。
> PoC が実測・実装したのもこちらである（「行ツリーの分岐数を 3 と見て、レベルを 1 つ落とすと
> 行数が 1/3 になり残った行の高さが 3 倍になる」＝ `../08-poc/POC-RESULTS-ja.md` §B-6）。
>
> **引き金で使い分ける**（§5-3 の表を見ること）:
>
> | 引き金 | 減らす軸 | 定数 |
> |---|---|---|
> | **幅**が足りない（`zoomX`） | **軸A**（WBS の深さ）＝ タスク LOD | `taskLevelOfDetailReadablePx` |
> | **フォント下限**を割る（`zoomY`） | **軸B**（`TaskGroup` の深さ）＝ グループ LOD | `groupLevelOfDetailBase` / `groupLevelOfDetailRatio` |
>
> **減らす量の式は未確定**（`../NEXT-STEPS-ja.md` 6-1）。確定しているのは「縮めるのではなく減らす」という方針と、上のどちらの軸かだけである。

> **🔎 「和文が 12px を割ると読めない」の出典は `handover/` に無い。**
> 実測でも引用でもなく、**そう決めた**という記録しか残っていない。
> しかしこの値は**「根 4 つ」の 1 つ**で、`actualMin`（= 12 ÷ 0.8 = 16px）と
> LOD のレベル削減の引き金を単独で決めている。**次期は根拠を持って決め直すこと。**
> 参考として、`../08-poc/POC-RESULTS-ja.md` は主要サイトの本文が 16px 前後であることを実測している。

> 🔴 **この節の「なぜ固定ピクセルをやめたか」は、後の PoC 追試で反証された。**
>
> 低ズームで段数が膨らむ主因は **担当ラベル＋完了率ラベル（バーの外側左）**であり、
> **マーカーの寄与はほぼ 0** だった（`../08-poc/POC-RESULTS-ja.md` §A-3。
> zoomX 0.25 で担当・完了率を隠すと段数 96 → 72）。**要因の取り違えである。**
>
> **「マーカーを文字サイズに従わせる」という結論自体は残す**（注釈が本体より大きくならないのは正しい）。
> ただし**それで段数膨張が原理的に消えるわけではない**。実際の手当ては
> **担当・完了率の既定を隠す**ことにした（`../02-data-model/grs-document-settings-ja.md` §4-1）。

**なぜ固定ピクセルをやめたか**（当時の理由・上の反証を読んでから）: PoC で、固定サイズのマーカーが**バーではなく行の高さを決めてしまう**ことが分かった。
横方向の張り出し（右端から 4px ＋ マーク幅）が隣のバーとの間隔より広くなり、
低ズームで段数が増える。マーカーを文字サイズに従わせ、**下限を割る前にレベルを減らす**ようにすれば、
バーが潰れる状況そのものが起きないので、この問題は原理的に消える。

**張り出しは占有幅に含めたままでよい**（4px ＋ マーク幅）。上の規則により低ズームでも支配的にならない。

> ⚠️ **既存の「フォント下限 10px」は 12px に置き換える。**（`../03-ui-naming/handover-ui-detail-spec-ja.md` §4-2 ほか）

### 2-5. Resume アイコン

**中断のときだけ**、進捗マーカーの右に出る。

- 形は **L 字の折れ矢印（角の丸い）**。下から上へ登って右へ曲がり、矢じりが付く。
- **幾何（確定 2026-07-30）**:

```
矢先の高さ   = 実績バーの高さの中心 = マーカーの高さの中心
矢印の下端   = マーカーの下端
```

- `resume` が空のときは**薄い〇**として出る。クリックすると日付が入る。
- 日付が入ったら `resume` の位置へ移り、**実績バーの右端から破線で繋がる**。以後はドラッグで動かせる。
- `resume` が空のまま中断している状態が **`resumeValid = false`（再開日未定）**。

### 2-6. 色の既定 — **確定 2026-07-30**

```
予定と実績は 同一の色相
予定  中彩度・やや薄い
実績  高彩度・濃い（原色は使わない）
依存線  橙で固定
```

- **青い予定に緑の実績、のような色相違いは禁止する。** 同じ 1 つの作業の 2 つの側面なので、色相を分けると別物に見える。
- **依存線は橙で固定**。ライトモードでもダークモードでも判別できる彩度・明度にする。
- **色は形と位置の冗長符号であって、色だけに意味を持たせない**（項 25 / WCAG 1.4.1）。

**コントラストの下限**: 重なる相手との比が **3:1 以上**（WCAG 1.4.11 非文字コントラスト）。
特に**実績 ÷ 予定**は必ず満たすこと。ダークモードでは明度を反転させるだけでは足りず、
**予定をより暗く、実績をより明るく**しないとこの比を割る（PoC で実測して調整した）。

参考値（PoC `../08-poc/poc-integrated.html` の「形状の基準」タブで実測。色相 214 の場合）:

| | ライト | ダーク |
|---|---|---|
| 予定 塗り | `hsl(214 46% 80%)` | `hsl(214 32% 26%)` |
| 予定 線 | `hsl(214 44% 46%)` | `hsl(214 46% 66%)` |
| 実績 塗り | `hsl(214 62% 34%)` | `hsl(214 62% 64%)` |
| 依存線 | `hsl(26 88% 44%)` | `hsl(30 92% 60%)` |
| **実績 ÷ 予定** | **4.81:1** | **3.74:1** |
| 依存線 ÷ 背景 | 3.78:1 | 8.25:1 |

> **予定の塗り単体は背景と 1.7:1 しかない**（薄い色なので当然）。**予定バーの輪郭は線が担保する**（両モードで 5:1 以上）。

### 2-7. 文字の色と縁取り — **確定 2026-07-31**

```
文字色は テーマの前景色 1 つに統一する
    ライトモード  黒
    ダークモード  白

バーの上に載る文字には、背景色の縁取りを付ける
    縁の色    背景色（＝ライトなら白、ダークなら黒）
    縁の太さ  フォントサイズ x 0.17（12px の文字で約 2px）
    描き順    縁 → 文字（SVG の paint-order="stroke fill"）
```

**「黒に統一」はダークモードでは成立しない。** 黒文字はダークの予定バーで 2.0:1、背景でも読めない。
**テーマの前景色 1 つ**という言い方にすれば、ライトで黒・ダークで白となり、規則は 1 つで済む。

#### なぜ縁取りが要るか

**名称ラベルは予定バーと実績バーの両方にまたがって載る**（§6-1「幅に収まれば中に書く」、
実績は左端から内側に重なる）。**1 本の文字列に背景色が 2 つある**ので、
どちらか片方に合わせた固定色では必ず他方で落ちる。

固定色のまま §2-6 の確定色を使うと、**既定色相の青ですら 文字 ÷ 実績 = 2.58:1**（要 4.5:1）で落ちる。

さらに **`fillColor` は人が選ぶ**（`user-order.md` 項 12 / 項 23）。任意の色に対して
固定の文字色で 4.5:1 を保証することは**原理的にできない**。

**縁取りを付けると、文字が接する色は縁＝背景色になる。** 比は **21:1 で固定**され、
バーの色にも人の選んだ色にも依存しなくなる。

#### 却下した案

| 案 | 却下理由 |
|---|---|
| バーの色を選び直して固定色を成立させる | 10 色相すべてに解はあるが、**すべて制約の角に張り付く**（実績÷予定 = 3.00:1、文字÷実績 = 4.50:1 と下限そのもの）。あとから明度を 1 ポイント動かすと必ずどれかが落ちる。さらに実績の明度を確定値から最大 35 ポイント動かす必要があり、**§2-6 の「実績は高彩度・濃い」と両立しない** |
| バーに重なる文字だけ白にする | 「文字色は 1 つ」という規則を捨てることになる。しかも実績と予定にまたがる 1 本の文字列は、どちらの色にしても片方で落ちる |
| 文字の背後に不透明な下地の矩形を敷く | ラベルごとに描画要素が 1 つ増える。さらに**下地がバーの形を隠す**ので、§6-1 の「ラベルを表示しても形状が見える」と衝突する。縁取りなら文字の隙間からバーが見える |

#### 性能 — 実測して採用した

**基準の環境**（§2-4-1）で、**全部消す → 片方だけ描く → 横スクロール 90 フレーム →
ズーム 90 フレーム**の手順で計測した（`../08-poc/poc-integrated.html` の「色と縁取り」タブ）。

| 操作 | 2000 本 縁取り無し | 2000 本 縁取り有り | 10000 本 無し | 10000 本 有り |
|---|--:|--:|--:|--:|
| 横スクロール | 13.9 ms | **13.7 ms** | 68.7 ms | 71.0 ms |
| ズーム | 16.6 ms | **16.1 ms** | 77.5 ms | 80.0 ms |

- **2000 本では差が測れない**（縁取り有りのほうが 0.2〜0.5ms 速く出た。ノイズの範囲）。
- **10000 本では +2.3〜2.5ms（約 +3.3%）**。ただしこの規模では**縁取りの有無にかかわらず
  69〜80ms/フレーム（約 13fps）**で既に破綻している。**そこを直すのは LOD（§5）であって縁取りではない。**
- **「最初に 1 回描く」の値は判断に使わない。** 2000 本で +9.1ms、10000 本で −55.4ms と符号が反転する。
  HTML のパースが支配的で、縁取りの寄与が埋もれる。

> ⚠️ **ズームの計測は `viewBox` を変えて行うこと。** CSS の `transform: scale()` は
> **既にラスタライズした絵を使い回す**ので文字を描き直さず、**測りたいコストが消える**。

| 実績 | 左端 | `actualStart` |
| 実績 | 右端 | **`actualDuration`**（置いた日付から稼働日数を算出する） |
| マイルストーン | 点そのもの | 平行移動のみ（端点は持たない） |
| Resume | アイコン | `resume` |

### 3-2. 掴み代は見た目より大きくとる

```
予定の端点      予定バーの上下に 6px ずつはみ出させる
実績の端点      実績バーの帯だけ（予定より狭い）
フェード        15 x 15px の角
ダミーの実績線  見た目 11px に対し 30 x 20px の当たり判定
```

**予定の高さ > 実績の高さ**なので、**上下の縁を狙えば予定、真ん中を狙えば実績**が掴める。
モードで切り替える必要がない。

> **ダミーの実績線の掴み代が小さすぎると着手できない。** モックで実際に起きた不具合である
> （11 x 10px では的が小さく、クリックできているのに気づけない）。

### 3-3. 優先順位

```
端点 > 名称ラベル > バー本体
```

理由: 端点は範囲が小さいので、大きい領域に負けると永久に掴めない。**小さいものを優先する。**

### 3-4. ダミーの実績線（初回入力）

実績が無いタスクには、**中抜き＋破線**の欠片を予定の開始位置に描く。掴むと `actualStart` が入り、
`actualDuration` が 0 の実績バーになってベタ塗りに変わる。

- **Start ボタンは作らない。** 最頻の操作（初回入力）の前に 1 クリック増え、モードも 1 つ増える。
- **中抜き・破線を選ぶ理由**: 作図慣行で「中抜き・破線枠＝未着手」の意味が定着しているため、
  学習が要らない。§2-4 で完了に中抜きを使わないと決めたのと矛盾しない（本来の意味どおりの用法）。

## 4. イナズマ線（Progress Line）

### 4-1. 頂点の規則

**規則は 1 文**: **動いているべき日を過ぎているものだけ、その日に頂点を打つ。**

| 状態 | 頂点 |
|---|---|
| 完了 | **打たない** |
| 中断・再開日未定 | **打たない**（止めると決めたものを遅れとして数えない） |
| 中断・再開予定あり | `resume` < 基準日 なら **`resume`** に打つ。まだ来ていなければ打たない |
| 未着手 | `start` < 基準日 なら **`start`** に打つ。まだ来ていなければ打たない |
| 進行中 | **実績バーの右端**（`actualStart + actualDuration`）に打つ |

未着手の `start` と中断の `resume` は、どちらも「ここから動くはずだった日」なので同じ扱いになる。

### 4-2. マルチバー行 — **段ごとに分けて計算し、同じ段では最も遅れた頂点が勝つ**

**`user-order.md` 項 53 は「最も遅れた頂点が勝つ」＋「段ごとに計算する」＋「途切れさせない」へ改訂済み。**

> ⚠️ **2026-07-30 追加**: 「行ごとに 1 頂点」ではなく「**段ごとに 1 頂点**」に細分化した。

```
同一行で【同じ段】に複数のタスクがある   →  最も遅れた頂点が勝つ（1 段につき 1 頂点）
同一行で【段が違う】                     →  段ごとに頂点を分けて計算する
```

**なぜ段で分けるか**: 段が違うタスクは**画面上の高さが違う**。高さの違うものを 1 つの頂点に丸めると、
イナズマ線が「どの高さのどのタスクを指しているのか」が読めなくなり、強い違和感が出る。
**同じ段＝同じ高さに並ぶものだけが、1 本の頂点を共有してよい。**

イナズマ線は結果として**段の数だけ折れ点を持つ**。行の中で 3 段あれば、その行で 3 回折れる。

**変更理由**: 項 53 自身がイナズマ線の目的を「**どこがボトルネックか可視化**」と書いている。
最良値を採ると、行内に致命的に遅れたタスクがあっても隠れてしまい、目的と矛盾する。
マルチバーは本ツール最大の差別化（最優先事項 2）なので、1 行に複数タスクが載るのが標準である。

**実証**（モックで確認）:

```
1 行に 3 本  基準日 7/17
  前工程  7/1–7/7    完了            → 打たない
  本工程  7/9–7/15   右端 7/11       → 頂点 7/11   遅れ 6 日
  後工程  7/17–7/25  右端 7/19       → 頂点 7/19   遅れなし

最も遅れた（新）  行の頂点 = 7/11   6 日の遅れが見える
最も進んだ（旧）  行の頂点 = 7/19   遅れが完全に消える
```

**イナズマ線は途切れさせない** — **確定 2026-08-01**

**上端から下端まで 1 本の折れ線で描く。** 行ごと・段ごとに切り離して描いてはならない。

```
頂点のある段    その頂点を通る（§4-1 の規則で決める）
頂点のない段    基準日の位置を通る
```

**頂点のない段**とは、完了だけの段・中断で再開日未定だけの段・まだ動く日が来ていない段である。
そこは**遅れていない**のだから、線は基準日の位置に戻る。

**根拠**: §4-3 で調べた描画ライブラリは、頂点を打つ条件を満たすものだけに頂点を置き、
**「それ以外は直線」**として実装している。基準日に戻すのはこの直線そのものである。

**なぜ切り離してはならないか**: 途切れた縦線が段ごとに浮いていると、
どこが遅れの先端なのか読めない。イナズマ線は**基準日という 1 本の縦線がどれだけ歪んだか**を
見せる図であって、段ごとの独立した目盛りではない。

> **完了した段でも基準日に戻すだけで、右へ尖らせてはならない。**
> 右へ尖らせると「進んでいる」という別の主張になり、§4-3 で外すと決めた作図と同じものになる。

### 4-3. 完了タスクを尖らせない根拠（調査）

| 裏付け | 強さ |
|---|---|
| ある描画ライブラリ 1 本の**実装コードを読んだ**（製品名は中立化で消したので**再検証不能**）。そのコードが明示 — 頂点を打つのは「基準日より前に開始 かつ 進捗 < 1」または「基準日以降の開始 かつ 進捗 > 0」だけ。それ以外は直線 | **強** |
| MS Project の実挙動 — 「100% 完了で進捗点より前のタスクに左への尖りは意味を成さない」 | 中（**公式ドキュメントに記述なし**） |
| MS Project は未来開始のタスクを進捗線から除外する | 中〜強 |

> ⚠️ **日本のイナズマ線の作図慣行どおりに作ると壊れる。** 複数の日本語資料が一致して
> 「完了した場合は右端に点を打つ」と書いており、そのまま実装すると**完了タスクが左へ尖って
> 「遅れている」ように見える**。意図的に外す判断である。

> ⚠️ **MS Project の進捗線を全面的に真似ない。** 調査で、サマリタスクが常に含まれて除外できず、
> その頂点位置は「意味がない」と専門家が述べていることが確認できた。参考にはするが基準にはしない。

### 4-4. 基準日の縦線は常時表示にしない

**却下した案**: 「`[実績]` が ON のときは基準日の縦線を常に描く（表示トグルで消させない）」。

**却下理由**: イナズマ線だけを見たいとき、カーソルだけを見たいときに邪魔になる。
**表示内容はユーザーが選べるべき**である。`user-order.md` 項 43 をそのまま維持する。

縦線を消しても遅れは読める。**進捗マーカーの `(!)`** が遅れの有無を（判定は §2-4 の 3 条件）、
**遅れの日数**が量を示す。

### 4-5. 採らない方式

**MS Project 式のデータ正規化は採らない。** MS Project は描画で例外処理する代わりに、
実績データをステータス日へ寄せるオプション（基準日より後の完了部分を基準日まで戻す等）を持つ。
これは**ユーザーの入力データを書き換える**ため、Undo・自動保存・MSPDI 往復整合のすべてに波及する。
本ツールの価値は構造化データを保持することなので採用しない。

## 5. LOD（拡大縮小による表示の増減）

### 5-1. 判定は WBS の階層の深さ

**`importance`（重要度）を廃止する。** 代わりに **WBS の階層の深さ**で判定する。

```
縮小すると、深い階層のタスクから順に消える
```

深さは MSPDI の `OutlineLevel` に対応するので、**拡張領域を 1 枠も消費しない**。
`user-order.md` 項 36 の「判定は `importance`」を差し替える。

### 5-2. `OutlineLevel` は導出する。クランプの議論も起きない

**階層を持つのは `wbs_parent_uid`（軸A）である**（既存の確定。`grs-native-erd-ja.md`）。
`OutlineLevel` はそこから**導出する値**なので、GRS は保存しない。

```
import   OutlineLevel ＋ タスクの並び順  →  wbs_parent_uid を組み立てる
export   wbs_parent_uid の深さ           →  OutlineLevel を算出して書く
LOD      wbs_parent_uid の深さに min( , 5) をかけて判定する
```

**これでクランプするかどうかの議論自体が消える。**

- **LOD の判定でだけ 5 で頭打ちにする。** 6 段以上のプロジェクトは実務でほぼ無いので、判定は 5 段で足りる。
  > **🔎 「6 段以上は実務でほぼ無い」の出典は `handover/` に無い。** 調査でも実測でもなく、推定である。
  > **これをデータ側の根抠に使ってはならない** — かつて WBS を 5 段に潰す根抠に流用されていた（§5-2 で撤回済み）。
  > **描画の判定に限って使う分には実害がない**（外れても深い階層が早く間引かれるだけで、データは動かない）。
- **書き戻す値は階層そのものから算出する**ので、7 段の階層が来れば 7 段で戻る。丸める処理が存在しない。
- 判定式に `min( , 5)` が 1 つ入るだけで、**モデルは複雑にならない**。

> 保存値を丸める案は採らない。`OutlineLevel` はタスクの並び順と組み合わせて**階層そのものを表す**要素なので、
> 5 に丸めると 6 段目以下が 5 段目に潰れ、親子関係が変わる。`UID` が保たれてもタスクの所属先が変わってしまう。
> 導出方式ならこの問題が発生しない。

### 5-3. 軸A と 軸B は別物

| 軸 | 何の深さか | 上限 | export | LOD の名前 | 引き金 | 定数 |
|---|---|:--:|:--:|---|---|---|
| **軸A** | `OutlineLevel`（WBS の階層） | 相手次第 | **する** | **タスク LOD** | **幅**が足りない（`zoomX`） | `taskLevelOfDetailReadablePx` |
| **軸B** | `TaskGroup` の階層 | **5**（項 27） | **しない** | **グループ LOD** | **フォント下限**を割る（`zoomY`） | `groupLevelOfDetailBase` / `groupLevelOfDetailRatio` |

**混同しないこと。両方に LOD がある。** — **引き金による使い分けを確定 2026-08-02（ユーザー判断）**

- **横に縮めて幅が足りなくなったら軸A を減らす**（深い WBS のタスクを描かない）。
- **縦に縮めてフォントが下限を割ったら軸B を減らす**（深い `TaskGroup` を親へ畳む）。
  行数が減って残った行の高さが増えるので、**フォントが下限を上回る**。§2-4-1 を見ること。

> **旧版は「LOD の判定に使うのは軸A の `OutlineLevel` である」とだけ書いていた。**
> これは**タスク LOD については正しいが、フォント下限の話には当てはまらない**。
> 軸A を減らしても行は高くならないので、引き金が解消しない。

**時間軸 LOD（`Time Ruler` の粒度）はどちらの軸でもない。** 3 つの LOD の一覧は
`../03-ui-naming/handover-ui-parts-ja.md` §1-2。

### 5-4. ユーザーが明示的に切り替える表示 / 非表示

**GRS の JSON だけで持ち、MSPDI へ渡さない。** 軸B を export しない方針と一致する。

## 6. ラベルとレイアウトの順序

### 6-1. 名称ラベルの配置

**考え方**: **ラベルを表示しても形状が見える / 触れること。**

```
1. タスクの幅に収まる            → 中に書く
2. 収まらない                    → まず 全角12 / 半角24 で打ち切る
3. 打ち切っても収まらない        → 右に出す
4. 右に出すと他と干渉する        → タスクを上下にずらす
```

- 打ち切ったときは**ツールチップで全文**を出す（項 17 の既存規則）。
- **データは切らない。** 表示だけ打ち切る（往復無損失）。
- フォントサイズは**タスクの高さの 80%。下限 12px でクランプ**（§2-4-1 で 10px から改めた）。ズームで変わる。

### 6-2. ラベル幅は概算する。キャッシュしない

```
ラベル幅 ≒ (全角の数 x 2 + 半角の数 x 1) x フォントサイズ x 係数
```

- **テキストの実測をしない。** ブラウザのテキスト計測は重く、1000 アイテムで毎フレーム呼ぶと 60fps が出ない。
- 掛け算 1 回なので**毎フレーム計算しても安い**。
- **キャッシュを持たない。** 古い値が残る事故を原理的に起こさないため。

### 6-3. 積み段に機能上の上限を設けない

**`user-order.md` 項 30-7 を書き換える。**

```
現行  段数には上限を設け、超えたら最終段を再利用する（帯高を無限に伸ばさない）

新    積み順（stackOrder）に機能上の上限は設けない。必要なだけ広げる。
      暴走を止める安全弁として十分に大きい上限を持ち、通常運用では到達しない値にする。
      到達したら人に知らせる。
```

**「最終段を再利用する」（＝重なりを許して同じ段に押し込む）挙動は廃止する。**
マルチバーが本ツール最大の差別化である以上、勝手に重ねてはならない。
安全弁に到達したときは**黙って捨てず知らせる**（項 61 と同じ考え方）。

> 項 30-7 の「段」は **`stackOrder`（積み順）** であって `OutlineLevel` ではない。
> 用語表が「`stackOrder` = 1 行の中の段」と定義しており、項 30 全体が
> 「1 行の中で時間が重なる `Task` を縦に積む」規則だからである。

### 6-4. レイアウトの計算順序

依存線・ラベル・積み順は互いに影響するので、**循環を切る順序**を定める。

```
1. 依存関係から「最小間隔の制約」を作る    経路は引かない。前後が接するなら間隔を空ける規則だけ
2. ラベルの占有幅を概算する                §6-2
3. 積み順の割当                            1 と 2 を占有幅の入力にする → タスクの位置が確定
4. 依存線の経路を引く                      位置が確定済みなので 1 回で決まる
```

**要点は「依存線が必要とする余地」と「依存線の経路そのもの」を分けること。**
前後のタスクが接しているときに引き出し / 引き入れの幅が要るのは**幾何的な最小間隔**であって、
経路探索の結果を待たなくても決まる。それを積み順割当の入力にすれば、経路は最後に一度引くだけで済む。

**再計算が要らず 1 パスで終わる**ので、ぬるサク（最優先事項 1）にも効く。
経路は保存しない（項 48）ので、最後に引き直す設計とも噛み合う。

### 6-5. 依存線とラベルの干渉は計算しない

**ラベルを避けて依存線を引く計算はしない。** やりすぎでバグの元になる。
依存線とラベルが重なることは許容する。

## 7. 進捗の編集入口

| 入口 | 採否 |
|---|---|
| **実績バーの右端をドラッグ**（`actualDuration` を変える） | **採用** |
| **進捗マーカーのクリック**（3 状態を巡る） | **採用** |
| **Resume アイコンのクリック / ドラッグ** | **採用** |
| Properties Panel での日付入力 | 採用（従来どおり） |
| 右クリックのクイック設定（0 / 25 / 50 / 75 / 100%） | **不採用**（理由は下記） |
| キーボードでの進捗増減 | **不採用**（同上） |

**不採用の理由は 1 つ**: **`percentComplete` は導出値であって、人が入力する値ではない**（§1-4）。

```
percentComplete = round( actualDuration ÷ (finish − start) x 100 )
```

率を直接入力させると、この式が成り立たなくなる。**率から `actualDuration` を逆算する**か、
**式を捨てて率を独立した保存値にする**かの二択になり、どちらもモデルが壊れる。

- 逆算すると、25% を選んだ瞬間に実績バーの右端が勝手に動く。**「完了にしても右端は動かない」（§2-1）と衝突する。**
- 独立させると、日付と率が別々に編集できてしまい、**両者が食い違った文書**を作れるようになる。

**人が置くのは日付である。率はその結果として出る。** これを守る限り、率を直接いじる入口は作れない。

> ⚠️ **次の担当者へ**: この 2 つは「便利そうだから」という理由で復活させたくなる。
> **復活させるとモデルが壊れる。** 率を動かしたいなら実績バーの右端をドラッグする。それが同じ操作である。

> **アクセシビリティの確認**: WCAG 2.1 の 2.1.1（キーボード操作可能）はドラッグ操作に
> キーボード等価物を要求する。**Properties Panel で日付を入力できればこれを満たす**
> （ドラッグは代替手段であって唯一の手段ではない）。Properties Panel が
> キーボードで到達・編集できることを実装時に確認すること。

**中断は専用操作を持たない。** 実績バーの右端をドラッグすることが「ここまで進んだ」であり
「ここで止まっている」でもある。同じ 1 つの操作なので、ボタンもモードも増えない。

**誤操作対策は Undo のみ。** 調査した範囲で、進捗のドラッグに確認ダイアログを出す製品も、
修飾キーを必須にする製品も 1 つも無かった。業界の答えは一貫して「確認するのではなく Undo で戻す」。

## 8. Undo / Redo

| 項目 | 決定 |
|---|---|
| 回数 | **50 回**。加えて**合計メモリの上限**でも打ち切る（1 操作で大量のタスクを変更した場合に備える） |
| 方式 | **不変更新のスナップショット**。明示的な差分機構（JSON Patch 等）は作らない |
| ドラッグ | **押した瞬間と離した瞬間で 1 エントリ**にまとめる |
| localStorage | **履歴を入れない**。保存するのは現在の文書だけ。クラッシュ復旧で履歴は失われるが許容する |
| Carry ストア | **履歴の対象に含める**。含めないと Undo で往復無損失が壊れる |

**スナップショットを選ぶ理由**: 状態管理が不変更新なので、**変更されていない部分は同じオブジェクトを共有する**。
50 スナップショット持っても実メモリは差分ぶんしか増えない。明示的な差分機構は
「差分の適用が壊れると文書が壊れる」という破壊的な失敗モードを持つので採らない。

**履歴に入れない操作**（入れると「Undo したのに何も戻らない」に見える）:


### 9-5. `progressStatus` を廃止する理由

1. **GRS 独自の語**であり、MSPDI に受け皿が無い（項 20 の表で「拡張領域」行き）。
   `PercentComplete` とは別物（自由文字列 対 整数）。
2. **状態が構造化されたので役目を失った。** 未完了 / 完了 / 中断（再開日あり）/ 中断（再開日未定）は
   `actualFinish` `resume` `resumeValid` で一意に表せる。遅れは基準日と
   `finish` / `start` / `resume` の比較で導出できる（§2-4）。
3. 廃止すると **`Progress` を冠する語が 3 つから 2 つに減る**（`Progress Line` と `Progress Marker`）。
4. **拡張領域の枠を 1 本節約**できる。
5. 自由文の説明は `notes` で書ける（テキスト列を増やさない方針とも合う）。

### 9-6. UI パーツ木への追加

本設計が足したパーツは **`Progress Marker`**（`Task Bars` の子）と **`Progress Line`**（`Canvas Overlays` の子）である。
**木の正は `../03-ui-naming/handover-ui-parts-ja.md` §3。ここには複製しない**（反映済み）。

`Progress Marker` と `Progress Line` は**別のパーツ**。語幹が揃うのは「どちらも進み具合を示す」ため。
片方は行を横断する線、片方はタスクに付く印、と役割で読み分ける。

## 10. MSPDI との対応

### 10-1. 書き出しの規則

```
常に書く        ActualStart
                ActualDuration = 実績バーの右端 − actualStart（稼働日）
                OutlineLevel   = wbs_parent_uid の深さから算出（§5-2）

未完了のとき    PercentComplete = ActualDuration ÷ (Finish − Start) x 100  ※頭打ちにしない

完了のとき      ActualFinish       実際に終わった日
                RemainingDuration  0 を書く
                PercentComplete    要素そのものを書かない
                Stop 空 / Resume 空

中断のときだけ  Stop = actualStart + actualDuration
                Resume / ResumeValid
```

**完了時の 3 行は §1-4 の確定（2026-07-30）である。** `ActualFinish` があり `RemainingDuration` が 0 なら
完了はその 2 つで一意に決まるので、`PercentComplete` を併記しない。
併記すると、100 超を丸めない方針と MS Project の意味論が衝突する場面をわざわざ作ることになる。

> **`RemainingDuration` は原則 `Carry`**（進行中タスクでは `Duration − 進捗` が破綻するため再計算できない。
> `../02-data-model/grs-mspdi-field-ledger-ja.md`）。**完了時だけ GRS が 0 を書く**（Own 扱い）— **確定**。
> 完了時は `ActualFinish` が入っているので残りが 0 であることが確定しており、破綻しない。
> **この 1 点だけが Carry の例外である。**

**`Stop` を中断のときだけ書く理由（重要）**

`Stop` / `Resume` は MS Project では**分割（中断）されたタスクの文脈**で使われる要素である。
中断していないタスクに `Stop` を書くと、**相手ツールが「このタスクは分割されている」と解釈して
隙間を描く恐れ**がある。解説書にその挙動の記述はなく、確かめる術がない。

`ActualDuration` の定義は "The span of actual working time for a task so far" で**一意**であり、
誤解の余地がない。**実績の長さは `ActualDuration` で伝え、`Stop` は中断の事実を伝えるときだけ使う。**

これは「`Stop` は中断、`Finish` は完了。わざわざ名称を変えているから別物」という直観とも一致する。

### 10-2. GRS が値を決めて書き出す要素

```
Start / Finish / ActualStart / ActualFinish / Deadline / Milestone
ActualDuration / PercentComplete
Stop / Resume / ResumeValid          ← 本セッションで拡張領域から Own へ変更
OutlineLevel                         ← ただし Own ではない。下記
```

> ⚠️ **`OutlineLevel` は Own ではなく Consume である**（2026-07-30 整理）。
> 台帳（`../02-data-model/grs-mspdi-field-ledger-ja.md` §7）の定義は
> **Own＝保存値を書く / Consume＝読む（必須）＋構造から再生成**であり、
> `OutlineLevel` は `wbs_parent_uid` から**再生成する**ので Consume に当たる。
> 台帳自身が Consume の代表例として `OutlineLevel`→WBS 木 を挙げている。
>
> **Own にすると「列として保存する」意味になり、`wbs_parent_uid` と二重管理になる。**
> 2 軸設計がドリフトを防ぐために避けた形に戻ってしまう。
>
> 本節の見出しを「Own」から「**GRS が値を決めて書き出す要素**」に改めたのはこのためである。
> この一覧は「GRS が値に責任を持つ」ものを並べており、**台帳の仕訳とは別の観点**である。

**変更点**: 前プロジェクトは §3-4 #8 で「`Stop` / `Resume` は MSPDI へ写さず拡張領域に置く」と決めていた。
理由は「MSPDI の `Stop` の意味は『実績が入っている境界』で、GRS の中断/再開とずれる」だった。

**この理由は消えた。** 解説書で `Stop` = "the end of the actual portion of a task" と確定し、
GRS の実績部分の終わりと**同じ意味**であることが分かったため。ずれていたのは旧モデルの
「中断/再開」であって、新しいモデルとは一致する。

### 10-3. 拡張領域の消費

| 属性 | 旧 | **新** |
|---|---|---|
| `progressStatus` | 1 枠 | **0**（廃止） |
| `stop` / `resume` | 2 枠 | **0**（MSPDI ネイティブへ） |
| 中止フラグ | （未検討） | **0**（`resumeValid` で表現） |
| `importance` | 1 枠 | **0**（廃止。LOD は `OutlineLevel`） |
| `fadeInDays` / `fadeOutDays` | 2 枠 | **2 枠** |
| **合計** | **6 枠** | **2 枠** |

**往復させる属性の別表**

| 属性 | 型 | 割当先 | 往復させる理由 |
|---|---|---|---|
| `fadeInDays` | 整数 | `Number1` | 日付の曖昧さは業務情報 |
| `fadeOutDays` | 整数 | `Number2` | 同上 |

**`Number` 枠が 2 本あれば足りる。** `Text` も `Date` も `Flag` も使わない。

### 10-4. 枠は先頭から使う（C-2 の反転）

**既存の確定 C-2「大きい番号から取る（衝突確率が低い）」を反転し、先頭から使う。**

**理由**: **上限を知らないと大きい番号から取れない。** `Text1` は必ず存在するが `Text30` が
存在するかは不明である。これは C-1 の但し書き「**本数を知らないまま惜しむのは根拠にならない**」と同じ論理。

衝突リスクは既存の仕組みで吸収される。

| 既存の確定 | 内容 |
|---|---|
| C-4 | 定義側と値側の**両方を見て**使用中か判定する |
| C-5 | 衝突したら未使用枠へ**退避**する。全枠満杯なら JSON のみ ＋ 通知 |

### 10-5. 設定ファイルは作らない（考慮のみ）

将来、入力するデータによって拡張領域の使用有無が変わる可能性がある。
**実装はしないが、設計で拡張点だけ確保する。**

```
枠の割当表を定数として埋め込まない。データとして持つ
```

C-6 で「割当は MSPDI の `FieldName` に書く（これが正）＋ JSON の `documentSettings` にも写す」と
確定しているので、その入口が外部化の受け皿になる。
**外部設定ファイルは単一 HTML・完全オフライン（最優先事項 4）に反するので作らない。**

### 10-6. 往復無損失の担保

- **未編集タスクは受け取った値をそのまま書き戻す**（既存の確定規則 §3-4 #3）。
  `PercentComplete` を日付から再計算すると丸め誤差が出るが、未編集なら Carry をそのまま返すのでずれない。
- **編集したタスクだけ再計算する。** 編集の定義は「`start` / `finish` / `actualStart` /
  `actualDuration` / `actualFinish` / `resume` のいずれかが変わったタスク」。
- **工数側（`Work` 系）は再計算も削除もせず温存して通知する**（既存の確定規則 §3-4 #5 / #6）。

### 10-7. XSD と解説書で確認した事実（推測ではない）

| 事実 | 内容 |
|---|---|
| `CompleteThrough` | **存在しない**。MS Project が進捗の塗りに使う日付は MSPDI に serialize されない |
| `Active` | **存在しない**。MS Project の「非アクティブ タスク」は本スキーマに無い |
| `IsNull` | 存在するが「**空行かどうか**」の意味。中止の表現に流用してはならない |
| `PercentComplete` | `xsd:integer`。**制約ファセットなし**。範囲の記述もなし |
| `ActualDuration` | "The span of actual working time for a task so far ... **can be calculated in two ways, either based on percent complete or remaining duration**" |
| `Stop` / `Resume` / `ResumeValid` | Min 0 / **Max 1**。履歴を持たない |
| `OutlineLevel` | `xsd:integer`。"The number that indicates the level of a task in the project outline hierarchy."（XSD 1682 行） |
| `Baseline` | **存在する**。当初の `Duration` / `Start` / `Finish` を保持する |
| `DurationFormat` | `7=d`（日）/ `8=ed`（経過日）を含む。**稼働日と暦日の区別がここにある** |
| `TimephasedData` | `maxOccurs="unbounded"` だが中身は工数・原価・完了率の時間配分。**バーの分割区間ではない** |

## 14. この設計で消えた問題

記録として残す。同じ議論を繰り返さないため。

| 消えた問題 | 理由 |
|---|---|
| 進行中の実績バーの右端が未定義 | `actualDuration` が定義そのもの |
| 「完了させるとバーが跳ねる」 | `actualFinish` に右端の日付が入るので動かない |
| 「未完了に戻したとき進捗率をどうするか」 | 完了率が導出値になったので自動で戻る。完了直前の値を覚える仕組みが要らない |
| 「完了率の分母をどちらにするか」 | MSPDI の `PercentComplete = ActualDuration / Duration` に一致させて決着 |
| 「到達点という新語をどう名づけるか」 | `ActualDuration` が同じ意味。新語が要らない |
| 「中止を拡張領域のどの枠に置くか」 | `resumeValid = false` で表現でき、枠を使わない |
| 「予実が重なって編集できない」 | 予定の高さ > 実績の高さ で幾何的に解決。モードが要らない |
| 「イナズマ線の頂点の 5 ケース」 | 実績バーの右端を参照するだけになり、式が消えた |
| 「LOD の重要度を誰が付けるのか」 | `OutlineLevel` で判定するので、人が付ける属性が要らない |
| 「拡張領域の枠が足りるか」 | 消費が 6 枠 → 2 枠に減り、先頭から使えばまず足りる |
| 「`Rows` と `TaskGroup` がどちらも『行』」 | `TaskGroup` = タスクグループ に改めて「行」が空いた |
| 「レイアウトの計算が循環する」 | 依存線の「余地」と「経路」を分けて 1 パスにした |
