## 0. この文書の使い方（先に読む）

### 0-1. コードのコピペは禁止

**本書に出てくる既存コードは、あくまで参考案である。** 次期は**完全新規に設計・実装する**こと。
理由は 2 つ:

1. **現行コードは全て旧名**（`item` / `itemKind` / `laneIndex` / `section` / `ScheduleItem` …）。
   確定名は `handover-ui-parts-ja.md` にある（`Task` / `Task.milestone` / `TaskGroupMember.stackOrder` /
   `TaskGroup`）。**コピペは旧語彙を次期に流入させる**。前プロジェクトで「バグが止まらない」根因は
   語彙の重複だった（`refactor-gui-data-separation-ja.md`）。同じ穴に落ちる。
2. **設計判断とその代償**が本書に書いてある。**判断を読んで、自分で書く**のが引継ぎの中身であって、
   動くファイルを受け取ることではない。

したがって本書は「この関数のこの判断が効いた / 罠だった」を**設計の言葉**で書き、
実物は凍結リポジトリのパスを指す。**参照はしてよい。写してはならない。**

### 0-2. 性能 PoC は「早期に」やる（手戻り削減の要）

前プロジェクトは Phase 4 M1（ウォーキングスケルトン）の時点で性能 PoC ゲートを置き、
そこで方式（SVG 継続 or Canvas 併用）を決めた（DEC-001）。**この順序は正しかった**ので次期も踏襲する。

> **次期への指示**: レンダリング方式を確定する前に、**骨格だけの状態で ~50 行 / ~1000 アイテムを
> 実ブラウザで計測する**。数字が出る前に機能を積むと、方式変更の手戻りが全機能に波及する。

ただし前プロジェクトは**その 1 回で終わってしまった**（§3-1 N-1）。次期は
「**機能を積んだ節目で再計測する**」を明示的に工程へ入れる。M1 の数字は M1 の数字にしかならない。

## 1. 効いた手

各項は「何をしたか」→「なぜ効いたか」→「代償」の順。パスは凍結リポジトリの参照先。

### E-1. ズームを world 座標に焼き込み、SVG は translate だけにした 〔最重要〕

`src/domain/usecase/view-transform.ts` / `svg-renderer.ts` の `diffRender`

- コンテンツ群 `<g>` に与えるのは `translate(leftPaneWidth - scrollX, topOffset - scrollY)` **のみ**。
  **`scale()` は一切使わない。** ズーム倍率はレイアウト時に world 座標へ掛け込む。
- **なぜ効いたか**: `scale()` を使うと線幅・フォントサイズ・矢じり・角丸 R・破線パターンが全部
  倍率で歪み、それを打ち消す `vector-effect` や逆スケールが全レイヤに伝染する。
  translate だけなら **world px == screen px** が恒真になり、
  ヒットテストの許容半径がそのまま「画面上の掴み代」になる。座標系のバグが構造的に消える。
- **代償**: ズーム 1 段ごとに**全アイテムの再レイアウトが必要**になる（→ 罠 T-2）。
  パン（スクロールのみ）は再レイアウト不要で transform 差し替えだけ、という非対称が生まれる。
  この代償は**意識して選んだ**ものであり、次期も同じ選択を推奨する。

### E-2. 座標空間を 3 つに命名し、値オブジェクトに閉じた

`view-transform.ts`（WORLD / CONTENT / CLIENT）

- 元は `worldToScreen`（rect 込み）と `worldToScreenX/Y`（rect 抜き）という**見た目が同じで空間が違う
  2 系統**があり、取り違えるとオーバーレイがビューポート offset ぶんズレた。
  **「テストは緑だが実機で X だけズレる」の典型**。
- メソッド名に必ず**行き先の空間名**を入れ（`toContent` / `toClient`）、各対が厳密な逆関数である
  ことを型で担保した。以後この種のズレは出ていない。
- 次期も**空間の命名は最初にやる**こと。後付けは全レイヤ改修になる。

### E-3. キー付き差分（create / patch / remove）

`src/adapters/render/layers/item-layer.ts` の `render()` / `mountedById: Map<itemId, MountedItem>`

- 可視集合を `desiredIds` に集め、無ければ生成、あれば**その場でパッチ**、集合から外れたら除去。
  ノードを作り直さないので、選択枠・フォーカスリング・ラベル層などの**子ノードの寿命が保たれる**。
- 生成数 / 除去数 / 現存数を毎フレーム記録する（→ E-9）。

### E-4. ビューポート仮想化 ＋ オーバースキャン

`src/domain/usecase/viewport.ts`（`computeViewportWindow` / `placementIntersectsWindow` /
`OVERSCAN_MARGIN = 96`）

- 可視矩形の外側 96px ぶんだけ先に作っておく。速いパンで空白が覗くのを防ぐ。
- **効果の実測**: 1000 アイテムで**実 SVG ノード 93**（§2）。DOM 量は総数ではなく
  **可視密度**に比例する、というのがこの設計の本質。

### E-5. LOD の閾値を単調関数にした

`src/domain/usecase/lod-selector.ts`（`lodThreshold(zoom) = 1 / (1 + zoom)`）

> ⚠️ **引き継ぐのは「単調関数にする」という一点だけ**（2026-07-30 追記）。
> **入力だった `importance`（重要度）は廃止した。** 次期の LOD は **WBS の階層の深さ**で判定する
> （`../07-plan-actual/handover-plan-actual-decisions-ja.md` §5-1）。**単調性の要求は入力が変わっても同じ。**

- 閾値がズームに対し**厳密に単調減少**。ゆえに「**縮小したのに可視集合が増える**」が原理的に起きない。
  経験則の羅列（「年表示なら深さ 2 まで、ただし…」等）にすると必ずこの逆転が混入する。
- **なぜ効いたか**: 縮小＝間引き強化が保証されるので、縮小操作が常に軽くなる方向へ働く。

### E-6. rAF バッチ（二重スケジュールのガード ＋ 同期版の cancel）

`svg-renderer.ts` の `requestRender()` / `renderNow()`

- `requestRender()` は `rafHandle !== null` なら**即 return**。1 フレームに何回状態が変わっても
  描画は 1 回。ドラッグ中に毎イベント同期再レイアウトしていた問題（レビュー M2-M-02）はこれで消えた。
- `renderNow()`（同期）は**保留中の rAF を cancel してから**描く。二重描画を防ぐ。
- 起動時は `renderNow()` を同期で呼ぶ。**rAF 任せにすると初回が空白になる**（→ 罠 T-7）。

### E-7. 「無限に増える集合」と「有界な装飾」で描画戦略を分けた 〔2層戦略〕

- **無限に増える側**（アイテム、依存線）= キー付き差分 ＋ 仮想化。
- **有界な側**（今日線・カーソル・イナズマ線・コメント引出し・角丸枠・透かし・ルーラー）=
  **毎フレーム全消去→全再構築**（`svg-renderer.ts` の `renderOverlay`）。
- **なぜ効いたか**: 装飾に差分機構を持ち込むとコードが倍になるのに、要素数は数十で頭打ち。
  **単純さを買った**。ただし境界を見誤ると効かない（→ 罠 T-1、T-5）。

### E-8. テキスト計測 API（`getBBox` 等）を一切使わなかった 〔効果大〕

`src/adapters/render/item-geometry.ts` の `estimateInnerLeftLabelExtentPx`
（`文字数 × fontSize × LABEL_CHAR_WIDTH_RATIO`）

- **`src/` 全体に `getBBox()` は 1 箇所も無い。** 文字幅は**解析的に推定**する。
- **なぜ効いたか**: `getBBox()` / `getComputedTextLength()` は**同期レイアウトを強制**する。
  ラベル 1 個ごとに呼べば、可視 100 アイテムで 1 フレームに 100 回の強制レイアウト。
  ここは「やらなかったから速い」典型で、**後から直すのが最も高い**部分でもある
  （ラベル衝突回避・自動配置がこの推定値の上に乗るため）。
- **代償**: 推定なので日本語・絵文字・プロポーショナル字形で誤差が出る。
  衝突回避が数 px 甘くなる。**この誤差は許容してよい**（ぬるサクが先）。
- `getBoundingClientRect()` は使うが、**wheel 1 イベントに 1 回**などに限定されている。
  ポインタ移動のホットパスには入れない。

### E-9. 構造化デバッグロガーで「仮想化が効いているか」を実機で見えるようにした

`svg-renderer.ts` の `log.debug('diff_render_complete', { live_node_count, created_count,
removed_count, total_item_count, dependency_node_count })`

- **実機で仮想化の生死を確認できる唯一の手段だった。** `live_node_count` が `total_item_count` に
  近づいたら仮想化が死んでいる、と 1 行で判る。
- 次期も**同等のフレーム計測ログを最初から入れる**こと。後から入れると
  「遅い」という報告に対して何も言えない期間が発生する。

### E-10. 依存線の障害物集合を「マウント済みアイテム」に限定した

`src/adapters/render/layers/dependency-layer.ts`

- 依存線は**少なくとも片端がビューポート内**のものだけ描く。障害物も可視集合のみ。
  総アイテム数に比例した経路探索を回避。
- `itemId -> Rect` を 1 フレーム 1 回だけ構築し、**同じ Rect インスタンス**を障害物としても
  端点としても使う。自分自身を障害物と見なす事故を同一性で防いだ。
- **代償**: 画面外の障害物を無視するので、パンすると**同じ依存線の経路が変わる**ことがある。
  経路を保存しない設計（`user-order.md` 48）なので破綻はしないが、**経路は安定しない**。

### E-11. スクリーン空間固定のオーバーレイ群を分けた（ADR-004）

- ズーム不変の装飾（角丸枠の R、透かし、ルーラー、カーソル）は world 群ではなく
  **screen 空間の別 `<g>`** に描く。ゆえに「角丸の R がズームで変わらない」（`user-order.md` 45）が
  逆スケール計算なしで満たされる。
- E-1（world は translate のみ）と組み合わせると、**倍率を打ち消す計算がどこにも要らない**。

### E-12. 入力の主導権を握った

`svg-renderer.ts` の `attachInputHandlers` / `handleWheel`

- `wheel` は `{ passive: false }` ＋ **常に `preventDefault()`**。ページが下でスクロールしない。
- パンは**明示ジェスチャ**（Ctrl/Cmd + ドラッグ、中ボタン）。素の左ドラッグではパンしない
  ＝ドラッグ中に日程表が滑って逃げない。
  > ⚠️ **この規則は改訂された（2026-08-01）**。**背景の上での素の左ドラッグはパンである**。
  > 懸念していたのは「アイテムを掴んだつもりで日程表が動く」事故で、**掴む対象があるかどうかで分ければ起きない**。
  > 正は `../03-ui-naming/handover-ui-detail-spec-ja.md` §5-2。
- ズームは**ポインタ中心**。ただし原点は「生のポインタ座標」ではなく
  **スケジュール局所座標**（左ペイン幅とルーラー高さを引いた点）。ここを間違えると
  ズーム時にカーソル下の行が画面外へ飛ぶ（実際に起きた）。
- **アイドル時は描かない**: ポインタ移動で再描画するのは
  **ガイドカーソルが有効なときだけ**（`guideMode !== 'none'`）。
  「常に再描画」にすると、何もしていないのに 60fps 描き続ける。

## 2. 実測値の基準線

### 2-1. 記録されている数字（**M1 骨格時点**）

計測: 2026-07-18、M1 ウォーキングスケルトン、実ブラウザ、**ユーザー立会い**。
出典: `project-records/decisions/DEC-001-rendering-approach.md` / `risk-register.md` RISK-001 /
`docs/spec/51-test-results.sdoc`。

| 規模 | 初期描画 | 平均 FPS | p95 フレーム | 実 SVG ノード | 判定 |
|---|---|---|---|---|---|
| **1000 アイテム / 50 行**（目標規模 = NFR-L1-002） | **4.6 ms** | **162.3** | **6.20 ms** | **93** | 大差で PASS |
| 10000 アイテム / 50 行（10 倍・スコープ外） | 45.2 ms | 20.0 | 66.70 ms | 860 | 既知上限 |

目標値: 初期描画 ≤ 1500 ms / 平均 ~60 FPS / p95 ~16.7 ms。

### 2-2. ⚠️ この数字の限界（必ず読む）

> **これは M1 骨格の数字であり、完成版の数字ではない。**
> 計測後に CR-004〜016、レンダラのレイヤ分割、予実 2 系統描画、オーバーレイ群
> （イナズマ線・コメント・角丸枠・透かし・ルーラー・ゴースト）が全部載った。
> **その状態では一度も再計測していない。** 数字は「方式選択の根拠」としては有効、
> 「完成品の性能」としては無効。

**次期は §0-2 の通り、骨格段階で自分の数字を取ること。** 上表は目標ではなく
「この方式ならこの桁が出る」という**桁の目安**として使う。

### 2-3. 読み取れる本質

| 観測 | 意味 |
|---|---|
| 1000 件で実ノード **93** | DOM 量は**総数ではなく可視密度**で決まる。仮想化が効いている証拠 |
| 10 倍で実ノード **860**（9.2 倍） | 総数 10 倍 → **可視ノードもほぼ 10 倍**。同じ画面に 10 倍詰めたので当然。**仮想化は密度を下げない** |
| 10 倍で初期描画 45.2ms（9.8 倍・線形） | 初期描画は**総アイテム数に線形**。仮想化しても**レイアウト計算は全件走る**（→ 罠 T-2） |
| 10 倍で p95 が 6.2→66.7ms（10.8 倍） | フレーム時間も総数に比例して崩れる。**DOM ではなく毎フレームの全件走査が支配的**である示唆 |

> **結論**: 前プロジェクトが仮想化したのは **DOM だけ**。**計算は仮想化していない**。
> 60fps を大差でクリアしたのは 1000 件が小さかったからで、方式が
> 密度に強いことを示したわけではない。**次期の伸びしろはここにある。**

## 3. 効かなかった手・踏んだ罠

### 3-1. 効かなかった / 効果を確認できなかった手

### 3-2. 踏んだ罠

**罠は「再描画を誘発するパターン」と「テストを通り抜けるパターン」の 2 系統**に分かれた。

#### A. 再描画・再計算を誘発するパターン

| # | 罠 | 何が起きたか | 教訓 |
|---|---|---|---|

> （`arrow` / `endpointSpan`）は実績バーを下にずらす**ことが確定したので、

> （同 §2-2。確定 2026-08-01）。

### 4-1. 依存線の自動配線

**凍結リポジトリの参照先**（読むだけ）:
`src/domain/usecase/dependency-router.ts`（428行, 汎用ルータ）/
`dependency-connector.ts`（257行, 日程表向けの特化規則）/
`tests/dependency-router.test.ts`（148行）/ `tests/dependency-connector.test.ts`（418行）

> 🔴 **本節の方式は撤回された（確定 2026-07-30）。経路の正は
> `../03-ui-naming/handover-ui-detail-spec-ja.md` §4-9 である。**
>
> | 前プロジェクトの方式 | 確定 |
> |---|---|
> | 9 点アンカーから経路を選ぶ | **2 点だけ**（先行の右辺中央 → 後続の左辺中央）。9 点は**アンカーの表現力**の話であって経路の規則ではない |
> | 候補を列挙して**辞書式に採点**する | **5 パターンを分岐 2 つで直接計算する。候補列挙も採点も探索も要らない** |
> | 折れ点は前進 0〜3 | **前進 0〜2 / 日程が重なる場合 ≤4**。「0〜3」と書いてはならない |
>
> 以下は**なぜその方式を採り、なぜやめたか**の記録である。設計としては採用しない。

**設計の要点（記録）**:

1. **層を 2 つに割る**。「矩形 A のアンカー → 矩形 B のアンカーを、障害物を避けて直交折線で
   結ぶ」という**汎用問題**（router）と、「日程表では先行の右辺から出て後続の左辺へ入る」という
   **ドメイン規則**（connector）を分けた。**この分割だけは生きている** — 確定版もドメイン規則の側だけを残し、
   汎用ルータを丸ごと不要にした。
2. **経路探索をしない**という判断は正しかった。A* 等の探索は密集時にコストが爆発し
   **フレーム時間が予測不能**になる。ぬるサクには「最良」より「**上限が読めること**」が重要である。
   - ただし**その先の手段が過剰だった**。候補列挙 ＋ 辞書式採点（障害物との重なり長 / 折れ点数 / 総長）まで
     必要だと考えたが、**アンカーを 2 点に固定したら経路は 5 パターンしか無く**、
     分岐 2 つで直接書ける。列挙も採点も要らなかった。
   - **教訓**: 「探索をやめる」と「候補を列挙して採点する」は別の判断である。
     **入力の自由度（アンカー 9 点）を先に絞れば、後段の機構がまるごと消える。**
3. **経路は保存しない**（`user-order.md` 項 48）。毎回再計算する。**これは生きている。**
   保存値と再計算結果がドリフトする問題が原理的に消える。
4. **折れ点の上限は非対称である**（DEF-005 で判明）。この事実は生きており、確定版に入っている。
   出口／入口の水平な走りも幾何として同節にある
   （入口の走り = 矢印の三角形の 2 倍。**出口の走りはそこから三角形ぶんを引いた 1 倍**。
   出口には矢印が無いので三角形の長さが要らない）。
5. **性能上の注意**: 障害物は可視集合に限る（E-10）。**確定版では経路が直接計算なので O(D·V²) は消えている**
   （旧方式の T-4 は候補ごとに障害物を舐めていたため）。

### 4-2. 多段レイアウト（マルチバー行）

**参照先**: `src/domain/usecase/layout-engine.ts`（477行）/ `tests/layout-engine.test.ts`（139行）/
`alignment-solver.ts`（82行）

**設計の要点**:

1. **行内で時間が重なるアイテムを段（サブレーン）に積む**。行ごとにバケット分けしてから
   段を割り当て、**行の帯高は段数で決まる**（段が増えた行は下の行を押し下げる）。
   固定行高を前提にすると必ず破綻する。**行高は可変が正**。
2. **縦横の独立**（異方性ズーム）: 行 y は行インデックス × 基準行高 × zoomY から導く。
   時間軸の zoomX と完全に分離する。この分離を最初から入れたのは正しかった。
3. **ラベルの張り出しを占有幅に含める**（`labelExtent` コールバック）。
   アイテムの内側左にラベルを出す形状では、**ラベルがはみ出す分だけ幅を広く見せて**
   次のアイテムを下の段に落とす。ラベル衝突回避を**レイアウトの段割当で解く**という判断。
   - この幅は**解析的推定**（E-8）。測らない。
4. ~~段数に上限を置き、超えたら最後の段を再利用する~~（`MAX_STACK_LANES = 64`）。
   → ⚠️ **この挙動は廃止した**（2026-07-30）。**積み順（`stackOrder`）に機能上の上限は設けない。**
   安全弁として十分に大きい上限だけを持ち、**到達したら人に知らせる**（黙って捨てない）。
   最後の段を再利用すると**重なりを許して同じ段に押し込む**ことになり、マルチバー
   （本ツール最大の差別化）を壊す。根拠は `../07-plan-actual/handover-plan-actual-decisions-ja.md` §6-3。
   **引き継ぐのは「上限の振る舞いを決めておく」という考え方だけ**で、その振る舞いは「再利用」ではなく「通知」である。
5. **人の明示指定が自動より優先**（`user-order.md` 30）。
   次期のモデルでは `TaskGroupMember.stackOrder`（`null` = 自動）。
   自動順は「milestone 優先 → start 昇順 → finish 降順 → uid 昇順」で**決定的**にする
   （`handover-data-model-entry-ja.md` §3）。**決定的でないと再描画ごとに段が入れ替わる。**
6. **性能上の注意**: これが T-2 の O(N) 本体。**行単位のキャッシュ**（変化した行だけ再レイアウト）が
   最も効く改善余地。次期は最初から**行を単位に切る**設計にしておくとよい。

### 4-3. ズーム・パンの描画経路

**参照先**: `src/adapters/render/svg-renderer.ts`（1414行, ただし**分割前の god object の残骸を含む**）/
`view-transform.ts`（150行）/ `viewport.ts`（583行）/ `lod-selector.ts`（84行）/
`time-coordinate-mapper.ts`（158行）/ `wheel-mode.ts`

**設計の要点** — これは §1 の E-1 / E-4 / E-5 / E-6 / E-12 の統合であり、
**フレームの流れを次の順で組む**のが要点:

```
入力（wheel / pointermove）
  → ViewState を不変更新（ズーム変化なら layoutDirty を立てる）
  → requestRender()（rAF 二重ガード）
  ── 次フレーム ──
  → layoutDirty なら recomputeLayout()（行の並び → 縦LOD畳み → 段割当 → 配置）
  → diffRender()
       transform を差し替え（translate のみ）
       ビューポート窓を計算（可視矩形 + オーバースキャン）
       各レイヤ:  無限に増える集合はキー付き差分 / 有界な装飾は再構築
       メトリクスをログ
```

**押さえるべき判断**:

1. **パンは再レイアウトしない。ズームは再レイアウトする。** この非対称を明示的に持つ。
2. **縦にも LOD がある**: zoomY が小さくなると行階層を畳む（小 → 中 → 大）。
   時間軸の LOD（E-5）と対になる。「縮小したら行も減る」（`user-order.md` 36）はここで実現する。
3. **ヘッダーと行見出しは常に表示**（`user-order.md` 8）: ルーラーは screen 空間に固定しつつ
   **world x だけは追従**させる（縦スクロールで動かず、横スクロール・ズームでは動く）。
   左ペインは transform の `leftPaneWidth` ぶんのオフセットで表現し、world x = 0 をその右に置く。
4. **ズームのポインタ中心はスケジュール局所座標で取る**（E-12）。生のポインタ座標では飛ぶ。
5. **`renderNow()` は起動時とベンチ計測時のみ**。通常は必ず rAF 経由。
