0. 基準（実装案ではない）

確定内容をそのまま描いた頁。どの案が正しく描けているかを判定する物差しとして先に見る。

形状の基準検証済

5 つのタスク形状と実績を同じ形状で描く規則 / Progress Marker 4 状態と文字サイズから導く大きさ / Resume アイコンの高さ合わせ / タスクの 4 状態 / 段ごとに分けたイナズマ線の頂点 / 予実は同一色相・依存線は橙（ダーク切替あり）。

DOM で検証済み。5 形状の占有高さは全て同一／実績は予定と同じ形状で描かれている（矢羽根は矢羽根、矢印は矢印）／Resume 矢先の高さ = 実績バー中心 = マーク中心、矢印の下端 = マーク下端／イナズマ線は行 5（1 段 3 タスク）で最も遅れた頂点が勝ち、行 6（3 段）で頂点が 3 つに分かれる／実績÷予定のコントラストはライト 4.81:1・ダーク 3.74:1（要求 3:1）。

1. レイアウト案 — 1 行に絡み合う依存線を描けるか

15 の負荷ケースを 1 ケース＝1 行として縦に積んである（直列 / 逆行 / 交差 / 扇形 / 完全結合 / 同一開始日 / 隣接 / 長い名称 / 密集 …）。行を足していけばケースが増える構造。

案 A — 直交チャネル配線

縦チャネル / 横チャネルを区間スケジューリングで排他割当し、線は直角のみで通す。

見るところ：配線が速く（route 3ms・60fps）タスクを横切る数は 1まで下がったが、その代償に線どうしの交差が 57に増えた（案 B は 8）。これはトレードオフであって改善ではない。57 回交差する絵が読めるかを目で判断してほしい（白フチで前後は分かる）。折れ点 3 で妥協した本数が 10（逆行する依存線は本来 4 折れ必要）。

案 B — 9 点アンカーの候補探索推奨

出口 × 入口 × 折れ点 0-3 を全列挙し、重み付きコスト最小を選ぶ。重みは画面のスライダーで動かせる。

見るところ：横切り 0 と交差 8 が同時に低い唯一の案。density も 27.0% で最も詰まっている。タスクをクリックすると 9 点アンカーと採用理由が出る。重みを動かして絵がどう変わるかを見てほしい。弱点は連続ズームが約 30fps（1 リンクあたり 110 候補を毎回 再探索するため）。

案 C — 予約が先・配線は 1 パス考え方の検証

「依存線が必要とする余地」と「経路そのもの」を分ける確定方針を、そのまま実装した案。経路探索をしない。

見るところ：行内の依存線は 57 本中 57 本が無交差（Fit 時）で、配線は 0.1ms（探索しないので最速）。行を跨ぐ 9 本は全て何かを横切る — 横レーンしか予約していないため。縦の通り道も予約する必要がある、というのがこの案の答え。「予約レーン」トグルで帯が見える。15 行の総高さは 1653px で、案 A（1464px）より 12% 高い。

2. マルチバー / LOD の追試（2026-07-30 追加）

レイアウト 3 案・ズーム 2 案は案を比べるための PoC だった。こちらは案を比べず、 確定した規則が狙いどおりに効くかを検算するための PoC。判定は画面上に出る。 担当・完了率・タスク名・進捗マーカー・Resume・依存線をすべて描くので、 ラベルが場所を食う量まで含めて測れる。

マルチバー行のパターン集検証済

1 行に複数タスクが入る 20 パターン（完全一致 / 入れ子 / 端が接する / 密集 / 手動段指定 / 完全結合 / 予定超過 …）を 同じ段割当エンジンに通す。担当・完了率・タスク名・進捗マーカー・Resume・依存線をすべて描いたうえで段を割り当てる。

確認済み — 全 20 パターンで overlap 0、 順序を変えても段割当は不変、手動 stackOrder は全ズームで保持、 240 段階の掃引で単調性の逆転 0、依存線がタスクを横切る 0。 完全結合 8 本は 8 段まで伸びる（上限なし方針どおり）。 ズームアウトで合計段数 49 → 102、総行高 1720 → 3840px。 主因は「担当＋完了率」のラベルで、形状だけなら 44 → 52 にしかならない。 進捗マーカーの寄与はほぼ 0 — §2-4-1 の見立てとは逆だった。

ズームと表示レベルの遷移検証済

時間軸 / アイテム（軸A・WBS 深さ）/ 行階層（軸B）の 3 系統について、狙った閾値と実測の遷移点を突き合わせる。 ライブ画面は 363 タスク全部に担当・完了率・名称・マーカー・Resume・依存線 222 本を描く。 単調性は 9,600 点の 2 次元掃引で検査。

確認済み — 遷移点 10 / 10 が狙いどおり（許容 0.5%、実測差は全て 0）。 単調性の逆転は 2 次元 9,600 点で 0 件、overlap も全ズーム域で 0。 行階層の一般式は現行の 2 点（0.32 / 0.60）を通る。 全要素を描くと Fit で見えるタスクが 120 → 39 に減る（ラベルの有無だけで縦 340 → 528px）。 Fit と LOD 閾値の衝突を 1 件発見 — スライダーの刻みで閾値を跨ぐと行が 9 → 21 に飛ぶ。本 PoC で修正済み。

3. ズーム案 — ズームアウトで L1 が 1 画面に収まるか

5 階層・445 タスク・21 行・720 日のプロジェクト。受入判定は「ズームアウト時に L1 が 1 画面に収まること」で、画面上に PASS / FAIL が出る。

案 A — 深さしきい値 LOD推奨

ズーム（px/日）から「描いてよい最大の WBS 深さ」を単調関数で決める。しきい値は可読下限 N px から導出する（表で根拠が見える）。

見るところ：判定 PASS。Fit で全 21 行が画面に入り density 31.1%、rAF 実測で平均 59.9fps（297 フレーム中 292 が 55〜62fps）。深さごとの中央値幅の表が、なぜその深さで切ったかを説明している。Fit 時に L1 の行が 2〜3 段になるのは、進捗マーカーの張り出しが原因（OPEN-QUESTIONS Q7）。2 案は同じ絵に着地した（どちらも L1〜L2 の 25 本）ので、差は挙動に出る。

案 B — 画面予算が深さを決める保証の作り方が良い

逆向き。画面の高さを予算とし、浅い階層から順に「まだ入るか」を足していく。入らない階層は丸ごと落とす（半端に混ぜない）。余った予算は行の高さに返す。

見るところ：判定 PASS。L1 が入ることが構造上保証される（最初に入れるから）— この保証の作り方は案 A に移植する価値がある。予算の内訳バーで、どこで切れたかが見える。ただし縦スクロールが原理的に発生しないので、縦ズームを上げると逆に階層が浅くなる。50 行規模の日程表で縦に送れないのは実用に合わないので、これを基本には採らない。

5. 計測項目の読み方

項目意味判定
overlap同一行内でタスク矩形どうしが重なった数0 でなければ不合格
line×icon依存線がタスク矩形を横切った数少ないほどよい
line×line依存線どうしの交差数少ないほどよい
bends折れ点の総数（1 本あたり 3 以下）少ないほどよい
densityタスク占有面積 ÷ 帯の総面積低すぎ＝空けすぎ / 高すぎ＝詰めすぎ
maxStack最大段数上限は設けない（安全弁のみ）
layout / route / paint ms各段階の所要時間合計が 16ms を大きく下回ること
