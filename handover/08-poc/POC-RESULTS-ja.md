## 2. レイアウト 3 案の計測

同じ入力（67 タスク / 66 リンク / 15 行）。既定ズームでの値。

| 指標 | 案 A 直交チャネル | **案 B 候補探索** | 案 C 予約先行 | 良し悪し |
|---|--:|--:|--:|---|
| **overlap** | **0** | **0** | **0** | 全案合格 |
| **line×icon**（線がタスクを横切る） | 1 | **0** | 8 | **B** |
| line×line（線どうしの交差） | **50** | **9** | 29 | **B が圧倒的** |
| bends（折れ点の総数） | 119 | **46** | 164 | B |
| 折れ点 3 で妥協した本数 | **10** | 0 | 0 | B / C |
| density（占有面積 ÷ 帯面積） | 17.0% | **28.2%** | 14.6% | **B が最も詰まっている** |
| maxStack | 5 | 5 | 5 | 同じ |
| svg ノード数 | 553 | 689 | **227** | C が最も軽い |
| layout ms | 0.3 | 0.4 | 0.6 | 差は無い |
| **route ms** | 3.6 | **11.3** | **0.1** | **C が最速・B が最も重い** |
| paint ms | 0.9 | 1.6 | 1.4 | 差は無い |
| **1 回の再レイアウトの合計** | 4.8ms | **13.3ms** | 2.1ms | **B は 60fps の予算 16.7ms にほとんど余裕が無い** |
| 1 リンクあたりの候補数 / 判定数 | — | 113 / 33 | 2 | B の重さの正体 |

> **「連続ズームが約 30fps」という旧記録は、`fps` の数字ではなく上の合計時間で読むほうが正確である。**
> スライダーの再描画は rAF で間引かれるため、合成イベントでは fps を測れない。
> 測れるのは**1 回の再レイアウトにかかる時間**で、案 B は **13.3ms**。
> 60fps の予算は 16.7ms なので、**この規模でぎりぎり収まり、少しでも重くなると落ちる**。
> 案 A は 4.8ms、案 C は 2.1ms で、いずれも十分な余裕がある。**B の弱点という結論は変わらない。**

> ⚠️ **案 A の数字は途中で大きく変わった。** 当初は `line×icon` 26 / `line×line` 25 だったが、
> 「タスクを横切らせない」ことを優先する迂回を入れた結果、**26 → 1 に下がる代わりに 25 → 57 に上がった**。
> **これはトレードオフであって改善ではない。** 確定内容は「線がタスクの上を横切らないこと」を上位に置いているので
> 方向は正しいが、**線どうしが 57 回交差する絵が読めるかどうかは目で見て判断してほしい**（白フチで前後は分かる）。

**読み方**: 品質と速度が**別の案に出ている**。
案 B は 1 リンクあたり 113 候補を列挙して 33 個を幾何判定し、**横切りも交差も同時に低い**。
案 C は候補を 2 個に絞って探索を捨てているので 0.1ms で終わる。**この 2 つは組み合わせられる**（§4-1）。

**段数の安全弁は作動しなかった**: 案 B を 1〜11 px/日 の全域で掃引しても `maxStack` は 5 のままで、
安全弁（上限 24）には**一度も到達しなかった**。**この規模では安全弁は不要**である。
ただし**表示の仕掛け自体は動く**ことを強制発火で確認してある（赤字でパネル内に出る）。

> ⚠️ 私は一度「安全弁が作動した」と書いたが、**誤りだった**。隠れている警告要素のテキストを読んで
> 発火していると誤認しただけで、実測では発火していない。**この規模では段数は 5 で頭打ちになる。**

### 各案が明らかにしたこと

**案 A — 直交チャネル配線**
チャネルを区間スケジューリングで排他割当する方式は、**線どうしの重なりは防げるがタスクとの重なりは防げない**。
チャネルはタスクの存在を見ていないため。折れ点 3 の上限に 10 本が当たった。

**案 B — 9 点アンカーの候補探索**
コスト関数に「タスクを横切った数」を最大の重み（w1=30）で入れれば **0 にできる**。
重みはスライダーで動かせるので、朝に動かして絵の変わり方を見てほしい。
**分岐限定の枝刈りで 185ms → 48ms** に落ちており、結果は 1 経路も変わっていない（エージェント実測）。

**案 C — 予約が先・配線は 1 パス**
確定方針「依存線が必要とする余地と、経路そのものを分ける」を**そのまま実装した案**。結果:

| | 結果 |
|---|---|
| 行内の依存線（57 本） | **Fit 時に 57 本すべて無交差。1 パスで足りた** |
| 行を跨ぐ依存線（9 本） | **9 本すべてが何かを横切った** |

**この差が答えである。** 予約しているのは**横レーンだけ**で、行を跨ぐ縦の移動は
「固定の x を通って複数の行を貫く」ため、予約の外にある。
**縦の通り道（行を跨いで共有する x の列）も予約すれば、この方式は完成する。**

## 3. ズーム 2 案の計測

同じ入力（445 タスク / 262 リンク / 21 行 / 720 日 / 5 階層）。

| 指標 | 案 A 深さしきい値 | **案 B 画面予算** |
|---|--:|--:|
| **L1 が 1 画面に収まる** | **PASS** | **PASS** |
| Fit 時に描かれるタスク | **25**（L1〜L2） | **25**（L1〜L2） |
| 切れた深さ | **2 / 5**（ズームで 1〜5 に動く） | **L1〜L2（丸ごと単位。半端に混ぜない）** |
| **描かれた行 / 全行** | **21 / 21** | 21 / 21 |
| **density** | **24.1%** | 4.5%（※分母が 720 日ぶんの帯なので横の空きを測っている） |
| overlap | **0**（ppd 0.17〜30 / 縦 0.12〜1 の全域） | **0** |
| **line×icon / line×line** | **0 / 0** | **6 / 0** |
| bends | 57 | 38 |
| maxStack | 2 | 2 |
| svg ノード数 | **308** | 334 |
| layout / route / paint ms | 0.10 / 0.00 / 0.40 | 0.50 / 0.10 / 1.50 |
| **1 回の再レイアウトの合計** | **0.5ms** | 2.1ms |

**案 A** は「ズームが深さを決める」。しきい値を**可読下限 N px から導出**しており、
深さごとの中央値幅の表が画面に出るので**なぜその深さで切ったかが説明できる**。
**Fit では全 21 行が画面に入り density 24.1%** と、空きも詰まりも過度でない。
**1 回の再レイアウトが 0.5ms** で、60fps の予算 16.7ms に対して 33 倍の余裕がある。

> **2 案は最終的にほぼ同じ絵を出した**（Fit で L1〜L2 の 25 本・全 21 行）。
> **方式の違いは結果ではなく挙動に出る。** 選ぶ基準は「縦に送れるか」「なぜ切ったかを説明できるか」である。

> **fps そのものは自動では測れない**（プレビューペインが前面でないと rAF が止まり、
> 合成イベントによるスライダー操作は rAF で間引かれるため）。上の表は
> **各ページが自分で計測している 1 回ぶんの layout / route / paint 時間**である。
> 実 fps を見たいときは通常のウィンドウで開き「自動ズーム往復」ボタンを押す。

**案 B** は逆向きで「画面の高さが深さを決める」。浅い階層から順に足していき、
入らない階層は**丸ごと落とす**（半端に混ぜない）。**L1 を最初に入れるので、収まることが構造上保証される。**
余った予算を行の高さに返す実装が入っており、**画面の空きが 52% → 0% になった**（エージェント実測）。

**案 B の要注意点**: 縦スクロールが原理的に発生しない。したがって
**縦ズームを上げると行が高くなり、代わりに階層が浅くなる**。
「ズームインすると情報が増える」という一般的な期待と逆になる。**この是非は判断が要る。**

## 4. 次に確かめること（PoC の続き）

### 4-1. 案 B の探索を、ズームのたびに走らせない

**問題**: ズームのたびに全 66 リンクを再探索するので、1 回の再レイアウトに **13.3ms** かかる。
60fps の予算 16.7ms にほとんど余裕が無い（案 A は 4.8ms、案 C は 2.1ms）。

**手当ての案**:

| 案 | 内容 |
|---|---|
| **B-1** | ズーム中は**前回の経路をそのまま拡大縮小**し、操作が止まってから再探索する（デバウンス） |
| **B-2** | 積み順が変わった行だけ再探索する（行単位のキャッシュ）。ズームで積み順が変わるのは**ラベルがはみ出す境界を跨いだ行だけ** |
| **B-3** | 案 C の「候補 2 個」を既定にし、**横切りが出た線だけ** 案 B の全探索に落とす（二段構え） |

**推奨は B-3 ＋ B-1**。案 C の計測が「行内は 1 パスで 57/57 きれい」を示しているので、
**全探索が要るのは少数の線だけ**である。

### 4-2. 行を跨ぐ依存線のための「縦の通り道」を予約する

3 案とも行跨ぎで破綻した。案 C の分析が原因を特定している。
**次の PoC はこれを主題にする**のがよい。横レーンと同じ区間スケジューリングを、
**行を跨ぐ x の列**に対して行う。

### 4-3. 実測できていないもの

| 項目 | なぜ測れなかったか |
|---|---|
| 実 fps（rAF ベース） | プレビューペインでは `visibilityState: hidden` で rAF が止まる。**通常のウィンドウで開けば画面のボタンで測れる** |
| Progress Marker の 4 状態 | **入力データが 4 状態を作らない**（`POC-SPEC-ja.md` §8）。字形は `poc-glyphs-reference.html` で確認済み |
| 100% を超える完了率の描き分け | 同上。実績が予定を超えるデータが無い |

### A-6. 依存線の経路 — **5 パターン確定（2026-07-30）**

**規則の正は `../03-ui-naming/handover-ui-detail-spec-ja.md` §4-9。** ここには実測だけを残す。

ユーザーが作図した正解例との突き合わせで **3 回直した**。直した順に:

1. **出口が違った。** 先行の**下端**から抜いていた。正しくは**常に右辺の中央**から出る。
2. **FS-4 / FS-5 の形が違った。** 右へ出て段間の通路を**左へ戻り**、そこから後続へ入る 4 折れである。
3. **矢印の手前に線が残っていなかった。** 曲がる位置が後続に寄りすぎて、
   垂直線の先端に三角形が直接乗っていた。走りを矢印の長さから導くようにした。

#### 定数（共有ストア `poc-ui.js`）

```
dependencyArrowLength    10    矢印の三角形の長さ
dependencyRunOfArrow  2     入口の走り ÷ 三角形。2 = 三角形 1 + 直線 1

入口の走り = dependencyArrowLength x dependencyRunOfArrow         = 20px
出口の走り = dependencyArrowLength x (dependencyRunOfArrow − 1)   = 10px
```

**出口用と入口用を別々の定数にしない。** 別々だと必ず食い違うので、**倍率 1 つから両方を導く**。
出口には矢印が無いので三角形ぶんの長さが要らない ——
その引き算を式に入れることで、定数は 1 つのままで済む（**2026-07-31 変更**。§4-9）。

**ライブ画面も全要素を描く**ように直した（363 タスク全部に担当・完了率・名称・マーカー、
中断タスクに Resume、行内に依存線 222 本）。overlap は全ズーム域で 0。

### B-1. 遷移点は **10 / 10 が狙いどおり**（実測差はすべて 0）

| 系統 | 遷移 | 狙い | 実測 | 差 |
|---|---|--:|--:|--:|
| 時間軸 | 年 → 年＋月（px/day = 1） | 0.16667 | 0.16667 | 0 |
| 時間軸 | 年＋月 → 年月＋日（px/day = 8） | 1.33333 | 1.33333 | 0 |
| アイテム（軸A） | 深さ 1 → 2 | 0.05000 | 0.05000 | 0 |
| アイテム（軸A） | 深さ 2 → 3 | 0.14815 | 0.14815 | 0 |
| アイテム（軸A） | 深さ 3 → 4 | 0.30769 | 0.30769 | 0 |
| アイテム（軸A） | 深さ 4 → 5 | 0.66667 | 0.66667 | 0 |
| 行階層（軸B） | 深さ 1 → 2 | 0.32000 | 0.32000 | 0 |
| 行階層（軸B） | 深さ 2 → 3 | 0.60000 | 0.60000 | 0 |
| 行階層（軸B） | 深さ 3 → 4 | 1.12500 | 1.12500 | 0 |
| 行階層（軸B） | 深さ 4 → 5 | 2.10938 | 2.10938 | 0 |

**行階層の一般式 `threshold(d) = 0.32 × 1.875^(d−2)` は現行の 2 点（0.32 / 0.60）を正確に通る。**
深さ 4 / 5 の値（1.125 / 2.109）は外挿である。

### B-2. 単調性 — **2 次元 9,600 点で逆転 0 件**

| 検査 | 段階数 | 逆転 |
|---|--:|--:|
| 時間軸 LOD（zoomX） | 4,000 | **0** |
| アイテム LOD（zoomX） | 6,000 | **0** |
| 行階層 LOD（zoomY） | 6,000 | **0** |
| レベル減を含む行階層（zoomY） | 6,000 | **0** |
| 2 次元（zoomX 120 × zoomY 80） | 9,600 | **横 0 / 縦 0** |

アイテム LOD が単調なのは、判定が**「代表期間 × px/day ≧ 24px」という 1 本の式**だからである。
代表期間が深さに対し単調減少なので、逆転が**構造的に起こり得ない**。
handover が「経験則の羅列にすると必ず逆転が混入する」と書いた点は、この形にすれば回避できる。

### B-3. **全要素を描くと Fit で見える量が 1/3 になる**

| | 表示行 | 表示タスク | 合計段数 | 必要な縦 |
|---|--:|--:|--:|--:|
| Fit（全要素あり） | **3 / 21** | **39 / 363** | 19 | 528px |
| Fit（ラベル類を消す） | 3 / 21 | 39 / 363 | **12** | **340px** |
| 参考: 第 1 版（ラベルを数えていない） | 9 / 21 | 120 / 363 | 27 | 754px |

同じズームでラベルの有無だけを切り替えると、**段数 12 → 19、縦 340 → 528px（1.55 倍）**。

**Fit で L1 は全部見える**（全要素ありでも 3 行とも残る）。
Fit 時点でフォントは下限 12px に張り付き、**レベル減 1 が発動している**。

### B-4. 両端の挙動（全要素あり）

| | 目盛 | WBS 深さ | 行深さ | 表示タスク | 合計段数 | 必要な縦 |
|---|---|--:|--:|---|--:|---|
| 最大ズーム | 年月＋日＋曜日 | 5 | 5 | 363 / 363 | 132 | 20,018px |
| zoomX 1 / zoomY 1 | 年＋月 | 5 | 3 | 363 / 363 | 168 | 6,630px |
| Fit | 年＋月 | 3 | 1 | 39 / 363 | 19 | 528px |
| 最小ズーム | 年のみ | 1 | 1 | 3 / 363 | 3 | 61px |

### B-5. **不具合を 1 件発見（PoC 内で修正済み）— Fit と LOD 閾値の衝突**

Fit が返す縦ズームは、収まる最大値を探す以上、**行階層 LOD 閾値のすぐ下**に着地する。
ところがスライダーの刻みが対数 0.005 なので、**素直に丸めると値が閾値を跨いで上へ飛ぶ**。
閾値 0.60 を挟んだ 1 刻みで**行が 9 → 21 に増える**。

対策（本 PoC に実装済み）: Fit の結果は刻みに対して**切り下げ**、切り下げた後で**実際に収まるまで 1 刻みずつ下げる**。

**次期でも同じ形の事故が起きる。** ズーム値を量子化する場所
（スライダーの刻み・ホイールの刻み・保存値の丸め）が LOD 閾値と独立に決まっているかぎり、必ず跨ぐ。
ズーム PoC B の「画面予算から深さを決める」向き（先に深さを決めてから高さを配る）なら、この衝突は起きない。

### B-6. フォント下限によるレベル減 — **式は未確定**

下限に最初に当たるのは **zoomY = 0.536**（タスク高 15px、フォント 12px）。

> ⚠️ **減らす量の式は本 PoC の提案であって確定ではない。**
> `減らすレベル数 = ceil( log_3( 15 / タスク高 ) )` とした。行ツリーの分岐数を 3 と見て、
> レベルを 1 つ落とすと行数が 1/3 になり残った行の高さが 3 倍になる、という見立てである。
> **分岐数は文書によって違う**ので、実装では実際の行数から求めるべきである。
> §2-4-1 で確定しているのは「さらに縮めるのではなくレベルを減らす」という**方針だけ**である。

## D. 文字色と縁取り（2026-07-31）

**規則の正は `../07-plan-actual/handover-plan-actual-decisions-ja.md` §2-7。** ここには実測だけを残す。
ページは `poc-color-and-halo.html`。

### D-1. 文字色を固定すると、色の自由度がほぼ無くなる

文字色を**ライト = 黒 / ダーク = 白**に固定したうえで、10 色相について
5 条件（文字÷予定 ≧4.5 / 文字÷実績 ≧4.5 / 実績÷予定 ≧3 / 輪郭線÷背景 ≧3 / 予定の塗り÷背景 ≧1.3）
を同時に満たす明度を探索した。

| | 結果 |
|---|---|
| 解の有無 | **10 色相すべてに解がある**（ライト / ダークとも） |
| 実績 ÷ 予定 の最小 | **3.00 : 1**（下限そのもの） |
| 文字 ÷ 実績 の最小 | **4.52 : 1**（下限そのもの） |
| 実績の明度を確定値から動かす量 | 最大 **35 ポイント** |

**すべての解が制約の角に張り付く。** あとから明度を 1 ポイント動かすと必ずどれかが落ちる。
また実績が中間の明るさになるため、**§2-6 の「実績は高彩度・濃い」と両立しない**。

既定色相の青（214）で、§2-6 の確定色のまま黒文字を置くと **文字 ÷ 実績 = 2.58 : 1**（要 4.5）。
**縁取り無しでは既定色すら成立しない。**

### D-2. 縁取りの性能 — 採用の根拠

**手順**: 全部消す → 片方だけ描く → 横スクロール 90 フレーム → ズーム 90 フレーム。
描き直しは 1 回だけで、あとは同じ絵を動かす。ズームは `viewBox` を変える
（CSS の `transform` は既にラスタライズした絵を使い回すので、測りたいコストが消える）。

| 操作 | 2000 本 無し | 2000 本 有り | 差 | 10000 本 無し | 10000 本 有り | 差 |
|---|--:|--:|--:|--:|--:|--:|
| 横スクロール | 13.9 ms | **13.7 ms** | −0.2 | 68.7 ms | 71.0 ms | +2.3 |
| ズーム | 16.6 ms | **16.1 ms** | −0.5 | 77.5 ms | 80.0 ms | +2.5 |
| 最初に 1 回描く | 34.2 ms | 43.3 ms | +9.1 | 202.5 ms | 147.1 ms | **−55.4** |

**判定: 採用。**

1. **2000 本では差が測れない。** 縁取り有りのほうが 0.2〜0.5ms 速く出ており、
   差はノイズより小さい。本プロジェクトの想定規模（中規模 ~1000 アイテム）の 2 倍にあたる。
2. **10000 本では +2.3〜2.5ms（約 +3.3%）。** ただしこの規模では縁取りの有無にかかわらず
   **69〜80ms/フレーム（約 13fps）**で既に破綻している。**直すのは LOD であって縁取りではない。**
3. **「最初に 1 回描く」は判断に使えない。** +9.1ms と −55.4ms で符号が反転する。
   HTML のパースが支配的で縁取りの寄与が埋もれる。

> ⚠️ **fps は自動では測れない。** ブラウザは**隠れているタブ・ペインで
> `requestAnimationFrame` を止める**。上の値は通常のウィンドウを前面にして計測したものである。

### D-3. 計測方法で踏んだ失敗（同じ轍を踏まないため）

| 誤り | どう見えたか | 直し方 |
|---|---|---|
| 表示中のキャンバスで計測した | 「縁取り 無しだけ」と表示しながら有りの絵が動く | **計測専用の領域**を別に持ち、閲覧用には触れない |
| 表示の辻褄をタイマーで合わせた | 9 秒後に絵が勝手に変わる（不具合と区別できない） | 計測完了時に**その場で**戻す |
| 表示モードと無関係に両方を測った | 「無しだけ」を選んでいるのに有りが計測される | **表示モードが計測対象を決める**ようにする |
| 作り直しを繰り返して測った | HTML パースのコストしか測れない | **1 回だけ描いて、あとは動かす** |
