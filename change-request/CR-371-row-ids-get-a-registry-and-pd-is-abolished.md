# CR-371 — 表の行 ID に登録簿を与え、`PD-` を `PTD-` と `PND-` に分けて廃止する

⭐⭐ **利用者の裁定 2026-09-12（逐語）**:

> 「**`PD-x` は廃止ね。`PTD-x` と `PND-x` に分けるなど、両者に別 ID を振れよ。**」
> 「**接頭辞表も作れ。どこにどう作って管理するのが良いか検討しろ。少なくとも仕様書の前の方に言及はされるべきだ。**」

⛔⛔ **実害が出たあとの裁定である。**
2026-09-12、掃除の巡で前に立つ者が `PD-\d+` を台帳に照合する分類器を書き、
**仕様書の表 T-023a の行を「閉じた決めごと」と判定した。**
体がその一覧で掃き、`item-hit-area.ts` から**生きた仕様の指し先を 3 箇所剥がした。**うち 1 件は文字どおり:

> `Table T-023a's PTD-3 says the same from the other side`

⭐ **ファイルごと戻したが、これは偶然ではなく構造が保証していた事故である** ——
**同じ分類器を次に誰が書いても、同じ判定をする。**

**台帳の行**: なし（本 CR が起点）。**計画の本文**: `docs/review/pd-id-split-plan.md`。

⛔ **`induced.py` を先に走らせた**（規則 02）——
**種 `T-023a` `T-023d` `T-006a` `FR-009` `MK-9a`: 5 of 5・辺 1・閉路 0。**
⇒ ⭐ **1 つずつ書いてよい。1 度に書かねばならない束は無い。**

---

## 0. ⛔ 立ちどまって答える 3 つ

### ① この変更は `CH-` / `GL-` のどれを前へ進めるか

⛔ **どの `CH-` も直接は進めない。これは足場である。**——
`CH-1`〜`CH-5` はいずれも**製品が利用者に何を与えるか**を述べており、ID の綴りは 1 つも与えない。

⭐ **それでも黙らない理由**を述べる。本件が守るのは **`GL-005`**（単一 `.html` で完結し、
特定の業種にも製品にも依存しない ＝ `CH-5`）**に至るまでの、仕様書そのものの可読性**である。
⚠️ **より正直な答えはこうである** —— 本件は **2026-09-10 の利用者の逐語**が名指した費用に効く:

> 「GRS は `.md` と `.ts` が主なのに、不具合修正や、俺の指摘対応に膨大な時間がかかる」

**同じ綴りが 2 つの別物を指す文書は、読むたびに判定を要求する。**⇒ その判定が費用である。

### ② 見直しの基準（`docs/development-rules/07-review-standards.md`）のどの条項を当てたか

| 条項 | 当てた結果 |
|---|---|
| **`R1.3`（一意性）** | ⛔ **破れている。**`PD-1` が表 T-023a の行と台帳の行の**両方**を指す。実測: `docs/spec` の行 ID 1,891 個のうち**仕様書の中で**重複するものは **0 個**だが、**文書をまたぐと `PD-` の 4 個が真に衝突する** |
| **`R1.5`（追跡可能性）** | ⛔ **破れている。**`PD-3` から原本へ至る経路が**読み手の推測に依存する。**機械には決められない |
| `R7.2`（命名） | ⭐ 本件が回復させる。`PTD` ＝ Pointer Down、`PND` ＝ Pending Decision で、**語幹が意味を持つ** |

### ⑧ 問わずに決めた

- **`PTD` / `PND` という綴りそのもの** —— 利用者は「`PTD-x` と `PND-x` に分けるなど」と**例示**した。
  ⭐ 空きを実測して確かめた（`PT` `PP` `PN` が空き、`PR` `PS` は使用中）が、**3 文字の `PTD`/`PND` を採ったのは前に立つ者の判断である。**⛔ 覆してよい。
- **接頭辞表を `docs/spec/_assets/` に置くこと** —— `docs/development-rules/` ではなく。
  根拠は §2。⛔ 覆してよい。
- **`previous-project-result/` を除外すること** —— 利用者が「修正不要」と裁定したものを、
  **検査の除外として書く**という形にしたのは前に立つ者の判断である。
- **`change-request/` の 254 箇所を、別の巡ではなく同じ手で直すこと** ——
  ⛔ 別にすると **CR だけが古い綴りで残る期間**ができるため。

## 1. 何を変えるか

### 1.1 行 ID の接頭辞に登録簿を与える

**いまの空白（実測 2026-09-12）:**

```
docs/spec が定義する行 ID        1,891 行 / 接頭辞 124 個
そのうち登録されているもの             0 個
```

`docs/development-rules/08-spec-template/spec-writing-rules.md` の「ID の接頭辞」節は
**「表に無い接頭辞を本文で使ってはならない（MUST NOT）」**と定めているが、
その表が持つのは **`GL` `UC` `FR` `NFR` `ADR` `SWS` `TC` `TR` の 8 つ**、
すなわち **StrictDoc のノード ID だけ**である。⇒ **行 ID には登録簿が無い。**

**置き場所と形:**

| | | 役割 |
|---|---|---|
| **SSOT** | `docs/spec/_source/row-id-prefixes.json` | ⭐ **意味だけを持つ。員数は持たない** |
| 生成器 | `docs/spec/_source/row_id_prefixes_json_to_md.py` | 原稿を歩いて員数を読み、意味と突き合わせる |
| 生成物 | `docs/spec/_assets/tbl-row-id-prefixes.md`（`DOC-TBL-ROW-ID-PREFIXES`）| 全数表 |
| 参照 | **`01-04-requirements.md` の `1.9 Notation`**、表 T-006a の隣 | ⛔ **写さない。指し先だけ** |

⭐⭐ **「員数を持たない」が肝である。**`_source/display-words.json` が既にこの形を宣言している:

> **THIS FILE HOLDS NO ROSTER. Which entries exist is read from `docs/spec` every run.**

⇒ **生成器がそのまま検査になる:**

```
原稿に在って json に無い  → ⛔ エラー（未登録の接頭辞）
json に在って原稿に無い  → ⛔ エラー（死んだ登録）
```

**別に検査を書かない。`npm run gen:check` が落ちる。**
⛔ **これがあれば `PD-` の衝突は登録の時点で見えていた。**

### 1.2 `PD-` を廃止する

```
表 T-023a の行（Pointer Down）              PD-n  →  PTD-n
台帳の未裁定の決めごと（Pending Decision）   PD-n  →  PND-n
```

⭐⭐ **両方を廃すことの値打ち** —— 片側だけ改名すると、残った `PD-3` は**永久に曖昧**である。
両方を廃せば **`PD-\d+` が 1 つでも残っていること自体が誤り**になり、**機械で終端を判定できる。**

## 2. ⛔ なぜ `spec-writing-rules.md` に足さないのか

あの表が縛るのは**要求の書き手**であり、`GL`→`UC`→`FR` という**トレースの鎖**を定めている
（「親をたどると必ず `GL` に着く（MUST）」）。⭐ **行 ID は鎖の外であり、仕様書自身の中身である。**

⭐ **正しい前例は `1.8 Glossary` である** —— 用語の正は `_assets/tbl-glossary.md` が持ち、
章からは**指し先だけ**を置いている。行 ID の接頭辞はこれと同じ性質（名前の権威）を持つ。
⚠️ `1.9 Notation` は既に **「同書が … を持つ。ここには写さない」** を実践しており、**同じ作法で足せる。**

### ⛔ 規則側に要る 1 文（別に諮る）

`spec-writing-rules.md` の「ID の接頭辞」節に:

> **本表が縛るのはノード ID である。表の行 ID の接頭辞は `_assets/tbl-row-id-prefixes.md` が持つ（MUST）。**

⚠️ **これが無いと、あの節の MUST NOT が行 ID にも掛かって読め、124 個すべてが違反に見える。**
⛔ `docs/development-rules/` の変更は裁定案件なので、**この 1 文だけ**を別に諮る。
