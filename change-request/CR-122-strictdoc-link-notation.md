# CR-122 — 「中身はあちら」を指す 3 か所を `[LINK:]` にし、外部リンクの限界を断る

## 1. 変更概要

**仕様書は他の文書を 83 か所で指しているが、リンクになっているものが 1 本も無い。**
**一方、リンクになっている 16 本は、書き出した HTML では 404 になる。**

| # | 決めること | 置き場 |
|---|---|---|
| ① | **括弧で「中身はあちら」を指している 3 か所に `→ [LINK: UID]` を足す** | `05-07-design.md` の 5.2 / 5.4 / 6.2 |
| ② | **`user-order.md` への 16 本が書き出し HTML では解決しないことを、表 T-011 の直前で 1 文だけ断る** | `01-04-requirements.md` の `:462` |

## 2. 変更の背景・目的

### 2-1. `[LINK: UID]` が StrictDoc の記法である（**自分の書き出しで実証した**）

**出典** —— `C:\StrictDocStarter\samples\md-basic-ja` の `00-ai-guide.md` と `02-guide-for-human.md`。

| 用途 | 記法 |
|---|---|
| **文書・要求・節へ** | `[LINK: DOC-FIG-ERD-OVERVIEW]` —— **パスを書かない。UID だけ。**宛先は見出し直下に `**UID**:` を宣言する |
| **文書でない添付**（SVG・CSV ほか） | `[説明](_assets/x.svg)` —— **実拡張子のまま。`_assets/` の中に限る** |

**実証**（`docs/spec` を 1 か所だけ書き換えて書き出し、確かめてから戻した）——

| | |
|---|---|
| **原稿** | `（[LINK: DOC-FIG-ERD-OVERVIEW]）` |
| **出た HTML** | `<a href="../spec/_assets/fig-erd-overview.html#DOC-FIG-ERD-OVERVIEW">🔗 データモデル — 概要（文書の全体像）</a>` |
| **リンク先** | `html/spec/_assets/fig-erd-overview.html` は実在し、`DOC-FIG-ERD-OVERVIEW` のアンカーも実在する |

### 2-2. 2 つの記法は両立しない —— **だから両方を並べる**

| 記法 | 書き出し HTML | GitHub で `.md` を読むとき |
|---|---|---|
| `[LINK: UID]` | ✅ リンクになる | ⛔ **`[LINK: DOC-…]` の文字がそのまま出る** —— 定義の無い shortcut reference link なので CommonMark はリテラルに落とす |
| `[説明](path.md)` | ⛔ **404** —— **StrictDoc は href をそのまま写す**（実測。`href="../../previous-project-result/user-order.md"` のまま出た） | ✅ リンクになる |

**サンプルはこの両立不能を、両方並べることで解いている**（`02-guide-for-human.md:284`）——

```
他の `.md` へリンクを張れる。 宛先は `_assets/note.md` である →
[LINK: DOC-NOTE]
```

**GitHub の読者にはパスが見え、HTML の読者にはリンクが効く。**①はこの形を採る。

### 2-3. ⚠️ バッククォートのファイル名は欠陥ではない（**当初の判断を訂正した**）

**起票の途中で「ファイル名を落として表番号だけにする」案を立てたが、原文に当たって取り下げた。**

**サンプル全体で生きている `[LINK:]` は 5 本しかない**（自分で数えた）——

| 位置 | 書き方 |
|---|---|
| `00-ai-guide.md:671` | 中断と後始末まで含めた大きい図は別文書にしてある → `[LINK: DOC-FIG-STATE]` |
| `02-guide-for-human.md:285` | （前行の `→` を受けて）`[LINK: DOC-NOTE]` |
| `02-guide-for-human.md:362` | …別文書にした → `[LINK: DOC-FIG-STATE]` |
| `06-lower.md:97` | …別文書にしてある → `[LINK: DOC-FIG-STATE]` |
| `_assets/fig-state.md:36` | 要求へ飛ばしたいときは、図の外に `[LINK: SW-004]` のように並べる |

**一方でバッククォートのファイル名は本文のあちこちに出る**（`01-ai-queries.md` / `06-lower.md` など）。
**つまり `[LINK:]` は「読む人をそこへ飛ばしたい箇所」に足すものであって、ファイル名を書いた箇所すべてを置き換えるものではない。**

### 2-5. なぜ `user-order.md` への 16 本が 404 になるのか

**`00-ai-guide.md:891`〜`:911` の実測** ——

> `_assets/` に置いたものを、StrictDoc は種類を問わず出力へ複製する（実測）。画像だけの仕組みではない。
>
> | 壊れ方 | 起きること |
> | --- | --- |
> | 参照先のファイルが無い | `<img>` や `<a>` は出る。開くと 404 |
> | **`_assets/` 以外に置いた** | **ファイルは実在するのに複製されない。開くと 404** |

**`previous-project-result/user-order.md` は `docs/spec` の外にあり、StrictDoc は走査すらしない。**

⚠️ **`docs/spec/_assets/` へ取り込む案は採らなかった**（利用者判断・2026-08-15）——
**`_assets/` に置いた `.md` は「添付」ではなく「文書」として解析される**（`note.md` 自身が「StrictDoc は 1 個の文書として扱う」と書いている）。
**637 行・見出し 26 個の前プロジェクトの成果物が仕様書の文書一覧に並び、検査の対象ファイルも 9 → 10 になる。**
**`previous-project-result/` は仕様書ではなく参照資料であるという本プロジェクトの位置づけを崩す。**
