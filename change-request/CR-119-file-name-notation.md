### 2-2. なぜ 5.3 に持たせず、要求へ足すのか

**1.9 が命名の規約を Chapter 1 の持ち物と定めているためである**（`01-04-requirements.md:292` 以降が「**命名の規約**」の節であり、
表 T-006a はその中にある）。**5.3 が自前でファイル名の記法を持つと、命名の規約が Chapter 1 と Chapter 5 の 2 か所に分かれる。**

⚠️ **Chapter 5.1 が 表 T-061 で規則を持ったのとは事情が違う。** 5.1 は「`R2.16` が層の定義と依存の向きを **Ch5.1 に置くよう要求している**」という
外部の規約を根拠にしていた（`05-07-design.md:62`）。**`R2.19` が Ch5.3 に置けと要求しているのは「各コンポーネントの公開面の宣言」であって、
命名の記法ではない。** したがってファイル名の記法に同じ根拠は使えない。

### 2-3. なぜ kebab-case か

| 観点 | 根拠 |
|---|---|
| **記法を増やさない** | **kebab-case は `W-4` が既に使っている。**PascalCase を採ると `W-1` と同じ記法をファイル名にも広げることになるが、それでも記法の数は増えない。**決め手は次の 2 つである** |
| **大文字小文字を区別しないファイルシステム** | Windows と macOS の既定のファイルシステムは大文字小文字を区別しない。**PascalCase では、大文字小文字だけが違う改名を版管理が取りこぼす。** kebab-case は全部小文字なのでこの事故が起きない |
| **先例** | **前プロジェクトの `src/` は 97 ファイルすべて kebab-case である**（`main` ブランチ。`git ls-tree` で数えた）。⚠️ **前プロジェクトのコードは参考にしないと決めているが、これは記法だけの実測であって設計を引き継ぐものではない** |

### 2-4. 語幹は中身の名前と一致する

**`:294` の MUST がそのまま掛かる** ——

> **同じ概念でも面が違えば記法が違う。矛盾ではない。ただし語幹は必ず一致させること（MUST）**

| 中身 | 面 | ファイル名 |
|---|---|---|
| `ScheduleLayout`（`W-1`） | 型 | `schedule-layout.ts` |
| `UseCase`（表 T-060 の層名） | 層 | `use-case/` |
| `layoutEngine`（表 T-060 の `LY-2`） | `Entity` の内側 | `layout-engine/` |

**`:318` の「大文字の略語を識別子に入れてはならない（MUST NOT）」も掛かる** —— 部品名が既に `SvgRenderer`（`SVG` ではない）なので、
**ファイル名は `svg-renderer.ts` になる。** ⚠️ **`SVGRenderer.ts` / `svgrenderer.ts` はどちらも語幹が一致しない。**

⚠️ **`use-case/` を `usecase/` と書かないこと。** 層名 `UseCase` は 2 語であり、kebab-case は語の境目にハイフンを置く。
**`usecase` は語幹が一致しない。**
