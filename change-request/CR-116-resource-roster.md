# CR-116 — 担当者の名簿を出し、消せるようにする

## 1. 変更概要

**割当を解いても担当者は文書に残るので、消す入口が無いと溜まり続ける。** 名簿を新設する。

| # | 決めること | 置き場 |
|---|---|---|
| ① | **名簿を出し、担当者を消せるようにする。入口はコマンドパレット** | **`FR-099` 新設** |
| ② | **消し方は 2 つ** —— 割当から参照されていない人をまとめて消す ／ 選んだ人を消す | 同上 |
| ③ | **選ぶ面に、すべて選ぶ操作とすべて解く操作を添える** | 同上 |
| ④ | **一覧のすべてを 1 つの操作で消す入口を設けない（MUST NOT）** | 同上 |
| ⑤ | **担当者を消すと、その人を指す割当が一緒に消える** | 表 T-050 の `CD-5`（新設） |
| ⑥ | `UN-15` が指す削除の持ち主を `FR-099` にする | `UN-15` |
| ⑦ | 名簿の名前 `Resource Roster` | 用語辞書 `U-49` |

## 2. 変更の背景・目的

### 2-1. 消せない担当者が溜まる

**利用者（2026-08-14）** ——

> タスクから担当者名を消したときは、割り当て解除でよい。**ただし、そうすると存在しない担当者が出てきてしまう。**
> **これがないと、消せない担当者＝幽霊を抱えることになるだろう？**

**データモデルがそのとおりの形をしている。** `Assignment`（`ET-10`）が `Task` と `Resource` を結び、
`Resource`（`ET-9`）は `schedule.resources` に独立して載る（表 T-052 の `DR-2`）。
**割当を消しても `Resource` の行は残る。** そして残った担当者は `FR-024` により JSON へ書き出され、
交換相手へも書き出される（`ET-9` は「書き出す」側である）。

### 2-2. 仕様書は「削除できる」と書いているのに、その規則が無かった

`UN-15`（取り消しの対象・`:1553`）——

> | UN-15 | 対象 | **担当者（資源）と割当の追加・改名・削除**（`FR-008`） |

**ところが `FR-008` が定めているのは「追加・編集・解除」だけである**（`:1497`）。
**担当者そのものを消す規則は仕様書のどこにも無かった**（`参照されていない担当者` の出現 0 件。**自分で数えた**）。
`docs/review/datamodel-findings-2026-08-16.md` の `D-8` がこれである。

### 2-3. 範囲外規定にも往復無損失にも触れない

| 触れそうに見えるもの | 実際 |
|---|---|
| 表 T-002 の `SO-8`「資源管理（工数・割当率・稼働率）は範囲外」 | **同じ行が「ただし担当者の表示と割当の追加・編集は範囲内」と書いている。** 名簿と削除はその線の内側 |
| `FR-021` の往復無損失 | **保証は「取り込み、合流させず、編集せずに書き出したとき」に限定されている。消すことは編集である** |

### 2-4. 「全削除」を設けない理由（利用者判断で落とした）

**起票時の案は削除を 3 種（全削除 / タスクが無い人 / 選んだ人）としていたが、全削除を落とした。**

- **すべて選んでから消せば同じことができる。** 入口を 2 つ置くと `FR-029`（同じ機能の入口を 2 か所に置かない）に触れる
- `FR-031` の RATIONALE は「**誤操作への備えは取り消しの 1 本に絞る。例外は `FR-032` が確認を求めると定めた削除だけである。例外を増やさない（MUST NOT）**」と定める。
  **1 クリックで全タスクの担当が外れる操作は、その例外をもう 1 つ増やすことになる**

**代わりに、すべて選ぶ操作とすべて解く操作を選ぶ面に置いた**（利用者判断）。
