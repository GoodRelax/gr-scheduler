# CR-375 — 仕様書は理由を持ち、履歴を持たない

> **閉じるもの**: ⛔ **利用者の裁定（2026-09-13）** ——「仕様書に裁定の履歴が残っているのでクリーニングしたい。
> いつ俺が何と言って裁定したのかは無用な情報だろ？ ましてや覆った最低の履歴が害悪でしかない。」
> ⭐ **ただし、同じ判断を繰り返さないという意図は残す** ——「なぜその仕様にしたのか/しなかったのかは、仕様書の RATIONALE などに残すべきだろ？」
> ⭐ 文案は利用者の OK を得た（「よしやれ。　他も同様に整理しろ」）。

## 0. ⛔ 立ちどまって答える 3 つ

### ① この変更は `CH-` / `GL-` のどれを前へ進めるか

⭐ **表 T-054 の `CH-1`〜`CH-6` と 1.3 の `GL-001`〜`GL-008` の、どれも前へ進めない。**仕様書の読み方を変える変更である。
覆った規則が生きた規則と読み違えられ、撤回済みの文を引いた欠陥が台帳に繰り返し載っている（`DFC-446` / `DFC-450` / `DFC-452` ほか）。
⇒ 仕様書が「いま何が正しいか」と「なぜか」だけを持てば、その読み違いの元が無くなる。

### ② レビュー観点のどの条項を当て、何が出たか

`R1`（要求品質）の**明確性**。原稿 17 ファイルを機械で数え、履歴の書き方を 1,261 回、文単位で 667 件見つけた（第 1 節）。

### ③ 利用者に問うたこと・**問わずに決めた**こと

**問うて裁定を得た**:

1. 仕様書から出どころ（誰が・いつ・逐語）と覆った履歴を消す ⇒ **消す**
2. 表 T-051 の `HF-2`（却下の履歴を消してはならない）と `HF-14`（日付つきの引用は記録である）⇒ **本書で改めて消す。意図は RATIONALE に残す**
3. 対象 ⇒ **仕様書の原稿すべて**。`docs/development-records/` は対象外。コードは後でまとめて直す
4. 表 T-222 の `DM-11`（逐語と読みの書き分け）⇒ 行を消す。裏にある要求は 表 T-023d の結びが既に MUST で持つ
5. 方法の書かれていない実測の数 ⇒ **数を落とし、主張だけ残す**
6. 仕様を直した結果、試験やコードコメントが追いつかなくなったもの ⇒ **`defects.md` に載せて後で直す**。引用を突き合わせる検査の基準線は、上がった分を上げてコミットする

**問わずに決めた（覆してよい）**:

- ⭐ 実測は、**方法が書かれている数だけ**、方法を 1 句残す。日付は、数が時間とともに変わるもの（出荷ビルドの状態など）に限って残す
- ⭐ 行 ID は振り直さない（`DM-11` を消した跡は空き番号になる）

### 2.4 `FR-004` の RATIONALE に足す

### 2.6 残りの 667 件

分類どおりに直す。1 ファイルずつ、下の行から上へ。宙に浮く指し先（「同裁定」「逐語は…が持つ」「上の段」）は同じ編集で直す。

### 2.7 書き方の規則と門

- `docs/development-rules/08-spec-template/spec-writing-rules.md` に、仕様書に出どころ・日付・覆った履歴を書かない規則を足す
- 検査を 1 本足し、原稿に「利用者の裁定」と「YYYY-MM-DD まで」が残っていないことを数える
  ⇒ 検査 54 `check-spec-holds-no-history.py`。日付の無い「利用者の裁定」（誰が決めるかを言う生きた規則）は数えない
- ⭐ **検査 43 の規則を改める**（利用者の裁定を得た）。仕様書が利用者の言葉を持たなくなったので、`rulings.md` の 適用済 の行は、逐語を仕様書から探すのではなく、**着地先が名指す ID（docs/spec が定めるもの）かファイルで**着地を示す。
  これで `JDG-06` / `JDG-08` の HELD 行も要らなくなり、基準線から消した
