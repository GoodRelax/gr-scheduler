# CR-114 — 仕様書から検討の経緯を取り除き、CR 側へ移す

⚠️ **本 CR は他の CR と性質が違う。** 個別の仕様を変えるのではなく、
**仕様書に何を書くかという編集の方針**を定め、それに反する既存の文を除く。

⚠️ **本 CR は取り除いた文の保管庫でもある。** §8 の付録に、除いた文を 1 文ずつ原文のまま記録する。
**除いた文はここにしか残らないので、消す前に必ず §8 へ写すこと（MUST）。**

## 1. 変更概要

**仕様書に入れるのは「仕様」と「それを採用する理由」だけとする。**

古い仕様・検討の経緯・レビューで何が足りなかったか・いつ誰が決めたかを、
`docs/spec/` から取り除き、**CR 側（本 CR の §8）へ移す。**

## 2. 変更の背景・目的

**利用者指示（2026-08-14）** ——

> Spec の方に古い仕様や検討経緯を乗せる必要はない。それらは全部 CR が引き受ける。
> Spec に入れるのは仕様とそれを採用する理由だけだ。
> **初見者は Spec だけを見ればよい。そこに古い情報が入っているとノイズになる。**

**いまの仕様書は、10 周のレビューの過程がそのまま本文に残っている。**
「この要求は、あの手順を受ける要求が無かったので足した」という**書かれた理由**は、
**書いた者にとっての理由**であって、**読む者にとっての理由ではない。**
初めて読む者には「無かった」の主語が分からず、**存在しないものを探しに行く。**

**目的** —— 仕様書を、**それだけを読めば製品が分かる**文書にする。
経緯を辿りたい者は CR と git の履歴を読む。

## 5. 変更後の仕様

### 5-1. 1.9（表記規約）に編集の方針を足す

> **仕様書に書くのは、仕様と、それを採用する理由だけとすること（MUST）。**
> **検討の経緯を書いてはならない（MUST NOT）** —— 古い仕様、レビューで何が足りなかったか、
> いつ誰が決めたか、前の版がどうだったか。**それらは変更要求（`change-request/`）と版管理の履歴が持つ。**
> **初めて読む者は本書だけを読めばよい状態に保つ。**
>
> **判定は 1 つである。「この文を消したら、仕様か、それを採る理由が失われるか。」** 失われないなら書かない。

### 5-2. 判定の基準（本 CR の作業で使う）

| 残す | 除く |
|---|---|
| こう動く（仕様） | 前はこう書いてあった |
| **こう決めた理由**（例: まとめて消すほうが利用者の直感に合う） | いつ誰が決めたか |
| 制約から導かれる帰結 | レビューで何が足りなかったか |
| **前プロジェクトの事実が理由として機能している場合** | 前プロジェクトがどうだったかの記述一般 |

⚠️ **一律の削除はしてはならない（MUST NOT）。1 件ずつ判定する。**

**残す側の実例** —— Chapter 7 の性能ゲートは「**前プロジェクトがここで落ちた**（計測を工程に紐づけず、
最初の節目より後で一度も測り直されなかった）」を理由として持つ。
**これは「なぜゲートを工程に縛るのか」の答えそのものなので残す。**

**除く側の実例** —— `FR-085` の「`UC-002` の手順 1 を受ける要求が無かった」は、
**なぜこの要求が要るかを説明していない**（要るのは「行を作れないと使えないから」である）。
**理由を書き直したうえで、経緯の文は除く。**

### 5-3. `ORIGIN` の扱い

⚠️ **`ORIGIN` は StrictDoc の必須フィールドである。フィールドごと消してはならない（MUST NOT）。**
`FR-032` の `UC-001 / UC-002（削除の手順が無かった）` のように、
**括弧の中だけを落として `UC-001 / UC-002` にする。**

### 5-4. 残すもの

⚠️ **`A-appendix.md` の変更履歴（版 0.1 〜）は残す**（利用者判断 2026-08-14）。
**「いつ何が変わったか」を仕様書の中で辿る唯一の索引**であり、
**変更履歴という独立した章の仕事**だからである。**本 CR の対象外とする。**
