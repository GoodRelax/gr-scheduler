# 名の辞書のレビュー —— ほかの AI に渡すプロンプト

使い方: 下のコードブロックをそのまま貼り、その後ろに 2 つのファイルの中身を貼る（または添付する）。

1. `studies/76-grs-json-beta-shape/terms/13-glossary-gqa.md`（決まったことと問 1 の案）
2. `studies/76-grs-json-beta-shape/terms/glossary-draft/glossary.schema.json`（辞書のスキーマの案）

```text
あなたは、公開する JSON の書式と API の名前を設計するレビュアーです。厳しく、具体的にレビューしてください。

## 背景
- GRS（GoodRelax Scheduler）は、ブラウザで動く日程表の道具です。文書は「GRS JSON」という JSON ファイルで保存します。AI は「Agent API」（MCP 経由）と「文書の命令」で文書を読み書きします。
- いま、すべての名（JSON の型・キー・値、画面の部品、設定、Agent API のメンバ、命令、コードの部品の名、設計原則の名）の意味を、1 つの「名の辞書」（glossary.json）に集めようとしています。辞書が唯一の正（SSOT）で、用語集・JSON スキーマの説明・MCP の説明はそこから生成します。
- GRS JSON・Agent API・文書の命令は、外との約束です。約束の相手が 100 万人になっても困らない、憲法のような約束にしたいと考えています。

## すでに決まっていること（前提として扱い、蒸し返さないでください）
- 名のキーそのものを ID にする。持ち主で意味が変わるキーだけ、持ち主ごとに別の語にし、持ち主は owner の欄に書く。
- 意味（definition）と人に見せる名（label）は { en, ja } —— 言語ごとに別のプロパティ。英語が主（正）、日本語が訳。1 つの文字列に 2 つの言語を入れない。
- OKPN（1 つの名前には 1 種類の値）と OMPV（1 つの値には 1 つの意味）を守る。
- 順が要るものは配列の並びだけで決める。順番号は入れない。
- 生成は全部、辞書などの原稿から 1 段で行う。生成物を次の生成の入力にしない。
- JSON の木の形そのものは、別の原稿（erd.json）だけが持つ。辞書は木を持たない。

## レビューしてほしいもの
添付の「問 1」の案（群の分け方と順、階層の扱い、約束としての決まり）と、辞書のスキーマ案です。

## 特に見てほしい観点
1. 群の分け方と順: 8 群（製品の名 6 群と、作るための名 2 群）で漏れや重なりはないか。「前に出た名だけで後の名の意味を書ける順」は守れるか。守れない例はあるか。
2. 階層: 入れ子・包み・参照の木・共通の型の 4 種類で足りるか。抜けている階層の形（再帰、多対多、同じ型が別の意味で 2 か所に入る、配列の中の配列 など）はないか。
3. 開発の名の線: 「境界を越える名だけを辞書に入れる」（層・部品・層をまたぐ口・設計原則の名は入れ、部品の中だけの名は入れない）は、多すぎず少なすぎない線か。
4. 約束としての強さ: 100 万人と約束しても後で困らないか。版の付け方（since）、名や意味を変えたいときの手順、退ける手順に穴はないか。
5. 多言語: 3 つ目の言語を足すとき、スキーマも生成も壊れないか。言語のタグの決め方は妥当か。
6. スキーマ案の欄: 足りない欄、要らない欄、OKPN・OMPV に反する欄はないか。
7. 名づけ: 欄の名（definition・label・uses・tags・children・avoid・nonLiteral・rowId・owner・since）は、初めて見る人にも意味が通るか。

## 答え方
- 日本語で答えてください。
- 指摘ごとに番号を付け、次の 4 つを書いてください: 重さ（高・中・低）／どこ（群・表の行・スキーマの欄）／何が問題か（具体例を 1 つ）／どう直すか。
- 良いと思う所は、最後に 3 行以内でまとめてください。
- 推測で書いた所は「推測」と明記してください。
```
