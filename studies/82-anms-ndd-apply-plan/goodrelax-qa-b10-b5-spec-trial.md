#### ❓ 問 4. 課題と目標の向きを直す形

ANMS では、子が親の ID を持ち、親は子の ID を持たない。今の表 T-054 は課題の行に「受ける目標」の列（`GL-008` / `GL-004` ほか）を持ち、親の課題が子の目標を指す —— 向きが逆である。目標の節点（`GL-001`〜`GL-009`）は親を持たない。直さないと、基準書の「親は子の ID を持たない」（MUST）が High の指摘として残り、トレーサビリティの漏れの検査（検査 97）が目的からの鎖を辿れない。

#### ❓ 問 6. 意図が 2 つあるユースケースを分けるか

ANMS は「1 ユースケースは 1 つの意図」とする。今の 15 個のうち 2 つが、2 つの意図を 1 つに持つ。

| UC | 今の意図 | 分けた形 |
|:---|:---|:---|
| UC-003 | タスクの属性を変える ＋ 日程表の表示と書式（表示の切り替え、テーマ）を整える | UC-003「タスクの属性を編集する」＋ 新しい UC-016「表示と書式を整える」 |
| UC-011 | JSON で保存する ＋ 画像で配る | UC-011「文書を保存する」＋ 新しい UC-017「日程表を画像で配る」 |

分けると、表示・テーマ・画像の書き出しの要求（例: `FR-041`・`FR-025`）の親を新しいユースケースへ付け替え、ユースケースの試験（8 章）とシナリオ（B10）を 1 本ずつ足す。分けないと、基準書のユースケースの質（R1c）の指摘が残る。

| 案 | 内容 |
|:---|:---|
| **a（推奨）** | **2 つとも分ける。付け替えは組み替え（B8）が行う** |
| b | 分けない（今の 15 個のまま。指摘を Medium として据え置く） |
| c | UC-003 だけ分ける |

### [b8] 組み替えの約束（❓ 1）

#### ❓ 問 7. 組み替えで新しい ID が増える間、漏れの検査の上限を上げてよいか

組み替え（B8）は、1 つの文に「〜すること」が 2 つ以上ある規範の文を分け、表に無い規範の文に新しい ID（子の要求 `FR-160` 〜、実装仕様 `IMPS-1` 〜）を振る。B5 の試し（3 章の 5 つの要求、規範の文 44 件）では、新しい ID が 27 個（子の要求 3、実装仕様 24）増えた。全体では同じ割合で約 1,260 個になる。新しい ID を指すコードの印（`// Spec:`）とテストは、コメントの判定（B11）と UseCase の分け直し（B12）が後で付ける。それまで、トレーサビリティの漏れを数える検査 97 の数が新しい ID の数だけ上がり、検査が赤になる（試しで当てた時: 実装の無い要求 29 → 32、実装かテストの無い実装仕様の行 8 → 42）。同じく、src と tests のコメントが逐語で引く仕様の文が消え、検査 42 が 32 → 39 になった。検査の上限（基準線）を上げることは、持ち主の許しが要る（`JDG-520`）。

| 案 | 内容 |
|:---|:---|
| **a（推奨）** | **B8 は、自分が振った新しい ID と書き直した文の数だけ、検査 97 と検査 42 の上限を上げてよい。B11・B12 が印を付けて下げ、B13 が β の前に 0 にする** |
| b | B8 は新しい ID を振らない。分けるべき文も今の行に残し、「1 文に動作 1 つ」の指摘を Medium として据え置く |
| c | B11・B12 が先に印を付け、その後に B8 が組み替える（B8 の始まりが 1 日ほど遅れる） |
