#### ❓ 問 1. 適用をいつ始めるか

今、β（11-28 の予定）へ向けて、CR-851 の当て（11-27）、CR-855（名の辞書のとおりに仕様とコードを改める）、CR-857（用語集の JSON `glossary.json` を作る）、Agent API の名の席が走っています。新しい規則 07 を途中で入れると、走っている SUB の書き方が途中で変わります。一方、CR-857 が今の形で `glossary.json` を作ると、新しい基準書のキーの形（`key`・`label`・`definition`・`avoid`・改名の記録 `renames[]`）に合わず、β の後に作り直しになります。

| 案 | 中身 |
|:---|:---|
| **a（推奨）** | β の前は、CR-857 の `glossary.json` を新しいキーの形で作ることと、CR-855 を新しい改名の手順（前の名で全部を検索し、`renames[]` に記録し、後で 0 件を確かめる）で行うことだけを、BOSS が各 SUB の指示に足す。規則 07 の書き換えと残りの全部は β のリリースの後に入れる |

| c | β の前は何もしない。CR-857 の `glossary.json` は β の後にキーを作り直す |

#### ❓ 問 2. コメントの移しをいつ、どう行うか

持ち主は 11-08 に「コメントについて、実質のコードに変更が無ければ俺の裁定は不要。 並列で一気に直せ。」と答えました（`JDG-3598`、β の前に移す案 b）。その後、移す窓は開かれず、今回の基準書でコメントの種類が `Why:`・`Spec:`・`Summary:`・`Temporary:`・`Unimplemented:`・`Provisional:` に決まりました。

- 移す量: src の `// see` 2,956 行（→ `// Spec:`）、`WHY:` 1,242 行（→ `Why:`）、tests の種類の無いコメント 7,462 か所。触るファイルは 約 700 です。
- `// Spec:` は「仕様の振る舞いを実装する所」にだけ書くので、`see` の 約 2,045〜2,289 行は置き所を判定します。
- 約 700 ファイルに触れるので、同じ時に走るコードの SUB の枝と必ずぶつかります。

| 案 | 中身 |
|:---|:---|
| **a（推奨）** | β のリリースの後に、ほかのコードの SUB を止める窓（2〜6 日）を開き、機械の移し（2〜4 時間）の後に置き所の判定を並列で行う。`JDG-3598` の「β の前」を「β の後」に改める。「並列で一気に」は守る |
| b | β の後に、窓を開かずにフォルダーごとに順に移す。ほかの仕事は止めないが、ぶつかりが多く、期間が長い |
| c | `JDG-3598` のとおり、β の前に移す。β の前の合流（CR-851 ほか）とぶつかる |

回答:

#### ❓ 問 3. 仕様の形を ANMS v0.36 へ組み替えるか

新しい基準書は、ユースケースの形（6 つの欄と印 `UC-xxx.OK`・`UC-xxx.RJn`、R1c）、Gherkin のシナリオ（R6）、「ID / 要求文 / 親の ID」で読める要求、トレーサビリティの漏れの数 0 を MUST にしました。GRS の仕様の今:

- 要求の本体 `01-04-requirements.md` は 1,444,611 バイトで、ANMS が割る目安の 100 KB の約 14 倍です。
- ユースケース 15 個は、きっかけ・前提・結果の欄と印を持ちません。Gherkin のシナリオは 0 本です。
- FR の ID と親の ID を持たない規範の文が、MUST 2,957 行と MUST NOT 1,007 行あります。
- 設計原則の準拠の章（ANMS の 7 章）は、GRS のテンプレートが消しました。

組み替えないと、上の行は新しい基準書のレビューで High の FAIL になり続けます。

| 案 | 中身 |
|:---|:---|
| **a（推奨）** | β の後に組み替える。先に 1 章と 2 章（ユースケース 15 個）を試しに組み替えて速さを測り、PMO が見積もりを測り直す。その後 3 章を切り分けて進め、5 章の実装仕様（IMPS）、6 章の Gherkin、7 章、100 KB での分割の順に進む。今の見込みは 2〜6 週 |
| b | GRS のテンプレートを保ち、テンプレートに頼らない行だけを当てる。ユースケースの形・Gherkin・要求の表の FAIL は、持ち主がレビューのたびに受容する |
| c | 一度に全部を組み替え、その間ほかの仕様の変更を止める |

#### ❓ 問 4. 1 章の「目的」と「問い」を誰が書くか

ANMS v0.36 の 1 章は、背景（BG）→ 目的（PUR）→ 分析（AN）→ 問い（ISS）→ 挑戦（CH）→ ゴール（GL）の推論の鎖です。GRS の仕様は CH 7 個と GL 9 個を持ち、PUR・AN・ISS を持ちません。ANMS は「why・for whom・what・how の構想を示すこと」を人の責任とします。プロジェクト憲章の下書き（計画の 253）があります。

| 案 | 中身 |
|:---|:---|
| **a（推奨）** | 席が憲章の下書きから PUR・AN・ISS の下書きを作り、持ち主が GQA で 1 回見て直す |
| b | 持ち主が PUR と ISS を書き、席が AN と鎖の残りを書く |

#### ❓ 問 5. 英語を正にするか（用語集と画面の文）

新しい基準書は、製品のコードが 10,000 行を超える（GRS は 52,283 行）ので、用語集を JSON で持つことを MUST にし、言語ごとの文に `en` を必ず持たせて英語を正にすることも MUST にしました。

- CR-857 の `glossary.json` の下書きは 1,511 語で、定義は英語と日本語を持ち、見せる名（`label`）は 447 語だけが持ちます。持ち主は BGQA2 で日本語の名を確定しています（確定 113 語）。
- 画面の文 `display-words.json`（1,103 項目）は英語と日本語を持ち、どちらが正かを書いていません。
- 仕様の原稿の和文 約 3,424 か所は日本語だけです。原稿にも当たるかはチーム T に問いました（T4）。

| 案 | 中身 |
|:---|:---|
| **a（推奨）** | 用語集と画面の文は英語を正にする。持ち主は語を確定するとき、英語の名と日本語の名を一緒に見る。仕様の原稿の和文は、チーム T の答え（T4）の後に決める |
| b | 日本語を正のままにする。基準書の「機械が読む原本」の行は、持ち主が FAIL として受容する |
| c | 仕様の原稿の全部にも `en` を足し、英語を正にする |

#### ❓ 問 6. 新しい基準書で初めてレビューする時と、High の受容の承認

新しい基準書では、守れない MUST の行は理由があっても FAIL（High）です。High は直すか、人が承認して受容するしかありません（据え置けません）。段 2〜5 の後でも、仕様の組み替え（問 3）が済むまで、ユースケースの形・Gherkin・要求の表・漏れの数の行は FAIL のままです。

| 案 | 中身 |
|:---|:---|
| **a（推奨）** | 段 5 の後に 1 回、別のセッションで全体をレビューする。組み替えを待つ High を 1 枚の表にまとめ、持ち主が 1 回で承認する。見直す条件は「その行を直す組み替えの切れ目が着いた時」と書く |
| b | 仕様の組み替えが終わるまで、新しい基準書でレビューしない（数週間、今の 07 で見る） |
| c | 規則 07 を入れた直後（段 2）にレビューする。受容の数が最も多くなる |

回答:

#### ❓ 問 7. テストの記録をどこに置くか

新しい基準書は、道具の報告（vitest や playwright の JSON）をテストの記録にすることを MUST にしました。今の GT-2 は、試験 11,091 件の報告を一時のフォルダーに書いてから消すので、記録は 0 です。報告は絶対パス（利用者の名を含む）を持ちます。リポジトリは公開です。報告の大きさは、まだ測っていません。

| 案 | 中身 |
|:---|:---|
| **a（推奨）** | GT-2 ごとに、試験した sha と、ファイルごとの passed・failed・skipped の数だけの要約を `docs/development-records/test-records/` にコミットする。道具の報告の全体は手元（git の外）に残す |
| b | 道具の報告の全体を、パスを消してからコミットする |
| c | git には残さず、手元だけに残す |
