# つかみシロ —— 「外は予定、内は実績」の 1 手で、重なりを構造から消す提案

- 日付: 2026-09-10
- 見本: [`grab-areas-sample.html`](grab-areas-sample.html)
  （**1 ファイルで完結。ダブルクリックすれば開く。**サーバーも通信も要らない）

⛔ **これは仕様書ではない。** 仕様へ下ろす前に、**姿を先に見ていただく**ための素描である。
⛔ **これは動く見本ではない。** 11・12 と違って触れない。**図と表だけ**である。
⭐ **判定していただいたのは、掴みシロの割り方と優先順位**である。

---

## 1. なぜ要ったか

2026-09-09、利用者が出荷ビルドの上に**掴みシロを桃色で描き込んだ画像**を出され、
こう述べられた —— **「今のままじゃダメだ。 だが言葉で表現するのはもはや困難。」**

⇒ **言葉では立たない。図で立てる。**それが本書の出自である。

⛔ **最初の案は全部却下された。**⚠️ **却下の理由が、そのまま次の案の設計条件になった:**

| 却下されたもの | 利用者の言葉 | そこから立った条件 |
|---|---|---|
| 矩形を上下のレーンに割る案 | **「レクタングル系を上下に分けるのは却下。」** | ⭐ **エリア分けと優先順位で調整する**（利用者が方式そのものを指定された） |
| 6 つの法則に整理した案 | **「悪くはないが、もっとシンプルにならんか？」** | ⭐ **法則は 3 つまで。** 4 つ目からは疑え |
| ダミーを四角い塊で描いた図 | **「未着手のつかみシロが着手済と形状が違い混乱する。」** | ⭐ **同じ役目のものは同じ形** |
| 予定 6px・実績 12px の掴み代 | **「縦幅の差は意図しているが、横幅は合わせろ。」** | ⭐ **差を担うのは 1 つの軸だけ** |

---

## 2. ⭐ 結論 —— 境目をバーの端に置く

**予定バーの端が境目である。⭐ 端の外は予定、端の内は実績。**

⇒ **優先順位を書く前に、重なりが 4 つとも消える:**

| 重なっていたもの | なぜ消えるか |
|---|---|
| 予定の 2 端どうし | **外どうしは背を向ける。**幅が 0 でも左は左へ、右は右へ伸びるだけ |
| 実績の 2 端どうし | **内側はバーの半分まで。**3 日の実績なら 9px ずつに割れる |
| 予定と実績 | **端が境目。**実績の開始日が予定の開始日と同じでも、外と内で分かれる |
| マイルストーンの予定と実績 | **実績の図形は予定の図形と同心で小さい。**外の環が予定、中が実績 |

⭐ **4 つ目は造りを読んで確かめた** —— 実績バーは予定バーの**中央**に置かれ
（`src/entity/layout-engine/schedule-geometry/schedule-geometry.ts` の `planTop + (planHeight - actualHeight) / 2`）、
マイルストーンの実績図形も**同じ中心の小さい図形**である（同ファイルの `barOf` の milestone の枝）。
⇒ **同心である以上、外／内は最初から成り立っていた。**

⚠️ **効いていなかった理由は 1 つ** —— `actualOfPlan`（`S-5`）が `0.73` で、
予定 28px に対し実績 20.4px、**予定だけの縁が上下 3.8px しか残っていなかった**からである。

---

## 3. 法則は 5 つ

| # | 法則 | 中身 |
|---|---|---|
| ① | **横** | 境目はバーの端。**外は予定、内は実績。**予定の端点は外側だけ 12px、実績の端点は内側だけ 12px（バーの半分を超えない） |
| ② | **縦** | 重なるものは入れ子。**予定 28 ⊃ 実績 16 ⊃ 依存線 12。**内側ほど細いので、外側の縁が必ず残る |
| ③ | **寸法** | **点は 16px 角**（マーカー・再開・マイルストーンの図形とダミー）／**端は 12px × 帯の高さ**／**角は 15px 角**（フェード）／**線は帯 12px**。⭐ 覚える数は 4 つ |
| ④ | **順** | **重なったら内が勝つ。**外へは逃げられるが、内へは逃げられない |
| ⑤ | **列** | **2 本ある。ダブルクリックが先。**ダブルクリックでは引けないので掴みと争わない |

## 4. 優先順位 —— 2 本の列

⭐ **読み順は 表 T-023d の結びが既に持っていた** ——
**「ダブルクリックの宛先は 表 T-023 の `MK-13` が持ち、本表の優先順より先に読むこと（MUST）」**

### ① ダブルクリックの列（先に読む）

```
(最高優先) コメントボックスの本文 ← 担当ラベル
         ← タスク（名称ラベル・予定バー本体・実績バー・未着手のダミー）
         ← 行見出しの行の名前 (最低優先)
```

⭐ **どれも同じ振舞い** —— **プロパティパネルを出し、対応する欄を編集できる状態にして焦点を置く（MUST）。**
⛔ **図の上に打ち換える器を置いてはならない（MUST NOT）。**

### ② 素の押下の列

```
(最高優先) パレットの掴み帯 ← フェード ← 実績の端点 ← 再開
         ← マイルストーンの実績図形 ← 依存線 ← 注記の箱 ← 予定の端点
         ← ステータスマーク ← 予定バー本体 ← 行見出し ← 基準日線
         ← スクロールバー (最低優先)
```

⭐ 層で読むと **浮 ← 選択中 ← 内 ← 線 ← 外 ← 面 ← 画面の道具**

⛔ **この列に並ばないものが 2 つある:**
**実績バー本体**（掴みシロにしない —— 取ると予定バー本体に手が届かない）と、
**完了率**（`PR-9` は読み取り専用の算出値なので、掴む対象そのものが無い）。

## 7. ⭐ 副産物 —— ほどけた鎖が 3 本

⛔ **どれも今回は値を動かしていない。**⭐ **鎖がほどけたことだけを記録する。**

| 鎖 | いま | ほどける理由 |
|---|---|---|
| `S-49 minShapeWidth` = 6px | 由来は「掴み代（`S-90`）より狭い形状は自分の胴で掴めない」 | ⭐ **予定の端点が外側だけになれば、胴は幅によらず必ず残る** |
| `S-93` が 2 つの用途を兼ねる | ダミーと再開の両方 | ⭐ **再開が `S-22` を読むので、`S-93` はタスクのダミー専用になる** |
| 実績の端点が担当ラベルを食う | `S-91` の 12px が横に張り出し、`S-32`（8px）の隙間を越えてラベルの右端に載る | ⭐ **内側だけにすれば、掴み代はバーの外へ 1px も出ない** |

## 8. ⛔ この提案が省いていること

⚠️ **実測はしていない。**⛔ **図の数は仕様の値から起こしたものであり、出荷ビルドを押して採った値ではない。**
（出典として引いた造りの 2 か所 —— 実績バーの中央寄せとマイルストーンの同心 —— だけは読んで確かめてある。）

⛔ **やり残し**: 拡大・縮小したときの振舞いを図にしていない。
⚠️ **`S-93` の 30px は既定倍率での話であり、大きく開いたときに 1 日の幅が 30px を超えると、
ダミーの帯が日の列より狭くなる。**⇒ **どちらを採るかは次の巡で測って決める。**

⛔ **タッチ（指）とキーボードだけでの操作は考えていない。ポインタの手つきだけを見た。**
