# gr-scheduler WCAG 2.1 AA チェックリスト (M5c)

本書は **WCAG 2.1 の A / AA 全 50 基準**を、この製品でどう満たすかに対応づけた突合表である。

**2026-08-02 に 2 つのことをした。**

1. **部分集合から全数へ広げた。** それまでは前プロジェクトが実装した **12 件**しか無く、
   「この表が全部緑なら AA 適合」と誤読できる形だった。残り 38 件を原文から補った。
2. **適合範囲を決めた。** ⚠️ **「WCAG 2.1 AA 適合」とは名乗らない。**
   **支援技術による読み上げは対象外**とし、**視覚と操作**に絞った。理由は下の「適合範囲」節。

| 欄 | 意味 |
|---|---|
| `判定` | **5 値**。下の表の直前に定義と件数がある |
| `根拠・満たし方` | なぜその判定か。方針ありの行は**前プロジェクトの実装の記録**でもある |
| `自動検証` | 自動テストで確かめられるもの |
| `人手確認` | 人が実機・支援技術で見るしかないもの |

- 対象要求: `docs/spec/25-nfr-a11y.sdoc` (NFR-L1-003/004/005/006)、`CLAUDE.md`
  品質目標 (WCAG 2.1 AA + 色弱者対応 + キーボード操作)。
- 自動 a11y スキャン: `tests/e2e/a11y.spec.ts` (Playwright + axe-core)。
  serious/critical 0 件で PASS。実行: `npm run build && npx playwright install chromium
  && npm run test:e2e`。
- 単体検証: `tests/{contrast,accessible-name,a11y-encoding,keyboard-commands}.test.ts`。

## 対応表 — **A / AA 全 50 基準の突合**（**確定 2026-08-02**）

**本表は WCAG 2.1 の A / AA の全数である。** 一次資料は W3C 勧告の原文
（**W3C Recommendation 2025-05-06**）で、入手手順とハッシュは `docs/spec/vendor/wcag/README.md`。
**基準の番号・名称・レベルは原文から機械抽出した**（目視で書き写していない）。

```text
WCAG 2.1 の達成基準  全 78
  レベル A    30
  レベル AA   20
  レベル AAA  28

AA 適合に要るのは A + AA = 50   ← 本表の対象
```

### 適合範囲 — **「AA 適合」とは名乗らない**（**確定 2026-08-02・ユーザー判断**）

**支援技術による読み上げは対象外とする。** 対象は**視覚と操作**である。

**なぜ「名乗らない」なのか**: 条文の **5.2.1 Conformance Level** が
「One of the following levels of conformance is **met in full**」と定めており、
**部分適合という選択肢が無い**（5.4 の Statement of Partial Conformance は
**後から第三者が追加するコンテンツ**のための仕組みで、この用途には使えない）。
**1 つでも外すなら適合は名乗れない。** だから札を返上して、満たすものを列挙する形にした。

**なぜ読み上げを外したのか**: a11y を有効にした動機は
**アフォーダンス（`../user-order.md` 項 6）／色弱者対応（項 24・25）／各国ユーザー**であって、
**読み上げは 1 つも挙がっていない。** 対して本製品は、意味のほとんどを**位置と形**で伝える道具である。

> ⚠️ **レベルを AA → A に下げる案は採らなかった。逆効果だからである。**
> **読み上げの核は Level A に集中**しており（1.1.1 / 1.3.1 / 1.3.2 / 2.4.3 / 4.1.2）、
> **動機そのものは AA にある**（1.4.3 コントラスト / 1.4.11 非文字コントラスト / 2.4.7 フォーカス表示 /
> 1.4.4 文字拡大 / 3.1.2 言語）。**レベルという刃では、落としたいものと残したいものを分けられない。**

**判定は 5 つに分かれる。**

| 判定 | 件数 | 意味 |
|---|--:|---|
| **適合** | **1** | 原文が「常に満たされる」と定めている（4.1.1 のみ） |
| **該当なし** | **14** | この製品には当たらない。**理由を必ず書いた**（音声・動画が無い / 単一ページ / タッチ対象外 ほか） |
| **範囲外** | **5** | **支援技術に構造を渡すためのもの。適合範囲から外した**（1.1.1 / 1.3.1 / 1.3.2 / 4.1.2 / 4.1.3） |
| **方針あり** | **11** | 満たし方が本資産に書いてある。⚠️ **実装はまだ無い** |
| **要対応** | **19** | 満たし方が書かれていない。**ここが残作業である** |

> ⚠️ **件数はあまり減っていない（21 → 19）。減ったのは重量である。**
> 範囲外にした 5 件が、**「SVG とは別に支援技術向けの出力経路を作る」という最大の設計負担**を
> 丸ごと持っていた。**残る 19 件はどれも、見える利用者・操作する利用者に直接効くもの**である。

> ⚠️ **「方針あり」は「適合」ではない。** 前プロジェクトの実装は引き継がない（`../README.md` §0-1）ので、
> **50 基準のうち実装として存在するものは 1 つも無い。** 本表が言うのは「**満たし方が決まっているか**」だけである。
>
> ⚠️ **表中の実装の記述は前プロジェクトのものである。** 考え方は使えるが、
> **ファイル名は凍結リポジトリを指す**ので、そのまま探しても本資産には無い。

## 1.3.1 だけは別枠で残す — **設計の健全性の指標として**（**確定 2026-08-02**）

**適合範囲からは外した。それでも捨てない理由がある。**

### 上位要求

```
原則 1  Perceivable        情報と UI 部品は、利用者が知覚できる形で提示できなければならない
  └ ガイドライン 1.3  Adaptable
        別の形で提示しても 情報と構造が失われない 内容を作れ
      └ 1.3.1  Info and Relationships
```

**目的は 1 文である** — **見た目を変えても情報が消えないようにすること。**
見た目にしか情報が無いなら、見た目を変えた瞬間にその情報は消える。

### なぜ a11y の外でも意味があるか

**このプロジェクトは同じことを、自分の言葉で既に要求している。**

| 出典 | 何と書いてあるか |
|---|---|
| `../user-order.md` 項 67 | **画面とデータを分離する** |
| `../README.md` §0-1 | **バグ根因は「画面とデータの語彙混在」だった** |
| `CLAUDE.md`（⚠️ **引継ぎ資産に入らない**・`../DISCARDED-ja.md` 方針 7） | Clean Architecture / DIP。**SVG 描画は Adapter へ分離** |

**1.3.1 は、この分離が本物かを外から測る物差しになっている。**

```
分離が本物   → 関係はデータ側にある → 別の提示形式を足すだけで満たせる
分離が名目   → 関係が描画側にしか無い → 原理的に満たせない
```

**満たせないなら、それは a11y の失点ではなく設計が壊れている合図である。**
前プロジェクトのバグ根因そのものが再発している、という警報として読む。

### 確認したこと

**関係は 4 つとも既にデータ側にある。**

| 1.3.1 が問う関係 | モデルのどこにあるか |
|---|---|
| WBS の親子 | `Task.wbs_parent_uid` |
| 所属（行・段） | `TaskGroupMember`（`stack_order` 込み） |
| 依存の先行 / 後続 / 種別 / ラグ | `Dependency` |
| 予定と実績の対応 | **1 個の `Task` が両方を持つ** |

**つまり分離は本物である。** 足りないのはモデルではなく、**出す経路**だけだった。

> ⚠️ **JSON を単一 HTML に埋めても 1.3.1 は満たせない**（検討した記録）。
> 条文の **text** の定義は「**支援技術が取り出せ**、かつ**人間の言語である**文字の並び」で、
> `<script>` の中身はどちらも満たさない。**content** の定義も
> 「**ユーザーエージェントによって利用者に伝えられる**もの」である。
> **JSON Schema の `description` はさらに遠い** — 説明しているのは**型**であって、その文書の事実ではない。

### 骨格段階での使い方

**測るのは「2 本目の出力を足すのが安いか」だけでよい。**
同じストアを読んで関係をテキストで出す経路を、骨格段階で 1 度作ってみる。

- **安く済んだ** → 分離は本物。以後この指標は不要
- **描画層をほどく必要があった** → **設計が壊れている。** その時点で直す

`../README.md` §0-2 が性能について言っていることと同じ理屈である — **骨格で測る。**
⚠️ **これは指標であって要求ではない。** 適合範囲には入らないので、**満たせなくても適合の判定は動かない。**
