1-2. 現行 11 個からの追加 6 個

追加置き場所理由
横ズーム、縦ズーム（4 個）表示群・Fit の隣 ユーザー要望。ホイール＋修飾キーが使えない環境への手当てで、WCAG 2.1.1（キーボード操作可能）の代替手段にもなる。 Fit と同じ「表示」の責務なので隣に置く。2 個ずつセグメントにまとめて幅を詰めた。 符号（＋／−）は使わず、矢印の向きだけで表す — 外向き ＝ 拡大、内向き（→←）＝ 縮小。縦は上下から挟み込む。 符号は 20px の中で 2 つ目の記号になり、軸（縦横）を読む邪魔をしていた。
表示言語（1 個）ヘルプ群・? の左 ユーザー指示によりヘッダーとモーダルの両方に置いた。表記の比較は §5 の言語切替の節。
文書の描画設定（1 個）App Header の表示群だけ documentSettings の 57 項目・themeHue / themeMonochrome / fontScale（S/M/L）を触る面が、これまで UI パーツ木に 1 つも無かった。 Properties Panel 側にはアイコンを置かない（下記）。

Properties Panel にアイコンを 1 つも置かない — 入口はヘッダー、切替は後勝ち

入口は App Header の 1 個だけにする。 Properties Panel には 選択物のアイコンも描画設定のアイコンも置かない。パネルは中身を出す面に徹し、 何を出すかは直前の操作が決める。

操作パネルが出すもの選択はどうなるか
キャンバスで何かを選ぶその選択物のプロパティ —（ヘッダーの設定ボタンは押下状態が解ける）
ヘッダーの描画設定を押す文書の描画設定 選択は解除しない。キャンバス上の選択表示もそのまま残す
もう一度押す直前の選択物へ戻る（選択が無ければ「選択なし」） —
選択を解除する（Esc / 背景クリック） 「選択なし」を出す ⚠️ 勝手に描画設定へ移らないこと。選択を捨てた結果、 見ていない面が出てくるのは驚きになる

いま何を見ているかは 2 つで示す。 ① ヘッダーの設定ボタンの押下状態（パレットや共同編集と同じ既存の符号）。 ② パネル先頭の見出し — 選択物ならその名前、設定なら「文書の描画設定」。 アイコンが無くても現在地が分かるので、タブは要らない。

この形の利点。 ① 重複コントロールが無い（ui-detail-spec-ja.md §2 が禁じた形を踏まない）。 ② パネルの上端を丸ごと中身に使える — パネル幅は propertyPanelWidth で人が縮められるので、幅の狭いパネルにタブ帯を載せると項目名が入らなくなる。 ③ 設定の入口が「文書に対する操作」の群に並ぶ — テーマ・出力と同じ責務で、探す場所が 1 つになる。

相談への回答 — ライセンス名を画面から省略するのは「あり」

Apache License 2.0 は、画面にライセンス名を出すことを義務づけていない。 第 4 条が頒布者に課すのは次の 3 つで、どれも「UI に出せ」とは言っていない。

条項義務本製品での満たし方
4(a)頒布物にライセンス全文の写しを添える ここだけは落とせない。成果物が単一 .html なので、添える先は .html の中しかない
4(c)著作権・特許・商標・帰属の表示をソース形式で保持同上
4(d)NOTICE の内容を、①頒布物内の NOTICE ②ソースか文書 ③生成される表示 のいずれか1 つで示す ③（画面表示）は 3 択のうちの 1 つにすぎない。①か②を選べば画面から消してよい

したがって推奨は次の 3 点である。

  1. ヘッダーは案② の 2 行（GR Scheduler ／ © 2026 GoodRelax）。 ライセンス名は出さない
  2. Help モーダルに「ライセンス」節を置き、NOTICE の全文 ＋ Apache-2.0 の全文を載せる （オフライン単一 HTML なのでリンクでは満たせない。全文を埋め込む）
  3. ビルド後の .html の先頭に、ライセンスのバナーコメントを残す（4(c) のソース形式の保持）
省略できないものが 1 つある — 第三者ライブラリの帰属表示。 MIT / BSD 系を 1 本でも同梱すると、その著作権表示と許諾文はビルド成果物に残す義務がある （各ライセンスの条文であって Apache-2.0 の話ではない）。 置き場所は上の 2（Help の「ライセンス」節）に集約する。 依存を足すたびに license-checker を通すこと（CLAUDE.md の必須プロセス）。
表記そのものについて 2 点。 ① 「GRScheduler」ではなく「GR Scheduler」にした — 前プロジェクトの実物が GR Scheduler（空白あり）で、リポジトリ名・パッケージ名の gr-scheduler とも語の切れ目が一致する。 詰める（GRScheduler）ご意向であれば戻す。 ② 「GoodRex」は「GoodRelax」と書いた — NOTICE と package.json が GoodRelax なので、そちらに合わせた。ここが食い違うと帰属表示として機能しない。

1-4. 並び順とアイコン一覧（App Header・22 個）

ご提案の並びを採る。左から右へ「文書を用意する → 画面を整える → AI に頼む → 困ったら見る」 という筋が通っており、次の 4 つがいずれも理屈で説明できる。

  • 左端が文書そのもの（ブランド・文書名・自動保存）で、その右に文書を動かす操作が続く
  • 粗 → 細（Fit で一発 → ズームで手加減）
  • 明暗と描画設定が隣接 — 明暗は描画設定の 1 項目（themePreference）への近道なので、隣にあると関係が見える
  • 右端がヘルプ — 世界的な慣行。初見の各国ユーザー（項 6-4）が最初に目で探す位置

群は線ではなく間隔で分ける。 群の内側は 2px、群と群のあいだは 10px。 縦線（|）は 1 本も引かない — 線は「意味のある枠」のためだけに取っておく（下の決着）。 Undo / Redo のまわりが間延びして見えたのは、2 個しかない群を左右から縦線で挟んでいたためである。

群中身入れた理由
① 文書開く / 保存 / 画像出力 / 変更前の予定 変更前の予定はご提案に無かったので足した。「別ファイルを読み込んで重ねる」操作なので、 責務はファイル入出力である
② 履歴元に戻す / やり直す これもご提案に無かった。編集のたびに使うので頻度は全ボタン中で最も高い。 視線の出発点に近い左へ置き、独立した群にした（多くの編集ソフトもファイル操作の直後に置く）
③ 表示パレット / 予実 / Fit / 全画面 / 横ズーム / 縦ズーム / 明暗 / 描画設定 ご提案の順どおり。全画面は Fit と横縮小のあいだに入れた （F11 を知らない人が多いため。解除は同じボタンのトグル）
④ AIチャット / JSONコピー / 共同編集ご提案どおり
⑤ 補助言語 / ヘルプご提案どおり

決着 — 予実はヘッダーに置く。ただし枠（セグメント）は残す

予実の 2 トグルは App Header の表示群に置く（ユーザー判断）。 パレットからは削除した — 2 箇所に置くと重複コントロールになるので、複製ではなく移設である。

群を仕切る縦線（|）は全廃したが、予実の枠だけは残す。 役割が違うからである。

何のための線か扱い
群と群のあいだの |ただの区切り。間隔で足りる廃止
予実を囲む枠 ／ ズームを囲む枠 「この 2 つで 1 つの状態」を示す符号。 予実は両方 OFF を作らせないという相互拘束を持ち、ズームは −／＋ の対である 残す

ここが唯一「線を引く理由がある」場所である。 区切りの線を全部消したうえで枠が 3 つだけ残るので、枠が意味を持っていることが逆に読み取りやすくなる。

4. 作画規則とマイルストーンの幾何

viewBox="0 0 24 24"、描画は 2〜22 の内側＝20×20 のデザイングリッド。 線幅は原則 1.6、端と角は丸、色は currentColor 1 色。 塗りを使う例外は 4 か所（§5 の意見 1）。

4-1. マイルストーン 8 種の作図

すべて同じ外接円 R = 7.5 に内接。向き：六角形は左右に頂点（flat-top）、 五角形・△ は頂点が上、▽ は頂点が下、 ☆ は頂点が上・starInnerOfOuter = 0.45、□ は辺が水平垂直。 赤い点は依存線のアンカー（外接矩形の左右・中心高さ）。

決着：依存線のアンカーは外接矩形のままとし、五角形・☆・△・▽ で図形から浮くことを許容する （ユーザー判断 2026-08-06）。設定値を増やさない方針（§4-9「新しい設定値キーは 1 つも増えていない」）を保つ。 ただし ui-detail-spec-ja.md §4-9 の「8 種はいずれも左右の極値が中心の高さに来る」は事実と違うので、 「4 種は浮くが許容する」と書き換える必要がある。△ は中心高さでの実幅が外接矩形の 50%（R=10px なら 2.5px 浮く）。

5. 質問・意見

決着（Help）— 1 画面は基準環境で保証する。狭い画面はスクロールを許す

基準は 1920×1080（ユーザー判断）。実測 789px なので、 1080px・900px の画面には収まり、768px の画面ではスクロールする（§3-3）。

この基準は本資産と一致している — 性能測定の基準環境は 「1920×1080 / ブラウザ全画面 / 拡大率 100%」 （plan-actual-decisions-ja.md §2-4-1、performance-notes-ja.md §2-0）。 ヘルプだけ別の基準を持ち込まずに済んだ。

採らなかった案と理由: 4 段組み（1366px 幅では 1 段 300px になり名前が省略される）／ 説明を削る（「全部を 1 画面」という要求そのものを捨てることになる）／ 折り畳み（探させる形に戻り、ヘルプの目的に反する）。

決着（Help）— ショートカットは 6 個を新設し、計 13 個にする

ui-detail-spec-ja.md §5 に実在したのは 7 個 （元に戻す / やり直す / Fit / ズーム 4 つ）だけだった。次の 6 個を新設する。

全画面ボタンについて — 確認しておきたいこと 2 点

本資産に全画面ボタンは無い。一次資料で F11 が出てくるのは 1 か所だけで、 ブラウザの機能としてである（ui-detail-spec-ja.md §5-1 の Esc の規則の理由： 「利用者は F11 の全画面表示から Esc で戻ろうとする」）。今回が新規追加になる。

  1. Esc の規則と噛み合う。 ボタンで入る全画面は Fullscreen API になり、 ブラウザ標準で Esc を奪って解除に使う。 §5-1 は「取り消す対象が無いときは Esc をブラウザに渡す」と決めているので、 この規則のままで全画面から抜けられる。矛盾しない。 ⚠️ ただし「モーダルを開いたまま全画面」だと Esc 1 打鍵でどちらが閉じるかが決まらない。 内側から閉じる（＝モーダルが先）でよいか確認したい
  2. 基準環境そのものへの導線になる。 性能の基準は「ブラウザ全画面」であり、 これまで製品にはその状態へ入る手段が無かった（利用者が F11 を知っている前提だった）。 ボタンを置くと基準環境と実使用が揃いやすくなるので、性能の観点からも足す価値がある

質問 3（Help）— [ja][en] はヘルプだけ切り替えるのか、画面全体か

モックでは画面全体（localStorage の language そのもの）を切り替える形にした。 ヘルプだけ英語で読むという使い方はできない。

全体を切り替える案を推す理由: 状態を 2 つ持つと 「画面は日本語なのにヘルプは英語」という組み合わせが生まれ、 ヘルプに書いてあるボタン名と画面のボタン名が食い違う。 ヘルプの価値は画面と同じ言葉で説明していることにあるので、ここは分けないほうがよい。

意見（Help）— この設計に賛成する理由

  1. 「探させない」が正しい。 ヘルプは学ぶ面ではなく思い出す面である。 折り畳みや検索窓を置くと「探す」作業が生まれる。1 画面に全部出すのが最短で、ご提案の狙いに賛成する
  2. 3 段の割り付けは画面の面と対応させた。 左＝上部のボタン、中＝パレット（キャンバスの上に浮くもの）、 右＝ボタンの無い操作。読む順と画面を見る順が揃う
  3. 件数でも割り付けた（24 / 27 / 27）。段ごとの高さが揃わないと 1 画面に収まらないので、 意味だけで割ると破綻する

ただし前提を 1 つ確認したい。 user-order.md 項 6-4 は「マニュアルを見ないで使える」ことを求めている。 ヘルプを見ないと使えないアイコンがあるなら、それはアイコンの失敗であって、 ヘルプで補う話ではない。この面は「忘れたときの保険」であり、設計の逃げ道にしないという位置づけでよいか。

申し送り — ライセンスは確実に洗うこと

ヘッダーからライセンス名を消したのは「表示しない」という判断であって、「同梱しない」ではない。 Apache-2.0 の第 4 条(a)(c) は頒布物にライセンス全文と帰属表示を含めることを求めており、 これは表示の有無と無関係に残る。成果物が単一 .html なので、含める先はその 1 ファイルの中しかない。 次の 6 点を実装・リリース工程に組み込むこと。

#やること根拠 / 注意
1Apache-2.0 の全文を成果物 .html に埋め込む 4(a)。完全オフラインなのでリンクでは満たせない。置き場所は Help モーダルの「ライセンス」節
2NOTICE の内容を同じ節に埋め込む 4(d)。現在の NOTICE は 「gr-scheduler / Copyright (c) 2026 GoodRelax / Apache-2.0」の 3 行
3ビルド後 .html の先頭にライセンスのバナーコメント 4(c)（ソース形式での保持）。⚠️ minify がコメントを消す。 /*! */ 形式にし、esbuild なら legalComments、terser なら format.comments を明示すること
4第三者ライブラリの帰属表示を全数、同じ節へ集約 ここは省略できない。MIT / BSD は「著作権表示と許諾文を複製物に残すこと」を条文で要求しており、 Apache-2.0 の話ではないので上の判断は及ばない
5依存を足すたびに license-checker を通す CLAUDE.md の必須プロセス。単一 HTML は全依存が成果物に溶けるので、 「開発時だけの依存」という逃げ道が無いものが混ざりやすい
6リリース前に成果物そのものを機械検査する ビルド後の .html に「Apache License」と各第三者の著作権行が実在することを grep で確認する。単一ファイルなので検査は 1 コマンドで済む。 CI の成果物検証（CLAUDE.md の品質目標「単一 .html で動作」）に 1 行足すだけでよい
いちばん危ないのは 3 と 6 である。 1 と 2 は「書いたか書いていないか」が目で見えるが、バナーコメントは minify で無言のうちに消える。 ソースに書いた時点では正しく、成果物では違反しているという状態になり、 成果物を検査しない限り誰も気づかない。
画面から省いた判断そのものも記録に残すこと（project-records/decisions/）。 「なぜヘッダーにライセンス名が無いのか」は、あとから見た人が必ず疑う点である。 根拠（第 4 条(d) の 3 択のうち画面表示は 1 つにすぎない）を書いておけば、同じ議論を繰り返さずに済む。
